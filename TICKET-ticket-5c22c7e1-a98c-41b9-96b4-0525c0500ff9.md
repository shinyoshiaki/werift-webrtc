# Issue #708 修正タスク詳細: configurable SCTP outbound MTU / padding-aware fragmentation

## 対象

- werift issue: https://github.com/shinyoshiaki/werift-webrtc/issues/708
- 参考実装: https://github.com/pion/sctp/pull/476
- Pion WebRTC 側 follow-up: https://github.com/pion/webrtc/pull/3476

## 目的

Issue #708 の「`USERDATA_MAX_LENGTH` を固定値 1200 から設定可能にする」という要求を、単純な payload 長の公開ではなく、Pion SCTP #476 と同じ考え方で **SCTP outbound MTU を設定し、SCTP common header / DATA chunk header / 4-byte padding を考慮して最大 user data payload を導出する**実装へ置き換える。

VPN / Tailscale / WireGuard / overlay / nested virtualization など、実効 Path MTU が小さい経路でも DataChannel の大きなメッセージが black-hole / stall しにくい送信サイズにできるようにする。

---

## 背景と現状分析

### 現在の werift

`packages/sctp/src/sctp.ts` に以下の固定値がある。

```ts
const USERDATA_MAX_LENGTH = 1200;
```

この値は少なくとも次の用途で共用されている。

1. DataChannel/SCTP message の fragmentation 単位
2. `DataChunk.userData` の slice 長
3. congestion window (`cwnd`) の初期値・増加量
4. `ssthresh` の下限計算
5. burst size
6. T3 timeout 後の `cwnd` リセット値

一方、`packages/sctp/src/chunk.ts` の `DataChunk` は、user data 以外に以下の overhead を持つ。

- SCTP common header: 12 bytes
  - source port: 2
  - destination port: 2
  - verification tag: 4
  - checksum: 4
- DATA chunk header: 16 bytes
- chunk padding: 4-byte alignment

したがって、現在の `USERDATA_MAX_LENGTH = 1200` は「SCTP packet MTU = 1200」ではない。

現在の最大 DATA packet は概ね次のサイズになる。

```text
12 (SCTP common header)
+ 16 (DATA chunk header)
+ 1200 (user data)
= 1228 bytes
```

1200 は 4-byte aligned なので、このケースでは追加 padding はない。

つまり現在の `USERDATA_MAX_LENGTH` は Path MTU を直接表現する値ではなく、**payload/MSS 相当の内部値**である。

### なぜ 1024 固定化より Pion #476 の方式がよいか

Issue #708 の downstream 事例では `1200 -> 1024` のローカルパッチで問題を回避しているが、Pion SCTP #476 ではより構造的に修正している。

Pion #476 の主な変更は次の通り。

- outbound SCTP MTU の既定値を `1228 -> 1191` に変更
- `maxPayloadSizeForMTU()` を追加
- SCTP common header と DATA/I-DATA header を MTU から差し引く
- 4-byte chunk padding を考慮して payload 上限を切り下げる
- 小さすぎる MTU を validation で拒否
- interleaving 有効化時に DATA/I-DATA header 差を反映
- serialized packet が MTU 以下になることをテスト

Pion WebRTC #3476 でも SCTP の outbound MTU を RTP 用の `1200` から分離し、`1191` を使うよう follow-up している。

werift は現在 I-DATA / message interleaving を実装していないため、まず DATA chunk の 16-byte header を対象にすればよい。ただし helper を独立させ、将来 I-DATA を追加した際に header size を差し替えられる構造にする。

## 採用する設計

### 1. `userDataMaxLength` ではなく `mtu` を公開設定にする

推奨 API:

```ts
const pc = new RTCPeerConnection({
  sctp: {
    mtu: 1191,
  },
});
```

低レイヤー SCTP API でも指定可能にする。

```ts
const sctp = SCTP.client(transport, 5000, {
  mtu: 1191,
});
```

あるいは constructor 直接利用時:

```ts
const sctp = new SCTP(transport, 5000, {
  mtu: 1191,
});
```

`USERDATA_MAX_LENGTH` そのものは public API にしない。

理由:

- 利用者が知りたいのは「1 fragment の payload 長」より「送信 SCTP packet の上限」
- header/padding 計算を利用者へ押し付けない
- Pion と同じ概念になる
- 将来 PMTU discovery / adaptive MTU を実装しやすい
- DATA と将来の I-DATA で header size が異なっても API を変えずに済む

### 2. 既定 MTU は 1191 を推奨

Pion SCTP #476 / Pion WebRTC #3476 に合わせ、werift の SCTP outbound MTU の既定値も `1191` とする。

DATA の場合:

```text
mtu                  = 1191
common header        = 12
DATA chunk header    = 16
raw payload budget   = 1191 - 12 - 16 = 1163
4-byte align down    = 1160
```

したがって:

```text
maxPayloadSize = 1160
serialized DATA packet = 12 + 16 + 1160 = 1188 bytes
1188 <= 1191
```

これは downstream の `1024` payload より大きく、Pion #476 を参照した issue コメントの「1024 より大きくできる」という指摘にも対応する。

参考として、現行と同じ 1200-byte payload を維持したい場合、それに相当する SCTP MTU は `1228` である。

```text
1228 - 12 - 16 = 1200
```

1024-byte payload に相当する SCTP MTU は `1052`。

```text
1052 - 12 - 16 = 1024
```

### 3. backward compatibility の扱い

Issue #708 の元提案では「default は 1200 のまま」としているが、1200 は payload 長であって packet MTU ではない。

Pion #476 の修正意図まで取り込む場合、既定動作を完全維持して `mtu = 1228` にすると VPN/Tailscale 系の問題を既定では解消できない。

そのため本タスクでは **default `mtu = 1191` を採用する**。

これは fragmentation と congestion-control の単位サイズが少し変化するため、release note には behavior change として記載する。Pion 側も同変更を patch ではなく minor release 相当として扱っている。

もしリリース互換性を最優先する判断になった場合のみ、代替案として:

- default `mtu = 1228`
- `sctp.mtu = 1191` を opt-in

とすることは可能。ただし、この代替案は Issue #708 の downstream workaround を API 化するだけで、Pion #476 相当の safer default にはならない。

## 低レイヤー SCTP の実装

### 対象ファイル

主に:

- `packages/sctp/src/sctp.ts`
- `packages/sctp/src/chunk.ts`
- `packages/sctp/src/index.ts`
- `packages/sctp/tests/sctp.test.ts`
- `packages/sctp/tests/packet.test.ts`
- `packages/sctp/README.md`

### 4. SCTP size constants を明示する

`chunk.ts` 内の magic number と `sctp.ts` の fragmentation 計算が乖離しないよう、packet/chunk の size constants を共有できる形にする。

例:

```ts
export const SCTP_COMMON_HEADER_SIZE = 12;
export const SCTP_CHUNK_HEADER_SIZE = 4;
export const SCTP_DATA_FIXED_HEADER_SIZE = 12;
export const SCTP_DATA_CHUNK_HEADER_SIZE =
  SCTP_CHUNK_HEADER_SIZE + SCTP_DATA_FIXED_HEADER_SIZE; // 16
export const SCTP_PADDING_MULTIPLE = 4;
```

`DataChunk.bytes` の `16` と `serializePacket()` の common header 長も、可能な範囲でこの定義と整合させる。

目的は Pion #476 と同様、**実際の marshal format と MTU 計算の header size が別々の magic number にならないようにすること**。

### 5. `DEFAULT_SCTP_MTU` と options を追加する

例:

```ts
export const DEFAULT_SCTP_MTU = 1191;

export interface SCTPOptions {
  mtu?: number;
}
```

constructor/static factory は既存呼び出しを壊さないよう optional third argument で追加する。

```ts
constructor(
  public transport: Transport,
  public port = 5000,
  options: SCTPOptions = {},
)
```

```ts
static client(
  transport: Transport,
  port = 5000,
  options: SCTPOptions = {},
)
```

```ts
static server(
  transport: Transport,
  port = 5000,
  options: SCTPOptions = {},
)
```

既存の以下はそのまま動作すること。

```ts
SCTP.client(transport)
SCTP.client(transport, 5000)
new SCTP(transport)
new SCTP(transport, 5000)
```

### 6. padding-aware `maxPayloadSizeForMtu()` を追加する

例:

```ts
export function maxPayloadSizeForMtu(mtu: number): number {
  const headerSize = SCTP_COMMON_HEADER_SIZE + SCTP_DATA_CHUNK_HEADER_SIZE;

  if (mtu <= headerSize) {
    return 0;
  }

  const payloadBudget = mtu - headerSize;
  return payloadBudget - (payloadBudget % SCTP_PADDING_MULTIPLE);
}
```

重要点:

- 単純な `mtu - 28` ではなく、4-byte alignment を考慮する
- 最終 fragment が 4-byte aligned でない場合でも `DataChunk.bytes` の padding 後 packet が MTU を越えない上限を返す
- I-DATA 実装時は header size を切り替えられる構造へ拡張可能にする

### 7. MTU validation を追加する

invalid value は silent clamp せず明示的に reject する。

最低条件:

- finite number
- integer
- positive
- `maxPayloadSizeForMtu(mtu) > 0`

現行 DATA chunk のみなら、実質最小 usable MTU は 32 bytes。

```text
12 common + 16 DATA + minimum aligned payload 4 = 32
```

例:

```ts
function validateSctpMtu(mtu: number) {
  if (!Number.isSafeInteger(mtu) || mtu <= 0) {
    throw new Error("SCTP MTU must be a positive integer");
  }

  if (maxPayloadSizeForMtu(mtu) === 0) {
    throw new Error("SCTP MTU is too small for a DATA chunk");
  }
}
```

Pion と同様、意味のない小さな MTU を association 作成前に失敗させる。

### 8. `USERDATA_MAX_LENGTH` を `mtu` + derived `maxPayloadSize` に分離する

`SCTP` instance に少なくとも以下を保持する。

```ts
readonly mtu: number;
private readonly maxPayloadSize: number;
```

constructor で:

```ts
this.mtu = options.mtu ?? DEFAULT_SCTP_MTU;
validateSctpMtu(this.mtu);
this.maxPayloadSize = maxPayloadSizeForMtu(this.mtu);
```

### 9. fragmentation は `maxPayloadSize` を使う

現在:

```ts
const fragments = Math.ceil(userData.length / USERDATA_MAX_LENGTH);
...
chunk.userData = userData.slice(pos, pos + USERDATA_MAX_LENGTH);
pos += USERDATA_MAX_LENGTH;
```

修正後:

```ts
const fragments = Math.ceil(userData.length / this.maxPayloadSize);
...
chunk.userData = userData.slice(pos, pos + this.maxPayloadSize);
pos += this.maxPayloadSize;
```

ordered / unordered、reliable / partial reliable のどの send path でも同じ fragmentation 上限になること。

### 10. congestion-control での `USERDATA_MAX_LENGTH` 利用を機械的に残さない

現在 `USERDATA_MAX_LENGTH` は fragmentation だけでなく congestion-control の単位にも使われているため、constant を削除すると以下も修正が必要。

- initial `cwnd = 3 * ...`
- slow start の `Math.min(doneBytes, ...)`
- congestion avoidance の `cwnd += ...`
- `ssthresh >= 4 * ...`
- fast recovery burst `2 * ...`
- normal burst `4 * ...`
- T3 timeout 後 `cwnd = ...`

この issue では congestion-control algorithm 自体の RFC 準拠化まで広げない。

**既存実装の単位を維持するため、これらは `this.maxPayloadSize` を使用する。**

これにより「今まで 1200-byte DATA payload を 1 congestion-control unit としていた」という現行動作を、新しい derived payload size に自然に置き換えられる。

Pion は cwnd 初期値を MTU ベースで計算しているが、それを werift に移植するのは別タスクとする。今回同時に変更すると、MTU fix と congestion-control behavior change が混ざり、回帰原因を切り分けにくくなる。

### 11. class field initialization の順序に注意する

現在:

```ts
private cwnd = 3 * USERDATA_MAX_LENGTH;
```

となっているが、`maxPayloadSize` は constructor options から決まるため、`cwnd` を constructor 内で初期化する必要がある。

例:

```ts
private cwnd: number;

constructor(...) {
  ...
  this.mtu = ...;
  this.maxPayloadSize = maxPayloadSizeForMtu(this.mtu);
  this.cwnd = 3 * this.maxPayloadSize;
}
```

`ssthresh` 等、`maxPayloadSize` に依存する初期値が他にもないか全検索する。

## WebRTC layer への設定伝播

### 対象ファイル

主に:

- `packages/webrtc/src/peerConnection.ts`
- `packages/webrtc/src/sctpManager.ts`
- `packages/webrtc/src/transport/sctp.ts`
- `packages/webrtc/tests/transport/sctp.test.ts`
- PeerConnection configuration 関連 tests

### 12. `PeerConfig` に SCTP config を追加する

例:

```ts
export interface PeerConfig {
  ...
  sctp: {
    mtu: number;
  };
}
```

default:

```ts
sctp: {
  mtu: DEFAULT_SCTP_MTU,
},
```

`maxMessageSize` は別概念なので統合しない。

- `maxMessageSize`: 1 DataChannel message として送受信可能な論理 message サイズ
- `sctp.mtu`: 1 outbound SCTP packet の上限
- derived `maxPayloadSize`: 1 DATA fragment の最大 user data 長

### 13. PeerConnection config を transport 生成まで伝播する

現在の経路:

```text
RTCPeerConnection.createSctpTransport()
  -> SctpTransportManager.createSctpTransport(maxMessageSize)
    -> new RTCSctpTransport(...)
      -> setDtlsTransport()
        -> new SCTP(new BridgeDtls(...), port)
```

修正後は `sctp.mtu` をこの経路で最後まで渡す。

例:

```text
RTCPeerConnection.config.sctp.mtu
  -> SctpTransportManager.createSctpTransport(maxMessageSize, sctpOptions)
    -> RTCSctpTransport(..., sctpOptions)
      -> new SCTP(..., { mtu })
```

DTLS transport を bundle の都合で差し替えて `SCTP` instance を再生成する場合も、同じ options を必ず再利用する。

### 14. `setConfiguration()` の扱いを明示する

推奨仕様:

- SCTP transport 作成前: `sctp.mtu` の変更を許可
- SCTP transport 作成後: MTU の変更は reject

理由:

- `maxPayloadSize`
- `cwnd`
- outbound queue
- sent queue

など association 内部状態がすでに MTU 前提で初期化されており、live association の途中で値だけ差し替えると不整合になりやすい。

例:

```ts
if (
  isReconfiguration &&
  normalizedConfig.sctp?.mtu !== undefined &&
  this.sctpManager?.sctpTransport &&
  normalizedConfig.sctp.mtu !== this.config.sctp.mtu
) {
  throw new Error("sctp.mtu cannot be changed after SCTP transport creation");
}
```

同じ値を再指定することは許可してよい。

`getConfiguration()` からは現在設定中の `sctp.mtu` が取得できること。

## テスト計画

### A. helper / packet sizing tests

`maxPayloadSizeForMtu()` を直接テストする。

最低限:

```text
mtu 1191 -> payload 1160
mtu 1228 -> payload 1200
mtu 1052 -> payload 1024
```

境界値:

- 0 -> reject
- negative -> reject
- NaN -> reject
- Infinity -> reject
- non-integer -> reject
- 28 以下 -> reject
- 29〜31 -> aligned payload が 0 なので reject
- 32 -> payload 4 で valid

### B. serialized packet が MTU を越えないこと

Pion #476 のテストと同じ観点を入れる。

`DataChunk` に `maxPayloadSizeForMtu(mtu)` bytes の userData を入れて `serializePacket()` し、

```ts
expect(packet.length).toBeLessThanOrEqual(mtu);
```

を確認する。

`mtu = 1191` の場合は packet length が 1188 になることも確認してよい。

さらに 4-byte alignment の境界をカバーする。

- final payload = 1157
- 1158
- 1159
- 1160

いずれも padding 後 packet が MTU を超えないこと。

### C. fragmentation tests

fake `Transport` で outbound SCTP packet を capture する。

default `mtu = 1191` の場合:

- 1160 bytes -> 1 DATA chunk
- 1161 bytes -> 2 DATA chunks
- 2320 bytes -> 2 DATA chunks
- 2321 bytes -> 3 DATA chunks

各 serialized SCTP packet が `<= 1191` であること。

各 chunk の reassemble 後 payload が original message と一致すること。

### D. custom MTU

`mtu = 1052` を指定し、derived payload が 1024 になることを確認する。

1025-byte message が 2 fragments になること。

これにより CodeTrellis の現行 `1200 -> 1024` source patch 相当を public config だけで再現できることを示す。

### E. ordered / unordered

同じ payload について:

- `ordered: true`
- `ordered: false`

の両方で同じ fragment size limit が使われること。

unordered の場合は既存 `SCTP_DATA_UNORDERED` flag のみが変わり、MTU 計算には影響しないこと。

### F. reliable / partially reliable

同じ fragmentation path を使うことを保証するため、少なくとも:

- reliable
- `maxRetransmits`
- `expiry` / maxPacketLifeTime 相当

で packet size が MTU を超えないことをテストする。

partial reliability の metadata によって fragment size が変わらないこと。

### G. RTCPeerConnection config propagation

```ts
const pc = new RTCPeerConnection({
  sctp: { mtu: 1052 },
});
```

から DataChannel/SCTP transport を生成し、low-level SCTP まで 1052 が伝播していることを確認する。

また default config で 1191 が使用されること。

### H. `setConfiguration()`

- SCTP transport 作成前の変更: success
- transport 作成後に同じ値を指定: success
- transport 作成後に異なる MTU へ変更: reject
- invalid MTU: reject

### I. browser interoperability / E2E

既存 browser E2E がある場合、Chrome/Chromium ↔ werift DataChannel で大きな message を round-trip するテストを追加または拡張する。

最低限:

- payload > 1160
- payload > 64 KiB も既存 maxMessageSize の範囲で送受信できる
- ordered DataChannel
- unordered DataChannel が E2E framework で安定しているなら追加

DTLS で暗号化された外側から DATA chunk size を直接検査する必要はない。packet sizing 自体は low-level unit test で保証し、browser E2E は interoperability/reassembly regression の検出に使う。

## Non-goals / follow-up

このタスクには含めない。

### Path MTU Discovery

Pion #476 でも PMTU は別 issue として扱っている。werift でもまず configurable/safe MTU を導入し、PMTU discovery や black-hole detection は別タスクにする。

### SCTP message interleaving / I-DATA

werift の現行 SCTP 実装には I-DATA がないため、本タスクでは DATA header だけを対象にする。

将来 I-DATA を実装する場合は Pion のように:

```ts
maxPayloadSizeForMtu(mtu, useInterleaving)
```

へ拡張し、I-DATA header size を反映する。

### congestion-control algorithm の全面的な Pion/RFC 追従

今回の目的は MTU と fragmentation の correctness。

Pion の `cwnd = min(4 * MTU, max(2 * MTU, 4380))` 等へ werift の congestion control を変更する作業は分離する。

## レビュー時に重点確認する点

1. **1191 を userData length として使っていないか**
   - 1191 は SCTP packet MTU
   - derived payload は 1160

2. **28 bytes を単純に引くだけになっていないか**
   - 4-byte padding まで考慮して align-down する

3. **`USERDATA_MAX_LENGTH` の置換漏れがないか**
   - fragmentation 以外にも cwnd / ssthresh / burst / timeout path に存在する

4. **`maxMessageSize` と混同していないか**
   - message size と packet MTU は別概念

5. **DTLS overhead を SCTP layer で二重に引いていないか**
   - `sctp.mtu` は Pion #476 と同様、DTLS に渡す SCTP packet 自体の上限として扱う
   - IP/UDP/DTLS overhead を `maxPayloadSizeForMtu()` でさらに差し引かない

6. **padding-aware test があるか**
   - 4-byte 境界以外の最終 fragment を含める

7. **transport 再生成時に config を失っていないか**
   - `setDtlsTransport()` が新しい low-level SCTP instance を作るため、stored options を再適用する

8. **live association の途中で MTU が書き換わらないか**
   - queue/cwnd の整合性を壊さない

---

## 期待される最終 API 例

### safer default

```ts
const pc = new RTCPeerConnection();
// SCTP outbound MTU = 1191
// DATA max payload = 1160
```

### VPN / overlay 用にさらに小さくする

```ts
const pc = new RTCPeerConnection({
  sctp: {
    mtu: 1052,
  },
});
// DATA max payload = 1024
```

### low-level SCTP

```ts
const client = SCTP.client(transport, 5000, {
  mtu: 1191,
});
```

これにより downstream project は werift source の `USERDATA_MAX_LENGTH` を直接 patch する必要がなくなる。

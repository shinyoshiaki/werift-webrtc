### Summary

The VP8 RTP packets that werift sends (from `createMp4WebmRegister()` and `createDummyRegister()`) always use the minimal 1-byte VP8 payload descriptor (`0x10` for the first packet of a frame, `0x00` otherwise). There is no extension byte, so no PictureID and no TL0PICIDX.

RFC 7741 makes these fields optional, so this is not a spec violation. But browsers (libwebrtc) always include a PictureID. Media servers and SFUs that expect the same packets as browsers send may then not handle werift's VP8 the same way.

### Observed behavior

- Peer-to-peer from werift to Chrome, the VP8 decodes fine.
- Through a mediasoup-based SFU, the same VP8 stream is never forwarded to subscribers. The sender's `outbound-rtp` keeps increasing and PLIs come back, but subscribers receive 0 video packets. Opus audio through the same SFU is forwarded normally.
- If the descriptor is rewritten just before sending to add a 15-bit PictureID and TL0PICIDX (`X=1, I=1, L=1`, both incremented per frame), the video is forwarded and decodes in Chrome.

We have not identified which part of the SFU path depends on these fields. The current mediasoup v3 `VP8::Parse` accepts the minimal descriptor, so it may depend on the SFU's version or configuration.

### Reproduction (werift only)

```js
import { createDummyRegister, createMp4WebmRegister, installPolyfill } from "werift/polyfill";

const source = process.argv[2] ?? "dummy";
installPolyfill({
  mediaRegister: [
    source === "webm"
      ? createMp4WebmRegister({ path: process.argv[3], loop: true })
      : createDummyRegister(),
  ],
});

const stream = await navigator.mediaDevices.getUserMedia({ video: true });
const [track] = stream.getVideoTracks();

const sender = new RTCPeerConnection();
const receiver = new RTCPeerConnection();
sender.onicecandidate = ({ candidate }) => candidate && receiver.addIceCandidate(candidate);
receiver.onicecandidate = ({ candidate }) => candidate && sender.addIceCandidate(candidate);

let count = 0;
receiver.ontrack = ({ track: remote }) => {
  remote.onReceiveRtp.subscribe((rtp) => {
    if (count++ < 5) {
      const head = [...rtp.payload.subarray(0, 4)].map((b) => b.toString(16).padStart(2, "0")).join(" ");
      console.log(`VP8 payload head: ${head}  X=${rtp.payload[0] >> 7}`);
    }
    if (count === 5) process.exit(0);
  });
};

sender.addTrack(track, stream);
await sender.setLocalDescription(await sender.createOffer());
await receiver.setRemoteDescription(sender.localDescription);
await receiver.setLocalDescription(await receiver.createAnswer());
await sender.setRemoteDescription(receiver.localDescription);
```

`node repro.mjs dummy` / `node repro.mjs webm ./clip.webm` (VP8/Opus WebM)

**Actual** (werift 0.25.0, Node v24.19.0):

```
VP8 payload head: 10 11 00 00  X=0     # createDummyRegister
VP8 payload head: 10 f1 0c 00  X=0     # createMp4WebmRegister
```

**For comparison**, Chrome 140 sending VP8 (P2P, no simulcast):

```
VP8 payload head: 90 80 83 d7          # X=1, I=1, M=1 (15-bit PictureID)
```

### Where it comes from

- `nonstandard/userMedia/packetizer` `Vp8Packetizer.packetize()`: the descriptor is always `Buffer.from([offset === 0 ? 0x10 : 0x00])`. This is the packetizer `createMp4WebmRegister()` uses.
- `nonstandard/dummyMedia`: `VP8_KEYFRAME` / `VP8_DELTA_FRAME` start with the fixed `0x10` descriptor.
- `createEncodedBinaryRegister()` also appears to use the same packetizer (not verified).

### Proposal

- Make `Vp8Packetizer` emit a browser-like descriptor: `X=1, I=1, M=1` with a 15-bit PictureID that starts at a random value and increments per frame (wrapping at `0x7fff`).
- Optionally add `L=1` with a per-frame TL0PICIDX. Chrome omits it when not using simulcast; we only tested PictureID and TL0PICIDX added together.
- Reduce the chunk size by the extra descriptor bytes so the payload stays within `maxPayloadSize`.
- Apply the same descriptor to the dummy register's VP8 frames.
- If changing the default is a concern, an opt-in option on the register or packetizer would also work for us.

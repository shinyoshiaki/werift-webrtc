# WebRTC latency budget demo

This demo pairs werift with the browser's Encoded Transform API and WebCodecs. Start it with `node --experimental-transform-types --import ./tools/node-ts/register.mjs examples/mediachannel/latency_budget/server.ts` from the repository root, then open the Vite-served `index.html` in Chrome. Choose a generated 440 Hz browser source or a microphone. The server also sends a valid Opus silence fixture at 20 ms intervals, so the downstream player remains testable when a browser capture source produces no RTP. Verification on 2026-10-28 used Chrome 149.0.7827.114. The page feature-detects both `createEncodedStreams()` and `RTCRtpScriptTransform`.

| MoQ article claim                                                 | Demo behavior                                                                                                                                                                                        | What the browser still controls                                                                       |
| ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Audio should be retransmitted while a consumer can still use it   | Choose a 0, 500, or 5000 ms werift NACK retry window; the server requests missing Opus packets and retains a larger sender history                                                                   | Browser audio NACK support and packet history depend on negotiated SDP and the browser implementation |
| Faster-than-realtime delivery should be paced by media timestamps | The server can replay retained RTP immediately; the Encoded Transform reads RTP metadata, decodes Opus, and feeds an AudioWorklet queue                                                              | The default `<audio>` path still uses NetEQ and its arrival-time behavior                             |
| Each subscriber needs its own latency budget                      | Start one publisher tab and two subscriber tabs; choose 500 ms and 5000 ms per subscriber. werift fans the same upstream RTP packets out through separate senders with separate peer configurations. | The shared source and packet cache are in-memory in the example process                               |
| An interrupted response should discard buffered old audio         | The interrupt button increments generation, resets the decoder, and clears the AudioWorklet queue before a new RTP burst                                                                             | This uses an application DataChannel message; it is not a standardized track-generation RTP extension |

The server applies deterministic periodic burst loss plus random inbound loss. Its audio offer advertises generic NACK feedback for Opus because browsers may omit it by default. The native `<audio>` element is muted while the timestamp driven player is active; use the toggle to compare paths. The `outboundPackets` counter indicates whether Chrome's local capture path produced media RTP on the current runtime.

The Encoded Transform player runs before native playback and does not change NetEQ. It demonstrates an application-owned decoder and playout queue, which is how this example works around the browser's default behavior. `createEncodedStreams()` is used when present; otherwise the page attaches an `RTCRtpScriptTransform` worker. `window.__latencyBudgetResult` exposes connection, frame, loss, decode, and generation counters for smoke tests.

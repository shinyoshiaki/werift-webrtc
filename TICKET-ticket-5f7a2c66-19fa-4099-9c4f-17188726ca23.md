## Summary

When `iceInterfaceAddresses` is configured, werift can bind the UDP socket to the requested interface address but advertise a different host address in the ICE candidate.

This was measured downstream in `terraboops/agent-mobile`: the UDP socket was bound to a Tailscale address, while the SDP advertised the same port on the default LAN address. Rewriting only the host candidate address to the address the socket was actually bound to made the ICE pair use the intended tailnet address in both directions.

Downstream evidence:
https://github.com/terraboops/agent-mobile/commit/4686654b9d4b6209762ab50a7b2c43b6cf556d24

## Current implementation

On current `develop`, `Connection.gatherCandidates()` first enumerates host addresses:

```ts
let address = getHostAddresses(...);

const { interfaceAddresses } = this.options;
if (interfaceAddresses) {
  const filteredAddresses = address.filter((check) =>
    Object.values(interfaceAddresses).includes(check),
  );
  if (filteredAddresses.length) {
    address = filteredAddresses;
  }
}
```

If the explicitly configured interface address is not present in the `getHostAddresses()` result, the code silently keeps the original/default address list.

Later, each UDP `StunProtocol` is created with the explicit `interfaceAddresses`:

```ts
await protocol.connectionMade(
  isIPv4(address),
  this.options.portRange,
  this.options.interfaceAddresses,
);
```

`UdpTransport` therefore binds with:

```ts
socket.bind({
  address: interfaceAddress(protocol, interfaceAddresses),
});
```

but the host candidate is constructed from the enumerated loop variable instead of the bound socket address:

```ts
const candidateAddress: Address = [
  address,
  protocol.getExtraInfo()[1],
];

protocol.localCandidate = new Candidate(
  ...,
  candidateAddress[0],
  candidateAddress[1],
  "host",
  ...
);
```

So the transport and candidate can disagree:

```text
actual UDP bind: 100.x.y.z:PORT
advertised host candidate: 192.168.x.y:PORT
```

## Impact

This is not cosmetic. The remote peer sends connectivity checks to the address from SDP. With VPN/overlay/multi-NIC setups this can create an asymmetric or unintended path even though the local socket is correctly pinned to the requested interface.

The downstream reproduction used Tailscale, but the same mismatch can affect:

- VPN / overlay interfaces
- multi-homed hosts
- containers / namespace networking
- interfaces that are bindable but omitted by host-address enumeration/filtering

## Expected behavior

If `iceInterfaceAddresses` explicitly selects a local address, the host candidate should describe the endpoint that was actually bound.

At minimum, werift should not silently bind one address and advertise another.

## Suggested fix

Possible approaches:

1. When an explicit interface address is configured, treat it as authoritative for host candidate generation after a successful bind.
2. Derive the candidate address from the actual bound transport when the socket was explicitly bound to a concrete address.
3. If the requested interface address cannot be reconciled with candidate gathering, fail clearly instead of silently falling back to unrelated enumerated addresses.

Care is needed for the normal wildcard-bind case: when no explicit interface is requested, advertising per-interface host candidates rather than `0.0.0.0` / `::` should remain unchanged.

## Regression tests

Please cover at least:

- explicit `udp4` interface address -> socket bind address and host candidate address match
- explicit `udp6` interface address -> same
- configured address not present in the generic host-enumeration list -> no fallback to a different advertised address
- no explicit interface -> existing multi-interface candidate gathering remains unchanged
- candidate port matches the actual bound socket port
- ICE connectivity succeeds using only the explicitly selected interface candidate

This is still visible in current `develop`; I did not find an existing issue covering the bind/advertisement mismatch.

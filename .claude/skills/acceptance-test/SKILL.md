# acceptance-test

レビュアーが大量の差分や個別テストを読まずに、**チケットの目的が達成されたこと**を確認できるテストを 1 ファイルにまとめる。手本は `packages/ice/tests/ice/acceptance.test.ts`（チケット 05c13603）。

網羅は既存の個別テストと property テストが担う。受け入れテストが答えるのは、「依頼された問題が、利用者から見える形で直ったか」だけ。

## 成果物

| 成果物 | 場所 | 目安 |
| --- | --- | --- |
| 受け入れテスト | 対象パッケージの `tests/<area>/acceptance.test.ts` | 150 行以内、数秒以内 |
| 共通の準備処理の追加（必要な場合だけ） | そのテスト領域の共通ユーティリティ（例: `packages/ice/tests/utils.ts`） | 既存の helper にオプションを足す程度 |
| 検出力の記録 | チケットの該当章 | 壊した箇所と結果の表 |
| レビュー文書からの案内 | `reviews/<ticket>-*.md` の概要の直後 | 10 行程度 |

実装（`src`）は変更しない。受け入れテストのためだけに実装を変えたくなったら、作業を止めて報告する。

## 手順

### 1. 目的を「Before → After」の 1 文にする

チケットの目的・完了条件・追加要件の章を読み、**利用者から見える振る舞い**として 1 文に書く。モード（オプション）ごとに期待が違うなら、モードごとに 1 文ずつ書く。

- 例: 「下位ペア（relay）が先に疎通して接続した後、上位ペア（host）が通ると、両端が上位ペアへ移り同じ 5-tuple でデータが流れる」
- 内部の関数名や状態名ではなく、外から観測できる結果（選択された経路、届いたデータ、API の戻り値、状態遷移）で書く。
- **仕様と矛盾しないか確かめる**。モードによっては、その振る舞いが仕様上起きないことがある（例: regular nomination は選択を置き換えない）。そのモードは同じ文に押し込まず、そのモード自身の要件で別の 1 文にする。

### 2. 元の問題を再現するシナリオを決める

- 実際の部品を使う（実ソケット、ローカルの STUN / TURN サーバーなど）。モックは、タイミングを制御する最小限（特定の経路の request を止める・失わせる）にとどめる。
- 問題が起きる条件（遅れて届く候補、先に通る下位の経路など）を、`open()` のような 1 回の操作で切り替えられる形にする。
- 既存の共通の準備処理を探し、オプションを足して再利用する。新しい準備処理はテストファイルではなく共通ユーティリティに置く（AGENTS.md の「共通の Arrange は 1 ファイルにまとめる」）。

### 3. テストを書く

- 1 つの describe に、モードごとの `test.each` か、モードごとの `test` を置く。
- テスト名に、チケットのどの章の要件かを入れる（例: `"(${mode}) 9章: 下位ペアで接続した後、上位ペアが通ると両端が上位ペアへ移る"`）。
- Arrange / Act / Assert で書き、各 Act / Assert に日本語のコメントを付ける（AGENTS.md）。
- Assert は 1 件あたり 4 つ程度まで。「Before の状態になっている」「操作の後に After の状態になる」「両端・前後で整合する」「利用者から見える効果がある（データが届く等）」。
- 待ちは `vi.waitFor`（上限つき）を使い、固定の sleep は使わない。
- ファイル冒頭の TSDoc に、チケット番号と、このファイルが何を証明するかを 3〜5 行で書く。

骨組み:

```ts
import { describe, expect, test, vi } from "vitest";

import { createSharedArrange, expectUserVisibleEffect } from "../utils";

/**
 * Acceptance test of ticket <id>: <Before → After の 1 文>.
 * <使う実部品と、問題の条件をどう切り替えるか>.
 */
describe("acceptance: <目的の短い言い換え>", () => {
  test.each([
    { mode: "default", options: {} },
    { mode: "option-x", options: { x: true } },
  ])("($mode) N章: <要件の文>", async ({ options }) => {
    const { subject, trigger, close } = await createSharedArrange(options);

    try {
      // Act: 問題の条件のまま処理を進める。
      await subject.run();

      // Assert: Before の状態になっている (前提の確認)。
      expect(subject.state).toBe("before");

      // Act: 条件を切り替える。
      trigger();

      // Assert: After の状態になり、利用者から見える効果がある。
      await vi.waitFor(() => expect(subject.state).toBe("after"), { timeout: 3000 });
      await expectUserVisibleEffect(subject);
    } finally {
      await close();
    }
  });
});
```

### 4. 動かして、検出力を確かめる

1. 対象ファイルだけ実行して通す（例: `cd packages/ice && npx vitest run tests/ice/acceptance.test.ts`）。
2. 10 回続けて実行し、1 回も落ちないことを確かめる。落ちるなら待ちの条件か準備処理を直す（再試行で隠さない）。
3. **わざと実装を壊して、受け入れテストが落ちることを確かめる。** 目的を支える仕組みごとに 1 か所ずつ壊す（例: 選択の置き換えをやめる、再指名の判定を外す、待ち時間を無視する）。
   - 1 か所ずつ「書き換え → 対象ファイルを実行 → 元に戻す」を行う。書き換えはスクリプトで行い、`finally` で必ず元に戻す。終わったら `git status` で `src` に差分が残っていないことを確かめる。
   - 壊している間は、他のテストを並行して実行しない。`src` を編集もしない。
   - 壊した箇所ごとに、どの件が落ちたかをチケットに表で記録する。落ちない箇所があれば、Assert かシナリオが目的を捉えていない。手順 1〜3 に戻る。
4. 可能なら、修正前のリビジョンで落ちることも確かめる。比較は一時 worktree で行う（`git worktree add --detach <tmp-dir> <rev>`）。作業中の worktree を checkout / reset / stash しない（AGENTS.md）。
5. パッケージのテストと型検査を通す（例: `npm test`、`npm run type`）。共通ユーティリティを変えたら、そのパッケージ全体を実行する。

### 5. 仕様と食い違ったとき

- 受け入れテストが落ちたら、まず実装の問題か、期待（手順 1 の文）の誤りかを、チケット・仕様（RFC など）・既存テストで判断する。
- **Assert を黙って緩めない。** 実装の問題なら報告する（実装の修正は、依頼がない限り受け入れテストの作業に含めない）。期待の誤りなら、正しい要件の文に直し、変えた理由をチケットと報告に書く。
- 落ちるテストを残したまま終えない。直せない行は取り消し、取り消した理由と、確かめるのに必要な別の手段を報告する。

### 6. レビュアーへの案内を書く

- レビュー文書の概要の直後に「受け入れテスト（ここだけ見れば目的の達成を確認できます）」の小節を置く。中身は、ファイルへの `review-file:` リンク、各テスト名と確認すること（表）、実行コマンドと所要時間、壊して確かめた箇所、モードごとの違い（あれば）。レビュー文書を `review-document` CLI で管理している場合は、`ide-review-document` Skill の手順で作成・検証する。
- チケットに「受け入れテスト」の章を追加し、手順 4 の表と手順 5 の判断を記録する。

## しないこと

- 個別テストの網羅を受け入れテストに移さない（境界値・異常系・ロール変更などは既存のテストに任せる）。
- 1 つの受け入れテストに複数の目的を詰め込まない。目的が複数あるなら、件を分ける。
- 受け入れテストのために `src` を変えない。テスト専用のフックが必要なら、まず既存の共通ユーティリティで実現できないか探す。
- 実行に外部ネットワーク（公開 STUN サーバーなど）を使わない。

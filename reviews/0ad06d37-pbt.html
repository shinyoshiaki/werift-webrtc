1. まず 1 分で

PBT が確かめていること どんな順序で交渉の操作を行っても、各操作の後に両 peer が invariant と性質（オラクル）を満たし、最後に その後も使い続けられる（次の offer・ICE restart・追加・相手からの offer の後に通信できる）。

3 つの PBT

  • episode fuzzer: 最初に作った乱択テスト。交渉 episode を seed で並べる
  • シナリオ property: 主張ごとに 1 つの property。操作列をテキストで書く
  • モデル property: 操作を 1 つずつ引き、どの操作の後にも 11 種のオラクルを掛ける

固定シーンと乱数シーン

  • 固定シーン: 過去の不具合や、置き換えたケースの操作列。CI で毎回決定的に実行する
  • 乱数シーン: seed から生成する。CI は少数、深い探索は 300 seed
  • seed を指定すれば同じ操作列を再生でき、モデル property は失敗を最小の操作列に縮める

数字（16 コア）

  • CI: fuzzer 12 件、シナリオ 70 件（固定 63 + 7 seed）、モデル 55 件（固定 51 + 4 seed）
  • 深い探索 npm run pbt:deep: 2,820 件を 16 プロセスで約 2 分
  • PBT が見つけて直した実装の不具合: 10 件以上（10 章）

PBT が初めてなら、2.1（簡単な例）→ 8 章（実際のテストに当てはめた例）→ 3 章（全体像）の順に読むと分かりやすいです。

2. PBT とケーステスト

ケーステスト（tests/negotiation/cases）は「この手順なら、この値になる」を 1 本ずつ固定して確かめます。PBT（tests/pbt）は「どんな手順でも、この性質は成り立つ」を、乱数で作った大量の操作列で確かめます。

観点ケーステストPBT
入力人が決めた固定の手順seed から生成した手順（固定シーンも併用）
判定具体値（toBe("have-local-offer")、参照同一性、イベント回数）性質（「rollback すると交渉前の状態に戻る」「pending 中は選択ペアが変わらない」）
期待値の出どころリテラル、または操作前に保存した値操作前後の比較と、SDP から決まる規則
得意なこと仕様の具体値、タイミング、特殊な環境想定外の操作順、状態の組み合わせ
失敗したときテスト名で何が壊れたか分かるseed・操作ログ・最小の操作列が出る

両者は役割分担します。PBT で探して見つかった不具合は、最小の操作列を固定シーンとして残し、CI で毎回決定的に検出します。タイミング・モック・TURN・close など、操作列で表せないものはケースに残します（12 章）。

2.1 いちばん簡単な例で考える

PBT の考え方は、WebRTC と関係ない例のほうが分かりやすいです。「配列を並べ替える関数 sort」を試すとします。

例ベースのテスト（ケーステスト）

sort([3, 1, 2]) は [1, 2, 3] になる。
人が入力と答えを 1 組ずつ書く。書いた組しか確かめない。

プロパティベーステスト（PBT）

どんな配列 xs でも、sort(xs) は昇順に並び、要素の個数と中身は xs と同じ。
入力は乱数で何百通りも作り、答えは書かずに「性質」で判定する。

どの PBT も、次の 3 つの部品でできています。このプロジェクトの 3 つの PBT も同じです。

① 入力をどう作るか（生成器）

  • sort の例: 長さも値もばらばらの配列を乱数で作る
  • このプロジェクト: createOffer・setRemoteDescription・rollback などの操作の並びを乱数で作る

② 何を判定するか（性質・オラクル）

  • sort の例: 昇順か、要素が同じか
  • このプロジェクト: 「rollback すると交渉前に戻る」「交渉中も確定済みの通信は止まらない」など、どの操作の後でも成り立つはずのこと

③ 失敗をどう再現するか（seed）

  • 乱数の種（seed）が同じなら、同じ入力ができる
  • 失敗したら seed を指定して再生し、操作を減らして最小の再現手順を探す

2.2 この文書で使う言葉

言葉意味
性質（property）どんな入力でも成り立つはずのこと。PBT はこれが破れる入力を探す
オラクル性質を判定するコード。モデル property では oracles.ts にまとめている
invariant交渉のどの時点でも成り立つ内部の整合性（current の SDP と実際の経路・ICE・DTLS の一致など）。3 つの PBT すべてが各操作の後に確かめる
seed乱数の種。同じ seed からは同じ操作列ができる
シーン・シナリオ・episode1 回のテストで実行する操作の並び。PBT ごとに呼び方と粒度が違う（3 章）
固定シーン乱数ではなく人が決めた操作列。過去の不具合や、置き換えたケースの手順を CI で毎回実行する
縮小（shrink）失敗した操作列から操作を減らし、まだ失敗する最小の手順を探すこと
継続確認expectSessionContinues。最後に次の交渉や ICE restart をして、その後も通信できるかを確かめる

4. 再現・縮小・固定シーン

seed から同じ操作列を作る

乱数は seededRandom(seed)（shared/random.ts:6）だけから引きます。同じ seed なら同じ操作列になるので、失敗した seed を環境変数で指定すれば再生できます。テスト名にも再生用のコマンドが入っています。

seed 38 (replay: WERIFT_NEGOTIATION_MODEL_SEED=38 WERIFT_NEGOTIATION_MODEL_SEEDS=1 WERIFT_NEGOTIATION_MODEL_STEPS=10)

ただし、実際の通信を使うので、結果は CPU の負荷に左右されることがあります。npm run pbt:deep は失敗した seed を単独で再実行し、通れば「flaky」、再び落ちれば「FAILED」と分けて報告します。

失敗を最小の操作列に縮める（モデル property）

実例: 2.19 で見つけた「適用済みの local description が交渉の外で書き換わる」不具合は、seed 38 の 10 操作から次の 4 操作に縮みました。

{"start":"unnegotiated","ops":[["a","addRecvonly",{"kind":"video"}],["a","offer",{"iceRestart":true}],["b","answer"],["a","splitOffer",{"mid":"1"}]]}

固定シーンとして残す

縮小した操作列は、名前と由来（ref）を付けて model/scenes.ts に追加します。固定シーンは乱数シーンと同じオラクルで判定されるので、期待値を書く必要はありません。

{
  name: "an answer releases the SCTP MID only an unapplied createOffer reserved",
  ref: "2.9-4; origin: model property (seed 545): the reserved MID collided with the peer's next m-line",
  start: "media",
  ops: [["b", "offer"], ["b", "dataChannel"], ["b", "createOnly"], ["a", "answer"]],
}

5. episode fuzzer

最初に作った PBT です（fuzz/negotiationTransactionProperty.test.ts）。1 step で次のどれかを 1 回行い、各操作の後に両 peer の invariant を検査し、step の後に video・audio・DataChannel の実通信を確かめます。

episode内容
交渉 episode（70%）
fuzz/episodes.ts:105		offerer、offer の種類（ICE restart、audio の追加、BUNDLE の分割・統合など）、終わり方（answer / pranswer → answer / rollback / replacement）、end-of-candidates を乱数で選ぶ
routing key の変更（30%）
fuzz/episodes.ts:225		RTX の付け替え、extmap URI の新 ID への移動（pending 中も現在の RTP が流れる）、使用中の extmap ID の再割り当て（拒否され、状態は変わらない）
description pool
fuzz/episodes.ts:369		保存した offer / answer を後で、または再度適用する（生成済み description の再利用契約）
m-line の拒否
fuzz/episodes.ts:289		相手が application / video / audio の m-line を port 0 で拒否する

乱数を系統に分けている: pool と拒否は後から足した episode なので、主操作とは別の乱数（seed × 7919 + 13 と seed × 104729 + 7）から引きます。こうすると、episode を足しても既存の seed の主操作は変わらず、過去に不具合を見つけた seed（3・4・6・17・19・28、20 step の 254・302・1385）が同じ操作を再生し続けます。

6. シナリオ property

主張（claim）ごとに 1 つの property を持ち、それぞれ固定シーンと乱数シーンを実行します（scenario/negotiationScenarioProperty.test.ts）。7 つの property はファイル内で並行に動きます（describe.concurrent）。

property主張判定関数
commitfinal answer は、両アプリが求めた方向を確定するjudgeCommit
pending交渉中も、確定済みの transport・DTLS role・SCTP・remote の ICE 資格情報・選択ペアの世代を保つjudgePending
rollbackrollback は交渉前の状態に戻すjudgeRollback
reject拒否された記述操作は、どちらの peer も変えないjudgeReject
trickletrickle した候補は、自分の世代の description に 1 回だけ入るjudgeTrickle
iceICE 資格情報は commit まで restart の要求に従う（W3C の [[LocalIceCredentialsToReplace]]）judgeIce
createoffer / answer を作るだけでは何も変わらないjudgeCreate

操作列はテキストで書きます（scenario()）。1 行か ; で 1 ステップです。

a offer restart; b reply pranswer edit=inactive; alive silent; a rollback

「a が ICE restart の offer を出す → b が inactive に書き換えた pranswer を返す → どのストリームも届かないこと（alive silent）を確かめる → rollback する」という意味です。各ステップの後に、宣言した結果（受理・拒否とエラー名）、両 peer の invariant、JSEP の状態遷移、その property の判定を行います。

7. モデル property

いちばん新しく、いちばん広い PBT です（2.17〜2.19）。どの操作の後でも成り立つ性質だけで判定するので、シーンには期待値を書きません。操作列は [peer, 操作名, 選んだ値] のデータです。

  • 開始状態を選ぶ
    接続済み（video 双方向 ＋ DataChannel）/ 未交渉（a が video ＋ DataChannel）/ 未交渉（a が video だけ）
  • 操作を 1 つ引く
    a か b を選び、その時点で適用できる操作から重み付きで選ぶ
  • 実行する
    記述操作（setLocal / setRemote / addIceCandidate）はハーネス経由
  • 毎回検査する
    invariant → 通信の性質 → 11 種のオラクル
  • 最後に
    DataChannel が開くこと、expectSessionContinues

実際のシーンを 1 つずつ追った例は 8.3 にあります。

両 peer の設定は modelConfig（model/generator.ts:49）です。VP8（NACK・PLI・REMB・transport-cc）と RTX、H264、Opus、PCMU、MID と transport-cc の header extension を持たせ、codec・feedback・RTX・extension の変化を作れるようにしています。

7.1 操作（STEPS）

分類操作
アプリの操作addTrack、addRecvonly、dataChannel、attachTrack（track を付けて sendrecv にする）、direction、codecPreferences（先頭の codec だけ／全体の逆順）、stop、restartIce。stable のときと、remote offer の pending 中（remote offer が作った transceiver にも）に行える
交渉offer（ICE restart あり／なし）、splitOffer（BUNDLE 分割）、glare、replacementOffer、pranswer、answer、lateAnswer（createAnswer の後、適用前に preferences か track を変える）、rollback
再利用・作るだけreapplyRemote（同じ remote description の再適用）、createOnly（offer / answer を作るだけ。offer は保存）、applyStale（保存した古い offer の適用）
ICEtrickle（新しい候補か description にある候補を、重複や end-of-candidates も含めて）
通信路wireOffer / wireReply（配送途中で SDP を書き換える。7.2）、settle（接続の確立を待って通信を確かめる）

7.2 通信路の SDP 書き換え（model/wireMutations.ts）

offer・pranswer・answer を配送する途中で、19 種の書き換えのどれかを掛けます。書き換えは 2 種類に分かれ、扱いが違います。

same 同じ session を表す（8 種）

codec の部分集合・逆順、fmtp、NACK・PLI・transport-cc の削除、max-message-size、end-of-candidates の削除。
両 peer は一致しているとみなす（c.equivalent）ので、通信と commit のオラクルもそのまま掛かる。

誤記述 送り手を誤って記述する（11 種）

m-line の inactive・拒否、SSRC の入れ替え・更新、RTX の削除、payload type の付け替え、header extension ID の移動・入れ替え。
両 peer は食い違ったままになるので通信は求めず、次の書き換えのない交渉で回復することを求める。

どちらも、current の session が交渉した payload type や header extension ID を付け替える書き換えなら、InvalidModificationError での拒否を求めます（RFC 3264 8.3.2、RFC 8285 7。remapsCurrentKeys）。それ以外は、受理されるか、状態を変えずに拒否されるかのどちらでもよく、拒否されたら元の description を配送し直します（deliver）。final answer には same の書き換えだけを使います。answerer が自分の answer と違う session を持ち続ける状態は、実在の peer 同士では起きないためです。

7.3 オラクル（ModelOracles.after）

記述操作のたびに、ハーネスが invariant と通信の性質を検査した後、次のオラクルを呼びます。

オラクル主張
traffic両 peer が同じ session を持つ間、送受信できるはずのストリームは RTP が 2 秒以内に届き、開いている DataChannel は双方向に届く（ハーネスの c.expectTraffic()）
jsep受理された操作は、その種類の signaling state に進み、適用した description を pending / current に置く。相手の peer は変わらない。m-line のない transceiver は currentDirection を持たない
rollbackdescription・ICE 資格情報・経路・確定済み MID・送信パラメータ・受信表・transport-cc feedback が交渉前に戻る。remote offer が作っただけの transceiver は消え、アプリが残したものは作成時の状態になる
events状態が変わったときだけ signalingstatechange が出る。rollback と再適用では track などを通知しない。remote の DataChannel の通知は 1 回
idempotent / create同じ remote description の再適用や、offer / answer を作るだけでは何も変わらない
trickle候補は SDP に 1 回だけ入り、現在の世代のものは稼働中の checklist にも届く
feedbackPLI は実効の a=rtcp-fb に nack pli があるときだけ送られ、transport-cc があれば feedback が動く。確定しない操作は transport-cc を始めない
ice確定しない操作は、接続済み transport の選択ペアを変えない
commit両側の currentDirection は鏡像で、送信 codec は相手の受信表にある。BUNDLE の transport が変わらない m-line は DTLS をやり直さない
channelsアプリの DataChannel は閉じず、最後に交渉済みなら両側で開く
reject拒否された操作は状態を変えない（ハーネスが negotiationSnapshot を比べる）

episode b addAudio pranswerRollbackb が audio を足して offer し、pranswer（仮の answer）まで進めてから rollback する
eoc候補の終わり（end-of-candidates）も送る
mutation a rtxPairinga の offer の中で RTX（再送用のストリーム）の対応を付け替えて b に適用し、pending のまま現在の RTP が届くことを確かめてから rollback する
pool b … stale offer refused保存しておいた古い offer の適用は拒否され、状態は何も変わらない（生成済み description の再利用契約）

② 判定: 細かい操作（createOffer、setLocalDescription など）の 1 つ 1 つの後に、両 peer の invariant を検査します。各 step の後には、video・audio・DataChannel を双方向に実際に送り、届くことを確かめます。拒否されるはずの操作（stale offer refused）では、両 peer の状態が操作の前と同じかも比べます。

③ 再現: WERIFT_NEGOTIATION_FUZZ_SEED=1 WERIFT_NEGOTIATION_FUZZ_SEEDS=1 で同じ 8 step を再生できます。失敗すると、上の記録がエラーメッセージに付きます。

この形で見つかった不具合の例: 回帰 seed 19 は「古い接続確認（check）が、捨てたはずの候補ペアを選んでしまう」不具合を見つけました。修正した今も、CI で seed 19 を毎回再生しています。

8.2 シナリオ property: pranswer の後の rollback

① 入力: rollback の property の固定シーンです（negotiationScenarioProperty.test.ts）。テキストは o（offerer）と t（answerer）で書かれ、(o=a) と (o=b) の 2 通りに展開されます。次は (o=a) です。

a offer; b reply pranswer; a rollback; alive
#ステップ何が起きるかその後に確かめること
1a offer接続済みの session で、a が再交渉の offer を作って適用し、b に届ける基本検査: 操作が受理されたか、両 peer の invariant、JSEP の状態遷移（a は have-local-offer など）、操作していない peer が変わっていないこと
2b reply pranswerb が仮の answer（pranswer）を返す。仮でも暫定の通信が始まりうる
3a rollbacka が交渉を取り消し、相手側も取り消す基本検査 ＋ rollback の判定（下）
4alive実際に通信してみる交渉済みの全ストリームと DataChannel が届く

② 判定: rollback の判定（judgeRollback）は、交渉を始めた時点（episode の開始時）に保存した状態と、rollback 後の状態を比べます。

  • 交渉の前からあった transceiver は、同じ MID と m-line の位置のまま残る
  • 交渉中にアプリが足した transceiver は残るが、MID と m-line を持たない
  • 予約された ICE restart は捨てられ、ICE の資格情報は current のもの
  • SSRC の経路・選択ペアなど、そのほかの状態も開始時と同じ

判定には「何が何になる」という具体値がありません。「開始時と同じ」という比較だけなので、同じ判定を乱数で作った rollback にもそのまま使えます。

③ 再現: 固定シーンなので、CI で毎回同じ手順を実行します。同じ property の乱数シーン（seed 1 など）は、rollback で終わることが多い episode を乱数で並べます。

この形で見つかった不具合の例: 乱数シーンの seed 15 と 52 が、「have-remote-pranswer から rollback すると、交渉中に足した transceiver に MID が残る」不具合を見つけました。

8.3 モデル property: seed 1 と PLI のシーン

乱数シーンの例: seed 1

① 入力: seed 1 からは、開始状態「未交渉（a が video と DataChannel を持つ）」と、次の 10 操作ができます（generateScene）。モデル property は episode ではなく 1 操作ずつ、その時点で適用できる操作の中から乱数で選びます。

#操作意味直後に判定するか
1["a", "offer", { iceRestart: false }]a が最初の offer を出し、b に届けるする（setLocal と setRemote のそれぞれの後）
2["b", "codecPreferences", { index: 0, codec: "video/VP8" }]offer の処理中に、b が受け取った video の codec を VP8 に絞るしない（アプリの操作。次の記述操作で判定）
3["a", "createOnly"]a が offer を作るだけで適用しないする（作るだけでは何も変わらない）
4〜7dataChannel ×2、addTrack audio、dataChannela が DataChannel と audio を足すしない
8["b", "codecPreferences", { index: 0, reversed: true }]b が codec の優先順を逆にするしない
9["a", "replacementOffer", { iceRestart: false }]a が答えを待たずに新しい offer で置き換える（足した audio と DataChannel を含む）する
10["a", "addTrack", { kind: "video" }]a が video を足すしない

② 判定: 記述操作のたびに invariant・通信・11 種のオラクルが走ります。たとえば 9 の置き換えの後には、次のことを確かめます。

  • jsep: a は have-local-offer のまま、pending の local description が新しい offer になり、current は変わらない
  • events: b の既存の transceiver について、track イベントがもう一度出ない（2.17 で直した不具合の再発を防ぐ）
  • channels: a が足した DataChannel は閉じず、a の SCTP transport の上にある

シーンの最後には、交渉済みの DataChannel が両側で開くことを確かめます（この seed では交渉が途中なので対象外）。その後に継続確認を行います。継続確認は、途中の交渉を rollback してから、次の offer・ICE restart・追加・相手からの offer を行い、通信を確かめます。

③ 再現: WERIFT_NEGOTIATION_MODEL_SEED=1 WERIFT_NEGOTIATION_MODEL_SEEDS=1 WERIFT_NEGOTIATION_MODEL_STEPS=10 で同じ 10 操作を再生できます。失敗すると、操作を 1 つずつ外して最小の失敗シーンを出力します（4 章）。

固定シーンの例: PLI のシーン

固定シーン「PLI a re-offer adds starts only at its answer commit, not while pending or after a rollback」です（model/scenes.ts）。PLI は「映像が乱れたので、次の完全なフレームを送って」と受信側から送り手に頼む RTCP の要求で、SDP の a=rtcp-fb:<pt> nack pli で交渉します。このシーンは、PLI を後から足す再交渉で「確定するまでは古い設定のまま、確定したら新しい設定」になるかを試します。

#操作（シーンの 1 行）何が起きるか
1["a", "wireOffer", { mutation: "noPli" }]a の offer を、通信路で PLI を消してから b に届ける
2["b", "answer"]b が答えて確定する。この session では PLI を交渉していない
3["a", "offer"]a が PLI ありの offer を出す（まだ確定していない＝ pending）
4["b", "rollback"]提案を取り消す
5["a", "offer"]もう一度提案する
6["b", "answer"]今度は PLI ありで確定する

8.4 3 つの例から分かること

入力の粒度が違う

  • fuzzer は「交渉 1 回分」、シナリオは「人が読めるテキスト」、モデルは「1 操作ずつ」
  • 粒度が細かいほど、人が思いつかない途中の割り込み（offer の処理中の preferences 変更など）が出る

判定に具体値がない

  • どれも「開始時と同じ」「SDP の規則どおり」「通信できる」で判定する
  • だから同じ判定を、固定シーンにも乱数シーンにも使える

見つけたら固定する

  • 乱数で見つけた手順は、回帰 seed（fuzzer）か固定シーン（シナリオ・モデル）として残す
  • CI では毎回それを再生し、同じ不具合の再発を確実に検出する

9. オラクルを書くときの注意

期待値を実装と同じ論理で作らない

  • オラクルは SDP（RFC・W3C の規則）と、操作前に保存した状態との比較で書く
  • 実装の内部の表を「正」として読むと、実装と同じ誤りをテストも持つ
  • 例: PLI の可否は受信側の内部の表ではなく、SDP の a=rtcp-fb から決める

失敗したら「実装か、性質の定義か」を切り分ける

  • オラクルを足すたびに、仕様どおりの動作を誤って失敗にする例が見つかる
  • 2.19 だけで 10 件ほど性質の定義を直した（例: answer は offer の payload type を使うのが SHOULD なので、payload type か codec 名の一致で交渉済みとみなす。停止した transceiver は MID がなくても stopped）
  • 実装の不具合と判断したら、develop で同じか確かめ、修正前に失敗する固定シーンを追加する

前提が成り立つときだけ判定する

  • 通信は「両 peer が同じ session を持つ」間だけ求める（片側だけ確定した間や、誤記述の書き換えの後は求めない）
  • 接続が確立していない transport は、操作の後は待たずに対象外にし、シーンの最後だけ 10 秒待つ

シーンの前提が弱いと見逃す

  • transport-cc が最初から動いている session では、「pending 中に誤って始まる」不具合（C1）を区別できない
  • current の世代が end-of-candidates で終わっていると、同じ世代の trickle（I2）を試せない
  • 固定シーンを追加したら、一時 worktree でバグを入れて実際に落ちることを確かめる

12. 向いているもの・向かないもの

種類扱い理由
invariant・状態が変わらないこと・通信の継続・rollback の復元PBT オラクルどの操作の後でも成り立つので、乱数の組み合わせで広く確かめられる
過去の不具合の手順PBT 固定シーンCI で毎回決定的に検出する
タイミング（同じ tick、n 個目の microtask）ケース 表駆動操作列の間に await が入るので表せず、seed で再現できない
モック・故障注入ケース期待値が故障ごとの規則で、汎用の性質にならない
TURN・ICE-lite など外部環境、closeケース実時間に依存して重い。close の後はオラクルが使えない
ICE・DTLS・BUNDLE・RFC の codec 規則の具体値ケースwerift 同士では両側が同じように間違えても通ってしまう
ブラウザとの相互接続E2E2.20 で、ブラウザ風の入力をあえて作るケースを削除し、実際の Chrome との E2E（e2e/）の責務とした（E2E への追加は未実施）

モデル property の通信路の書き換え（7.2）も「相手の SDP を作る」ものですが、目的は相互接続ではなく「どんな入力でも状態の一貫性が保たれること」です。2.20 の削除対象（tests/negotiation/cases）の外にあるので残しています。

13. 失敗したときの読み方

AssertionError: case "seed 38 (replay: WERIFT_NEGOTIATION_MODEL_SEED=38 …)" (2.1-5 2.1-10 …; property: model)
after operation #29: traffic (current differs)          ← 最後に実行した記述操作・検査
setLocal(offer): current: expected [ …(2) ] to deeply equal [ …(2) ]   ← どのオラクルの何が違ったか
operations:                                              ← 直前までの操作ログ
  #1 start: unnegotiated
  #2 op 1: b addTrack {"kind":"video"}
  …
  #27 op 10: a splitOffer {"mid":"1"}
  #28 setLocal(a, offer)
smallest failing scene: {"start":"unnegotiated","ops":[…]}   ← 縮小した最小シーン
  1. オラクル名とメッセージで、どの主張が破れたかを見る（例: setLocal(offer): current は jsep オラクルの「offer は current を変えない」）。
  2. 最小シーンを固定シーンとして一時的に追加し、再現させる。
  3. 実装の不具合か、性質の定義の誤りかを切り分ける（9 章）。develop と比べるときは、別の一時 worktree を使う。
  4. 実装を直したら、修正前に失敗することを確かめてから、固定シーンを残す。

0. この文書について

このチケットで実装した WARP（SPED + DTLS 1.3 + 0.5-RTT）対応 WebRTC transport を、根拠となる RFC と draft の条文に対応づけて解説します。各節は次の色分けで書いています。

1. 全体像と最重要の不変条件

WARP は、ICE の接続確認（STUN Binding）に DTLS の handshake を相乗りさせ（SPED）、ICE と DTLS 1.3 を同時に進めることで接続までの往復を減らす仕組みです。werift の transport は次の層でできています。

最重要の不変条件SDP fingerprint の照合が済むまで、DataChannel のデータ・RTP・RTCP を上位へ一件も配送しない。DTLS の暗号的な認証（Finished の検証）と、WebRTC としての相手の認証（SDP に書かれた証明書であること）は別物で、後者が済んで初めて配送する。

典型的な接続（SPED 有効、DTLS server が early server data を opt-in）の流れは次のとおりです。

2. DTLS 1.3 コア（packages/dtls）

2.1 3 段階の readiness

仕様

RFC 9147 §5.8.1: 相手の Finished を受け取るまでは、epoch 3 以上の application data を破棄するかバッファしなければなりません。

Implementations MUST either discard or buffer all application data records for epoch 3 and above until they have received the Finished message from the peer.

RFC 9147 §5.8.1 の状態機械では、最終 flight の ACK を受け取ると FINISHED に遷移します。server は client の最終 flight を受け取った時点で FINISHED になり、その後も再送された最終 flight には ACK を再送しなければなりません（MUST）。

実装

DTLS の進行を、一度だけ true になる 3 つのフラグで表します（dtls/src/engine/v1_3/connection-base.ts:96）。

マイルストーン意味server で立つ場所client で立つ場所
writeReadyepoch 3 で送信できる自分の Finished 送信後 dtls/src/engine/v1_3/flight/server/flight4.ts:665自分の Finished 送信後 dtls/src/engine/v1_3/flight/client/flight5.ts:130
peerHandshakeAuthenticated相手の Finished を検証した（暗号的な認証）dtls/src/engine/v1_3/flight/server/flight5.ts:48dtls/src/engine/v1_3/flight/client/flight5.ts:41
handshakeComplete最終 flight の ACK まで済んだclient の最終 flight の全 record を ACK し終えた時点 dtls/src/engine/v1_3/record-rx.ts:363自分の最終 flight が ACK された時点 dtls/src/engine/v1_3/record-rx.ts:786
werift の判断readiness を 3 段階に分けるのは werift の設計で、仕様にこの概念はありません。peerHandshakeAuthenticated は DTLS の暗号的な検証だけを表し、SDP の照合は含みません（3.1）。

2.2 server の 0.5-RTT application data

仕様

RFC 8446 §4.4.4: server は最初の flight を送った後にデータを送ってかまいません（MAY）。ただしその時点では、相手の身元も生存も保証されていません。

Servers MAY send data after sending their first flight, but because the handshake is not yet complete, they have no assurance of either the peer's identity or its liveness (i.e., the ClientHello might have been replayed).

RFC 9147 §4.2.1: 受信側はそれをバッファしても破棄してもかまいません（MAY）。上位が SCTP のような信頼性のある transport ならバッファすべきです（SHOULD）。

For instance, the server may send its Finished message and then start transmitting data. Implementations MAY either buffer or discard such records, though when DTLS is used with a reliable transport (e.g., SCTP [RFC4960]), they SHOULD be buffered …
実装server は Finished の送信後に epoch 3 の鍵を設定し、writeReady を立てます。0.5-RTT の送信を実際に許すかどうかは WebRTC 層が判断し、明示的に opt-in した server だけに限ります（3.4）。0-RTT（epoch 1）は実装していません。この文書の「early data」は TLS の early_data 拡張ではなく、接続確定前に届く epoch 3 のデータを指します。

2.3 early data の受信バッファ

実装

接続確定前に届いた epoch 3 の record は、受信順を保つ上限付きキュー dtls/src/engine/v1_3/early-data-buffer.ts:9 に保持します。上限は 256 record / 256 KiB / 2 秒で、DTLS engine、WebRTC の受信 gate、early media バッファの 3 つが同じ定数 dtls/src/engine/v1_3/types.ts:90 を使います。

  • 上限を超えたら、古い record を残して新しく届いた record を捨てます（順序の途中を欠かさないため）。
  • 先頭の record が期限切れになったら、キュー全体を捨てます（dtls/src/engine/v1_3/early-data-buffer.ts:106）。欠けた先頭の後ろだけを上位に見せないためです。
  • 期限はタイマーだけでなく、読み出し（snapshot() / packets）と追加・取り出しのたびに評価します。Node のタイマーは monotonic clock で動くため Date.now() より約 1 ms 早く発火することがあり、そのときは再武装します（dtls/src/engine/v1_3/early-data-buffer.ts:124）。以前はこの早期発火で期限切れの data が残り続ける不具合がありました。
  • EARLY_APP_DATA_UNLIMITED が外すのは record / byte の上限だけで、2 秒の retention は残ります（dtls/src/engine/v1_3/types.ts:108）。
werift の判断2 秒の retention と「先頭が期限切れなら全体を捨てる」方式は werift の判断です。overflow や期限切れは handshake を失敗させません（drop として統計に計上）。

テスト: early_data_buffer.test.ts、self13_early_server_appdata.test.ts

2.4 最終 flight の ACK と server の完了判定

仕様RFC 9147 §5.8.1: server は FINISHED 状態でも、再送された client の最終 flight に ACK を再送しなければなりません。§7.1: 受信した flight の record は ACK で確認します。
… when in the FINISHED state, the server MUST respond to retransmission of the client's final flight with a retransmit of its ACK.
実装

server の handshakeComplete は「client の Finished を受け取り、最終 flight（相互認証なら Certificate・CertificateVerify・Finished）の全 record を含む ACK の送信に成功した」時点で立てます（dtls/src/engine/v1_3/record-rx.ts:363）。

  • 受理した record は dtls/src/engine/v1_3/connection-base.ts:248 に記録し、その record を含む ACK の送信が成功したときだけ消します（dtls/src/engine/v1_3/flight-tx.ts:788）。
  • sendAck() は送信前に ACK 対象を queue から取り出すため、送信が throw したら対象を queue に戻します（dtls/src/engine/v1_3/flight-tx.ts:773）。
  • 完了判定は、通常の ACK の後だけでなく、replay / 重複 handshake への再 ACK が成功した後にも行います。最初の ACK の送信が（例えば Finished の処理中の世代変更で）失敗しても、再送への ACK で完了できます。

テスト: 最終 ACK の再送で完了、相互認証で Finished の ACK 失敗中は完了しない

2.5 readiness の latch 契約（DTLS 1.2 / 1.3 共通）

実装

各マイルストーンは association で一度だけ true になり、close・失敗・renegotiation でも false に戻りません。終了は onClose / onError で通知します（dtls/src/socket.ts:146）。

  • DTLS 1.2 には段階がないため、最初の connected で 3 つ同時に latch します（dtls/src/socket.ts:72）。
  • 到達済みのマイルストーンを待つ waiter は、close 後でも即座に resolve します。終了状態より先に到達済みかを判定します（dtls/src/socket.ts:275）。DTLS 1.3 を含む設定（dual 構成で 1.2 に決まった場合も含む）と 1.2-only の挙動をそろえています。

テスト: self_readiness_latch.test.ts（DTLS 1.3 / dual client → 1.2 server / DTLS 1.2）

2.6 受信世代（rxGeneration）による ICE restart の隔離

werift の判断受信世代は werift 独自の仕組みです。近い根拠は RFC 9147 §4.5.2（無効な record は黙って捨てる）と draft §9.1（埋め込まれた DTLS は ICE の認証で保護され、再送の重複は replay として扱う）です。
実装

datagram を受け取った時点の ICE generation を DTLS の受信キューまで運び、処理する時点で世代が変わっていたら捨てます（dtls/src/engine/v1_3/host.ts:15）。restart 後に旧世代の SPED inject が新しい association を動かさないためです。

このフィルタを設定するのは SPED transport だけです（webrtc/src/transport/dtls.ts:941）。SPED でない経路では restart をまたいでも同じ DTLS association の datagram なので、`warp` と同じく遮断しません（6 章）。

2.7 SRTP 鍵の exporter

仕様RFC 5764 §4.2: label "EXTRACTOR-dtls_srtp"、空の context で鍵素材を導出し、client_write_key / server_write_key / client_write_salt / server_write_salt の順に切り出します。
実装waitForWriteReady の時点で SRTP profile を反映するので、server は 0.5-RTT の段階で SRTP 鍵を導出できます。鍵を実際に使ってよいかは WebRTC 層が判断します（3.3）。DTLS client の送信鍵 = server の受信鍵であることは、両方向の RTP / RTCP の E2E で確認しています。

3. WebRTC の認証境界（packages/webrtc）

3.1 SDP fingerprint の照合を認証の境界にする

仕様

RFC 8122 §5: 提示された証明書が SDP の fingerprint と一致すれば、SDP の作成者が接続の開始者だと確信できます。§5.1: 相手が提示した中で最も優先するハッシュ関数の fingerprint 群を選び、証明書がそのどれかと一致することを確認します。

An endpoint MUST select the set of fingerprints that use its most preferred hash function (out of those offered by the peer) and verify that each certificate used matches one fingerprint out of that set. If a certificate does not match any such fingerprint, the endpoint MUST NOT establish the TLS connection.

RFC 5763 §5: 一致しなければ、ただちに media session を終了しなければなりません（"If the fingerprint does not match the hashed certificate, then the endpoint MUST tear down the media session immediately."）。

RFC 8827 §4.1: SDP は「通信を鍵ペアに束縛する fingerprint 属性」を運びます。§6.5: すべての media は DTLS-SRTP で鍵を交換した SRTP / SRTCP で、すべての data channel は DTLS で保護しなければなりません。

実装

DTLS 層の peerHandshakeAuthenticated を待ってから、webrtc/src/transport/dtls-fingerprint.ts:46 で照合します（未対応のアルゴリズムは捨て、残りの中で最も強いものだけを比較）。

  • 成功: peerAuthenticated を立て（webrtc/src/transport/dtls.ts:549）、SRTP 鍵を設定して保持していた media を復号し、受信 gate を開いて保持していたデータを配送し、最後に connected にします。
  • 不一致: webrtc/src/transport/dtls.ts:265 が gate とキューを破棄し、SPED を中止し、DTLS engine を close して failed にします。
  • 送信側の境界: 認証前の sendData は、early server の送信許可がない限り SCTPSendPermissionRevokedError を投げます（webrtc/src/transport/dtls.ts:1237）。

テスト: fingerprint 不一致で SCTP / RTP / RTCP を一件も配送しない（実 PeerConnection で、early に送られた DataChannel / RTP / RTCP が 0 件、SPED 中止、engine close、failed を確認）

3.2 受信 gate と公開 state

実装webrtc/src/transport/dtls-application-gate.ts:4。SPED の abort・fallback・同一世代の reset では discardPending() で認証前の保留分だけを捨て、世代の切り替えは restartForNewAttempt() で行います。
仕様W3C webrtc-pc §5.5.1 RTCDtlsTransportState: connecting は "DTLS is in the process of negotiating a secure connection and verifying the remote fingerprint."、connected は "DTLS has completed negotiation of a secure connection and verified the remote fingerprint."、failed は "… failure to validate the remote fingerprint" を含みます。werift の state はこの定義どおりで、fingerprint の照合が済むまで connected にしません。
werift の判断connected は final ACK を待たずに出し、early server 送信中も公開 state は connecting のままにします。

3.3 方向別の SRTP 有効化と replay 対策

仕様RFC 5764 §4.2: 鍵は方向ごとに使い分けます。§5.1:
Within each RTP session, SRTP processing MUST NOT take place before the DTLS handshake completes.
実装

鍵の設定と送受信の許可を分けています（webrtc/src/transport/dtls.ts:1080）。

方向許可する条件
受信（復号して上位へ）鍵がある かつ peerAuthenticated
送信鍵がある かつ（peerAuthenticated または early server の送信許可）

認証前に届いた media は暗号化されたまま保持し（earlyMediaPolicy: "drop" が既定で容量 0）、認証後に復号します。

仕様

RFC 3711 §3.3.2: replay 対策は RECOMMENDED です。受信側は replay list（sliding window）を持ち、window の大きさは 64 以上でなければなりません（MUST）。

Only packets with index ahead of the window, or, inside the window but not already received, SHALL be accepted. After the packet has been authenticated (if necessary the window is first moved ahead), the replay list SHALL be updated with the new index.

§3.4: SRTCP の replay 対策は、SRTCP index を index として、別の replay list で同じ規則を適用します。

実装

これまで werift の SRTP / SRTCP には replay 対策がありませんでした。rtp/src/srtp/replay.ts:8（window 64）を受信 context に追加しました。

  • SRTP の index は ROC × 216 + SEQ、SRTCP は packet 末尾の 31 bit index です。
  • check は復号前、accept（window への記録）は認証成功後だけです。改ざん packet では window は進みません。
  • 新しい SSRC の window も認証成功後にだけ作ります（rtp/src/srtp/context/srtp.ts:43）。未知の SSRC の偽造 packet を大量に送られても、受信側の状態は増えません。
  • replay は SrtpAuthenticationError のサブクラスとして投げるので、WebRTC の既存の破棄経路でそのまま捨てられます。

テスト: replay.test.ts（AES-CM / AES-GCM、replay・rollover・改ざん・未知 SSRC の偽造・SRTCP）

逸脱受信の復号は final ACK を待たず「相手を認証できた時点」で始めます（§5.1 の「handshake completes」を相手の認証完了と解釈）。opt-in した server だけは相手の認証前に SRTP を送ります。これは §5.1 から外れる実験的な拡張で、既定では無効です。

3.4 early server data の opt-in と設定の検証

実装

0.5-RTT で送ってよいかの判定は webrtc/src/transport/dtls.ts:344 の 1 か所だけで、次のすべてを満たすときに限ります: SPED transport、DTLS role が server、warp.allowEarlyServerData を opt-in、fallback していない、writeReady、DTLS 1.3、現在の attempt。

不正な組み合わせ（SPED なしの allowEarlyServerData、DTLS 1.3 を含まない SPED、SPED と helloRetryRequest）は、constructor と setConfiguration() で同期的に throw し、設定は変更しません（webrtc/src/peerConnection.ts:2214）。以前は connect() の中で失敗するだけで、呼び出し側にエラーが返りませんでした。

3.5 先頭バイトによる多重分離（RFC 7983 §7 / RFC 9443 §3）

仕様RFC 9443 §3（RFC 7983 §7 を更新）: 先頭バイトが 0–3 は STUN、20–63 は DTLS、64–79 は TURN Channel、128–191 は RTP / RTCP。どれにも当てはまらないものは破棄します。
実装DTLS の判定は webrtc/src/utils.ts:52、RTP / RTCP の判定は rtp/src/helper.ts:31。DTLS を受け取る carrier は、振り分けに加えて「認証済みの pair・現在の世代・送信元 5-tuple の一致」も確認します（ice/src/internal/datagram.ts:59）。

4. ICE / SPED（packages/ice）

4.1 SPED の STUN 属性（DATA / ACK）

仕様draft-hancke-webrtc-sped-00 §3.3.2.1: DTLS-IN-STUN-DATA は DTLS の handshake packet を 1 つ運ぶか、空の値で SPED 対応を示します。空の値を DTLS 層に渡してはいけません（MUST NOT）。先頭バイトが RFC 9443 §3 の DTLS 範囲外なら黙って捨てるべきです（SHOULD）。§3.3.2.2: DTLS-IN-STUN-ACK は受け取った DATA の CRC-32 のリストです。
実装属性のコードポイントは draft で TBD のため 0xC070 / 0xC071 を使っています（ice/src/sped/draft00/constants.ts:6）。DTLS の flight（L1）から 1 packet を round-robin で選んで DATA に入れ、MESSAGE-INTEGRITY より前に挿入します。

4.2 相手の SPED 対応の判定と fallback

仕様draft §4.3 step 1:
If this is the first authenticated STUN message received from the peer, and the DTLS-IN-STUN-DATA attribute is not present, conclude that the peer does not support SPED, and conclude SPED processing.
実装

判定は世代ごとに 1 回です（ice/src/sped/draft00/session.ts:163）。非対応なら、L1 の最初の bytes をそのまま通常の DTLS として送ります（同じ ClientHello flight で direct fallback）。DTLS を開始する前に届いた認証済みの Binding には空の DATA だけを返し、相手が「非対応」と誤判定しないようにしています。

外部に見せる状態（disabled / probing / active / fallback）と carrier（sped / direct）は ice/src/sped/runtime.ts:167 で、stats の warpSpedState / warpCarrier になります（webrtc/src/transport/dtls-stats.ts:120）。

逸脱SPED は DTLS 1.3 に限っています（draft §3.2 は DTLS 1.2 以上を目標）。dual 構成で 1.2 に決まった場合は direct DTLS に確定し、WARP の early semantics を 1.2 に持ち込みません。relay の pair・未確定の prflx・古い世代の ufrag への応答には DATA を付けません（§3.3.2.1 の「active の間はすべての Binding に DATA」からの逸脱）。

4.3 direct carrier と再送モード

仕様draft §4.4: 有効な pair ができたら DTLS を直接送ってもかまいません（MAY）。§6: SPED の間は DTLS 内部のタイムアウトを止め、最初の Binding Response で再開することを推奨します。
実装runtime を作った時点で DTLS の再送を ICE 側に任せる external モードにし、送信元が対称な認証済み Response を受け取ったら internal に戻して直接送信を許します。direct に切り替えても状態は active のままで、carrier が direct になります。

4.4 ICE restart と、以前に選択されていた pair

仕様RFC 8445 §9: restart では ufrag とパスワードを両方変えなければなりません（MUST）。restart の間も既存の data session でデータを送り続けてかまいません。
… data can continue to be sent using existing data sessions, and a new …

RFC 8842 §6: ICE restart は新しい DTLS association を必要としません。同じ component の ICE candidate はすべて同じ DTLS association に属します。

However, an ICE restart does not by default require a new DTLS association to be established. Each ICE candidate associated with a component is treated as being part of the same DTLS association.
実装

ice/src/ice.ts:234 は generation を進め、ufrag とパスワードを作り直し、SPED をリセットします。以前に選択されていた pair は退避し、相手が新しい pair に移るまでは、そこから届いた datagram に fromPreviousSelectedPair の印を付けます（ice/src/ice.ts:497）。

  • media（RTP / RTCP）はこの経路も受け付けます。
  • SPED でない DTLS も、この経路から受け付けます（webrtc/src/transport/dtls-ice-transport.ts:30）。handshake 中に restart すると、相手の最終 flight は旧 pair で届くためです。SPED の carrier は従来どおり現在の世代だけを受け付けます。

テスト: 新しい selected pair へ移り、同じ SCTP association を維持する（sped:false / SPED）

5. SCTP / DataChannel

5.1 SCTP の役割と stream id の偶奇

仕様RFC 8831 §6.1: SCTP は RFC 8261 の DTLS カプセル化で運びます。§6.5:
… the streams are picked based on the DTLS role (the client picks even stream identifiers, and the server picks odd stream identifiers).

RFC 8832 §4（DCEP）も同じ規則を MUST で定めています（"the side acting as the DTLS client MUST use streams with even stream identifiers; the side acting as the DTLS server MUST use streams with odd stream identifiers"）。RFC 8261 は SCTP を DTLS で運ぶ手順そのものを定めます。どちらの側が INIT を送るかは、どの RFC も定めていません。

実装webrtc/src/transport/sctp.ts:506 — DTLS server が INIT を送り、DTLS client が応答します。DTLS client は、early server の INIT が届いたときに偶奇が未確定にならないよう、相手の認証前に passive 側を待受け状態にします（webrtc/src/peerConnection.ts:1219）。
werift の判断DTLS server を INIT の送り手にするのは、early server data を JSEP のどちらの役割の組み合わせでも成り立たせるための方針です。

テスト: DTLS role の parity で双方向に通る（client / server）

5.2 開始の確定点と、early start の取消し規則

仕様RFC 9260 §5.1: INIT → INIT ACK（State Cookie）→ COOKIE ECHO → COOKIE ACK の 4-way handshake。§4 の状態遷移の注記: T1-init / T1-cookie が満了したら再送し、'Max.Init.Retransmits'（既定 8、§16）回を超えたら初期化を中止して利用者にエラーを返します（werift も上限 8）。RFC が定める association の放棄は ABORT（§9.1）とこの再送上限だけで、「開始の取消し」は werift が定義した境界です。
実装

確定点: 相手が association の状態を持ちうる時点で開始を確定とします。開始側は COOKIE ECHO、応答側は COOKIE ACK を送信処理に渡した時点です（sctp/src/sctp.ts:285）。確定後は取り消しません。

取消し規則: SPED の reset・ICE restart・early 送信許可の取消しで届く通知に対し、webrtc/src/transport/sctp.ts:136 は次の判定で取り消すかどうかを決めます。

この規則にたどり着くまでに、レビューで次の回帰が見つかり修正しました。

  • 認証後に始めた通常の SCTP 開始まで、SPED の reset で取り消されていた（connecting → failed → connecting）。→ 条件 1。
  • DTLS client の passive association が取り消され、作り直された association では送信済み INIT_ACK の cookie 鍵が失われ、相手の COOKIE_ECHO を検証できず接続が完了しなかった。→ 条件 2。
  • 認証前に始めて、認証後も COOKIE_WAIT が続いた early start が、その後の restart で取り消された。→ 条件 3。

テスト: sctp.test.ts（認証前後の取消し）、warpLifecycle.test.ts（確定後は作り直さない）

5.3 送信失敗は損失として扱う

実装

SCTP の送信失敗（INIT / INIT_ACK の送信、T1 再送、即時再送）で開始を取り消すのは、transport が sctp/src/sctp.ts:112 を投げた場合だけです（sctp/src/sctp.ts:1574）。それ以外の失敗は損失として T1 の再送に任せます（`warp` と同じ）。

この error を投げるのは、SPED の early 送信経路（許可の取消し・世代の変更・期限切れ）と、DTLS の未認証送信の拒否だけです。認証後の送信は SPED の applicationReady 経路を通り、失敗してもログに出すだけで SCTP には伝わらないため、認証後の association がこの error で取り消される経路はありません。

6. 既定経路（sped:false）と SPED の非回帰

SPED / early 用に入れた中断処理（cancel・revoke・discard・attempt の付け替え）が、本来対象外の経路に効いてしまう回帰が、深いレビューのたびに見つかりました。そこで、SCTP の開始中に障害を注入し、ICE restart を重ねる 88 通りのマトリクスを常設テストにしました（4 構成 × DTLS role 2 通り × 11 シナリオ）。

軸値

8. 仕様からの逸脱と未確認事項

意図的な逸脱

  1. 0.5-RTT の SRTP / SCTP 送信（RFC 5764 §5.1）: opt-in した server だけ。既定では無効。RFC 8446 §4.4.4 が認める 0.5-RTT 送信を使うが、送信側は相手の身元をまだ確認していない。RFC 5763 §6.2 の early media（answerer が setup:active で SDP answer 前に DTLS を張る）とは別の仕組みで、いずれの場合も受信側は fingerprint の照合まで配送しない。
  2. SRTP の受信を、相手の認証完了の時点で始める: final ACK は待たない。
  3. SPED を DTLS 1.3 だけに限る（draft §3.2 は 1.2 以上が目標）。
  4. relay 上の SPED を除外し、association path を 1 本だけ使う（チケットのスコープ境界とも一致）。
  5. SPED が active の間でも、一部の Binding に DATA を付けない（draft §3.3.2.1 の MUST から逸脱）。
  6. 古い世代の、AEAD 認証済みの DTLS 1.3 record（Alert を含む）を適用しない（SPED transport のみ）。
  7. STUN の認証失敗時に 400 / 401 を返さない（RFC 8489 §9.1.3 は request に 400 / 401 の error response を MUST で求める。既存の挙動）。
  8. SCTP の既存の逸脱（RFC 9260）: T1-init は §6.3 の規則に従うべき（§5.1、SHOULD）だが、満了時に RTO を倍にしない（§6.3.3 rule E2）。応答側は INIT を受けた時点で状態を持つ（§5.1 (B) は INIT ACK 送信後に資源や状態を持たないことを MUST で求める）。開始側は相手の INIT を無視し、§5.2.1 の INIT 衝突を処理しない。
  9. tls-id（RFC 8842）を実装していない: RFC 8842 §3.1 は、fingerprint が変わったら offer/answer の後に新しい DTLS association を確立しなければならないとする。werift は新しい association を作らず、確立済みの association の証明書で照合し直して、一致しなければ失敗させる。
  10. stats: dtlsRole は未確定時に undefined（webrtc-stats §8.17 は DTLS ネゴシエーション開始前を "unknown" と定める）。warpHandshakeRttMs は RTT ではなく「handshake 開始から相手の認証まで」の時間。DTLS 1.2 の warpDtlsRetransmissions は常に 0。

未確認の事項

  • W3C 仕様は版によって節番号が変わります。この文書は §0 に記した版（webrtc-pc 2025-03-13 Recommendation、webrtc-stats 2025-09-25 CR Draft）に基づきます。
  • Pion 同士の full SPED（controlling / controlled、Full / Lite、SPED 上の restart）は、upstream の対応が前提のため未確認です。
  • BoringSSL harness が確認するのは handshake と双方向データだけで、exporter・KeyUpdate・negative cases の外部実装との組み合わせは未確認です（ローカルの self テストは成功）。
  • npm run examples:e2e は実行していません。
  • early send 無効時に DataChannel の送信が認証まで保留されることを、DataChannel レベルで直接確認するテストはありません。

werift · Google Congestion Control

動画が途切れないように、
送り方をその場で変える仕組み

GCC（Google Congestion Control）は、むずかしい数式の名前です。やっていることはシンプルで、 「道が混んできたら、少しゆっくり送る」です。

たとえ話 動かして見る 3つの観察 3本の時計 返事の処理順 遅延の中身 ロスの中身 試し打ちの中身 2つの待ち時間 アプリが見るもの

高速道路で荷物を運ぶ話

ビデオ通話は、小さな荷物（パケット）を連続で相手に届けています。道（ネットワーク）の幅は毎回ちがいます。 速く送りすぎると料金所の手前で車が並び、遅れて届きます。もっと押し込むと、車が落ちて消えます。

GCC の仕事は「運転手」ではなく「交通整理」

荷物そのものを作るのはカメラやエンコーダです。GCC は 今この道に、秒間どれだけ流してよいか（ビットレート）を提案します。 アプリはその数字に合わせて、画質や送り量を落とします。

狭い区間が「ボトルネック」。車が並ぶ＝遅延、落ちる＝ロス、わざと少し速く走ってみる＝probe（試し打ち）です。

観察は3種類だけ

GCC は魔法ではありません。返事のカード（TWCC）を見て、次の3つを読みます。

遅

遅延 — 並び始めていないか

届くまでの待ちが右肩上がりなら「送りすぎ」。少し減速します（overuse）。

失

ロス — 消えた荷物はないか

何度も届かない報告が続くと、天井を下げます。あとから届いたら「実は届いていた」と直せます。

試

試し打ち — もっと速くてよいか

最初は 3倍・6倍の短いバーストで道を探ります。返事がよければ、おすすめ速度を上げます。

時計は3本。混ぜない

「送るたびに計算する」わけではありません。役割を分けると、あわてて数字が暴れません。

① 送ったとき

荷物に番号を付けて「何時に出したか」をメモするだけ。この瞬間には速度を変えません。

  1. 番号（TWCC seq）を貼る
  2. サイズと時刻を控える

② 返事が来たとき

受け手が「届いた／届いていない」をまとめて返します。ここで遅延・ロス・試し打ちの結果を見ます。

  1. 遅延の傾きを見る
  2. 必要なら試し打ちの結果を載せる
  3. そのあとロスで天井を掛ける

③ 25ミリ秒ごと

返事がしばらく来なくても、待ちすぎていないか点検します。動画が止まっている間の安全装置です。

  1. 待ち時間が長すぎたら速度を 0.8 倍
  2. 試し打ちの予定を進める

届いていない報告は「今回は見えなかった」です。あとから届いたら取り消せます。番号が履歴に無い返事は、捨てます（差し替え直後など）。

遅延経路 — 「並び始めていないか」を傾きで見る

1個1個の遅れではなく、荷物の群れと群れのあいだで「送った間隔」と「届いた間隔」を比べます。 届く間隔の方がだんだん長くなると、料金所の列が伸びています。

群れにまとめる（InterArrival）

送り時刻が 5ms 以内の荷物は、同じ群れです。群れが閉じたら、前の群れとの差を出します。

send差 = 群れAの最後 − 群れBの最後
recv差 = 届いた時刻の差

順番が入れ替わった報告は無視します。3回続くと計測をやり直します。

傾きを読む（Trendline）

直近 20 群れが揃ってから直線を引きます。点が右肩上がり＝ overuse です。

傾きが急 → 送りすぎ

3つの判定

overuse

列が伸びている。速度を下げます。このときは試し打ちの「もっと速く」は採用しません。

underuse

列が解けている最中。新しい試し打ちは出しません。空になったと早合点しないためです。

normal

傾きが落ち着いている。underuse からここに戻った瞬間だけ、回復の試し打ちを検討します。

速度の増減（AIMD）

判定をビットレートに翻訳します。werift は Chrome と同じ式です。

減らすとき

次の速度 = 実際に届いた速さ × 0.85
5 kbps より大きければ、さらに −5 kbps

例: 400 kbps 届いていたら 335 kbps。少し余裕を残して列を溶かします。

増やすとき

上限 ≈ 届いた速さ × 1.5 + 10 kbps
掛け算で増やすか、RTT に応じた足し算

AIMD の待ち時間（RTT）は、TWCC ではなく受信レポートの生の値です。平滑化しません。

ロス経路 — 消えた量で天井を掛ける

遅延だけで足りないことがあります。列が見えなくても、荷物が落ちていれば道は満杯です。 ロス側は観察を溜めてから動き出します。準備前の数字は採用しません。

increasing 上げてよい increase_using_padding 空き埋めの余白を送る decreasing 下げる / 一時キープ delay_based 遅延側に任せる

最終値は「低い方」

おすすめ速度 = min( 遅延側の上限 , ロス側の提案 )

「届いていない」は仮の印です。あとから届いたら取り消します。同じ番号が何度も「未到達」でも、ロスの観察には数えます。

試し打ち — 短く、速く、数えながら

最初はいまの推定の 3倍と6倍 を短い固まりで送ります。固まりが「必要なバイト数かつパケット数」に達したら送り終わりです。 返事が 80% 来ただけでは送りを止めません。送り切ってから結果を待ちます。

送り始め minBytes かつ minPackets
次に送ってよい時刻 = 開始時刻 + (送ったバイト × 8 × 1000) / 目標bps

最初の間隔は 20ms、そのあとは 2ms。予定より 10ms 以上遅れた固まりは捨てます。 まだ送っていない待ち行列だけ、5秒で期限切れです。

いつ出してよいか

いまの様子新しい試し打ち
遅延が overuse / underuse出さない（列の観察を優先）
行き帰りの待ちが 3秒超出さない。1秒ごとに速度を 0.8 倍
ロスで下げている / 余白送信中出さない
ロスで上げている最中出してよい（上限は推定の 1.5 倍）
遅延側が主で、normal出してよい
underuse から normal に戻った回復用の試し打ちを検討

待ち時間は2種類。混ぜない

どちらも「遅さ」ですが、使い道が違います。片方の数字をもう片方に流し込むと、減速のタイミングが狂います。

TWCC の行き帰り（backoff 用）

返事が届くまでの時間から、受け手側で待たされた分を引きます。残ったのが道そのものの遅さです。

CorrectedRtt = 返事が途絶えた時間 + 道の遅さ

3秒を超えたら、25ms 点検のたびに（最短1秒おき）目標を 0.8 倍。床は 5 kbps。

受信レポートの生 RTT（AIMD 用）

SR を出してから RR が返るまでの生の値です。統計用にならした値は AIMD に渡しません。

raw = 今 − 最後の SR − DLSR

次に減速してよいかの間隔は、この RTT を 10〜200ms に収めて使います。省略時は 200ms。

アプリが知る必要があるのは、一つの数字

overuse や probe といった内部状態は、エンコーダには渡しません。 変わるのは 「次はこれくらいの速さで送ってよい」 という bps だけです。 同じ値の繰り返しは通知しません。うるさい切替を防ぐためです。 

sender.setBandwidthEstimator(new GccBandwidthEstimator());

sender.onAvailableBitrate.subscribe((bps) => {
  // 画質やレイヤを、この bps に合わせる
});
# TWCC の返事が溜まる

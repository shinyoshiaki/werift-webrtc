1. まず 1 分で

このチケットが守る唯一の不変条件 最終 answer の適用だけが negotiated state の commit 境界。それまでの pending negotiation は、通信中の current session を壊さない。rollback した後の current session も通信できる。

何を変えたか

  • 再交渉（offer / pranswer / answer / rollback / replacement、ICE restart、BUNDLE、SCTP、trickle ICE、m-line の拒否）を、1 つの transaction として扱うように作り直した
  • 「live に書き、rollback で戻す」方式から、「stage して、commit で切り替える」方式へ変えた

なぜ必要だったか

  • 以前の方式で守れるのは rollback した後だけで、pending の間に current の RTP が止まる反例が次々に見つかっていた
  • 指摘を 1 件ずつ直すのをやめ、ルーティングキーの種類ごとに規則を決めて、まとめて塞いだ

どう確かめたか

  • 各操作の後に、current SDP と live の状態が一致するかを検査する invariant helper
  • seed を固定したランダム操作列の property test（深い探索は 300 seed × 20 step）
  • webrtc の全テスト、Chrome E2E、WPT

3. 交渉のライフサイクル

3.1 signaling state と transaction の操作

signaling state の遷移ごとに、transaction の操作が 1 つずつ対応します。begin で baseline を取り、commit で確定し、rollback で baseline に戻します。

3.2 交渉の途中で、どの設定が通信に使われているか

再交渉の途中には、「いま通信に使っている設定」と「相手と交渉中の新しい設定」が同時に存在します。この 2 つを混ぜずに扱うことが、このチケットの中心です。まず用語を定義し、具体例で流れを追います。

current 確定済みの設定

最後に完了した offer / answer で合意した設定です（currentLocalDescription / currentRemoteDescription）。実際に RTP や DataChannel を流しているのはこの設定です。

pending 交渉中の設定

offer を出したものの、まだ最終 answer で合意していない設定です（pendingLocalDescription / pendingRemoteDescription）。pranswer を受けても、まだ pending のままです。

baseline 巻き戻し先

交渉を始める直前の状態を丸ごと記録した snapshot です。交渉を取り消す（rollback する）ときに、ここへ戻します。

commit 確定する瞬間

最終 answer（type: "answer"）の setLocalDescription / setRemoteDescription が成功した瞬間です。ここで pending が current に入れ替わります。pranswer では commit しません。

例: 音声だけで通話している（確定済みの設定 A）ときに、映像を追加する re-offer（新しい設定 B）を出し、相手から pranswer、最後に answer が返ってくる場合です。

4. description 適用の順序

setRemoteDescription（peerConnection.ts:1265）は、失敗しうる処理をすべて先に済ませ、live の transport を変える処理は最後に回す順序で進みます。どの段階で失敗しても、状態はその操作の前に戻ります。

事前検証で拒否する内容（descriptionValidation.ts:107）:

  • offer と共通の codec がない。使用中の payload type や extmap ID を別のものへ付け替える（sdpManager.ts:372）
  • DTLS の fingerprint と role の変更（RFC 8842 §5.5）、SCTP port の変更、接続済み SCTP の別 transport への移動
  • offer で共有した transport を answer が分割する（RFC 8843 §7.3.2、bundleTopology.ts:249）

local 側（peerConnection.ts:796）も同じ順序です。準備済みの ICE 資格情報を使っているか、DTLS role を変えていないかを descriptionValidation.ts:42 で先に検証します。

5. ルーティングキーの staging

レビューが収束しなかった主な原因は、pending の間に、current が使っている共有の live table（ssrcTable・ridTable・extIdUriMap・受信 codec 表）へ直接書き込んでいたことです。これをキーの種類ごとに、次の 1 つの規則で閉じました。

committed（current が使う）

RTP の解決は常にこちらを優先します。最終 answer の commit まで、既存キーの値は変えません。

staged（pending の提案）

current のキーと競合する変更はここに置きます。commit で committed へ移し、rollback で捨てます。

新しいキー（新しい SSRC・MID+RID・PT・extmap ID）は、暫定 RTP を受けるために即時に追加します。current にないキーなので、current の通信を奪いません。commit: router.ts:68、後から来た pranswer / answer の前に古い staged 値を捨てる処理: negotiationTransaction.ts:339

7. ICE generation（restart / pranswer / trickle / EOC）

  • restart の切り替え: offer の時点では資格情報を stage するだけで、live の ICE は answer の commit で切り替えます。answer は毎回 secureTransportManager.ts:522 を通りますが、実際に restart するのは restart を stage した transport だけです。
  • provisional check: 送信した時点の revision と pair の所属を記録し、応答を処理するときに照合します。replacement pranswer より前の遅延応答が、新しい checklist を nominate することはありません（ice.ts:402）。
  • EOC（7.1 拡大図）: live と provisional のどちらの generation も完了させます（RFC 8838、ice.ts:294）。webrtc 層でも、EOC 済みの m-line への候補は無視します（secureTransportManager.ts:323）。
  • trickle の振り分け: 候補が対象とする m-line の ufrag で、current と pending のどちらの generation に属するかを決めます（remoteCandidates.ts:44）。EOC は transport 単位なので、BUNDLE group 全体に及びます（remoteCandidates.ts:234）。
  • restartIce(): current と pending 両方のローカル ufrag を「置き換える対象」として記録します（W3C の [[LocalIceCredentialsToReplace]]）。rollback や glare の後も要求は残り、確定した資格情報がその対象と重ならなくなったときに解除します（iceRestartRequest.ts:18、peerConnection.ts:1257）。

7.1 拡大図: EOC と、その前後に届く候補

EOC（end-of-candidates）は、相手からの「この ICE generation の候補はこれで全部です」という通知です。次の 2 つの経路で届きます。

  • trickle ICE で、addIceCandidate(null) または候補の文字列が空（{ candidate: "" }）で呼ばれたとき（secureTransportManager.ts:256）
  • offer / pranswer / answer の SDP の m-line に a=end-of-candidates があるとき（sdp.ts:153）

EOC を受けると、ICE は「これ以上候補は来ない」と判断できます。すべての pair の check が失敗した時点で、それ以上待たずに failed にできます。EOC を受けていない間は、新しい候補が来るのを待ち続けます（ice.ts:1231）。

7.2 Q&A: EOC の後に届いた候補

質問回答
どういうときに起きるか 仕様どおりの相手は、EOC を送った後に同じ generation の候補を送りません。起きるのは主に次の場合です。
  • シグナリングで順序が入れ替わった（EOC のメッセージが先に届き、その前に送られた候補が後から届く）
  • SDP が a=end-of-candidates を含んで「完了済み」になっている m-line に、アプリや相手が候補を追加した
  • 相手の実装が EOC の後に候補を送る（仕様違反）
新しい ICE generation（ICE restart による新しい ufrag）の候補はこれに当たりません。その候補は新しい generation に振り分けられ、受け付けられます（7 章の trickle の振り分け）。
単に捨てられるか はい。エラーにはせず、addIceCandidate() は成功として返ります。候補は remote description（SDP）にも checklist にも加わらず、mDNS の名前解決も始めません。webrtc 層（secureTransportManager.ts:323）と ICE 層（ice.ts:308）の両方で捨てます。
それで問題はないか 通常は問題になりません。理由は次の 3 つです。
  • RFC 8838 の規則に従っている。EOC で完了した generation は、それ以上候補を受け付けません。
  • 受け付けると判定が矛盾する。EOC の後は「全 pair が失敗した = failed」と判定できます。後から候補が増えると、failed と判定した後に check の対象が増えることになり、状態が合わなくなります。
  • 救済経路がある。捨てた候補のアドレスから相手が check を送ってくれば、ICE はその送信元を peer-reflexive 候補として学習し、pair を作ります（RFC 8445 §7.3.1.3、ice.ts:2064）。この学習は EOC の後も止めていません。そのため、実際に通信できる経路であれば、多くの場合は接続できます。
残るリスク 相手からの check がこちらに届かず、こちらからの check だけが通るネットワークでは、捨てた候補でしか繋がらないことがあります。その場合は接続が失敗します。これは EOC の後に候補を送る相手側の誤りや、シグナリングの順序の入れ替わりで起きるもので、仕様どおりの相手と順序を保つシグナリングの組み合わせでは起きません。

7.3 ICE restart 中の通信: RFC・他の実装との比較

このチケットの werift は、ICE restart の commit（answer の適用）で旧 pair を手放します。そのため、新しい generation の pair が nominate されるまで、RTP / DataChannel を送れない時間があります。RFC の規定と Chrome の実装はこれより強く、新しい pair が選ばれるまで旧 pair で送り続けます。RFC と同等ではありません。一方で、Pion や develop の werift は restart を始めた時点で旧 pair を手放すので、それよりは途切れる時間が短くなっています。

対象restart 中の送信根拠
RFC 8445 / RFC 8839途切れない restart 前に選ばれていた pair（previous selected pair）を記録し、新しい selected pair ができるまで、その pair で送り続けるRFC 8445 §9「restart の間も、既存のセッションでデータを送り続けられる」、§12.1（checklist が Running の間の selected pair = previous selected pair）、RFC 8839 §4.4.3.1.1（previous selected pair を覚え、そこへ送り続ける）
Chrome（libwebrtc）途切れない 選択中の connection は restart の間も残し、新しい generation の connection が選ばれた時点で古いものを捨てるp2p/base/p2p_transport_channel.cc のコメント「Any selected connection is kept so that it can be used to send data during ICE restart per RFC 8445」（main 71b521e4af）
werift（このチケット）answer の commit から nominate まで途切れる offer と pranswer の間は旧 pair で送り続け、commit で ICE agent を作り直すice.ts:294 → ice.ts:186（nominated を消す）
werift（develop）restart を始めた時点から途切れる createOffer({ iceRestart }) の中で、その場で transport を restart するdevelop の createOffer → secureManager.restartIce()
Pion（pion/webrtc v4.2.22、pion/ice v4.4.6）restart を始めた時点から途切れる offerer は CreateOffer(ICERestart)、answerer は資格情報が変わった offer の SetRemoteDescription で Agent.Restart を呼び、selected pair・checklist・候補をすべて消すicetransport.go の restart() と agent.go の Restart()（setSelectedPair(nil)、deleteAllCandidates()）。開発版の pion/ice（v5.0.0-rc.7）も同じ動作

RFC に合わせるには、commit で ICE agent を作り直すのではなく、新しい generation の pair が nominate されるまで旧 generation の nominated pair を送信先として残し、nominate された時点で切り替える必要があります。このチケットでは pranswer の間の provisional generation までを扱い、ここは対象外の既知の制約として残しています（12 章）。

8. BUNDLE topology

8.1 BUNDLE group の仕組み

BUNDLE は、複数の m-line（音声・映像・DataChannel など）を 1 本の ICE / DTLS 接続にまとめて流す仕組みです（RFC 8843）。どの m-line をまとめるかは、SDP のセッション行 a=group:BUNDLE <mid> <mid> … で表します。

  • group は各 Peer が別々に持つものではなく、offer / answer で 2 者が合意するものです。offerer が offer で group を提案し、answerer が answer でそのうち受け入れる m-line だけを返して確定します。確定した group は両側で同じです。
  • 実体として、各 Peer は group ごとに transport（ICE + DTLS）を 1 つ持ちます。group 1 の音声と映像は、A 側の transport と B 側の transport の間の 1 本の接続を共有します。
  • group の先頭の MID を tag と呼びます。member が共有する transport のパラメータ（ICE 資格情報・DTLS fingerprint など）は、tag の m-line のものを使います。
  • 1 つの SDP に group を複数置けます。m-line が属せる group は 1 つまでで、どの group にも属さない m-line もあり得ます。

8.2 「group 外」はいつ現れるか

werift が自分で作る offer は、拒否済み（port 0）以外の全 m-line を 1 つの group に入れます（sdpManager.ts:617）。そのため、werift 同士の通常の交渉では group 外も複数 group も現れません。現れるのは次の場合です。

場面何が起きるかwerift の扱い

確立済みの member を group から外す re-offer（RFC 8843 §7.5）その m-line だけ別の transport に移る（split）新しい transport を準備して staged にし、answer の commit で切り替える。それまでは共有中の transport で通信を続ける
answer で m-line を拒否する（port 0）その m-line は group から外れ、transport も持たない自分の answer は、受け入れた MID だけで group を作る（sdpManager.ts:827）

11. 判断理由

stage → commit を選んだ

live に書いて rollback で戻す方式では、rollback した後の状態しか守れません。キーの種類ごとに「追加は即時、変更は拒否か staged」と決めたことで、反例を 1 件ずつではなく種類ごとに閉じました。develop の codec 統合も同じ規則に合わせています。

拒否か staged かの基準

RFC と Chrome の実際の挙動に合わせました。extmap ID の再割当ては拒否します（RFC 8285 §7。Chrome も拒否）。SSRC の移動と RTX の付け替えは staged にします（Chrome は受理する）。

snapshot を持ち主に置いた

transaction が他のオブジェクトのプロパティを列挙すると、状態を追加するたびに漏れが生じます。実際、develop の codec 統合ではこの箇所の修正が必要になりました。

機械的に検出する

各操作の後に、current SDP と live 状態が一致するかを検査します（negotiationTransactionUtils.ts:471、ルーティング表は negotiationTransactionUtils.ts:540）。ランダムな操作列の生成は negotiationTransactionUtils.ts:1444 です。

完了条件を有限にした

遷移表・mutation matrix・操作カタログに載っていない新しい組み合わせは、後続チケットで扱います（設計文書の Scope 章、チケットの 6 章）。

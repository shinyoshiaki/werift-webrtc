PeerConnection negotiation transaction
— 実装レビュー解説

チケット: TICKET-ticket-0ad06d37-d829-4a08-8e49-2da46e551b79.md HEAD: 5dae7059 比較基準: develop との merge base 404b3929 設計の正: NEGOTIATION_TRANSACTION.md

1. まず 1 分で

このチケットが守る唯一の不変条件 最終 answer の適用だけが negotiated state の commit 境界。それまでの pending negotiation は、通信中の current session を壊さない。rollback した後の current session も通信できる。

何を変えたか

  • 再交渉（offer / pranswer / answer / rollback / replacement、ICE restart、BUNDLE、SCTP、trickle ICE、m-line の拒否）を、1 つの transaction として扱うように作り直した
  • 「live に書き、rollback で戻す」方式から、「stage して、commit で切り替える」方式へ変えた

なぜ必要だったか

  • 以前の方式で守れるのは rollback した後だけで、pending の間に current の RTP が止まる反例が次々に見つかっていた
  • 指摘を 1 件ずつ直すのをやめ、ルーティングキーの種類ごとに規則を決めて、まとめて塞いだ

どう確かめたか

  • 各操作の後に、current SDP と live の状態が一致するかを検査する invariant helper
  • seed を固定したランダム操作列の property test（深い探索は 300 seed × 20 step）
  • webrtc の全テスト、Chrome E2E、WPT

3. 交渉のライフサイクル

3.1 signaling state と transaction の操作

signaling state の遷移ごとに、transaction の操作が 1 つずつ対応します。begin で baseline を取り、commit で確定し、rollback で baseline に戻します。

3.2 pending の間、何が live か

offer を出してから answer が確定するまで、current・pending・baseline の 3 つが同時に存在します。commit 境界より左側では、current のキーと経路は書き換えません。

4. description 適用の順序

setRemoteDescription（peerConnection.ts:1238）は、失敗しうる処理をすべて先に済ませ、live の transport を変える処理は最後に回す順序で進みます。どの段階で失敗しても、状態はその操作の前に戻ります。

  1. 事前検証

    peerConnection.ts:1288✗ 失敗 → 状態不変で reject
  2. codec 計画
    全 m-line の codec を副作用なしで先に決める

  3. checkpoint
    この操作の分だけ戻せる地点

    対応付け → BUNDLE 所有 → RTP / SCTP の受け入れ → transport 更新の計画
    peerConnection.ts:1364✗ 失敗 → checkpoint へ戻す
  5. transport 更新を実行
    計画した更新を最後にまとめて実行
    peerConnection.ts:1375
  6. answer なら commit
    ICE restart の切替（stage したものだけ）・BUNDLE topology・staged 経路と受信設定を一斉に切り替える
    peerConnection.ts:1197

事前検証で拒否する内容（descriptionValidation.ts:107）:

  • offer と共通の codec がない。使用中の payload type や extmap ID を別のものへ付け替える（sdpManager.ts:372）
  • DTLS の fingerprint と role の変更（RFC 8842 §5.5）、SCTP port の変更、接続済み SCTP の別 transport への移動
  • offer で共有した transport を answer が分割する（RFC 8843 §7.3.2、bundleTopology.ts:249）

local 側（peerConnection.ts:799）も同じ順序です。準備済みの ICE 資格情報を使っているか、DTLS role を変えていないかを descriptionValidation.ts:42 で先に検証します。

5. ルーティングキーの staging

レビューが収束しなかった主な原因は、pending の間に、current が使っている共有の live table（ssrcTable・ridTable・extIdUriMap・受信 codec 表）へ直接書き込んでいたことです。これをキーの種類ごとに、次の 1 つの規則で閉じました。

committed（current が使う）

RTP の解決は常にこちらを優先します。最終 answer の commit まで、既存キーの値は変えません。

staged（pending の提案）

current のキーと競合する変更はここに置きます。commit で committed へ移し、rollback で捨てます。

新しいキー（新しい SSRC・MID+RID・PT・extmap ID）は、暫定 RTP を受けるために即時に追加します。current にないキーなので、current の通信を奪いません。commit: router.ts:68、後から来た pranswer / answer の前に古い staged 値を捨てる処理: negotiationTransaction.ts:339

キー新しいキーcurrent キーの変更実装
payload type → codec即時追加再割当ては拒否 fmtp / rtcp-fb は stagedrtpReceiver.ts:194
extmap ID → URI即時追加再割当ては拒否（RFC 8285 §7）sdpManager.ts:346
SSRC → receiver / RTX 対応即時追加別 m-line への付け替えは stagedrouter.ts:136

7. ICE generation（restart / pranswer / trickle / EOC）

  • restart の切り替え: offer の時点では資格情報を stage するだけで、live の ICE は answer の commit で切り替えます。answer は毎回 secureTransportManager.ts:523 を通りますが、実際に restart するのは restart を stage した transport だけです。
  • provisional check: 送信した時点の revision と pair の所属を記録し、応答を処理するときに照合します。replacement pranswer より前の遅延応答が、新しい checklist を nominate することはありません（ice.ts:400）。
  • EOC: live と provisional のどちらの generation も完了させます（RFC 8838、ice.ts:292）。webrtc 層でも、EOC 済みの m-line への候補は無視します（secureTransportManager.ts:324）。
  • trickle の振り分け: 候補が対象とする m-line の ufrag で、current と pending のどちらの generation に属するかを決めます（remoteCandidates.ts:44）。EOC は transport 単位なので、BUNDLE group 全体に及びます（remoteCandidates.ts:234）。
  • restartIce(): current と pending 両方のローカル ufrag を「置き換える対象」として記録します（W3C の [[LocalIceCredentialsToReplace]]）。rollback や glare の後も要求は残り、確定した資格情報がその対象と重ならなくなったときに解除します（iceRestartRequest.ts:18、peerConnection.ts:1230）。

8. BUNDLE topology

BUNDLE group は最初の 1 つだけでなく、すべての group を扱います。各 group の tag（先頭の MID）が、member の transport を決めます（bundleTopology.ts:32）。

group 1: BUNDLE 0 1

mid 0 (tag)mid 1
transport T1 を共有

group 2: BUNDLE 2 3

mid 2 (tag)mid 3
transport T2 を共有

group 外

mid 4
独自の ICE 資格情報を持つ transport T3

分割・統合・新しい owner は staged topology として準備し（local offer は bundleTopology.ts:120、remote re-offer は bundleTopology.ts:136）、answer の commit で切り替えます（bundleTopology.ts:228）。所有のためだけに作った transport は rollback で閉じます。

11. 判断理由

stage → commit を選んだ

live に書いて rollback で戻す方式では、rollback した後の状態しか守れません。キーの種類ごとに「追加は即時、変更は拒否か staged」と決めたことで、反例を 1 件ずつではなく種類ごとに閉じました。develop の codec 統合も同じ規則に合わせています。

拒否か staged かの基準

RFC と Chrome の実際の挙動に合わせました。extmap ID の再割当ては拒否します（RFC 8285 §7。Chrome も拒否）。SSRC の移動と RTX の付け替えは staged にします（Chrome は受理する）。

snapshot を持ち主に置いた

transaction が他のオブジェクトのプロパティを列挙すると、状態を追加するたびに漏れが生じます。実際、develop の codec 統合ではこの箇所の修正が必要になりました。

機械的に検出する

各操作の後に、current SDP と live 状態が一致するかを検査します（negotiationTransactionUtils.ts:463、ルーティング表は negotiationTransactionUtils.ts:532）。ランダムな操作列の生成は negotiationTransactionUtils.ts:1436 です。

完了条件を有限にした

遷移表・mutation matrix・操作カタログに載っていない新しい組み合わせは、後続チケットで扱います（設計文書の Scope 章、チケットの 6 章）。

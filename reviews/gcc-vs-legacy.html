legacy は、受信が確認できたパケットのサイズと送受信時刻から平均速度を計算します。GCC は、それに加えて受信間隔が送信間隔より長い状態が続くかを調べ、待ち時間の増加を検出すると送信目標を下げます。

違いは「ロスが出るまで待つか」だけではありません。受信済みデータの平均速度を出す処理と、増え続ける待ち時間を解消するために目標を下げる処理を、同じ入力で比べます。

ロスがなくても、待ち時間は増える

1,200 byte のパケットを 12 ms ごとに送ると、送信レートは 800 kbps です。600 kbps の区間では 1 個を通すのに 16 ms かかるため、次のパケットが 4 ms 早く来て待たされます。バッファに収まる間は、全パケットが届いていても待ち行列が増えます。

legacy も受信間隔が広がれば推定値は下がります。GCC の違いは、遅延増加を検出した後、到達スループットより低い目標を選んで待ち行列を減らそうとする点です。GCC が常に低い値になるわけではありません。

推定器に与える合成入力の例です。40 個を送った後の TWCC 1 通を両方式に入力します。GCC の内部開始目標は比較用に 800 kbps、probe は発生させず、RTT 制限・追加のロス制限がかからない条件です。実際の通話のフィードバック周期や送信適応を再現するベンチマークではありません。

LEGACY / 受信済みの平均

同じバイト数を、二つの時刻幅で割る

送信レート側も「受信が確認できたパケット」だけが分子・時刻幅の対象です。全送信パケットの平均とは限りません。

なぜ受信速度と完全には一致しないか

この実装は 40 個分のバイト数を、最初と最後の間の 39 間隔で割ります。一定間隔でも、実際の定常レートに対し 40 / 39 倍の値になります。

B = 受信済みパケットの合計 byte
send = B × 8 × 1000 / (S最大 − S最小)
recv = B × 8 × 1000 / (R最大 − R最小)
availableBitrate = min(send, recv)

計算の目安は 100 ms 以上の経過と 20 パケット以上の蓄積。receiveTWCC 冒頭で 1 秒超の古い累積は破棄されます。遅延の傾きや「平均速度から一定割合を引く」処理はありません。

GCC / 遅延増加から目標を制御

間隔の差 → 平滑化 → 傾き → 判定

GCC の到達スループット推定も、送信側・受信側の両方を使います。既定の RobustThroughputEstimator は窓の端の 1 パケットを除いて計算し、極端な受信間隔にも補正をかけます。等間隔のこの例では 600 kbps（待機あり）、800 kbps（待機なし）です。

実際は送信時刻でグループ化し、完了した群同士の間隔を使います。この例は送信間隔が 12 ms なので 1 個ずつ別の群です。次の群が必要なため、40 個から得られる間隔差は 38 個です。

右肩上がりの点が一つ出ただけでは減速しません。履歴 20 個で回帰し、正の判定用スコアが適応閾値を超え、継続時間・回数・傾きの条件を満たすと overuse になります。減速の実行には AIMD の更新間隔条件もあります。

グラフは横にスクロールできます。

操作で状態を進める模式図です。5 個の報告から帯域値が出るという意味ではありません。GCC の loss 経路は byte ベースの観測を蓄積し、既定では送信時刻幅 250 ms 以上の観測が最低 3 個必要です。後着によるロス取消しは未確定の観測内だけで、確定済みの過去の観測は書き換えません。

legacy はロス率を明示的にモデル化しません。ただし、受信済みの合計 byte が減ったり時刻幅が広がったりすれば推定値は下がり得ます。「未受信を飛ばすから帯域が下がらない」という説明は正しくありません。

probe は測定のための送信。pacing は送信時刻の調整

GCC は短いパケット群（probe cluster）を決めたレートで送り、TWCC の受信結果から帯域の候補を得ます。probe の設定値は、使えると確認できた帯域ではありません。pacing はパケットを送る間隔を調整します。画質やエンコーダの生成量を自動で変える機能とは別です。

既定は SenderBandwidthEstimator（legacy）。差し替えは setBandwidthEstimator を使います。通常の RTP/TWCC 観測と probe 送信・pacing は TWCC 拡張の交渉が前提です。

差し替え時は推定を引き継がない

旧推定器を dispose / reset し、注入する推定器も reset します。sender の共通イベント購読は残ります。リセットで公開値が 0 に戻ること自体は、帯域変更通知を発火しません。

legacy 固有: onCongestion / onCongestionScore（1〜10）。GCC 固有: onOveruseDetected / onProbeClusterConfig。これらは共通 interface の帯域イベントとは別です。

推定器は通知する帯域を決めます。実際にエンコーダの目標を下げたり、メディアの生成量を減らしたりする処理はアプリ側に必要です。pacing だけで生成量を減らせるわけではありません。

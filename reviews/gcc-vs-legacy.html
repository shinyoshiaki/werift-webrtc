同じ返事を見ても、
legacy と GCC は別の答えを出す

入力はどちらも TWCC です。既定の legacy は「届いた荷物の速さの小さい方」をそのまま採用します。 GCC は列の伸び・穴・試し打ちまで見て、次に送ってよい速さを決めます。

共通契約 同じ道で比べる 返事の処理順 穴を数えるか 傾きを見るか 試し打ちと pacing イベント どちらを使うか

共通しているところ

差し替えできるように、表向きの約束は同じです。アプリはアルゴリズム名を知らなくてよい、というのが設計です。

どちらも同じ入口・出口

rtpPacketSent(SentInfo)
receiveTWCC(TransportWideCC)
onAvailableBitrate → bps（変化時のみ）

TWCC が交渉されていなければ、どちらも動きません。差し替えは setBandwidthEstimator だけです。

既定は legacy

// 最初から入っている
new SenderBandwidthEstimator()

// 明示的に GCC へ
sender.setBandwidthEstimator(new GccBandwidthEstimator());

既存アプリは何もしなくても従来どおりです。

同じ道を流したときの、二つのおすすめ速度

下はたとえです。legacy は届いた荷物だけから速さを出します。穴や列の伸びは見ません。 だから「混んでいるのに数字が高い」ことが起きます。GCC はそこで減速します。

道は空いています。両方とも速く送ってよい、と判断します。

返事が来てから、数字が決まるまで

GCC 解説と同じ問いです。legacy はこのうち半分しかやりません。手順を押すと、両側の動きが並びます。

1. 照合番号で送り履歴を探す
→
2. 穴届いていない荷物
→
3. 遅れ列が伸びているか
→
4. 速さbps の出し方
→
5. 試し打ちもっと速くてよいか
→
6. 通知アプリへ渡すもの

穴を数えるか、通り過ぎるか

LEGACY

届いた行だけを積む

if (!result.received) continue; なので、穴は統計に入りません。届いた荷物が速く見えれば、道が欠けていても数字は下がりません。

受信済み かつ 時刻あり
→ サイズと時刻を累積
GCC

番号順で穴も数える

未到達は仮の印です。あとから届いたら取り消します。同じ番号が何度「未到達」でもロス観察には数えます。遅延計算とは順が違います（遅延は届いた時刻順）。

seq 順で soft loss
recv 時刻順で delay / probe

傾きを見るか、平均の速さだけか

LEGACY

窓の最初と最後から割り算

send = 合計バイト / 送り時刻の幅
recv = 合計バイト / 届き時刻の幅
bps = min(send, recv)

条件は「経過 ≥ 100ms かつ 20 パケット」。1秒超たまらないと congestion カウンタが増えます。勾配は見ません。

GCC

群れの間隔の傾き → AIMD

overuse: 届いた速さ × 0.85、必要なら −5kbps
試し打ち成功: その値を delay に載せる
最後に min(delay, loss)

列が伸びていれば、平均速さがまだ高くても減速します。underuse 中は新しい試し打ちを出しません。

試し打ちと pacing は GCC だけ

legacy はアプリが渡した速さのまま出します。送信ホットパスで推定も probe も回しません。GCC は capability が付いているときだけ、sender が待ちと余白パケットを足します。

legacyGCC
送信時履歴に残すだけ（16-bit キー、10秒で捨てる）履歴（unwrap、最大60秒）＋ ALR ＋ probe の send-fill。推定はしない
25ms タイマ無しprocess() で RTT backoff と probe 進行
メディア pacing無し初回 TWCC 前 2.5×、以降 1.1× の token-bucket
probe padding無し3×/6× の短い固まり。送信前に cluster id を予約

アプリが見るイベントも、同じではない

LEGACY 固有

混雑スコアがある

共通 interface には載せません。具象をキャストしたときだけ使えます。

onAvailableBitrate(bps)
onCongestion(boolean)
onCongestionScore(1〜10)
GCC 固有

overuse と probe 設定

アプリの本線は sender の onAvailableBitrate だけです。残りは GCC インスタンス、または sender の probe ブリッジです。

onAvailableBitrate(bps)
onOveruseDetected(usage)
onProbeClusterConfig(...)

16-bit の番号の扱いも違います。legacy はワイヤーの 16-bit をそのままキーにするので、一周すると上書きします。GCC は unwrap して世代を分けます。

## Summary

`Connection.close()` destroys the shared mDNS socket, but pending `.local` candidate lookups keep their 10-second timers/listeners/promises alive. A lookup that resolves just before/after close can also continue `addRemoteCandidate()` and append a candidate to an already-closed ICE connection.

This is reproducible downstream and is still present in `werift@0.25.1`.

Downstream evidence:
- ArcaneArts/Cantrip PR #2139: https://github.com/ArcaneArts/Cantrip/pull/2139

That PR uses the real werift package and shows:
- pending mDNS lookups keep Node alive after ICE shutdown;
- multiple pending lookups still have response listeners after `connection.close()`;
- a late mDNS answer can resume `addRemoteCandidate()` after close;
- tracking/cancelling pending lookups and rejecting late candidates makes the worker exit naturally.

## Current 0.25.1 behavior

`packages/ice/src/dns/lookup.ts`:

```ts
lookup(host: string): Promise<string> {
  return new Promise((r, f) => {
    const cleanup = () => {
      this.mdnsInstance.removeListener("response", l);
      clearTimeout(timeout);
    };

    const timeout = setTimeout(() => {
      cleanup();
      f(new Error("No mDNS response"));
    }, 10000);

    ...
    this.mdnsInstance.on("response", l);
    this.mdnsInstance.query(host, "A");
  });
}

close() {
  this.mdnsInstance.destroy();
}
```

`close()` does not settle/reject pending lookup promises and does not clear their timeout/listener state.

`Connection.addRemoteCandidate()` also awaits the lookup and does not re-check `state === "closed"` after the await before mutating the candidate/connection.

## Why this is separate from #744

#744 tracks cancellation/joining of **local candidate gathering**, especially pending TURN creation.

This issue is about **remote candidate mDNS resolution** started by `addRemoteCandidate()`. It has a separate owner (`MdnsLookup`), timer/listener lifecycle, and late-continuation race.

## Expected behavior

After `await connection.close()`:

1. all pending mDNS lookup timers/listeners owned by that connection are cancelled;
2. their promises settle promptly instead of waiting up to 10 seconds;
3. new mDNS lookups are rejected/ignored;
4. late mDNS answers cannot append remote candidates to the closed connection;
5. repeated `close()` is safe/idempotent.

## Suggested direction

Track pending lookup cancellation callbacks (or use an AbortSignal) in `MdnsLookup`.

On `close()`:
- mark the lookup owner closed;
- reject/cancel every pending lookup;
- remove response listeners and clear timers;
- destroy the mDNS instance.

In `Connection.addRemoteCandidate()`:
- return immediately when already closed;
- after awaiting DNS/mDNS resolution, check closed state again before mutating state.

## Regression tests

Please cover:

- two unresolved `.local` candidates, then `close()`: no 10s timers/listeners remain;
- a response arriving immediately before close: continuation must not append the candidate;
- `addRemoteCandidate()` after close: no lookup owner is created and no candidate is appended;
- repeated close;
- normal successful mDNS resolution still works.

Cantrip's PR #2139 includes concrete ESM/CommonJS child-process regression tests that can be adapted upstream.

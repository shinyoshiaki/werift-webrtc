## 1. 目的と背景

### 1.1 目的

正常なピアが期限内に**真正な** consent 応答を返し続けている経路で、ICE consent（RFC 7675）が 30 秒で誤って失効し、`failed` になってアプリデータ送信が止まる問題をなくす。同時に次の安全要件は弱めない。

- 4〜6 秒間隔（4 秒未満禁止）
- 最後の有効応答から 30 秒で失効
- 失効後は送信停止、遅延応答では再確立しない
- 認証・送信元・transaction ID の検証

### 1.2 下流からの報告（wolkesson/dronelink）

- SITL 障害試験（`docs/sim/flight-control-drills.md`）では、loopback UDP に NFQUEUE で**パケットごとの遅延と損失**を注入している。
  - Scenario 3: 完全 blackhole
  - Scenario 4a: 500 ms 遅延 + 20 % 損失
  - Scenario 4b: 2000 ms 遅延 + 20 % 損失
- Finding 9: 3 → 4a → 4b を連続実行すると約 4 回に 1 回 consent が失効する。下流の記録では「RTT が 1〜4 秒のとき応答がすべて捨てられていた」。
- 下流パッチ（`patches/werift+0.24.4.patch`）の consent 部分は次の 3 点。
  1. `consentResponseTimeoutMs()` が RTT を無視し、`CONSENT_INTERVAL * 0.8 * 1000`（= 4000 ms）を返す。
  2. 最後の成功から `CONSENT_INTERVAL`（5 s）を超えて応答がないと、次のチェックを **1 秒後**に送る。回数に上限はない。
  3. 次の request を送る前の `abort()` を削除し、request を重複させる。
- 下流の `werift-patch.test.ts` はビルド済みコードを文字列一致で確かめるだけで、実際の挙動は検証していない。1 秒間隔を前提にしたテストも含まれている。
- 同じパッチには SCTP の `maybeAbandon` 修正と recorder の修正も入っているが、本チケットの対象外。

### 1.3 RFC 7675 の要件（§5.1 / §8）

| 要件 | 内容 |
| --- | --- |
| 間隔 | 基本 5 s を 0.8〜1.2 倍でランダム化する。**4 秒未満にしてはならない（MUST NOT）**。この間隔は expiry timer と独立している |
| 失効 | 30 s の間に有効な応答がなければ、その 5-tuple での送信を停止する（MUST） |
| 失効時 | 未完了の consent transaction はすべて破棄する（MUST）。失効後に届いた応答で consent を再確立しない |
| transaction | request ごとに新しい transaction ID を使う（MUST）。各 request は **1 回だけ送る**（再送しない） |
| **遅延応答** | 「すべての request に応答が返るとは限らず、**応答は直前の request ではなく以前の request に対するものかもしれない**」 |
| 応答待ち | 推定 RTT と遅延変動の余裕をもとに応答を待つべき（SHOULD） |
| 安全性 | transaction ID は 96 bit の暗号学的乱数とし、アプリケーションから取得も制御もできないこと |

→ 「以前の request への遅延応答」を受け入れることは RFC の想定内。一方、下流パッチの **1 秒間隔は §5.1 の MUST NOT（4 秒未満）に違反する**ので移植しない。

### 2.2 特定した誤失効の経路

**(A) RTT 推定の自己ロック（主因・決定的に再現可能）**

1. RTT が低い時期に selection（または最後の成功応答）があり、`pair.rtt` は小さい値（例: 10 ms）になる → `responseTimeout` は 500 ms。
2. その後 RTT が 500 ms を超えたまま続く（下流 4a: 片方向 500 ms × 往復で RTT ≈ 1 s）。
3. どの request も 500 ms で `TransactionTimeout` になり、transaction は map から消える。応答は 1 s 後に届くが txid が未登録なので破棄される。
4. `nominated.rtt` は**受理した応答でしか更新されない**ので、timeout は 500 ms のまま伸びない。真正な応答が毎回届いていても、30 s 後に `failed` になる。

RTT が不明なとき（1000 ms 固定）も、RTT が 1 s を超えれば同じことが起きる。

**(B) 次の request による abort（RTT ≥ 約 4 s）**

下流 4b（片方向 2 s → RTT ≈ 4 s）では、仮に timeout が十分長くても、4〜6 s 後の次の request 開始時に `requestAbort.abort()` が前回の transaction を中断し、応答を捨てる。

**(C) 損失バーストとの組み合わせ**

20 % 損失では、request と response のどちらかが落ちる確率は 1 − 0.8² = 36 %。30 s に 5〜7 回しか送らないので、(A)/(B) で応答の一部が捨てられると、最後の有効応答から 30 s を超えやすい。純粋な損失だけなら、30 s の間に 1 回でも往復が成功すれば維持される（設計どおり）。

**(D) 既存テストが検出できない理由**

`packages/ice/tests/utils.ts` の `ConsentMockProtocol` は、success の場合 `responseTimeout` も abort も無視して `responseDelayMilliseconds` の後に解決する。そのため「timeout を超えた遅延応答が捨てられる」経路を一度も通らない。実際の `StunProtocol` と `Transaction` を通すハーネスが必要。

### 2.3 下流パッチの評価

| 変更 | 評価 |
| --- | --- |
| response wait を 4 s に固定 | (A) は概ね解消するが、RTT ≥ 4 s では (B) が残る。RTT の SHOULD とも離れる |
| abort の削除（重複 request） | 方向は妥当。ただし未完了 transaction の上限と、失効・restart 時の破棄がない |
| 未応答時に 1 秒ごとに追加送信 | **RFC 7675 §5.1 の MUST NOT（4 秒未満）に違反**。高損失時に負荷を増やす。**移植しない** |

## 3. 実装すべき変更

### 3.1 決定的な再現ハーネス（変更前に失敗を示す）

`packages/ice/tests/utils.ts` の consent 用 Arrange に、**実際の `StunProtocol` + `Transaction`** を使うネットワーク模擬を追加する（既存の `ConsentMockProtocol` / `createConsentHarness` と同じファイル、共有 utility は 1 つに保つ）。

- 偽の transport（`consent-wire.test.ts` と同じく `(protocol as any).transport` を差し替える）で送信した request を捕捉する。
- 「ピア応答器」は、受け取った request の txid に対して、remote password で署名した `BINDING RESPONSE`（MESSAGE-INTEGRITY + FINGERPRINT）を作り、スクリプトどおりの遅延の後に `datagramReceived()` へ渡す。
- スクリプトで指定できるもの: パケットごとの往復遅延、drop、順序入れ替え、送信元アドレスの変更、署名鍵の変更、RTT のステップ変化、損失バースト。
- `vi.useFakeTimers()` と `Math.random` の固定で決定的にし、30 s を超える経過（例: 60〜120 s）も再現する。
- 計測項目: request の送信時刻と txid、transaction の終了理由（timeout / abort / 成功）、応答の受理と破棄（破棄理由）、最終受理時刻、expiry 発火時刻、`protocol.transactions` の残数、`vi.getTimerCount()`。
- 必要なら `ConsentFreshness` に、テストからだけ観測できる診断フック（debug log か内部カウンタ）を追加する。公開 API にはしない。

### 3.2 修正の設計（推奨案）

**案 A（推奨）: consent transaction を「consent の有効期間中」は受理可能のまま残し、abort は lifecycle イベントに限る**

1. **response wait**: consent request の `responseTimeout` を、RTT から求めた短い値ではなく「その request を受理しても意味がある期間」にする。上限は、その request の送信から `CONSENT_TIMEOUT`、または現在の expiry までの残り時間の短い方。送信は `retransmissions: 0` のまま 1 回だけで、**wire 上の送信回数と間隔は変えない**。
   - consent では、timeout に達しても再送も追加チェックも起きない。早く諦めても利点はなく、遅延応答を失うだけになる。RTT による待ち時間（SHOULD）は「損失とみなすタイミング」の診断値として残す（例: `consentResponseTimeoutMs()` はログ・統計用に残す）。
2. **重複を許す**: 次の request の前の `this.requestAbort?.abort()` をやめる。未完了の transaction を `Set<AbortController>` などで管理し、**上限を設ける**（30 s ÷ 最短 4 s ≈ 8。超えたら最古の transaction を abort する）。
3. **一括破棄**: `stop()`（restart / close / pair リセット / TCP 切断）、expiry 発火、`start()` による session の置き換えのいずれでも、すべての未完了 transaction を abort する（RFC: 失効時に MUST discard）。
4. **受理条件**（現行の照合を維持し、遅延応答にも同じ条件を課す）:
   - Transaction / Protocol 層: txid が一致し、送信元が `expectedAddr` と一致し、MESSAGE-INTEGRITY（SHA-1 または SHA-256）が検証でき、success class であること
   - Consent 層: `sessionId` が一致し、selected pair の id が一致し、remote generation と remote password が一致し、state が `closed` / `failed` でないこと
5. **RTT**: 受理した応答の RTT は、その transaction の送信時刻から計算する（現行の closure の `requestStartedAt`）。これで (A) の自己ロックは原理的になくなる。ただし応答の順序が入れ替わったとき、古い transaction の RTT が新しい測定値を上書きしないかを検討する（stats の `currentRoundTripTime` の意味に注意）。
6. **expiry の延長**: 「受理した時刻」から 30 s を延長する（現行どおり）。古い request への応答でも、受理時点で真正ならピアが今も応答している証拠になる。ただし session を跨いだ受理と失効後の受理はしない。

**案 B（最小変更・比較用）**: `responseTimeout` を次の request 開始までの値（≈ `CONSENT_INTERVAL*0.8`）にし、abort は残す。下流パッチの timeout 部分に相当する。RTT ≥ 4 s（4b）が救えないので、採用するなら制約として明記する。

→ ハーネスで両案を比較し、案 A を第一候補とする。**追加送信（1 s 間隔など）は実装しない。** 将来検討する場合は、RFC の根拠と負荷試験を伴う別チケットにする。

### 3.3 ドキュメントと公開 API

- `consentResponseTimeoutMs`、`CONSENT_RESPONSE_TIMEOUT`、`CONSENT_RESPONSE_TIMEOUT_MIN` は公開 export なので互換のため残す。意味を変える場合は TSDoc を更新し、`npm run doc` で `packages/ice/doc` / `doc/` を再生成する（テキストマージはしない）。
- `changelog.md` に、PR #649 との差分（「RTT ベースで 1 回だけ待つ」から「有効期間中は遅延応答を受理する」へ、abort の契機の変更）と下流の再現条件を記載する。
- `packages/ice/README.md` に consent の記述があれば合わせて直す。
- #860 との違い（本件は真正な応答がある経路の誤失効、#860 は経路を失ったときの遷移遅延）を PR 本文に記録する。

## 4. 回帰テスト（Arrange / Act / Assert、Act と Assert には日本語コメント）

配置先は `packages/ice/tests/ice/consent.test.ts`（または `consent-network.test.ts` を新設）。Arrange は `tests/utils.ts` にまとめる。

**維持すべき系（変更前に赤、変更後に緑になることを示す）**

1. RTT のステップ上昇: selection 時の RTT 10 ms → 以後の往復 1000 ms を 90 s 続ける → `connected` のまま、`fresh === true`、送信できる。
2. RTT 不明（1000 ms 既定）→ 往復 1500 ms
3. 往復 4500 ms（間隔 4〜6 s を超える）→ 前回の request への応答が受理される（(B) の再現）
4. 下流 4a / 4b 相当: 往復 1 s / 4 s と 20 % 損失を、シード固定の決定的なパターンで 120 s
5. 単発 loss、遅延ジッタ（例: 100〜3000 ms）、応答の順序入れ替え
6. 損失バーストが 25 s 続いた後に回復 → 維持される

**失効すべき系**

7. 30 s 以上、有効な応答がまったくない（blackhole 31 s）→ `failed` になり、`send()` が transport に到達しない
8. 失効後に届いた真正な遅延応答 → `failed` のまま（既存テストの実プロトコル版）

**期限を延長してはならない系**（どれも遅延応答のタイミングで検証する）

9. 旧 remote generation（ICE restart 前の request）への応答
10. 旧 selected pair（pair 切替前の request）への応答
11. 不正な MESSAGE-INTEGRITY、署名なし、別の送信元アドレス、未知の txid

**lifecycle と leak**

12. close、ICE restart、pair 切替、expiry の各時点で未完了の transaction が複数ある状態から → `protocol.transactions` が空、consent 由来の timer が 0、未処理の Promise rejection がない（`process.on("unhandledRejection")` で検出する）
13. 未完了 transaction の上限（約 8）を超えない
14. 既存の不変条件を維持する: 送信間隔は 4〜6 s で 4 s 未満にならない、wire 上の送信は request ごとに 1 回、txid は request ごとに一意、統計値（`consentRequestsSent` / `requestsSent` / `responsesReceived` / `retransmissionsSent = 0`）が実際の数と一致する
15. UDP / TCP（`TcpActiveProtocol`）/ TURN（`StunOverTurnProtocol`）で、長い `responseTimeout` と abort が正しく扱われる（`consent-wire.test.ts` を拡張）

再現できなかった場合は挙動を変えず、ハーネスの計測結果と結論をこのチケットに記録する。

## 5. 制約・注意点

- **RFC 7675 の MUST を守る**: 間隔は 4 s 以上、30 s で失効、失効時に transaction を破棄する、遅延応答で再確立しない、txid はアプリケーションから制御できない。
- **安全側の優先**: 遅延応答の受理を広げても、認証・送信元・txid・session・pair・generation の照合は一切緩めない。応答の受理は「ピアが今も同意している」証拠として扱う。
- **リソース**: 未完了 transaction ごとに timer が 1 つ増える。上限と一括破棄で bounded に保つ。`Protocol.close()` も `transaction.cancel()` で全件を終了させることを確認する。
- **コード規約**: `enum` とパラメータプロパティは使わない（`erasableSyntaxOnly`）。通知は既存の `Event` / `cancelable` パターンに従う。広い catch-and-ignore はしない（consent の `.catch` は損失を想定したログに留める）。
- **公開 API の互換**: 既存の export は削除しない。意味が変わる場合は TSDoc、docs の再生成、changelog を同じ変更で更新する。
- **関連問題と混同しない**: #860（disconnected 遷移）と #730（イベントループ飢餓）はスコープ外。修正で disconnected の導入や間隔の短縮をしない。
- **テスト環境**: このホストでは HEAD でも失敗するテストがある（tcp active-only の件数、setConfiguration 系、modern_sdp）。比較は一時 worktree（`git worktree add --detach`）で行い、active worktree の checkout / reset / stash はしない。
- **作業の記録**: 長時間の検証の前に、revision、未コミットの変更、意図を記録する。

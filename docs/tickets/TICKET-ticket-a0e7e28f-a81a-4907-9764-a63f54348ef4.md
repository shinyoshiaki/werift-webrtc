## 背景・下流の実証

下流の [wolkesson/dronelink](https://github.com/wolkesson/dronelink) は、遅延・損失の多い実通信環境を模したSITL障害試験で、正常なピアから返答を得られる経路にもかかわらずICE consentが30秒で失効し、送信が停止する状況を報告しています。

- [下流の独自パッチ](https://github.com/wolkesson/dronelink/blob/main/patches/werift%2B0.24.4.patch)
- [パッチ要件の検証テスト](https://github.com/wolkesson/dronelink/blob/main/packages/ground-client-sdk/src/werift-patch.test.ts)
- [下流の障害試験](https://github.com/wolkesson/dronelink/blob/main/docs/sim/flight-control-drills.md)

下流パッチでは、長めの応答待ち時間、未応答時の追加チェック、重複するチェックの許容によって改善しています。ただしパッチをそのまま採用せず、RFC 7675と安全な送信制御に照らして調査する必要があります。

## 現行実装と疑わしい経路

2026-11-19時点のv0.28.0 / `develop`：
- [`packages/ice/src/consent.ts`](https://github.com/shinyoshiaki/werift-webrtc/blob/v0.28.0/packages/ice/src/consent.ts) の `ConsentFreshness.start()` はconsent requestを4〜6秒間隔で開始し、次のrequest直前に `this.requestAbort?.abort()` で前回リクエストを中断する。
- [`packages/ice/src/iceBase.ts`](https://github.com/shinyoshiaki/werift-webrtc/blob/v0.28.0/packages/ice/src/iceBase.ts) の `consentResponseTimeoutMs(rtt)` は概ね `max(500ms, 2*RTT+200ms)`（RTT不明時は1秒）。
- 有効なresponseを受理すると独立した30秒のexpiry timerが更新される。これは既存のPR #649で改善済み。

RTTが急増して直前の推定値を上回る、または連続lossが発生すると、**遅れて届いた有効な応答がtransaction timeout/abortで捨てられ、30秒のconsentが失効する**可能性がある。具体的な再現条件と、再送0回・期限・transaction識別子を含めたRFCとの適合性を確認する。

※ このIssueは「有効な経路の**誤失効**」を扱う。[#860](https://github.com/shinyoshiaki/werift-webrtc/issues/860)（本当に経路が消えた場合のdisconnected遷移遅延）とは別問題。

## 調査・修正方針

1. 2ピア間のSTUN request/responseを遅延・欠落させる決定的なテストハーネスを構築。RTT変動、損失バースト、再順序化、および30秒を超える長時間接続を再現する。
2. requestの発行時刻、transactionのタイムアウト・abort、有効応答の受理可否、最終応答時刻、expiryを計測し、何が応答を捨てているか切り分ける。
3. 有効な旧transactionの遅延応答を許容する必要がある場合、**selected pair、ICE generation、認証(MESSAGE-INTEGRITY)、送信元、transaction ID** の整合を維持したうえで限定的に受理する設計を検討。
4. RTT見積もりを超える遅延へのresponse timeoutの設計と、古いリクエストをabortする要否を見直す。終了・ICE restart・pair変更時には必ず旧リクエストを無効化する。
5. RFC 7675の基本4〜6秒間隔、最後の有効応答から30秒で停止、無許可送信禁止という要件を維持。**下流の1秒ごとの追加送信はそのまま移植しない**（必要なら仕様根拠・負荷試験を伴う別設計とする）。
6. 関連する既存 #860、旧実装の修正PR #649との差分を文書化する。

## 回帰テスト・完了条件

- 4〜6秒間隔の通常条件、単発loss、遅延ジッタ、連続損失、RTT急上昇で、真正かつ期限内の応答がある間は不当に`failed`にならない。
- 本当に30秒間有効な応答がない場合はconsentが失効し、アプリデータ送信を停止する。
- 過去generation/旧selected pair/不正認証/期限切れ応答では有効期限を延長しない。
- close / ICE restart / pair切替でタイマー・transactionが漏れず、未処理Promise rejectionがない。
- 変更前に下流条件を可能な限り再現して失敗を示し、変更後に回復するテストを追加する。再現不能であれば調査結果を記録し、無理に挙動を変えない。

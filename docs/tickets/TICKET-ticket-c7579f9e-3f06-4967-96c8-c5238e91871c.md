# FirefoxのE2Eテストについてテスト側の問題か、実装側の問題か調査して修正する

## 1. 目的と背景

- `cd e2e && npm run firefox:record` を実行したところ、25 分経っても終わらずタイムアウトで止めた。その時点でメディア系のテスト（`packetize_*`、`repacketize_*`、`mediachannel_*`）がタイムアウトで失敗していた。
- 最後に Firefox のフルスイートを記録したのは `e2e/firefox-runs/20261121T032323Z-affd1237e.json`（約 348 秒）。そこでは `codecRtp` の packetize / repacketize もメディア系も通っていて、失敗は既知の ICE 6 件（`ice/nomination` 4 件、`ice/failover` 2 件）だけだった。
- このチケットでは、失敗がテスト側の問題か werift 本体の問題かを切り分け、根本原因を直す。最後に Firefox のフルスイートが完走し、その run record をコミットできる状態にする。
- **Firefox の失敗は、このチケットの中ですべて直す。** DTLS の回帰（§2.2）に加え、以前から残っている ICE の失敗（`ice/nomination` と `ice/failover`、§2.3）も対象にする。
  - 別チケットへ先送りして `firefoxKnownIssue` でスキップすることはしない。
  - スキップしてよいのは、Firefox がその機能を持たないテストだけ。例：RED の `createEncodedStreams()`、H.264、TURNS の IP リテラル。根拠を示したうえで `firefoxUnsupported` でスキップする。
  - 最終的に Firefox と Chrome の E2E が、失敗 0 件で全件通る状態にする。
- 今回の回帰（§2.2）は Chrome だけの CI では見つからず、ローカルで手動実行する Firefox の記録でしか分からなかった。このため、**Firefox E2E を GitHub Actions の CI に加え**、PR ごとに Firefox との相互接続の回帰を検出できるようにする（§3.5）。これは「Firefox は CI に入れない」という今までの方針（`e2e/AGENTS.md` の Don't）を変更するものなので、関連ドキュメントも同じ変更で書き換える。

## 2. 調査結果（HEAD `843bb1155`、変更なしのツリー）

### 2.1 再現

`e2e/AGENTS.md` の手動手順で再現した（サーバーは `/stop` と PID で止めたので run record は作っていない）。

```bash
cd e2e
export PLAYWRIGHT_BROWSERS_PATH=$PWD/node_modules/.cache/ms-playwright
node node_modules/playwright/cli.js install firefox   # 新しい worktree では未導入
E2E_PORT=18931 DEBUG=werift* npm run server &
VITE_E2E_PORT=18931 npx vitest run --browser.headless --config vitest.firefox.config.mts \
  tests/mediachannel/codecRtp.test.ts -t "packetize_vp8|depacketize_vp8"
E2E_PORT=18931 node stop.js
```

| テスト | 結果 |
| --- | --- |
| `depacketize_vp8`（Firefox → werift） | 成功 |
| `packetize_vp8` | 失敗：`waitVideoPlay timed out after 30000ms`、リトライ込みで約 60 秒 |
| `repacketize_vp8` | 失敗：`depacketize poll timeout: frames=0 keyframes=0 rtp=0`、リトライ込みで約 80 秒 |

失敗したテストはどれもリトライを含めて 60〜80 秒かかり、その間もテストイベントは出続ける。そのため idle 制限（5 分）には掛からず、時間制限の 60 分までスイートが進み続ける。これが「25 分たっても終わらない」の正体。

### 2.2 原因：werift 本体（DTLS 1.2 サーバーの HelloVerifyRequest の cookie 長）

サーバーログ（`DEBUG=werift*`）では、werift が **DTLS サーバー**になる接続のすべてで次の流れになっている。

```
packages/dtls/src/server.ts : association selected DTLS 1.2
packages/dtls/src/server.ts : send flight2 (HelloVerifyRequest)
packages/dtls/record/receive.ts : err ContentType.alert Alert { level: 2, description: 50 } DecodeError
packages/webrtc/src/transport/dtls.ts dtls failed DtlsAlertError: dtls received fatal alert: DecodeError (source: 'remote')
```

- Firefox（NSS）は、werift が送った HelloVerifyRequest に対して fatal の `decode_error` を返している。
- `packages/dtls/src/flight/server/flight2.ts` の HVR cookie は `mintDtls12HelloVerifyCookie()` → `mintAddressCookie()`（`packages/dtls/src/handshake/extensions/cookie.ts`）が作る。長さは `ADDRESS_COOKIE_LENGTH = 1 + 16 + 32 + 32 + 1 + 2 + 4 + 16 = 104` バイト。
- NSS の `dtls_HandleHelloVerifyRequest`（`lib/ssl/dtlscon.c`）は cookie が `DTLS_COOKIE_BYTES`（32）を超えると `decode_error` を返す。RFC 6347 §4.2.1 は DTLS 1.2 で cookie の上限を 255 バイトに広げたが、NSS は旧来の 32 バイト上限のまま。Chrome の BoringSSL は 255 バイトまで受け付けるので、Chrome の E2E と DTLS スイートでは見つからなかった。
- 変更前（`affd1237e`）の flight2 は `dtls.cookie ||= randomBytes(20)` で、20 バイトの cookie を送っていた。ステートレスな HMAC cookie に変えたのは `52658c757 Epic 1: Direct DTLS 1.3 endpoint (#674)`。これは `affd1237e` 以後に develop へ入った。
- werift が DTLS クライアントになる向き（Firefox が offer して werift が answer で `active` になる向き。例：`depacketize_*`）は HVR を受ける側なので影響を受けない。werift が offer して Firefox が DTLS クライアントになる向き（`packetize_*`、`repacketize_*`、`mediachannel_*_offer` など）だけが全滅する。ログの数字もこれと合う：HVR 送信 8 回に対して `DecodeError` が 56 行出ている（1 接続あたり複数のログ行）。

結論：**実装側（`packages/dtls`）の回帰であり、テスト側の問題ではない。** e2e のハーネスと設定の差分（`vitest.shared.mts` で `tests/dtls/**` と `tests/sped/**` を除外したこと、`fixture.ts` の待ち時間を引数にしたこと、`ensure-browser.js`）は、この失敗とは関係がない。

### 2.3 以前から残っている ICE の失敗（今回の回帰とは別、このチケットで直す）

`20261118T233958Z-bcbcc593a.json` と `20261121T032323Z-affd1237e.json` の時点から失敗しているもの。`docs/tickets/TICKET-ticket-be690c2e-...md` の §7 では範囲外として記録だけされていた。各テストはリトライ込みで 2 回とも同じ理由で失敗しているので、flaky ではなく決定的に失敗している。

| テスト | 失敗箇所（record のメッセージ） | 何が成り立っていないか |
| --- | --- | --- |
| `ice/nomination` chrome offers, renomination: false / true | `expected 'prflx' to be 'relay'`（約 0.7 秒で即失敗） | 最初の Assert。ブラウザ側の選択ペアの `remoteCandidateType` が `relay` だと決め打ちしている。Firefox は werift の relay 候補を `prflx` と記録する。werift が controlling の分岐では既に `["relay", "prflx"]` を許しているが、Chrome が offer する分岐では許していない。 |
| `ice/nomination` werift offers, renomination: false | `expected 'relay' to be 'host'`（約 30 秒） | `waitForHostPath()` の最初の expect。保留していた host 候補を Firefox に渡したあとも、**werift 自身**の `nominated.localCandidateType` が relay のまま。werift（controlling）が host ペアへ再指名していない。 |
| `ice/nomination` werift offers, renomination: true | 20 秒のテストタイムアウト | 同じく host への移行が終わらない。テスト自体の待ち時間（15 秒の waitFor と roundTrip）が `testTimeout` 20 秒に収まっていない可能性もある。 |
| `ice/failover` renomination: false | `expected 'host' to be 'relay'`（約 39 秒） | L111。host ソケットを切ったあと、werift の `nominated.localCandidateType` が 20 秒たっても relay にならない。werift 自身のフェイルオーバーが Firefox 相手では起きていない。 |
| `ice/failover` renomination: true | 60 秒のテストタイムアウト | 同上。 |

調べる前の仮説（実装時に検証し、結論を §2.3 に追記する）：

- **A. テスト側（Chrome 固有の前提）**
  - `nomination` の chrome offers 分岐は、`remoteCandidateType === "relay"` という Chrome 固有の記録に依存している。Firefox は TURN の送信元アドレスを `prflx` として学習する。
  - `e2e/AGENTS.md` Do 5 に従い、ブラウザ非依存の検証（ペアの相手アドレスとポートが werift の relay 候補と一致するか）に置き換える。`relay` / `prflx` の型の区別はブラウザ固有の検証として扱う。
  - `describe` 名の "with Chrome" と、"Chrome controlled" をブラウザ非依存の名前に直す。
- **B. werift 側（controlling 時の再指名とフェイルオーバー）**
  - werift offers の場合と failover の場合は、どちらも **werift 自身の**選択ペアが動いていない。ブラウザが選択に従わないだけなら、werift 側の expect は通るはず。
  - 次の可能性を、`DEBUG=werift-ice*` のログと werift の check list の状態で切り分ける。
    1. Firefox（nICEr）が送る connectivity check の形（`USE-CANDIDATE` の有無、`PRIORITY`、trickle された候補へのチェックの順序）が Chrome と違い、werift の triggered check → 指名の経路に乗っていない。
    2. host 候補を後から trickle したとき、werift の check list の状態遷移（frozen / waiting / succeeded）や、指名済みペアがある場合の「より良いペアへの切り替え」判定が、Firefox の応答タイミングでは成立しない。
    3. failover で relay ペアが valid list に無い（Firefox との relay ペアのチェックが成功していない、または consent が更新されていない）。そのため host を切っても退避先が無い。
  - werift の不具合と分かれば、`packages/ice`（必要なら `packages/webrtc`）で直す。
- **C. Firefox の非対応**
  - renomination（`a=ice-options:renomination` と `NOMINATION` 属性）は Chrome（libwebrtc）独自の拡張で、Firefox（nICEr）は実装していない見込み。renomination: true の 3 件（nomination 2 件、failover 1 件）は、テストが renomination の交渉成立（`remoteRenomination === true` や `nomination > 1`）を前提にしている部分だけ Firefox で成り立たない。
  - Firefox が renomination を広告しないことを SDP と STUN で確かめ、その場合は `firefoxUnsupported.renomination` を追加してスキップする。ただし renomination: false の同じシナリオは Firefox でも通す。
  - 同様に、controlled 側の nICEr が指名済みペアより優先度の低いペア（host → relay）への切り替えを受け入れないことが nICEr のソースか Firefox のログで示せた場合に限り、failover のブラウザ側の追従の検証を Firefox で外す。werift 側の退避の検証は残す。根拠が示せない場合は werift 側の問題として直す。

## 3. 実装する変更

### 3.1 DTLS 1.2 の HVR cookie を 32 バイト以下にする（本題）

- `packages/dtls/src/handshake/extensions/cookie.ts` に、DTLS 1.2 の HelloVerifyRequest 専用のコンパクトな cookie 形式を追加する。`mintDtls12HelloVerifyCookie` と `verifyDtls12HelloVerifyCookie` をこの形式に切り替える。
  - 案：`version(1) || issuedAt(4) || mac(<=27)`。`mac = HMAC-SHA256(secret, version || issuedAt || peerKey || ch1ImmutableHash)` を先頭から切り詰めたもの。
  - DTLS 1.2 の CH2 は CH1 と cookie 以外が同じでなければならない（RFC 6347 §4.2.1）。そのため検証側は CH2 から `clientHelloImmutableFieldsHash()` を計算し直して MAC を照合すればよく、ハッシュを cookie に入れる必要はない。`ch1MessageHash` は TLS 1.3 HRR の transcript（message_hash）にしか使わないので、DTLS 1.2 の cookie には要らない。
  - 今のセキュリティ上の性質は残す：送信元アドレス（`peerKey`）への束縛、CH パラメータへの束縛、有効期限（`ADDRESS_COOKIE_MAX_AGE_SEC` と clock skew）、`timingSafeEqual` による比較、ステートレスであること（サーバーに map を持たない）。
  - 定数は、たとえば `DTLS12_HVR_COOKIE_MAX_LENGTH = 32` として、根拠（NSS の `DTLS_COOKIE_BYTES`、RFC 4347 の `cookie<0..32>`）をコメントに書く。
- DTLS 1.3 の HRR cookie 拡張（`mintAddressCookie` と `verifyAddressCookie`、`src/engine/v1_3/flight/server/flight4.ts`）は `opaque cookie<1..2^16-1>` なので 104 バイトのままでよい。変更は DTLS 1.2 の経路に限る。
- 呼び出し元の `packages/dtls/src/server.ts`（L357 付近の flight2 呼び出し、L368 付近の `verifyDtls12HelloVerifyCookie`、L393 付近の re-HVR）と、dual-capable（1.3 / 1.2）経路の HVR（`self13_dual_hvr_resume` など）がすべて新しい形式で一貫していることを確かめる。
- HVR を作る側には、cookie が 32 バイトを超えたら送らずに例外にする上限チェックを入れて、将来の回帰を防ぐ。

### 3.2 テスト（Arrange / Act / Assert、日本語コメント）

- `packages/dtls/tests/e2e/self12_cookie_binding.test.ts`（または `tests/handshake/message/server/helloVerifyRequest.test.ts`）に次を追加する。
  - wire 上の HVR の cookie 長が 32 バイト以下であること。flight2 の送信バッファを `ServerHelloVerifyRequest` として deserialize して確かめる。
  - 短くした cookie でも、送信元アドレスの束縛、CH パラメータの束縛、期限切れ、MAC の改ざんで検証が失敗すること。既存の binding テストを新しい形式で通す。
- `tests/handshake/tls13/pre_cookie_and_validation.test.ts` の `ADDRESS_COOKIE_LENGTH`（104）の期待値は 1.3 用なので変えない。DTLS 1.2 用の定数を別に検証する。
- 可能なら、NSS 由来の 32 バイト上限をまねたクライアント（HVR cookie が 32 バイトを超えたら `decode_error` を返す）との自己対向テストを足す。

### 3.3 ICE の失敗を直す（`ice/nomination` と `ice/failover`）

§2.3 の仮説を、1 ファイルずつ手動の手順（§2.1 と同じ。`DEBUG=werift-ice*` を付ける）で確かめてから直す。

1. **再現とログ**
   - `tests/ice/nomination.test.ts` と `tests/ice/failover.test.ts` を、Firefox と Chrome のそれぞれで単体実行する。
   - 次を比べる。
     - werift の check list（ペアごとの state、nominated、valid）。
     - 受信した STUN Binding の属性（`USE-CANDIDATE`、`NOMINATION`、`PRIORITY`、`ICE-CONTROLLING` / `ICE-CONTROLLED`）。
     - ブラウザ側の `getStats()` の candidate-pair。
   - ハンドラーは `server/handler/ice/nomination.ts` と `failover.ts`。stats を返す `type: "stats"` に、切り分けに要る項目（valid list、ペアごとの state）が足りなければ追加する。テストの観測点を増やすのはよいが、ハンドラーで werift の挙動を補正することはしない。
2. **テスト側の修正（仮説 A）**
   - chrome offers 分岐の `remoteCandidateType` の決め打ちをやめる。ブラウザ非依存の検証として、選択ペアの相手アドレスとポートが werift の relay 候補（TURN の割り当てアドレス）と一致することを確かめる。`relay` / `prflx` の型の区別は、Chrome でだけ確かめる。
   - werift offers / renomination: true のテストが待ち時間の合計で `testTimeout`（20 秒）を超えるなら、test 単位の timeout を明示する。これは待ち時間の見直しであって、失敗を隠すためではない。
   - describe とテスト名、コメントの "Chrome" を、ブラウザ非依存の表現（"the browser"）に直す。
3. **werift 側の修正（仮説 B）**
   - controlling 時に、後から有効になった、より優先度の高いペア（host）へ指名を移すこと。そして指名中のペアが consent を失ったとき、valid な relay ペアへ退避すること。この 2 つを、ブラウザの実装に依存しない形で `packages/ice` に直す。
   - `packages/ice` に、Firefox（nICEr）の check の出し方を再現する単体テストまたは property テストを追加する。対象は、指名済みペアがある状態での trickle、triggered check の順序、`USE-CANDIDATE` を伴わない controlled 側の check。
   - Chrome の経路（`npm run e2e`）と既存の ICE テストが回帰しないことを確かめる。memory のメモにあるとおり、ICE の failover / nomination は role × mode × topology の組み合わせで回帰しやすい。controlling / controlled × renomination 有無 × host / relay の組み合わせを、表形式のテストで押さえる。
4. **Firefox 非対応の部分（仮説 C）**
   - Firefox が renomination に対応しないことは、Firefox の offer / answer に `renomination` が無いこと、STUN に `NOMINATION` 属性が無いことで確かめる。そのうえで `firefoxUnsupported` に `renomination: "[firefox-unsupported:renomination] Firefox (nICEr) は ICE renomination（a=ice-options:renomination / NOMINATION 属性）を実装していない"` を追加し、renomination: true のケースだけを `itSkipOnFirefox` にする。`test.each` の場合は、ケースごとに `it` / `itSkipOnFirefox` を選ぶ形に組み替える。
   - renomination: false のケースは、Firefox で通るように直す（スキップしない）。
5. **Firefox E2E で確かめる**
   - 修正をコミットしたあと、clean な HEAD で `cd e2e && npm run firefox:record` を引数なしで実行する。`outcome: completed`、`failed: 0`、`unfinished: 0` で終わること、生成された run record をコミットすることを確かめる。
   - `codecRtp`、`recordPlayback*`、`vp8Playback`、`simulcast` などのメディア系が通ること、ICE の 6 件が「通る」か「`firefoxUnsupported` で理由付きスキップ」のどちらかになっていることを確かめる。

### 3.4 Firefox 非対応のテストのスキップを整理する

- 今の `firefoxUnsupported`（`e2e/tests/fixture.ts`）と、その使用箇所：
  - `h264`：`codecRtp.test.ts`（depacketize / packetize / repacketize の H.264）。Playwright の Firefox には OpenH264 が無い。
  - `encodedStreams`：`red.test.ts`（`mediachannel_red_client_answer` / `_offer`）。RED を Chrome 独自の `RTCRtpReceiver.createEncodedStreams()` で読んでいる。
  - `turnsIpLiteral`：`turnRelay.test.ts` の TLS。Firefox の TURNS は FQDN と信頼済み証明書を要求する。
  - 追加予定の `renomination`（§3.3 の 4）。
- 各理由について、それが本当に Firefox の非対応であって werift の不具合ではないことを、ブラウザの機能（API の有無、SDP、仕様）で裏付け、理由文に書く。
  - RED は、Firefox が `createEncodedStreams()` を持たなくても、標準の `RTCRtpScriptTransform`（Firefox は対応）で読める可能性がある。その場合、Firefox で RED を検証できるなら、スキップより検証経路を足すほうを優先する。ただし今回の完了条件ではなく、調べた結果を理由文かチケットに残す。
- `firefoxKnownIssue` は空のまま終える。werift の不具合は、このチケットで直すかぎり known issue としてスキップしない。
- `grep -rn "itSkipOnFirefox" e2e/tests` の結果がすべて `firefoxUnsupported` の理由であること、理由の無い `it.skip` や `test.skip` が無いことを確かめる。

### 3.5 Firefox E2E を CI に加える

前提：§3.1 から §3.4 で、Firefox のフルスイートが clean な HEAD で失敗なく完走していること。スキップは Firefox 非対応（`firefoxUnsupported`）だけ。赤いままのスイートを CI に入れない。

**現状の調査**

- `.github/workflows/nodejs.yml` の `build` ジョブ（Node 24.x / 26.x の matrix）が、`npm run ci` の中で `npm run e2e` → `e2e/run-ci.js`（Chrome）→ `run-dtls-ci.js`（DTLS）を順に実行する。Firefox はどこからも実行されない。
- Firefox の実行経路は `e2e/run-firefox.js`（`npm run firefox:record`）だけ。これは次のように動く。
  - Playwright の Firefox を `e2e/node_modules/.cache/ms-playwright` に入れる。
  - サーバーを空きポートで起動する。
  - 時間制限（`FIREFOX_E2E_TIMEOUT_MIN`、既定 60）と idle 制限（`FIREFOX_E2E_IDLE_MIN`、既定 5）で止める。
  - 終了コードは vitest のものを返す。
  - 記録は `e2e/firefox-runs/`（`RECORDS_DIR`、`firefox-run-record.js` で固定）に書き、古いものを prune する。
- このため CI では、記録の出力先を repo の外に向けることと、prune を止めることができればよい。サーバーの起動と停止、タイムアウトの仕組みはそのまま流用できる。

**変更内容**

1. `nodejs.yml` に独立したジョブ `firefox-e2e` を追加する。`build` の matrix には入れず、`build` と並列に走らせる。
   - 実行環境は `ubuntu-latest`、Node.js 24.x のみ。`timeout-minutes` は 30 程度。
   - 手順：
     - checkout と `git submodule update --init --recursive`。
     - `build` と同じ apt パッケージ（gstreamer や ffmpeg。`recordPlayback*` と `vp8Playback` のサーバー側で使う）を入れる。
     - `npm i` を実行し、`cd e2e && npm install --prefer-offline --no-audit --no-fund --no-update-notifier` を実行する。
   - Firefox は `npx playwright install --with-deps firefox` で、`e2e` の playwright と同じリビジョンのものを `PLAYWRIGHT_BROWSERS_PATH=e2e/node_modules/.cache/ms-playwright` に入れる。システムライブラリもこれで入る。あるいは `e2e/ensure-browser.js` / `scripts/install-playwright-browsers.js` に Firefox 用の関数を追加し、そこを通してもよい。
   - 実行は `cd e2e && npm run firefox:ci`（新設）。
   - `if: always()` で `actions/upload-artifact` を使い、run record の JSON と `e2e/.vitest/attachments/`（失敗時のスクリーンショット）を artifact として保存する。
2. `e2e/run-firefox.js` に CI モードを追加する（例：`--ci` 引数、または `FIREFOX_RECORDS_DIR` 環境変数）。
   - 記録の出力先を repo の外（`$RUNNER_TEMP` など）にし、prune しない。commit 済みの記録は変更しない。
   - 終了コードは今の仕様のまま使う。`result: passed` 以外（失敗、timeout、未完了、module error）は非 0 にして、ジョブを失敗させる。
   - CI では `FIREFOX_E2E_TIMEOUT_MIN` を 20 前後に下げる。今回のような全滅の場合でも、ジョブの timeout より先に runner が記録を書いて止まるようにするため。
   - `e2e/package.json` に `"firefox:ci": "npm run build && node run-firefox.js --ci"` を追加する。ローカルの `firefox:record` は TypeScript ソースのサーバーを起動するので、CI でもソースのまま起動するなら `build` は不要になる。どちらかに統一する。
3. Firefox を `npm run ci`、`npm run e2e`、`e2e/run-ci.js` には入れない。ローカルの既定の検証時間を延ばさないため、別ジョブ・別スクリプトにする。
4. 方針とドキュメントを同じ変更で更新する。

     - Commands に `firefox:ci` を追加する。

   - ルートの `AGENTS.md`：Commands 表の「Firefox E2E with a committed run record (local only, not in CI)」と、Validation の Firefox の記述を更新する。
   - `e2e/firefox-runs/README.md`：冒頭の「CI does not run the Firefox E2E suite」を直し、CI では記録を artifact に保存すること、CI モードの仕様を追記する。
   - `e2e/run-firefox.js` 冒頭の JSDoc を直す。
   - run record の commit 運用は、CI が履歴を持つようになるので「必須」から「ローカルで調べた結果を残すときに使う」に緩めることを推奨する。決めた運用を AGENTS.md と README に反映する。

**安定性の確認**

- CI ランナーはインターフェース構成がローカルと違う（`ice/nomination` と `ice/failover` は TURN、relay、host の経路に依存する）。ブランチの PR か `workflow_dispatch` で、1 回通ることを確かめる。
- 不安定なテストを見つけた場合：
  - werift の不具合なら、このチケットで直す（`firefoxKnownIssue` でスキップしない）。
  - CI ランナーでしか起きない環境の制約（ネットワーク構成など）であることを示せた場合に限り、理由を明記してスキップする。
  - `retry` を増やしたり、ジョブの `continue-on-error` で隠したりはしない。
- 外部 STUN（`stun.l.google.com`）への依存は Chrome の CI と同じ前提とし、Firefox だけを特別扱いしない。

## 4. 制約・注意点

- `e2e/server/handler/*` での回避や SDP の書き換えで werift のバグを隠さない（`e2e/AGENTS.md` の Don't）。直すのは `packages/dtls` と `packages/ice`（必要なら `packages/webrtc`）。テストの `holdBackNonRelayCandidates` や `advertiseRenomination` のような、シナリオを作るための SDP 操作は今のまま使ってよい。
- テストの期待値を緩めるのは、ブラウザ固有の記録（候補の型の表記など）に依存している部分だけにする。werift 自身の状態（`nominated`、`controlling`、`connectionState`）に対する検証は緩めない。
- ICE の修正は Chrome との経路にも効く。`npm run e2e`（Chrome の `ice/*`）、`packages/ice` の `npm test`、`npm run pbt:deep --workspace packages/ice` で回帰を確かめる。pbt:deep には develop でも落ちる既知の seed があるので、`--baseline <develop worktree>` で比べる。
- cookie を短くしても、`self12_preauth_dos`、`anti_amp`、`self12_hvr_rechallenge`、`self12_hvr_stale_retransmit`、`self12_commit_transactional` などで守っている pre-auth DoS と増幅攻撃への耐性、re-challenge の挙動を壊さない。
- HVR の `server_version` は今 `{254,253}`（DTLS 1.2）。RFC 6347 は DTLS 1.0（`{254,255}`）を推奨（SHOULD）しているが、今回の原因ではないので変えない（変えるなら別に検討する）。
- `src/engine/v1_3/` に多段の継承を入れない。module scope に状態を持たない（cookie secret は今どおり `dtls.cookieSecret` に置く）。
- Firefox の run record は、コミット済みで clean な HEAD から引数なしで実行したものだけを結果の根拠にする。記録は手で編集しない。
- 長時間の検証の前には、リビジョン、未コミットの変更、意図を書き残す（ルート `AGENTS.md` Do 8）。サーバーとブラウザは PID か `/stop` で止め、`pkill -f` は使わない。
- Firefox CI ジョブは §3.1 の DTLS 修正と §3.3 の ICE 修正が終わってから有効にする。順序を逆にすると、最初から赤い CI になる。
- CI ジョブの依存インストールはキャッシュが効き、audit をしない形にする（`--prefer-offline --no-audit --no-fund --no-update-notifier`）。プロセスは runner の PID / `/stop` で止める方式のままにし、`pkill` は使わない。
- CI ではブラウザ（Firefox）とテスト用の TURN / e2e サーバーが同じホストで動く。`vitest.firefox.config.mts` の IPv4 の host 指定と loopback の prefs は CI でも必要なので、変えない。
- 新しい worktree には Playwright の Firefox が入っていない（`e2e/node_modules/.cache/ms-playwright`）。`firefox:record` が自動で入れるが、手動でデバッグするときは先に入れる。

# polyfill 使用時に `as unknown as ProducerOptions["track"]` のようなキャストを不要にする

## 1. 目的と背景

`werift/polyfill` を使って Node.js 上で `mediasoup-client` などのブラウザ向けライブラリを動かすと、アプリ側で次のようなキャストが必要になる。

```ts
const track = new MediaStreamTrack({ kind: "audio" }); // werift の MediaStreamTrack
// mediasoup-client types the track as the DOM MediaStreamTrack; werift's
// track is what the polyfilled RTCPeerConnection actually sends.
const producer = await sendTransport.produce({
  track: track as unknown as ProducerOptions["track"],
  appData: { type: "webcam" },
});
```

実行時は polyfill の `RTCPeerConnection` が werift の track をそのまま送るので問題なく動く。問題は型だけで、`mediasoup-client` の `.d.ts` が `track?: MediaStreamTrack`（DOM のグローバル型）を要求するため、werift のクラスを渡すと型が合わない。
目的は、polyfill の利用者が型安全を捨てる二重キャストを書かずに、werift の track を DOM 型の API へ渡せるようにすること。

### 現状の型エントリ（調査結果）

| import | 型の振る舞い | ファイル |
| --- | --- | --- |
| `werift/polyfill` | `declare global { var MediaStreamTrack: typeof WeriftMediaStreamTrack }` で値だけを宣言し、**型（interface）`MediaStreamTrack` は宣言していない** | `packages/webrtc/src/polyfill/globals.ts` |
| `werift/polyfill/dom` | DOM の `interface MediaStreamTrack` に `writeRtp` / `writeRtcp` / `onReceiveRtp` / `onReceiveRtcp` を追加しているだけ | `packages/webrtc/src/polyfill/dom.ts` |

`tsconfig` で `lib` を指定しない場合も TypeScript は既定で `lib.dom` を読み込むので、多くの利用者は DOM 型がある環境でこの問題に当たる。

### 再現結果（`lib: ["esnext", "dom"]` + `werift/polyfill/dom`、一時 fixture で確認）

```
TS2740: Type 'MediaStreamTrack' is missing the following properties from type 'MediaStreamTrack':
  contentHint, onended, onmute, onunmute, and 4 more.
```

DOM の `MediaStreamTrack` と比べた werift `MediaStreamTrack`（`packages/webrtc/src/media/track.ts`）の差分:

- **存在しないメンバー**: `contentHint`, `onended`, `onmute`, `onunmute`, `applyConstraints()`, `getCapabilities()`, `getConstraints()`, `getSettings()`
- **型が合わないメンバー**:
  - `id?: string`（DOM は `string`）。コンストラクタで常に `this.id ??= this.uuid` しているので、実際には undefined にならない
  - `onReceiveRtp`: クラスは `Event<[RtpPacket, Extensions?, RtpReceiveInfo?]>`、`dom.ts` の augmentation は `Event<[RtpPacket, Extensions?]>` で、定義が食い違っている
  - `clone()`: 上の 2 点に引きずられて合わない
- `MediaStream` も同じ状況:
  - 存在しない: `addEventListener`, `removeEventListener`, `dispatchEvent`, `onaddtrack`, `onremovetrack`
  - 型が合わない: `clone`, `addTrack`, `removeTrack`, `getTracks`, `getAudioTracks`, `getVideoTracks`, `getTrackById`（いずれも track 型の差に起因）
- `lib.dom` がある環境では、グローバルの `MediaStreamTrack` コンストラクタは DOM の `new(): MediaStreamTrack`（引数 0 個）になる。そのため `new MediaStreamTrack({ kind: "audio" })` は TS2554 になり、利用者は `werift` から直接 import するしかない。
- `navigator.mediaDevices.getUserMedia()` で得た track は、`/dom` では DOM の戻り値型になるのでキャストなしで `produce()` に渡せる。問題になるのは「werift のクラスを直接 new した track」と「werift API の戻り値の track」。

### DOM なし環境（`werift/polyfill`, `lib: ["esnext"]`）での確認結果

- グローバルの型 `MediaStreamTrack` が存在しないので、`skipLibCheck: true` の下では `mediasoup-client` の `.d.ts` の `MediaStreamTrack` が解決できず、暗黙に any 相当になる。キャストは不要だが、`producer.track?.nonexistent` もエラーにならず、型情報が失われている。
- アプリ側で `MediaStreamTrack` を型として書くと TS2749（"refers to a value, but is being used as a type"）になる。
- `integration/werift-mediasoup-interop` は DOM なし（`lib: ["ES2023"]`）で、独自の `test/globals.d.ts` に最小限の `interface MediaStreamTrack` を宣言して回避している。DOM あり構成の型検証は、このリポジトリのどこにも無い。

### mediasoup-client（3.22.0）が実行時に使う track のメンバー

`enabled`, `readyState`, `stop()`, `addEventListener("ended")` / `removeEventListener("ended")`（Producer / Consumer / Transport）。どれも werift に実装済みで、型だけ埋めれば足りる。

## 2. 実装すべき変更

### 必須

1. **werift `MediaStreamTrack` を DOM `MediaStreamTrack` に代入できるようにする**（`packages/webrtc/src/media/track.ts`）
   - `id` を `string` 必須にする。コンストラクタ引数（`Partial<MediaStreamTrack>`）では省略できるままにする。
   - `contentHint: string`（既定値 `""`）を追加する。
   - `onended` / `onmute` / `onunmute`（`((ev) => any) | null`、既定値 `null`）を追加する。`"ended"` を emit したときに `onended` も呼ぶ。mute 状態が変わったときに `mute` / `unmute` イベントを出すかどうかは仕様に合わせて決め、出さない場合はその旨を TSDoc に書く。
   - `getSettings()` / `getConstraints()` / `getCapabilities()` / `applyConstraints()` を追加する。
     - polyfill の `getUserMedia` で得た track は、`selectSettings.ts` が選んだ settings / constraints を返すのが自然。
     - 手で new した track は、`kind` などから最小限の値を返す。
     - `applyConstraints()` は未対応の制約を `OverconstrainedError` で reject するか、受け付けて保持するかを決める。werift の既存 `OverconstrainedError`（`packages/webrtc/src/errors.ts`）を使う。
   - コア `werift` は `lib.dom` なしでビルドするので、`MediaTrackSettings` などの DOM 型は参照できない。werift 側に構造的に互換な型（例: `WeriftMediaTrackSettings`）を定義する。
2. **`werift/polyfill/dom` の augmentation をクラスと一致させる**（`packages/webrtc/src/polyfill/dom.ts`）
   - `onReceiveRtp` を `Event<[RtpPacket, Extensions?, RtpReceiveInfo?]>` にする。
   - augmentation とクラスの定義が今後ずれないよう、一方から他方を導出する形（例: `Pick<WeriftMediaStreamTrack, ...>` を extends する）にする。
3. **`MediaStream` も同じように DOM 互換にする**
   - `addEventListener` / `removeEventListener` / `dispatchEvent`、`onaddtrack` / `onremovetrack` を用意する。werift の `EventTarget`（`packages/webrtc/src/helper.ts`）を継承するのが既存パターンに沿う。
   - 対象: `const dom: MediaStream = new WeriftMediaStream([track])` のような代入。
4. **compile fixture に回帰テストを追加する**
   - `packages/webrtc/tests/nonstandard/polyfillDomCompile/consumer.ts`（`lib.dom`, `skipLibCheck: false`）に、`mediasoup-client` の `ProducerOptions` を模した `declare function produce(o: { track?: MediaStreamTrack }): ...` を置き、次のコードがキャストなしで通ることを確認する。
     ```ts
     import { MediaStreamTrack as WeriftMediaStreamTrack, MediaStream as WeriftMediaStream } from "werift";
     produce({ track: new WeriftMediaStreamTrack({ kind: "audio" }) });
     const stream: MediaStream = new WeriftMediaStream([...]);
     ```
   - このテストは既存の `polyfill.test.ts` の `"public polyfill entry compiles with TypeScript DOM lib"` から実行される。
5. **実行時テスト**: 追加したメソッドとハンドラ（`getSettings` などの戻り値、`onended` の呼び出し、`applyConstraints` の resolve / reject）を Arrange / Act / Assert で書き、日本語コメントを付ける。

### 推奨（スコープ内で検討し、入れない場合は理由を残す）

6. **DOM ありで `new MediaStreamTrack({ kind })` を書けるようにする**
   - 案: `werift/polyfill/dom` から、`new (init: { kind: "audio" | "video"; ... }) => globalThis.MediaStreamTrack` 型のコンストラクタを `MediaStreamTrack` として export する。
   - `lib.dom` の `declare var MediaStreamTrack` は再宣言できないので、グローバルの型を差し替える方法は取れない。
7. **DOM なし（`werift/polyfill`）でも型を失わないようにする**
   - 案: `globals.ts` に `interface MediaStreamTrack extends WeriftMediaStreamTrack {}`、`interface MediaStream extends WeriftMediaStream {}` を追加し、値と型を merge する。こうすると `mediasoup-client` の `.d.ts` が werift の型に解決される。
   - 既存の `polyfillNodeCompile` fixture が通り続けることを確認する。
8. **逆方向の受け渡し**
   - 例: `mediasoup-client` の `consumer.track`（DOM 型）を werift の `new MediaStream([...])`、`addTrack`、`replaceTrack` に渡す場合。
   - werift 側が werift 固有のメンバー（`uuid`、`remote` など）を要求していないかを確認する。必要なら、polyfill から使う公開シグネチャを DOM 型でも受けられる形にするか検討する。
9. **`integration/werift-mediasoup-interop` で実物の `mediasoup-client` を使って型検証する**
   - DOM ありの tsconfig（例: `tsconfig.dom.json` を `npm run type` に追加）で、実物の `mediasoup-client` 型に対して `produce({ track: new MediaStreamTrack(...) })` がキャストなしで通ることを確認する。
   - script を追加したら、そのディレクトリの `AGENTS.md` の Commands 表も更新する。

## 3. 技術的アプローチ（要約）

- **採用する方針**: werift の実装クラスを DOM の `MediaStreamTrack` / `MediaStream` と構造的に互換にし、利用者もライブラリ内部もキャストせずに済むようにする。
- **採用しない方針**: `asDomTrack(track)` のような型変換ヘルパーや、ライブラリ内部での `as unknown as` は使わない。キャストの場所が変わるだけで、DOM 型が要求するメソッド（`getSettings` など）が実行時に存在しない嘘の型になる。
- 型の不一致は、`Exclude<keyof globalThis.MediaStreamTrack, keyof WeriftMediaStreamTrack>` と、プロパティごとの `extends` 判定で列挙できる（第 1 節の一覧はこの方法で取得した）。テストにも同じ型レベルの検査を入れると、DOM 型が将来変わったときに検知できる。
- 主な変更対象:
  - `packages/webrtc/src/media/track.ts`（`MediaStreamTrack` / `MediaStream`）
  - `packages/webrtc/src/polyfill/dom.ts`
  - `packages/webrtc/src/polyfill/globals.ts`
  - `packages/webrtc/src/polyfill/mediaDevices.ts` と `selectSettings.ts`（settings / constraints を track に渡すため）
  - `packages/webrtc/tests/nonstandard/polyfillDomCompile/`
  - `packages/webrtc/tests/nonstandard/polyfillNodeCompile/`

## 4. 制約・注意点

- **公開 API の変更になる**
  - `MediaStreamTrack.id` の型が `string | undefined` から `string` に変わる。
  - メソッドとプロパティが増える。
  - これらに合わせて `changelog.md`（Unreleased）、`docs/polyfill/guide.md` の「TypeScript entrypoints and compatibility」節、`docs/polyfill/README.md` を更新する。`mediasoup-client` にキャストなしで渡す例を載せる。
  - 生成ドキュメント（`doc/`, `packages/*/doc`, `doc/_media/README-1.md` など）は、手で編集せずに `npm run doc` で再生成し、`npm run doc:check` で確認する。
- **コアは DOM 非依存のままにする**。`packages/webrtc/src` は `lib.dom` なしでビルドされるので、DOM 型を直接参照せず、構造的に互換な独自型で表す。
- **erasable syntax のみ**（`enum` とパラメータプロパティは使わない）。
- **モジュールスコープに状態を置かない**。settings や constraints は track インスタンスのフィールド（`@internal` か `private`）に持たせる。
- `onended` などのハンドラ追加で、既存の `"ended"` イベントの発火順序と回数を変えない。`trackStop.ts` の `bindOwnTrackStop`、`TrackBroadcastSource.stopAllTracks`、`clone()` の共有 source の挙動が回帰しないようにする。
- `clone()` で新しいフィールド（`contentHint`、settings / constraints）を引き継ぐかどうかを、DOM 仕様（clone は constraints を引き継ぐ）に合わせて決める。
- WPT の strict 挙動は `packages/webrtc/tools/wpt-runner/*` に閉じ込める方針を守る。`applyConstraints` を厳密化する必要があれば wrapper 側で行う。
- 既存の型テスト `packages/webrtc/tests/types/publicTypes.test.ts` と、`polyfillDomCompile` が検査している TS2403 / TS2687 / TS2717（グローバル宣言の衝突）を再発させない。
- `mediasoup-client` を親パッケージの依存に加えない（`integration/werift-mediasoup-interop/AGENTS.md`）。型を模すのは compile fixture 内の `declare` で行う。

## 6. 実装メモ（推奨項目の対応状況）

- **推奨 6（対応）**: `werift/polyfill/dom` が `MediaStreamTrack` / `MediaStream` を export する。中身は werift のクラスで、型は DOM クラスのコンストラクタ（`new (init) => globalThis.MediaStreamTrack`）。`polyfillDomCompile` fixture で確認している。
- **推奨 7（対応）**: `globals.ts` に `interface MediaStreamTrack extends WeriftMediaStreamTrack {}` / `interface MediaStream extends WeriftMediaStream {}` を追加した。`polyfillNodeCompile` fixture で、型として使えること、存在しないメンバーが `@ts-expect-error` になることを確認している。
- **推奨 8（見送り）**: werift 自身の API（`new MediaStream([...])`、`addTrack`、`replaceTrack`）は werift 固有の内部（`uuid`、broadcast source、`writeRtp` など）を使うので、引数は werift の track 型のままにした。DOM 型を受けるようにすると、DOM 型が実行時の中身を保証しない「嘘の型」になる。DOM 型の値は `instanceof MediaStreamTrack`（werift のクラス）で絞り込む。この方針は `docs/polyfill/guide.md` に書いた。`werift/polyfill/dom` の `MediaStream` が返す DOM 型の `addTrack` は、DOM 型の track を受け付ける。
- **推奨 9（ローカル検証のみ。commit は interop リポジトリ側へ）**: `integration/werift-mediasoup-interop` は別リポジトリの git submodule なので、この変更には含められない。実物の `mediasoup-client@3.22.0` の型を使い、次の構成で確認した。
  - 構成: `tsconfig.dom.json`（`lib: ["ES2023","DOM"]`、`moduleResolution: "bundler"`、`allowImportingTsExtensions`、`noImplicitAny: false`）と、`test/types/domProduce.ts`（`sendTransport.produce({ track: new WeriftMediaStreamTrack({ kind: "audio" }) })` などを型検査するだけのファイル）。
  - 結果: この変更では通る。変更前のリビジョンでは、チケット記載の TS2740 と、MediaStream の TS2739 で失敗する。
  - 取り込む場合: interop リポジトリで、`npm run type` に `tsc --noEmit -p tsconfig.dom.json` を加え、`AGENTS.md` の Commands 表も更新する。
- **mute / unmute と addtrack / removetrack**: werift 自身はこれらのイベントを出さない。ハンドラは DOM と同じく listener の一種なので、アプリが `dispatchEvent` したイベントでは呼ばれる（第 7 節の方針 B）。`"ended"` は従来どおり `stop()` でも 1 track につき 1 回発火する。`onended` は最初に設定された位置の listener として、同じ Event を受け取って呼ばれる。
- **`MediaStreamTrack<K extends Kind = Kind>`**: `mediabunny` が `@types/dom-mediacapture-transform` を読み込み、DOM の `MediaStream.getAudioTracks()` の戻り値を `MediaStreamAudioTrack[]`（`kind: "audio"`）に狭めている。werift の `MediaStream` をこれに代入できるよう、track の `kind` を型引数にした。

## 7. 追加要件: DOM イベント互換の収束（レビュー 8 回分の打開策）

### 背景

DOM 互換で追加したメンバーは、それぞれネイティブ DOM との比較観点になる。修正を再現箇所だけに入れると、同じ種類の差異が別のクラス・ファイルに残り、次のレビューで指摘された（例: `dispatchEvent` の戻り値を `MediaStream` だけ直し、`MediaStreamTrack` に残った）。そこで、挙動を 1 か所の層にまとめ、ネイティブ実装を基準にした組み合わせテストで確認する。

### 要件

1. **残っていた差異をまとめて直す**
   - G: `changelog.md` の "unknown names are ignored" を実装・guide に合わせる。
   - A: `MediaStreamTrack.dispatchEvent` も DOM の戻り値（cancelable なイベントが `preventDefault()` されたときだけ `false`）にする。
   - B / E / F: 下記の方針で解消する。
2. **イベント互換を 1 か所にまとめる**: `packages/webrtc/src/media/domEventTarget.ts` の `DomEventTarget` を track と stream が継承する。共通の `helper.ts` の `EventTarget` は変えない（`RTCPeerConnection` などの既存の利用先に影響させない）。扱う範囲は、`dispatchEvent` の戻り値、`on<type>` ハンドラ属性、`handleEvent` オブジェクト、重複登録の無視、`once` / `passive` / `signal`、dispatch 中に削除された listener、ハンドラの例外。
3. **ネイティブ実装との差分テスト**: Node のネイティブ `EventTarget`（`onabort` ハンドラ属性を持つ `AbortSignal`）を基準に、{track の `onended` / `onmute` / `onunmute`、stream の `onaddtrack` / `onremovetrack`} × 長さ 3 までの全操作列（関数 / `once` / `handleEvent` / `handleEvent`+`once` / `preventDefault` / `passive`+`preventDefault` / dispatch 中の削除 / remove / ハンドラ設定・変更・`null`）× cancelable の有無で、2 回の dispatch の戻り値・`defaultPrevented`・呼び出し順・回数・`this`・Event の同一性が一致することを確認する（`tests/media/domEventTarget.test.ts`）。
   - ネイティブ側が HTML 仕様と違う 2 点は比較から外し、仕様どおりの期待値で別に検査する: (a) Node はハンドラを `null` にしても位置を保持するが、HTML の "deactivate an event handler" は listener を外すので、再設定したハンドラは後から足した listener の後に呼ばれる。(b) HTML ではハンドラが `false` を返すと cancelable なイベントがキャンセルされる（Node は未対応）。
   - 例外は Node では非同期の uncaught exception として報告されるため比較できない。werift 側の期待値（呼び出し元に伝わらず、後続の listener が呼ばれる）を別に検査する。
4. **ドキュメントの主張と裏付けテストの対応を保つ**: 挙動を変えたときは TSDoc・`docs/polyfill/guide.md`・`docs/polyfill/README.md`・`changelog.md` を同時に更新する（下表）。
5. **範囲を広げすぎない**: DOM 互換の主張は、DOM 型への代入と、DOM 型を使うライブラリ（`mediasoup-client` など）が使うメンバーに限ると TSDoc に明記する。イベント経路（capture / bubble）、`event.target` / `currentTarget` は扱わない。

### 方針判断

- **F（ハンドラの例外）: 記録して隔離する。** DOM は listener の例外を報告するだけで、`dispatchEvent` の呼び出し元に伝えない。#815 の DataChannel も「投げた listener はログに出して隔離する」方針なので揃える。`DEBUG=werift*` で `werift:packages/webrtc/src/media/domEventTarget.ts` に記録する。これにより `stop()`、`stopMediaSource()`、polyfill の cleanup は `onended` の例外で失敗しなくなる（以前の回帰テストの期待値「例外は再送出される」を「伝わらない」に変更）。`TrackBroadcastSource.stopAllTracks` と polyfill の cleanup の例外集約は、`register.stop` など他の例外のために残す。
- **B（`dispatchEvent` で `on*` を呼ぶか）: 呼ぶ。** HTML ではハンドラ属性は listener の一種なので、`dispatchEvent(new Event("mute"))` で `onmute` が呼ばれる。werift 自身は `"mute"` / `"unmute"` / `"addtrack"` / `"removetrack"` を発火しないことを TSDoc に書く（「never called」という表現はやめた）。
- **E（`{ handleEvent }`）: 受け付ける。** `handleEvent` は呼び出し時に参照し、`this` はそのオブジェクト。
- **onended の呼び出し位置**: 以前は「`"ended"` の listener の後」だったが、DOM と同じく「最初に設定された位置」に変えた。`"ended"` の発火回数（1 track につき 1 回）は変えていない。
- **ended の track**: mediacapture-main の `getSettings()` は ended の track について inherent なプロパティ（`deviceId` / `groupId` / `facingMode`）だけを返すので、`getSettings()` は停止後 `deviceId` / `groupId` だけを返す。`applyConstraints()` の汎用アルゴリズム（ConstrainablePattern）には ended の分岐が見当たらなかったため、ended でも通常どおり判定する（判定には ended 時の settings を使う）。仕様の MediaStreamTrack 節の全文は照合できていない。
- **既知の非互換（意図的）**: werift は `stop()` で `"ended"` を発火する（DOM は発火しない）。`capture` は登録の区別にだけ使い、呼び出し順には影響しない。`event.target` は設定しない。EventEmitter の `on` / `emit` は従来の意味のまま（`emit` は例外を隔離しない）。

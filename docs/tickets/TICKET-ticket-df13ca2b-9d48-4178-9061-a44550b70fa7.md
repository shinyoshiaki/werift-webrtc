# [RTP] Audit malformed packet error isolation so one stream cannot terminate the process

## Problem（原文）
Downstream homebridge-ring-secure-video reported fixing cases where malformed RTP packets or stream-processing exceptions could terminate the Homebridge process. That downstream fix does **not** prove werift is the source of the exception.

## Investigation / acceptance criteria（原文）
- Fuzz or inject truncated/invalid RTP headers, header extensions, payloads, RTX and codec-specific data at the werift ingress path.
- Confirm parsing/dispatch failures cannot become uncaught exceptions or unhandled rejections that terminate the Node.js process.
- Distinguish packet-local drops from fatal transport failures; do not mask programmer errors indiscriminately.
- Ensure invalid packets cannot corrupt SSRC/RID routing state or affect unrelated tracks.
- Add targeted regression tests only for concrete failures found.

## Scope（原文）
Security/robustness hardening investigation, not a confirmed werift crash. Consider existing routing work in PR #838 and open PR #855 to avoid overlapping changes.

---

## 1. 目的と背景

- downstream（homebridge-ring-secure-video）が「不正な RTP やストリーム処理中の例外で Homebridge プロセスが落ちる」問題を自前で修正した。werift が原因かどうかは分かっていない。
- このチケットの目的は次の 2 つ。
  1. werift の受信経路（ICE → SRTP → RTP パース → `RtpRouter` → `RTCRtpReceiver` → `MediaStreamTrack.onReceiveRtp`）で、不正パケットが **uncaught exception / unhandled rejection になってプロセスを落とさない** ことを確かめる。
  2. 不正パケットが **SSRC / RID の経路状態を壊さず、無関係な track に影響しない** ことを確かめる。
- 調査の過程で、**後者の具体的な失敗を 1 件再現した**（§2.3）。修正と回帰テストはこの具体的な失敗に絞る。
- 関連 PR の状態（2026-11-19 時点）:
  - #838「receive RTX with RID-based simulcast and track NACK per SSRC」は **MERGED**。`rejectedSsrcs` / `forgottenSsrcs`、RID の媒体 SSRC 切り替え（`switchRidMedia`）、retired SSRC を導入した。
  - #855「Learn and deliver RTP for m-lines without a=ssrc (#356)」も **MERGED**（チケット原文では open）。`media/routing/*` への分割と、SSRC を学習する経路を導入した。
  - どちらも取り込み済みなので、重複を避ける相手はマージ後のコードになる。この 2 つが作った仕組み（`takeRejectedSsrcs` / `takeForgottenSsrcs` による経路の取り消し）は作り直さず、その上で直す。

## 2. 調査結果の要約

### 2.1 同期例外はプロセスを落とさない（確認済み）

受信経路の同期例外は、次の 3 段の catch のどこかで止まる。プロセスは落ちない。

| 層 | 場所 | 挙動 |
| --- | --- | --- |
| STUN/TURN ソケット | `packages/ice/src/stun/protocol.ts:60-90`, `packages/ice/src/turn/protocol.ts:152` | `datagramReceived` の例外を `log` して捨てる |
| ICE | `packages/ice/src/ice.ts:1019-1035` | `onData.execute` の例外を `log("dataReceived")` して捨てる |
| DTLS/SRTP | `packages/webrtc/src/transport/dtls.ts:618-683` | `SrtpAuthenticationError` / `SrtpReplayError` は破棄する。認証エラー以外は rethrow し、ICE 層の catch で止まる。`RtpPacket.deSerialize` / `RtcpPacketConverter.deSerialize` の失敗は "dropping malformed" として破棄する。`onRtp.execute` / `onRtcp.execute` の例外は `log("RTP error")` / `log("RTCP error")` して捨てる |

既存のハードニングも確認した。

- `packages/rtp/src/srtp/packet.ts`: 長さの足りない SRTP/SRTCP を `SrtpAuthenticationError` に正規化する。
- `RtpPacket.deSerialize`: 拡張ヘッダの切り詰め、padding の不正、短すぎるパケットで `Error` を投げる。
- `rtpHeaderExtensionsParser`（`packages/rtp/src/rtp/headerExtension.ts:64-109`）: 個々の拡張の解析失敗を飛ばす。
- `unwrapRtx`: 2 バイト未満の payload で投げる。`RTCRtpReceiver.handleRTP` は事前に `payload.length < 2` で return する。
- codec の depacketizer（`packages/rtp/src/codec/assertPayload.ts` を使う H264/VP8/VP9/AV1）と `extra/processor/depacketizer.ts` の try/catch。

### 2.2 ランダム入力による fuzz（一時スクリプトで実施、リポジトリには残していない）

- パーサ単体（各 20,000 件、長さ 0〜63 のランダムバイト列）:
  - `RtpPacket` / `Red` / `H264` / `H265` / `VP8` / `VP9` / `AV1` / `Opus` / `AAC` / `TelephoneEvent` が投げるのはすべて `Error`。`TypeError` / `RangeError` やハングはなかった。
  - `RtcpPacketConverter.deSerialize` だけが **1〜3 バイトの入力で `RangeError`**（`offset out of range`）を投げる。SRTCP 経由では最小長のチェックが先に効くので受信経路からは届かないが、型付きの "truncated" エラーになっていない。修正するかは任意（§3.4）。
  - ヘッダを正しく作った RTCP（PT 200〜207、length 整合）の 200,000 件は例外 0 件だった。
- `RtpRouter.routeRtp` 経由（`createSimulcastRtxReceiver` + RED codec PT 98。PT / RID / RRID / MID / SSRC / payload 長 0〜5 をランダムに組み合わせて 300 回 × 200 パケット）:
  - `routeRtp` から漏れた例外は **RED の 3 種類だけ**（`RED payload truncated` / `RED header truncated` / `RED block truncated`）。
  - `__proto__` / `constructor` / 空文字列の RID・MID では例外も経路の破損も起きなかった。`ridTable` は `ridRouteKey` の複合キーと `Object.keys` で引くので、prototype のキーに当たらない。

### 2.3 具体的な失敗: 不正な RED パケット 1 個で RID の媒体 SSRC が乗っ取られる（再現済み）

**再現手順**（`tests/media/rtpReceiverTestUtils.ts` の `createSimulcastRtxReceiver({ rtx: false })` に `video/red` PT 98 を追加して実施）:

1. RID `high` の正規パケット（SSRC 1000, seq 10, VP8）→ track に届く。`mediaSsrcByRid = { high: 1000 }`
2. RID `high` + 交渉済みの RED PT 98 + **payload `0x80` の 1 バイト**（F=1 なのに続きがない）の SSRC 5555 のパケット → `Red.deSerialize` が `RED header truncated` を投げる
3. 状態を確認すると `mediaSsrcByRid = { high: 5555 }`、`retiredSsrcsByRid = { high: [1000] }`、`trackBySSRC` のキーは `['5555']`、`forgottenSsrcs = [1000]` が未処理のまま残っている
4. RID `high` の正規パケット（SSRC 1000, seq 11）→ **届かない**（retired として破棄される）

**原因**:

- `RTCRtpReceiver.handleRtpByRid`（`packages/webrtc/src/media/rtpReceiver.ts:1105-1142`）は、payload の妥当性を確かめる前に状態を変える。
  - 未交渉 PT は `rejectedSsrcs` に入れて弾くが、交渉済み PT で payload が壊れているケースは通してしまう。
  - そのまま `switchRidMedia(rid, ssrc)`（旧 SSRC の retire、NACK の forget、RTX の unbind）と `trackBySSRC` の学習を済ませてから `handleRTP` を呼ぶ。
- `handleRTP`（同 `:1375-1465`）も、`remoteStreams` の統計、TWCC の観測、`payloadTypeBySsrc` の更新を済ませてから `Red.deSerialize`（`:1429-1438`）を呼ぶ。
- 例外が `RtpRouter.routeRtp`（`packages/webrtc/src/media/router.ts:639-786`）を突き抜けるので、後処理がすべて飛ぶ。
  - `takeForgottenSsrcs` / `takeRejectedSsrcs` による取り消し（`learnedNow` で今追加した経路だけを取り消す処理）、`sdesMid` / `latestRepairedRid` の更新が飛ぶ。
  - その結果、`learnSsrc` で追加した不正 SSRC の learned route がそのまま残る。
  - 未処理のキューは次のパケットの後処理で別パケットのものとして消費される。
- 最終的に dtls.ts の `log("RTP error")` に吸収されるので、プロセスは落ちない。しかし #838 が守っている不変条件 **「無効なパケットはストリームを切り替えず、経路を教えない」** が RED の不正 payload では破れている。
- SSRC 学習経路（`learnUnknownSsrc` → `handleRtpBySsrc`、#855）でも同じく、`learnedNow = true` のまま例外になり、学習した経路が取り消されない。
- 前提: SRTP 認証を通る必要があるので、攻撃者は交渉済みの相手（または壊れた送信側・中継）に限られる。ただし RED は Chrome が audio / video の両方で offer する codec なので、実運用で届きうる。

### 2.4 構造的なリスク（具体的な失敗は未再現。再現できた場合だけ修正対象にする）

| # | 場所 | 内容 |
| --- | --- | --- |
| R1 | `packages/webrtc/src/media/receiver/receiverTwcc.ts:147,174-179` | `runTWCC()` を fire-and-forget で呼んでいて `.catch` がない。`sendTWCC()` が投げると **unhandled rejection** になり、Node のデフォルト設定ではプロセスが終了する。`RecvDelta.parseDelta` は clamp するので、現時点で投げる入力は見つかっていない。`runRtcp`（`rtpReceiver.ts:851-899`）は外側の try/catch で保護されている |
| R2 | `packages/webrtc/src/media/rtpSender.ts:562-566` | 受信 track を中継する `RTCRtpSender` は `track.onReceiveRtp.subscribe(async (rtp) => { await this.sendRtp(rtp) })` で購読している。`Event.execute`（`packages/common/src/event.ts:42-66`）は同期 stack の戻り値 Promise を待たないので、`sendRtp` が reject すると unhandled rejection になる。受信した拡張ヘッダの再シリアライズ（非標準 profile、two-byte の長さ 0）を試したが、例外は出なかった。ただし非標準 profile では negotiated の拡張（mid / twcc）が黙って落ちる（`RtpHeader.serialize` の default 分岐は `extensions[0]` だけを書く）。別チケットにする候補 |

| R4 | `packages/webrtc/src/transport/dtls.ts:676-680` | `log("RTP error")` が、パケット固有の不正（RED の不正 payload）、werift の内部バグ、アプリの購読者の例外をすべて区別せずに飲み込む。§3.1 でパケット固有の不正を発生源で破棄するようにすれば、この catch に届くのは「本当に予期しない例外」だけになる |
| R5 | `packages/rtp/src/rtcp/rtcp.ts`（`RtcpPacketConverter.deSerialize`） | 1〜3 バイトの入力で `RangeError` を投げる。受信経路からは届かない（§2.2） |

## 3. 実装内容

### 3.1 必須: 不正 payload を状態変更の前にパケット単位で破棄する

- `RTCRtpReceiver` に、payload の妥当性を確かめる処理（例: `private parseRedPayload(packet, codec): Red | undefined` か、codec ごとに破棄理由を返す小さな関数）を追加する。
  - **`handleRtpByRid` の `switchRidMedia` / `trackBySSRC` の学習より前**に呼ぶ。
  - `handleRtpBySsrc` / `handleRtxByRid` から入る `handleRTP` でも、**統計・TWCC・`payloadTypeBySsrc` の更新より前**に呼ぶ。
- RED の場合:
  - `codecName(codec) === "red"`（現在は `codec.name.toLowerCase() === "red"`）で、padding-only ではない。
  - `Red.deSerialize` が投げるか `fields[0]` がない場合は、不正なパケットとして扱う。
  - 扱いは未交渉 PT と同じにする: `rejectedSsrcs.push(ssrc)` で router に「経路を教えない」ことを伝え、debug log `"malformed RED payload dropped"` を出して return する。
  - 既存の `blockPT` 未交渉チェック（`:1432-1437`）も同じ場所にまとめる。
- TWCC の扱いは決めて明記する。transport 全体の番号なので、`dropRetired` と同じく観測してよい。#838 の「RID without a track」も TWCC を記録している。RTX の payload 長 2 未満（padding-only RTX）の扱いと揃える。
- **やらないこと**: `handleRTP` 全体を try/catch で包んで握りつぶすこと（プログラマのエラーまで隠れる）。対象は「入力由来と分かっているパースの失敗」だけにする。

### 3.2 必須（多層防御）: router の後処理を例外でも必ず走らせる

- `RtpRouter.routeRtp` の `takeForgottenSsrcs` / `takeRejectedSsrcs` / `sdesMid` / `latestRepairedRid` の後処理（`router.ts:766-785`）を `try { ...handle... } finally { ...後処理... }` にする。
  - receiver 内やアプリの購読者で予期しない例外が起きても、キューが次のパケットに持ち越されないようにする。
  - 例外そのものは再送出する（dtls.ts の最終 catch に任せ、隠さない）。
- 例外で終わったパケットが `learnedNow` で追加した経路を取り消すかどうかは決める。
  - 推奨は「取り消さない」。理由: アプリ購読者の例外は経路の正しさと関係がない。パケット固有の不正は §3.1 で `rejectedSsrcs` に入るので、正規の取り消しで処理される。
- `routeRtcp`（`routing/rtcpRouting.ts`）の `takeForgottenSsrcs`（`router.ts:993,1004` 付近）にも同じ構造があれば、揃える。

### 3.3 回帰テスト（具体的な失敗に限定）

テストは Arrange / Act / Assert で書き、Act / Assert には日本語コメントを付ける。共有する Arrange は既存のユーティリティに追加する。

- `packages/webrtc/tests/media/rtpReceiverTestUtils.ts`: `createSimulcastRtxReceiver` に `red?: boolean` オプション（`video/red` PT を codecs と `resyncCodecs` に含める）を追加する。不正な RED パケットを作るヘルパ（payload `[]`, `[0x80]`, F=1 で block 長が超過、などのバリエーション）も置く。
- `packages/webrtc/tests/media/router.test.ts` の simulcast describe:
  1. 確立済みの RID に、別 SSRC の不正 RED パケットを流しても `mediaSsrcByRid` が変わらず、旧 SSRC が retire されず、続く正規パケットが届く（§2.3 の再現そのもの）。
  2. 不正 RED パケットの SSRC は learned route として残らない（`endpointBySsrc` が undefined のまま / 後続の同 SSRC 正規パケットで初めて学習される）。
  3. 他の RID（`low`）の配送と NACK 状態に影響しない。
- SSRC 学習経路（#855）: `packages/webrtc/tests/media/ssrcLess/` の既存 arrange（`arrange.ts`）を使う。a=ssrc のない m-line で、不正 RED パケットが SSRC を学習させないこと、後続の正規パケットが通常どおり学習・配送されることを確かめる。
- audio RED（`audioRedHandler`）: 不正な RED で `RedHandler` の状態が進まず、後続の正規 RED から復元される block が正しいことを確かめる。既存の RED 受信テストがあれば、そこに追加する。
- §3.2 の `finally` 化: アプリの購読者が `onReceiveRtp` で投げても、同じパケットで発生した `rejectedSsrcs` / `forgottenSsrcs` が処理されることを確かめる。例外は routeRtp から再送出されることも確かめる（`expect(() => router.routeRtp(p)).toThrow()` と状態の両方を検証する）。
- 任意（プロパティテスト）: `tests/pbt/simulcastRtx/generator.ts` か `tests/pbt/model/wireMutations.ts` に「交渉済み PT の payload を切り詰める」変異を追加し、既存の oracle（誤った SSRC に配送しない、retire されない）で検査する。追加した場合は `pbt:deep` に影響しないか確認する。

### 3.4 任意（具体的な失敗が再現できた場合のみ）

- R1: `runTWCC()` の呼び出しに `.catch((e) => log(...))` を付ける（`runRtcp` と揃える）。再現テストには `tests/fixture.ts:796` の `captureUnhandledErrors()` を使う。
- R2: 中継の購読を `void this.sendRtp(rtp).catch(log)` にする。非標準 profile で拡張が黙って落ちる件は別チケットに切り出す。
- R5: `RtcpPacketConverter.deSerialize` の先頭で 4 バイト未満を `Error("RTCP packet truncated")` にする（`packages/rtp`）。

## 4. 制約・注意点

- **プログラマのエラーを隠さない**: 新しい catch は「入力由来と分かっているパース失敗」に限り、その場で破棄する。広い try/catch による握りつぶしは追加しない（root AGENTS.md の Do 3）。dtls.ts の最終 catch（`log("RTP error")`）は「プロセスを守る最後の砦」として残す。範囲を広げることも狭めることもしない。
- **#838 / #855 の不変条件を保つ**: 経路の取り消しは今あるキュー（`rejectedSsrcs` / `forgottenSsrcs`）の仕組みに乗せる。新しく経路を取り消す仕組みは作らない。retired SSRC、上限（`MAX_RETIRED_SSRCS_PER_RID` / `MAX_RTX_SSRCS_PER_RID`）、rollback の挙動を変えない。
- **TWCC / 統計の扱い**: 不正パケットを TWCC で観測するか、`StreamStatistics` に数えるかは仕様として決めて、TSDoc に書く。推奨: TWCC は観測する（transport 層の番号）、受信統計は数えない（`dropRetired` と同じ）。
- **公開 API は変えない**。挙動の変化（不正 RED を route learning に使わない）は `changelog.md` の Unreleased に書く。`RtpRouter` / `RTCRtpReceiver` の TSDoc を変えた場合は `npm run doc` で `doc/` を再生成する。
- **テストのハング**: `RTCRtpReceiver` は `runRtcp` / NACK / TWCC のタイマーを起動する。テストでは既存ユーティリティの後始末（`receiver.stop()` など）を使い、一時スクリプトでは `process.exit` が要る（調査中に確認した）。
- **ホスト依存のテスト失敗**: このホストでは HEAD でも失敗する既知のテストがある（tcp active-only、setConfiguration、modern_sdp）。比較は `git worktree add --detach` の一時 worktree の develop と行う。
- `packages/rtp` を変更する場合（R5）は、ブラウザ向け entry の制約（`packages/rtp/AGENTS.md`）を守り、`npm test`（`type:public` を含む）を実行する。
- 作業中のワークツリーで checkout / reset / stash をしない（外部ツールが自動 commit する）。

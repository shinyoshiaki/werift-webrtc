# ICE: 選択中のペアが切れたら ICE restart なしで次のペアへ移る（libwebrtc 互換のフェイルオーバー）

親チケット: 05c13603-5044-4cc6-8d8f-7cc322c68db1（semi-aggressive nomination / renomination）の §10 で「後続タスク」とした項目 3。

## 1. 目的と背景

- 今の werift は、選択中のペア（`Connection.nominated`）が使えなくなると回復できない。consent freshness（RFC 7675）が 30 s（`CONSENT_TIMEOUT`）で切れると `failed` になる。選択中の TCP 接続が閉じたときも `failed` になる。どちらもアプリ側の ICE restart が必要。
- libwebrtc（Chrome）は、選択後も他のペアに ping を続けて疎通状態を持つ。選択中のペアが疎通しなくなると、ICE restart なしで別のペアへ切り替える。対象の場面は、TURN サーバーの停止、NAT の再割り当て、回線の切り替え（Wi-Fi ↔ 携帯回線）、片方向の経路断。
- 親チケットで入れた semi-aggressive / renomination では、上位ペアへの切り替えはできる。一方、下位ペアへの退避はできない。親チケットの §10 T1 で controlled 側は「相手がデータを送るペアに従う」ようになったので、相手（Chrome）が退避すれば werift も追従する。werift が controlling のときは退避できない。

## 2. 現状調査（親チケット HEAD 時点、`packages/ice/src/ice.ts`）

| 箇所 | 現状 |
| --- | --- |
| `checkComplete()` の 8.1.2 の処理 | 最初の選択で、選択より下位の Waiting / Frozen ペアを FAILED にする（上位は semi-aggressive / renomination で残す） |
| `admitsPair()` / `pairLocalProtocol()` / `tryPair()` | 選択後は、選択より上位のペアしか作らない |
| `checkOutrankingPairs()` / `scheduleOutrankingRetries()`（§10 T2） | 選択より上位のペアだけを check し、失敗したら 1, 2, 4, 8, 16 s で再 check する。下位のペアは監視しない |
| `queryConsent()` | 選択中のペアだけに consent check を送る（`CONSENT_INTERVAL` 5 s、応答待ち `CONSENT_RESPONSE_TIMEOUT`）。30 s 応答がないと `failed` |
| `handleConnectionClosed()` | 選択中の TCP 接続が閉じると `failed` |
| `IceState` | 型には `disconnected` があり、consent の応答で `disconnected` → `connected` に戻す処理もある（`queryConsent` 内）。しかし `disconnected` に入る経路がない（consent の失敗はいきなり `failed`） |
| ペアの単位 | `CandidatePair.protocol` が、ローカルの UDP socket（host と、同じ socket を使う srflx）か TURN allocation（UDP / TCP / TLS）を指す。退避先を保持する単位にそのまま使える |
| controlled 側（§10 T1） | 同じ値の指名どうしでは、相手がデータを送るペアに移る。相手が下位ペアへ退避すれば追従できる |

## 3. libwebrtc の挙動（main、2026-11-13 取得のソースで確認）

- **semi-aggressive の指名条件**: 選択中のペアが疎通しなくなると（`!selected_connection_->writable()`）、他のペアの ping にも USE-CANDIDATE を付ける（`basic_ice_controller.cc` `GetUseCandidateAttr` の a.3）。
- **切り替えの判定**: `ShouldSwitchConnection` → `CompareConnections`。比較の順は次のとおり。
  1. 書き込み可能か、書き込み状態
  2. 受信しているか（receiving。受信状態が変わってから `receiving_switching_delay` の間は保留し、後で再判定）
  3. controlled なら指名の値と最終受信時刻
  4. ネットワークコスト・優先度
  5. RTT（`kMinImprovement` = 10 ms 以上良くなる場合だけ）
- **刈り込み（prune）**: 同じネットワークで、書き込み可能で弱くない（weak でない）より良い接続がある場合、それ以下の接続は prune する（`PruneConnections`）。prune した接続は書き込み状態が timeout になり、データを受けても書き込み可能に戻らない（`connection.cc` の `!pruned_` 条件）。つまり libwebrtc の退避先は、主に「別のネットワークの接続」と「選択より上位で prune されていない接続」になる。
- **死んだ接続**: 30 s 受信がない接続は捨てる（`DEAD_CONNECTION_RECEIVE_TIMEOUT`）。
- **ping 間隔**: 弱い状態や安定前は短い間隔、安定した書き込み可能な接続は `stable_writable_connection_ping_interval` の長い間隔（`basic_ice_controller.cc:130-140, 280-290`）。
- **本チケットで参照する定数**（`p2p/base/connection.h`、`ice_config.h` など）

| 定数 | 値 | 意味 |
| --- | --- | --- |
| `STRONG_PING_INTERVAL` | 480 ms | 書き込み可能な接続がないときの ping 間隔 |
| `WEAK_OR_STABILIZING_WRITABLE_CONNECTION_PING_INTERVAL` | 900 ms | 弱い、または安定前の接続の ping 間隔 |
| `STABLE_WRITABLE_CONNECTION_PING_INTERVAL` | 2500 ms | 安定した書き込み可能な接続の ping 間隔 |
| `CONNECTION_WRITE_CONNECT_FAILURES` / `CONNECTION_WRITE_CONNECT_TIMEOUT` | 5 回 / 5000 ms | 応答のない ping が 5 回以上、かつ最後の応答から 5 s 以上で書き込み不可（`STATE_WRITE_UNRELIABLE`） |
| `CONNECTION_WRITE_TIMEOUT` | 15 s | 応答がないまま 15 s で `STATE_WRITE_TIMEOUT` |
| `WEAK_CONNECTION_RECEIVE_TIMEOUT` | 2500 ms | 2.5 s 何も受けなければ receiving でなくなる |
| `DEAD_CONNECTION_RECEIVE_TIMEOUT` | 30 s | 30 s 何も受けなければ接続を捨てる |
| `MIN_PINGS_AT_WEAK_PING_INTERVAL` | 3 回 | 短い間隔で最低 3 回 ping してから安定扱いにする |
| `receiving_switching_delay` | 1000 ms | 受信状態の変化による切り替えを保留する時間 |


## 4. 決定事項

### D1. 対象範囲

- 対象は、werift が full ICE で、semi-aggressive nomination か renomination を使う場合（`replacesSelection()` が真になる組み合わせ）。controlled 側は、相手の再指名に追従する既存の経路（§10 T1）を使う。
- 対象外（従来どおり。退避の処理は一切動かさない）
  - regular nomination（`nomination: "regular"`）: RFC 8445 §8.1.1 は ICE restart なしの再指名を認めていない
  - ICE-TCP: TCP ペアは退避先にも退避元にもしない。選択中の TCP 接続が閉じたときは従来どおり `failed`
  - ICE-lite（自分が lite、相手が lite のどちらも）
- TURN over TCP / TLS の relay 候補は ICE-TCP ではない（候補は UDP）。対象に含める。

### D2. 退避先を保持する単位: ローカルの `Protocol` ごとに 1 ペア

- 単位は `CandidatePair.protocol`。ローカルの UDP socket（host と、その socket を使う srflx）か、TURN allocation 1 つに当たる。libwebrtc の「network ごとの最良接続」に相当し、経路の違いを表す最小の単位になる。
  - 同じ socket の host と srflx を分けても、送信元は同じ socket なので経路の冗長にならない。このため候補の種類ごとには分けない。
  - すべての valid ペアを監視すると、ペアの数（ローカル × リモート）に比例して ping が増える。またペアの状態管理も重い。このため採用しない。
- 不変条件（§13 で整理）: 選択中のペアと経路が異なる（別ソケット、または同じソケットの別リモートアドレスへの）`replacesWith()` を満たすペアは、順位とロールに関係なく監視の候補になる。各 `Protocol` で最上位の非 FAILED ペアを 1 つ監視する。失敗したら次へ進み、全滅したら 16 s ごとに再試行し続ける。
  - 例外は 1 つ: 自分で選択を上へ移す agent（controlling で semi-aggressive / renomination）は、選択中のソケットで選択より上位のペアを `SelectionReplacement` に任せる。そのペアが valid になった時点で `evaluate()` が上へ指名する。再試行は 1, 2, 4, 8, 16 s の後も 16 s ごとに続く。選択が書き込み不可で退避先もないときは、FAILED の上位ペアをすぐ check する。退避元として demote した経路は、上位でも監視する。
  - 変更の経緯: 第 7 回で、選択中のソケットの別リモートアドレスへの下位ペアを追加した（当初は退避先を持たないとしていた）。第 12 回（§13）で、controlled 側では上位も含めるようにした。
- 退避先候補がまだ check されていなければ（Waiting / Frozen）、選択後に check する。8.1.2 の処理では、退避先候補を FAILED にしない。失敗したら、同じ `Protocol` の次のペアを候補にする。1 つの `Protocol` で試すペアの数には上限を設ける（3 ペア。超えたらその `Protocol` は 1, 2, 4, 8, 16 s、その後は 16 s ごとに、選択が続く間ずっと最上位ペアから再試行する）。
- リモート側の経路だけが切れる場合（ローカルのソケットは 1 つで、相手の host への経路だけが切れ、相手の relay にはまだ届く）にも退避できるよう、選択中のソケットにも別のリモートアドレスへの退避先を 1 つ持つ（第 7 回で変更。当初は「リモート側の経路の違いは含めない」としていた）。同じソケット内で退避した場合は、元のリモートアドレスへの経路だけを demote する。その経路が 3 回連続で応答するまで戻らない。別のソケットへ退避した場合は、元のソケット全体を demote する。

### D3. 書き込み不可の判定と ping 間隔（libwebrtc の定数に合わせる）

ペアごとに「最後に応答を受けた時刻」「最後に何か受けた時刻」「連続で応答がない check の数」を持つ。応答だけが「書き込み可能」の根拠になる（RFC 7675 の consent と同じく、データの受信では書き込み可能にしない）。

| 状態 | 条件 | 選択中のペアの ping 間隔 | 退避先の ping 間隔 |
| --- | --- | --- | --- |
| 安定 | 応答が続いている | consent の `CONSENT_INTERVAL` 5 s（0.8〜1.2 倍、従来どおり） | 2500 ms（`STABLE_WRITABLE_CONNECTION_PING_INTERVAL`）。0.8〜1.2 倍の乱数をかける |
| 安定前 | 退避先になってから応答が 3 回（`MIN_PINGS_AT_WEAK_PING_INTERVAL`）未満 | — | 900 ms |
| 弱い（weak） | consent の応答を 1 回取りこぼした、または 2500 ms 何も受けていない（`WEAK_CONNECTION_RECEIVE_TIMEOUT`） | 900 ms（`WEAK_OR_STABILIZING_WRITABLE_CONNECTION_PING_INTERVAL`） | 900 ms |
| 書き込み不可 | 応答のない check が連続 5 回以上、かつ最後の応答から 5000 ms 以上（`CONNECTION_WRITE_CONNECT_FAILURES` / `_TIMEOUT`） | 900 ms のまま続ける（回復の検出と、30 s の consent 失効の判定のため） | 900 ms のまま続ける |
| 死亡 | 30 s 何も受けていない（`DEAD_CONNECTION_RECEIVE_TIMEOUT`、`CONSENT_TIMEOUT` と同じ値） | consent 失効。退避先がなければ `failed` | FAILED にして D2 の次のペアへ |

- 選択中のペアが切れてから退避するまでの時間は、最短で約 5 s、最長で約 10 s になる（consent の間隔 5 s のどこで切れたか + 判定の 5 s）。libwebrtc と同程度にする。
- consent の判定時間を短くするために consent の間隔自体は短くしない。弱い状態のときだけ 900 ms にする（RFC 7675 は consent の上限 30 s を定めるが、check を間隔より頻繁に送ることは禁じていない。libwebrtc も同じ動作）。
- `CONSENT_FAILURES`（deprecated）は使わない。新しい定数は `iceBase.ts` に置き、libwebrtc の名前と値の出典をコメントに書く。テストは fake timer で検証できるようにする。
- 送信は既存の check のペーシング（Ta）に従う。退避先の check には USE-CANDIDATE / NOMINATION を付けない（指名は F3 の切り替え時だけ）。

### D4. 切り替えの規則（controlling）

- 選択中のペアが書き込み不可になったら、書き込み可能な退避先のうち最上位のペアを指名する。semi-aggressive は USE-CANDIDATE 付きの check、renomination は NOMINATION の値を 1 増やした check。指名の check が成功したら選択を移す（既存の `nominateSelection` / `checkComplete` の経路）。
- 退避の候補は「書き込み可能」で「弱くない」ペアに限る。該当がなければ、書き込み可能なペアを使う。
- 古い選択中のペアは、その `Protocol` の退避先として監視を続ける。回復して上位であれば、既存の上位ペアへの切り替え（semi-aggressive / renomination）で戻る。行ったり来たり（flapping）を防ぐため、戻すのは、退避した後で応答が 3 回連続で返ったときに限る。
- RTT やネットワークコストによる切り替え（libwebrtc の `CompareConnections` の 4・5）は入れない。切り替えの理由は「書き込み不可」だけにする。

## 6. 設計方針

- 選択後の check を 2 種類に分ける。上位ペア（既存の `checkOutrankingPairs`）と退避先（新規）。
- 退避先の監視は、1 つのスケジューラ（ペアごとに次回時刻を持ち、最も近い時刻で 1 本の timer を張る）にまとめる。ペアごとに `setInterval` は張らない（leak を防ぐ）。中断は既存の `AbortController`（`remoteChecks` など）にぶら下げる。
- 選択中のペアの判定は、既存の `queryConsent` の応答・失敗のコールバックを使う。弱い状態の間隔の切り替えも `queryConsent` のループの中で行う。
- ペアごとの監視状態（最終応答時刻・最終受信時刻・連続失敗数）は、`CandidatePair` か、`Connection` 内の `WeakMap<CandidatePair, …>` に持つ。最終受信時刻は、受信の処理（`dataReceived` 相当）で更新する。
- 状態遷移（F5）は、`setState` の呼び出し元を「選択中のペアの書き込み状態」「退避先の有無」「consent の失効」の 3 つから決める関数にまとめる。
- `packages/webrtc` 側は既に `disconnected` を集約している（`secureTransportManager.ts` の `anyMatch("disconnected")`）。`iceConnectionState` / `connectionState` が `connected` → `disconnected` → `connected` と動くことを確認し、W3C 仕様と WPT に合うかを確かめる。

## 8. テスト

テストは Arrange / Act / Assert で書き、Act / Assert に日本語のコメントを付ける。共通の Arrange は ice のテスト用ユーティリティにまとめる。

1. 単体（fake timer）: 選択中のペアの応答が止まる → 900 ms 間隔になる → 5 回・5 s で書き込み不可 → 書き込み可能な退避先へ指名して移る（semi-aggressive / renomination の両方）。退避までの時間が D3 の範囲に収まる
2. 単体: 退避先は `Protocol` ごとに 1 つだけ監視される。退避先の check が失敗すると同じ `Protocol` の次のペアに移る。間隔が安定前 900 ms → 安定 2500 ms になる
3. 単体: 退避先もない場合は `disconnected` → 30 s で `failed`。途中で回復すれば `connected`
4. 単体: 退避した後、元のペアが 3 回連続で応答したら上位の元のペアへ戻る。応答が 1〜2 回では戻らない
5. 単体: 対象外（regular nomination、ICE-TCP の選択、ICE-lite）では退避先の check を送らず、従来どおり 30 s で `failed`
6. 単体: restart / close / ロール変更で監視が止まり、timer と transaction が残らない
7. 実ソケット（werift 同士）: host ↔ host で接続後、host の経路を遮断 → relay ペアへ両端が移り、データが届く（controlled 側は §10 T1 で追従）
8. E2E（Chrome）: werift が controlling。werift の host socket を遮断し、werift が relay に退避し、Chrome が追従することを確認する。Chrome（controlled）は同じネットワークの下位接続を prune しているので、追従しない可能性がある（未確定事項 1）

### レビュー指摘への対応（第 3 回）

- P2（高 RTT）: failover 対象の consent check は前の要求の結果を待たずに `nextPingAt` の間隔で送る。要求は取り消さず、それぞれ RTT に基づく応答待ちで結果を出す。RTT 1.2 s で経路が切れた場合、遮断から退避の指名までは 8.7 s（D3 の上限 10 s 以内。修正前の方式では約 15.5 s）。退避先の check も同じく結果を待たずに送る。一度も応答していない退避先の応答待ちは 3 s（`BACKUP_UNKNOWN_RTT_RESPONSE_TIMEOUT`、libwebrtc の `DEFAULT_RTT`）。これは同じテストで見つかった問題への対応で、従来の 1 s では RTT が 1 s を超える退避先がいつまでも有効にならなかった。
- P2（指名中の回復）: 退避の指名先を `failoverNomination` として記録する。指名の途中で元のペアが回復しても、指名は取り消さない（相手がすでに切り替えている可能性があるため）。指名が成立すれば切り替え、元のソケットを demote する。3 回連続で応答するまで元のペアには戻らない。

### レビュー指摘への対応（第 4 回）

### レビュー指摘への対応（第 5 回）

- P1（consent 失効後の状態）: 方針を次のように定めた。選択中のペアの consent が失効した時点で、そのペアでは送信しない（RFC 7675）。失効したペアは新しく選択し直されない限り、再び check も使用もしない。
  - 書き込み可能な退避先がなければ、ただちに `failed`。
  - 書き込み可能な退避先があれば `disconnected` にし、`FAILOVER_CONSENT_EXPIRED_GRACE`（10 s）の間、選択が退避先に移るのを待つ。controlling なら自分の退避の指名、controlled なら相手の指名を待つ。移れば `connected` に戻る。移らなければ `failed` にして、監視とタイマーを止める（ICE restart で復旧できる）。
  - 10 s にした理由: 相手が退避する場合は経路断から 5〜10 s で切り替わり、30 s の consent 失効よりずっと前に済む。猶予は進行中の指名の往復分にあたる。
- テスト（controlled、相手の指名がない場合を含む）: 失効すると `disconnected` になり、送信しないこと。失効後に元の経路が戻っても、猶予期間の後に `failed` になり、以後 check を送らないこと。猶予期間内に相手が退避先を指名すれば `connected` に戻り、データが退避先で送られること。どちらのテストも変更前の `ice.ts` では失敗することを確認した。
- 追加の修正（memleak の負荷調査で判明）: 高負荷時に、応答が RTT に基づく期限より遅れて届くと、その request が未応答と数えられていた（イベントループが詰まると、期限のタイマーが先に処理される）。failover 対象の consent request は、期限の時点で未応答と数えるが、transaction は `CONNECTION_WRITE_CONNECT_TIMEOUT`（5 s）まで開いておき、遅れて届いた応答も応答として数える（libwebrtc と同じ）。テストを 1 件追加し、修正を戻すと失敗することを確認した。
- memleak の datachannel シナリオ: 今回の既定設定の実行で 1 回、受信が timeout した。調査の結果、送信が集中して受信側の UDP 受信バッファがあふれ、consent の要求が 30 s 届かずに失効していた（`RcvbufErrors` が増え続ける）。同じ負荷を変更前の `e83850f0e` で実行しても cycle 1 で両端とも consent が失効し、`failed` になって受信が timeout した。この失敗は本チケットの変更によるものではない（consent の 30 s 失効は RFC 7675 の既存の動作）。結果は下の検証欄に書く。
- 検証（第 5 回）: `npm run type`、ice の全テスト（550 件）、`npm run test:small`（webrtc 1729 件を含む）、`npm run e2e`（25 ファイル / 73 件）、`npm run wpt`（PASS 444、退行 0）は通過。
  - `npm run memleak`（既定設定）を 2 回実行し、2 回とも datachannel が失敗した。leak の判定はいずれも `leaked=false`。
  - 1 回目は 1800 s の timeout。その後も datachannel の処理が残った状態で合成 leak の自己検証が leak を検出できなかった。
  - 2 回目は cycle 29 で受信が timeout した。connection・media・renegotiation は PASS、合成 leak は想定どおり検出された。
  - 実行中、ホストの load average は 6〜22 だった（別のワークロードによるもの）。前回までの実行より media / renegotiation が 3〜4 倍遅かった。上記のとおり変更前の HEAD でも同じ失敗が起きる。この環境では memleak の datachannel を完走させられていない（未確認事項）。

## 13. 追加要件（第 12 回）: 不変条件への整理と failover の行列テスト

### 13.1 背景（レビューを通過できなかった理由）

- 落とす側のレビュアーは、毎回共通ハーネス `createFailoverHarness` で一時テストを書き、まだ検証していない組み合わせを再現して非承認にしていた（第 5・7・9・11 回）。指摘はすべて同じ族だった。「疎通し得る eligible なペアがあるのに、監視されない／使われない／状態が誤る」。

### 13.2 探索で見つかった未修正の穴（修正前の行列で再現）

### 13.3 修正

1. `FailoverMonitor.backupEligible`（`failover.ts`）: 選択中のソケットの別リモートアドレスへのペアは、順位に関係なく候補にする。上位を除外するのは、自分で選択を上へ移す agent（`FailoverHost.movesSelectionUp()` = controlling かつ semi-aggressive / renomination）のときだけ（A）。
2. `SelectionReplacement.scheduleRetries`（`selectionReplacement.ts`）: failover が有効な間（`retriesForever`）は、上位ペアの再試行を 5 回目の後も 16 s ごとに続ける。ICE-TCP の選択などの対象外では、従来どおり 5 回で止める（F7）。さらに `evaluateFailover`（`ice.ts`）は、選択が書き込み不可で書き込み可能な退避先がないとき、FAILED の上位ペアをすぐ check する（`checkFailedOutranking`。libwebrtc が書き込み可能な接続がないときに強い間隔で ping するのに相当）（B）。
3. `SelectionReplacement.replaces` の controlled 分岐: nomination の値が等しく、選択中のペアが down（host フック `selectionDown`）で、指名されたペアが valid なら置き換える。controlling の `failoverReplaces` の鏡像（C）。

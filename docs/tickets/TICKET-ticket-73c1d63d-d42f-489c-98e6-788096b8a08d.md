## 1. 目的と背景

- 親チケット 21a27c92（Firefox `a=bundle-only` 対応）のレビューで、`npm run pbt:deep` が model property の **seed 275（10 steps）** で「the transport did not settle」により exit 1 になることがあった。
- この失敗は親チケットの変更とは無関係で、develop（比較元）でも同じ形で再現する（親チケットのレビューで確認済み）。`packages/webrtc/tests/pbt/leak/negotiationLeakProperty.test.ts` の冒頭コメント（"Known flakes of the model property ..."）に、2026-10-25（`ba91c88be`）から既知の flake として記載されている。単独で再実行しても失敗することがある。
- 失敗する流れは、rollback 後の `addTrack` → trickle → glare → answer で、transport が settle しない、というもの。
- 手元（16 CPU）では単独 3 回・16 並列 16 本ともに成功し再現しない。レビュー環境（sysbox コンテナ）では失敗するため、負荷・タイミング依存が疑われる。
- これが残っている限り `pbt:deep` は確率的に exit 1 になり、negotiation 変更のレビュー（`packages/webrtc/AGENTS.md` Do 7）が通らない。

## 2. 作業内容

1. コンテナ環境（sysbox）で `WERIFT_NEGOTIATION_MODEL_SEED=275 WERIFT_NEGOTIATION_MODEL_STEPS=10` の単独再生と、`pbt:deep -- --suite model` の並列実行で再現させる。CPU 負荷（`--jobs` の増減、`stress` 相当の並列負荷）やタイマー精度を変え、再現率を記録する。
2. shrink した scene とログから、transport が settle しない原因（ICE/DTLS の状態、glare 時の pending transport、rollback で戻した transport の扱い、trickle candidate の適用先 generation など）を特定する。
3. 原因が実装の不具合なら `packages/webrtc/src` を直し、seed 275 の scene を negotiation case（`tests/negotiation/cases`）の回帰テストとして固定する。テストの判定や時間予算の緩和で隠さない。
4. ハーネス側（時間予算・待ち方）の問題なら、その根拠を示したうえでハーネスを直す。
5. 解消後、`negotiationLeakProperty.test.ts` の既知 flake の記述から seed 275 を外す（leak seed 57 の記述も同じ原因なら合わせて扱う）。

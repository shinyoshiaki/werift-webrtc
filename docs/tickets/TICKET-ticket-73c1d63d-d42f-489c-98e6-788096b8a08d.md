- 親チケット 21a27c92（Firefox `a=bundle-only` 対応）のレビューで、`npm run pbt:deep` が model property の **seed 275（10 steps）** で「the transport did not settle」により exit 1 になることがあった。

- 失敗する流れは、rollback 後の `addTrack` → trickle → glare → answer で、transport が settle しない、というもの。

- これが残っている限り `pbt:deep` は確率的に exit 1 になり、negotiation 変更のレビュー（`packages/webrtc/AGENTS.md` Do 7）が通らない。

## 5. 作業記録（2026-11-26、HEAD `892bc48a8` + 未コミット差分）

### 再現手順
- 現在の generator では seed 275 の操作列が変わっているため、過去の記録（チケット e7d0e0c9 の 3.12）にある縮小後の 8 操作を固定シーンにして再生した: `unnegotiated`、`bundlePolicy: "max-compat"`、a の `codecRenumbered` の wireOffer → b answer → b の wireOffer（`audioInactive`）→ a rollback → a addTrack(video) → a trickle → b glare → b answer（`tests/pbt/model/scenes.ts` の "a re-offer and a glare while the first checks run keep the ICE roles, and the transport settles"）。
- 旧 revision `1e89ac22b`（一時 worktree）で 16 並列で再生すると 48 回中 9 回失敗した（「channel dc0 did not open on both peers」）。seed 275 の全 10 操作は 24 回中 4 回失敗した。HEAD では 48/48 成功し、hermetic STUN の setup を外しても再現しなかった。
- `packages/ice/src` だけを入れ替えた二分探索で、HEAD で再現しなくなったのは ICE の regular nomination の取り込み（`de54f7ce2`）からだと分かった。この変更で role conflict の修復（`switchRole`）が nomination を評価し直すようになり、失敗の窓が狭まっただけで、原因は残っていた。

### 原因
- `SecureTransportManager.setLocalRole` は `setLocalDescription` のたびに ICE ロールを付け直す（offer なら controlling、answer なら controlled）。ICE の `Connection.iceControlling` setter は、pair が選択済みのときだけ付け直しを無視していた。
- 失敗時の状態: 両 peer とも host pair は succeeded だが nominate されていない。初回の answerer の b が controlling、offerer の a が controlled に逆転し、a の DTLS は `new`、ICE は `checking` のまま。HEAD でも計測すると、checks 開始後・nominate 前に setter がロールを付け替え、続いて role conflict の修復で両者のロールが入れ替わっていた。
- 初回の checks が進んでいる間に、ICE restart のない後続の offer/answer（answerer からの再 offer、glare）が来ると、ロールが決め直されて両者が controlling、または両者が controlled になる。checks がすでに終わっていると、どちらも nominate せず、transport は settle しない。RFC 8445 §6.1.1 では、一度決まったロールはセッションの間維持する。
- 決定的な再現: `packages/ice/tests/ice/ice.test.ts`「an offer/answer without an ICE restart keeps the roles of the checks in progress (RFC 8445 §6.1.1)」（regular nomination の待ち時間中にロールを付け替える）。修正前は、ロールの assert を外しても接続がタイムアウトする。

### 修正
- `packages/ice/src/ice.ts` の `iceControlling` setter: その generation の checks が始まった後（`checksBegun`）も、offer/answer によるロールの付け替えを無視する。変えられるのは role conflict の修復だけ。`restart()` / `restartRemote()` は `checksBegun` を戻すので、ICE restart では従来どおり offer/answer がロールを決める。
- 回帰テスト: 上記の ICE テスト、`tests/negotiation/cases/negotiationTransactionCoverageIce.test.ts`「[2.8] a re-offer without an ICE restart keeps the ICE roles of checks still in progress (RFC 8445 §6.1.1)」（修正を外すと失敗することを確認済み）、model の固定シーン（上記）。
- 旧 revision `1e89ac22b` にこのガードだけを入れると、縮小シーン 48/48、seed 275 の全 10 操作 24/24 が成功する（ガードなしは 9/48、4/24 が失敗）。
- leak seed 57（SCTP の handshake が DTLS connected のまま進まない）は症状が違い、ICE ロールとは別の原因と判断して、既知 flake の記述に残した。HEAD での単独再生は 3/3 成功した。

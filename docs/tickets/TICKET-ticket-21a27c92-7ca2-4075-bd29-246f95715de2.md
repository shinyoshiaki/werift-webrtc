## 1. 目的と背景

- 親チケット #269（bundleCandidates）の相互接続確認（親チケット §9.6）で見つかった既存の不具合。**develop `1f007fe89` でも再現する**。`bundleCandidates`（`legacy` / `compatible`）とは関係がない。
- Firefox 157 は、BUNDLE の非tag m-line を `port 0` + `a=bundle-only`（RFC 8843 §6）として offer する。対象は次のとおり。
  - 再 offer で追加した m-line
  - ICE restart の offer に含まれる、既存の非tag m-line（受け入れ済みのものも含む）
  - `max-bundle` の初回 offer の非tag m-line
- werift はこれを「拒否された m-line」と解釈し、answer で `port 0`・`a=inactive` を返し、BUNDLE group からも外す。返す m-line には `c=` 行がない。Firefox は `SIPCC Failed to parse SDP: ... c= connection line not specified for every media level` で answer を拒否し、交渉が失敗する。
- `packages/webrtc/src` には `bundle-only` を扱う処理がない（`grep -rn "bundle-only" packages/webrtc/src` が 0 件）。

## 2. 再現（親チケットの作業で確認済み）

Firefox 側の ICE restart offer（抜粋）:

```
a=group:BUNDLE 0 1 2 3
m=video 9 ... / a=mid:0
m=application 9 ... / a=mid:1
m=video 0 UDP/TLS/RTP/SAVPF ...
c=IN IP4 0.0.0.0
a=bundle-only
a=sendrecv
a=mid:2
m=video 0 ... / a=bundle-only / a=mid:3
```

werift の answer（抜粋）: `a=group:BUNDLE 0 1`。mid 2 / 3 は `m=video 0 ...` + `a=inactive` で、`c=` 行がない。

- 直結スクリプト（Node の werift ↔ Playwright の Firefox）では、Firefox 起点の ICE restart と、Firefox が video を足した再 offer の両方が、すべてのポリシー・すべてのモードで失敗した。
- `e2e/tests/bundle/max-bundle.test.ts` を Firefox で実行（mDNS 秘匿を無効化）した場合も、同じ `c=` エラーが出る。

## 3. 調査・実装の方向

- RFC 8843 §6 / §7.3.3: `a=bundle-only` 付きの `port 0` は拒否ではない。answerer は BUNDLE を受け入れるなら、その m-line を group に含めて受け入れる。answer の非tag m-line は port 0 とし、`a=bundle-only` は付けない（§7.3.1 も確認する）。
- JSEP（RFC 8829）§5.8 / §5.10 の、bundle-only の m= section の扱いを確認する。
- 拒否する m-line（本当に port 0 で拒否するもの）も、session level に `c=` がないなら media level に `c=IN IP4 0.0.0.0` を出す（RFC 4566 / RFC 8866 §5.7）。Chrome の拒否 m-line の出力形とも比べる。
- 受信側（`remoteMediaApplication.ts`、`bundleTopology.ts` など）で `port 0 && bundle-only` を受け入れ扱いにする。`isBundledNonTag()` などの判定も見直す。
- werift 自身が `max-bundle` で offer するときに `bundle-only` を出すかどうかは、Chrome 互換を優先して判断する（Chrome は出さない）。範囲を広げる場合は分ける。
- negotiation の変更として扱う（`packages/webrtc/AGENTS.md`）。`tools/negotiation-diff` と `npm run pbt:deep` で確認する。

### 5.1 原因（コードで確認したこと）

| 箇所 | 問題 |

### 5.2 仕様の整理（実装前に条文を再確認する）

- **RFC 8843 §6**: `a=bundle-only` 付きで port 0 の m-line は、「BUNDLE を受け入れるときだけ使う m-line」であり、拒否ではない。
- **RFC 8843 §7.3.1 / §7.3.3**: answerer が BUNDLE を受け入れるなら、bundle-only の m-line を group に入れて受け入れる。answer の非tag m-line は port 0 とする（bundled の非tag は §7.3.1 で port 0 + `a=bundle-only` なし。tag は通常の port）。BUNDLE を受け入れない、または m-line を group から外すなら、その m-line は拒否（port 0）とする。
- **RFC 8829（JSEP）§5.8 / §5.10**: bundle-only の m-line を受け取ったときの扱いと、「`bundle-only` を含み、BUNDLE group に入っていない m-line は拒否と同じ」という規則を確認する。
- **RFC 8866 §5.7（RFC 4566）**: session level に `c=` がないなら、全 m-line に `c=` が必要。port 0 の m-line も例外ではない。Firefox（SIPCC）はこれを厳密に検証する。

### 5.3 実装方針

1. **パース**: `MediaDescription` に `bundleOnly = false` を追加する。`parse` で `a=bundle-only` を読み、`toString()` でも出力できるようにする（werift 自身は出さない。下の 5）。他の属性の書き方に合わせる。
2. **判定の一元化**: remote の m-line が拒否かどうかを、1 つの関数で判定する。例: `isRejectedRemoteMedia(media, description)` = `port === 0 && !(media.bundleOnly && description の BUNDLE group に MID がある && bundlePolicy !== "disable")`。置き場所は `negotiation/bundleTopology.ts`（`isBundledNonTag()` の隣）か `sdp.ts` のヘルパー。5.1 の remote 判定を順にこの関数へ置き換える。判定ごとに次を区別する。
   - 拒否判定（関連付け、transceiver の stop、answer での受け入れ）: bundle-only を受け入れ扱いにする。
   - 「transport の属性を読むか」判定（候補、ICE/DTLS パラメータ）: bundle-only の m-line は非tag なので、もともと `isBundledNonTag()` で読まない。port 0 で読まないのと結果は同じなので、ここは変えなくてもよい。ただし、bundle-only の m-line が tag（group の先頭）になっている offer は不正として扱うか、拒否にする（§6 の要件を確認する）。
3. **answer の生成**（`buildAnswerSdp()`）: bundle-only の m-line を、通常の m-line と同じ経路で受け入れる（transceiver または SCTP の描画）。そのうえで `buildAnswerBundleGroups()` で group に入れる。answer の非tag m-line の port は、既存の answer の形（`DISCARD_PORT` = 9、`bundleCandidates` の規則）に揃える。Chrome は bundle-only を受けた answer の非tag に port 9 を返すので、Firefox が受理する形を直結スクリプトで確認したうえでどちらにするか決める。`a=bundle-only` は answer に付けない。
   - **（2026-11-12 追記・実測値）** 親チケット #269 で、ブラウザ同士の in-page 交渉を測った値（`/tmp/chromeprobe`）。BUNDLE を受け入れた answer の非tag m-line の port は次のとおり。
     - **Chrome 156**: 収集後の `localDescription` で、tag は実ポート、非tag は `port 9` + `c=IN IP4 0.0.0.0`。初回も再交渉も同じ。
     - **Firefox 157**: 非tag m-line に、tag と同じ実ポートと `c=` を書く（例: tag と非tag がどちらも `59152` / `172.20.0.3`）。候補と eoc は tag だけに書く。
     - どちらのブラウザも、受け入れた非tag m-line に port 0 を返さない。Firefox が werift の answer（非tag は port 9、`c=0.0.0.0`）を受理することは、`bundle-only` を含まない交渉では確認済み（親チケット §9.6 の手順 1〜3、7）。したがって、bundle-only を受け入れたときも port 9 / `c=IN IP4 0.0.0.0` に揃えるのが最も安全。RFC 8843 §7.3.1 の port 0 との違いは、Chrome / Firefox の実装に合わせた判断として記録する。
4. **拒否 m-line の `c=`**: L919 の分岐で `media.host = DISCARD_HOST` を設定する。可能なら `createRejectedMediaDescription()` に寄せ、拒否 m-line の形を一本化する。Chrome の拒否 m-line（`m=video 0 ...` + `c=IN IP4 0.0.0.0` + `a=inactive` + `a=mid`、ICE/DTLS あり）と比べ、`tools/negotiation-diff` に出る差分を説明できるようにする。offer 側の port 0（`mLineReuse: "aggressive"` の inactive、`setLocal` L1293 の `m.port = 0`）も、`addTransportDescription()` で `host` を設定しているので `c=` が出ることをテストで固定する。
5. **werift の offer**: `max-bundle` でも `a=bundle-only` は出さない（Chrome と同じ）。範囲を広げる場合は別チケットに分ける。
6. **ICE restart の offer**: Firefox は ICE restart の offer で、受け入れ済みの非tag m-line も bundle-only にする。この m-line の transceiver を止めず、direction・codec・SSRC・RTP の経路を維持し、tag の新しい generation に従うことを確認する（`deliverSameGenerationDescription` と、m-line ごとの ufrag の検証。bundle-only の m-line には ufrag がない場合もある）。
7. **validation**（`descriptionValidation.ts`）: bundle-only の m-line に ICE/DTLS 属性がない場合も、group の tag から取れるなら受け入れる。BUNDLE group に入っていない bundle-only の m-line は拒否扱いにする（JSEP の規則）。

### 5.4 制約・注意点

- negotiation の変更として扱う（`packages/webrtc/AGENTS.md`）。`tools/negotiation-diff` で develop と比べ、差分を説明できること（拒否 m-line の `c=` は意図した差分になる）。レビュー前に `npm run pbt:deep` を実行する。
- `mLineReuse: "aggressive"` の port 0 + inactive（拒否ではない）と、本当の拒否と、bundle-only を混同しない。
- `bundleCandidates`（`legacy` / `compatible`）の出力規則は変えない。bundle-only を受け入れた非tag m-line の候補の扱いは、既存の規則（`applyBundleCandidates()`）にそのまま従う。
- rollback: bundle-only の offer を rollback したとき、関連付けた transceiver と transport の割り当てが元に戻ること。
- 他実装の SDP は捏造しない。negotiation case では、Firefox の実 SDP（§2 の抜粋、または直結スクリプトで取得したもの）を元にした値を使い、出典をコメントに書く。
- テストは Arrange / Act / Assert で書き、Act / Assert のコメントは日本語にする。共通の Arrange は既存の `tests/negotiation/harness` に置く。
- Firefox の E2E（`e2e/vitest.firefox.config.mts`）は、現状では保守されておらず全件失敗する（親チケット §9.6）。回帰確認は直結スクリプトで行うか、サブタスク「Firefox E2E の保守」の完了を待つ。
- ブラウザや test server は PID で止める。

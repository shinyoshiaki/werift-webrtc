## 元報告・判定
元Issue: #815（sidorares）。**妥当（developのコード上で確認）**。RFC 8832 §6ではDTLS clientが偶数ID、serverが奇数ID。元Issueの`a=setup:passive`を用いた逆転ケースで衝突し得る。

## 原因
- [sctp.ts L129–133](https://github.com/shinyoshiaki/werift-webrtc/blob/6cef593e8a5ca0a429da64787dfeca5b9a49ec46/packages/webrtc/src/transport/sctp.ts#L129-L133) の `isServer` は`iceRoleAtStart ?? iceTransport.role`でICE roleから推定する。
- [sctp.ts L334–364](https://github.com/shinyoshiaki/werift-webrtc/blob/6cef593e8a5ca0a429da64787dfeca5b9a49ec46/packages/webrtc/src/transport/sctp.ts#L334-L364) と [L425–439](https://github.com/shinyoshiaki/werift-webrtc/blob/6cef593e8a5ca0a429da64787dfeca5b9a49ec46/packages/webrtc/src/transport/sctp.ts#L425-L439) は`isServer ? 0 : 1`を採用。通常ICE roleとDTLS roleが対応している場合にだけ偶然正しい。
- 現在の自動採番はSCTP ESTABLISHED後の`dataChannelFlush()`まで遅延し、SDPでroleが確定した時点でも`id`がundefined。

## 修正方針
1. SCTP用の採番方向を`RTCDtlsTransport.role`（`client`→偶数0,2,...、`server`→奇数1,3,...）に変更する。`auto`の間は決め打ちせず、SDPのsetup属性とremote/local answerの確定に従ってroleが定まった後に実行する。
2. **ID予約**と**DCEP送信**を分離する。role確定後、未採番のin-band DataChannelへIDを予約し、SCTPが接続するまでOPEN送信だけキューイングする。
3. explicit `id`を持つ`negotiated:true`チャネル、先行して相手からOPENされたID、close/rollback/ICE restartを考慮し、衝突なく偶奇を進める。SCTPストリーム上限も検証する。
4. DTLS roleが最終的に確定する前に手動でIDを仮割当しない。ICE roleが後から変わってもDTLS roleベースの割り当ては維持する。

## 回帰テスト
- [ ] passive answerでoffererがDTLS clientになればローカル作成DataChannelのIDは0,2,...。
- [ ] active answerでDTLS clientになるanswererも偶数ID。
- [ ] answer適用後かつSCTP established前に、in-band DataChannelの`id`が取得できる。
- [ ] 両端同時OPENでストリームIDが衝突しない。
- [ ] rollback、手動ID、接続前生成・接続後生成、再交渉の状態遷移を検証。
- [ ] WPT `RTCDataChannel-id.html` 等の相当ケース。

参考: https://www.rfc-editor.org/rfc/rfc8832.html#section-6
**完了条件:** ICE roleの偶奇推定を廃止し、DTLS roleとID確定時期が仕様に一致する。

# [SCTP] DataChannelのStream IDをDTLS roleに基づいて割り当て確定時期も修正する（#815）

## 1. 目的と背景

### 元報告・判定
- 元Issue: #815（sidorares）。**妥当（developのコード上で確認）**。
- RFC 8832 §6: **DTLS client が偶数**、**DTLS server が奇数**の Stream ID を使う。
- W3C webrtc-pc §4.4.1.6（set description）step 2.2.6: 「description が SCTP transport の DTLS role を確定させ、`id` が null の RTCDataChannel があれば、その時点で ID を生成する。生成できなければ channel を `closed` にし、`OperationError` の `error` と `close` を発火する」。
- werift は現在 **ICE role** から偶奇を推定し、**SCTP ESTABLISHED 後**に採番している。そのため以下の 2 点が仕様と食い違う。
  1. `a=setup:passive` / `active` を明示して ICE role と DTLS role の対応が通常と逆になると、偶奇が逆転し、相手の ID と衝突し得る。
  2. answer を適用した直後（SCTP 接続前）でも `channel.id` が `undefined` のまま。

### 現状コードの整理（develop / `packages/webrtc/src`）
| 箇所 | 現状 |
| --- | --- |
| `transport/sctp.ts` `get isServer()` | `dtlsTransport.iceRoleAtStart ?? iceTransport.role` が `controlling` 以外なら `true`。 |
| `transport/sctp.ts` `assignRole()` / `dataChannelFlush()` | `dataChannelId = isServer ? 0 : 1`。つまり **ICE controlled → 偶数**、**ICE controlling → 奇数**。 |
| `transport/dtls.ts` `start()` | role が `auto` のままなら **ICE controlling → DTLS server、controlled → client** に決める。上の対応はこの `auto` の場合だけ偶然 RFC と一致する。 |
| `negotiation/remoteMediaApplication.ts` L540 付近 | remote answer / pranswer の `a=setup` から `dtlsTransport.role` を決める（`actpass` かつ live な association なら維持）。 |
| `sdpManager.ts` L930 付近 + `secureTransportManager.setLocalRole()` | local answer の `a=setup` を `dtlsTransport.role` に反映する（`roleByTransport` / fallback）。 |
| `transport/sctp.ts` `dataChannelFlush()` | `associationState !== ESTABLISHED` なら即 return。**ID の予約と DCEP OPEN の送信が同じループで行われる**。 |
| `transport/sctp.ts` `dataChannelOpen()` | `negotiated:false` でも `parameters.id` があればその ID で登録する（W3C では in-band の `id` は無視）。→ 2.5 で W3C どおり無視することに決定。 |
| `transport/sctp.ts` `datachannelReceive` (OPEN) | 既に登録済みの streamId に OPEN が来ると「再送」とみなして ACK を返すだけ。偶奇の逆転による衝突を検出できない。 |
| `transport/sctp.ts` `resetAssociation()` | ID 未割当の OPEN だけ残して `dataChannelId = undefined` に戻す。 |
| `sctpManager.ts` `restoreNegotiationState()` | rollback で application-owned transport を残し、pending-only の association は `resetAssociation()` する。 |
| `packages/sctp/src/sctp.ts` | `MAX_STREAMS = 65535`、`maxChannels = min(inbound, outbound)`（交渉後に確定）。`sctp.isServer` は INIT 送信制御にも使われる。 |

## 2. 実装すべき変更

### 2.1 偶奇の決定を DTLS role ベースに変える
- `RTCSctpTransport` から ICE role を使った偶奇推定（`isServer ? 0 : 1`）を外し、`dtlsTransport.role` で決める。
  - `client` → 0, 2, 4, …
  - `server` → 1, 3, 5, …
  - `auto` → **採番しない**（保留のまま）。
- 実装案: `private get idParity(): 0 | 1 | undefined` を用意し、`assignRole()` / `dataChannelFlush()` の `dataChannelId ??= …` をこれに置き換える。
- `sctp.isServer`（`packages/sctp` の INIT 制御）は**別の関心事**として扱う。ID の偶奇とは結び付けず、既存の挙動（`iceRoleAtStart` ベース）を維持するか、変えるならこのチケットで影響を確認する。現状の結合をほどくのが主な変更。
- `dtls.ts` `start()` で `auto` から role を決めるケース（SDP に role が無いまま DTLS が始まる場合）は、DTLS が開始した時点で role が確定するので、そこで採番できるようにする（下記 2.2 のフック）。

### 2.2 ID 予約と DCEP 送信を分離する
- 新しい内部メソッド（例: `assignPendingStreamIds()`）で、**role 確定時**に未採番の in-band channel へ ID を予約する。
  - 呼ぶタイミング:
    - remote answer / pranswer の適用で `dtlsTransport.role` が `client` / `server` に決まった後（`remoteMediaApplication`）
    - local answer / pranswer の適用で `setLocalRole()` が role を決めた後（`peerConnection` / `secureTransportManager`）
    - `RTCDtlsTransport.start()` が `auto` から role を決めた後（DTLS の `onStateChange` などで通知する）
    - role が確定した後の `createDataChannel()`（`dataChannelOpen()` 内で即時採番する）
  - W3C の手順に合わせ、`setLocalDescription` / `setRemoteDescription` の Promise が resolve する前に `id` が見えるようにする。
- `dataChannelFlush()` は**送信専用**にする。ESTABLISHED まで DCEP OPEN とユーザーデータをキューに残すことは変えない。採番済みの `channel.id` を使い、ここではもう採番しない。
- 役割の一元化: role を直接書き込む箇所が 3 つ（remote answer / local answer / DTLS start）に分かれているので、`RTCDtlsTransport` に role の変更通知（例: `onRoleChange`、custom `Event`）を追加し、`RTCSctpTransport.bindAssociation()` で購読する案を推奨する。購読の解除は `eventDisposer` で管理する。

### 2.3 衝突回避と上限
- 予約時に、次の ID と一致するものはスキップする（`dataChannels` マップで判定）。
  - explicit `id` を持つ `negotiated:true` チャネル（偶奇違反の ID も含む）
  - 相手が先に OPEN してきた ID
  - ローカルで予約済みの ID
- 予約開始点: 毎回 `parity` から走査するか、`dataChannelId` を次候補として保持する。close によって ID を再利用できるので（WPT「ids are reusable after close event」）、**最小の空き ID**を選ぶ方式が安全。
- 上限: `0..65534`（`nStreams = 65535`）。SCTP 交渉後は `sctp.maxChannels` で絞る。空きが無ければ W3C 2.2.6 に従い、channel を `closed` にして `error`（`OperationError`）と `close` を発火する（`createDataChannel` 時点で確定済みなら `OperationError` を throw）。
- remote OPEN の受信時、streamId が**ローカルで予約済みかつ自分の偶奇**のものなら、ACK を返さず log を残して拒否する（または stream reset）。偶奇違反の OPEN を黙って ACK しない。

### 2.4 状態遷移ごとの扱い
| 遷移 | 期待挙動 |
| --- | --- |
| role 確定前の `createDataChannel()` | `id` は `undefined`（WPT wrapper では `null`）。仮の ID を割り当てない。 |
| answer / pranswer で role が確定 | 未採番の channel すべてに ID を予約する。SCTP 未接続でも `id` が見える。 |
| role 確定後の `createDataChannel()` | 即時に ID を予約する。 |
| ICE role conflict（487）や ICE restart で ICE role が変わる | ID も偶奇も変えない（DTLS role は維持される）。 |
| rollback（role を確定させた pranswer の後など） | pending の description で予約した ID の扱いを決める。推奨: `resetAssociation()` で ID 未送信の channel を `id=undefined` に戻し、`dataChannels` からも外す。その後の再交渉で正しい偶奇で採り直す。 |
| `resetAssociation()` / `rejectApplication()` | 上と同様に、OPEN 未送信の予約は解放する。 |
| close | `dataChannels` から削除して ID を再利用可能にする（既存の挙動）。 |
| 再交渉（DTLS role 維持） | 既存 ID は変えない。新規 channel は同じ偶奇で採番する。 |

### 2.5 in-band チャネルの explicit `id`（**決定: (a) `src` の既定 API でも W3C どおり無視する**）

#### 決定内容
- `negotiated:false`（または未指定）の `createDataChannel(label, { id })` では、`id` を**黙って無視する**。チャネルは `id === undefined` で生成され、2.2 の自動採番（DTLS role の偶奇）で ID が決まる。
- 警告も拒否もしない。throw はしない。`debug` ログ（`werift:packages/webrtc/src/sctpManager.ts`）に「in-band なので id を無視した」と 1 行残すだけにする。W3C は無視と定めており、ブラウザと同じ結果になる。
- 固定 ID を使いたい利用者には `negotiated: true` を案内する（README / changelog に記載）。
- `tools/wpt-runner/*` の wrapper は追加しない。`src` が仕様どおりに動くので、WPT 専用の shim は不要になる。

#### 判断根拠
| 観点 | 調査結果 |
| --- | --- |
| 仕様 | W3C webrtc-pc `createDataChannel` は `[[DataChannelId]]` を「`negotiated` が true のときだけ `id`、それ以外は null」で初期化する。WPT `RTCDataChannel-id.html`「In-band negotiation with a specific ID should not work」は、両端が `id: 42` を指定しても、両方の ID が 42 になることはないと検証する。また、`exchangeOfferAnswer` 前の `dc.id` が null であることも確認する。 |
| ブラウザ | Chrome / Firefox / Safari はいずれも in-band の `id` を無視する。ブラウザと werift の間で挙動を揃えられる。 |
| 由来 | aiortc から移植した際の名残である。e98bc2c33 で `if (channel.id)` を `!== undefined` に直した以外、意図して設計した形跡はない。README / `doc/` / changelog にも記述がない。 |
| 利用箇所 | リポジトリ内では `examples/untested/google-nest/server.ts:100` の `{ id: 1 }` の 1 か所だけである。これは Google のブラウザ向けサンプルを移植したもので、ブラウザでは元から無視される。werift が offerer、Nest が `active` の answer を返す構成では、werift が DTLS server になり、最初の奇数 = 1 が自動で割り当たる。結果は今と同じ。 |
| 本チケットとの整合 | 指定値を受け入れ続けると、#815 と同じ種類の衝突（相手の偶奇の ID を使う）が `src` に残る。そのための警告や拒否の経路、ID を早く予約する処理との競合、rollback の扱いまで必要になる。(b) は根本原因の修正（AGENTS.md Do 2）に反する。 |
| AGENTS.md Do 5 | 「werift の convenience behavior」は利用者の手間を減らす挙動を指す。仕様に反し、衝突を招く入力をそのまま採用することは convenience に当たらないので、(a) は Do 5 に反しない。 |

(b) を採らないので、「相手の偶奇の ID を警告に留めるか拒否するか」の検討は不要になる。

#### 実装上の要点
- 無視する処理は**公開入口の `SctpTransportManager.createDataChannel()`** で行う（`negotiated` が true でなければ `RTCDataChannelParameters.id` に `undefined` を渡す）。`RTCDataChannel` constructor では行わない。相手の OPEN から作るチャネル（`datachannelReceive` → `new RTCDataChannel(this, parameters, false)`）は `parameters.id = streamId` を使うので、constructor で消すと壊れる。
- 範囲検証（`0..65534`）と `negotiated:true` で `id` 未指定のときの TypeError は、これまでどおり `negotiated:true` のときだけ行う。in-band では `id: 65535` や負の値も無視の対象であり、エラーにしない（W3C の初期化順序どおり）。
- `RTCSctpTransport.dataChannelOpen()` の `if (channel.id !== undefined)` 分岐は、ローカルの in-band チャネルからは到達しなくなる。2.2 で予約を作り直すときに、この分岐は削除するか、内部の不変条件（予約済みの ID 以外は来ない）を確かめる assert に置き換える。
- `RTCDataChannel` / `RTCDataChannelParameters` を直接 `new` する利用（`src/index.ts` から `export *`）は内部用途とみなし、互換性の対象にしない。changelog で「`pc.createDataChannel` 経由の挙動」と明記する。
- 公開型 `id: number` の実際の値が `undefined` になり得る問題は既存のもので、本チケットでは型を変えない（別途検討する）。

## 3. 技術的アプローチ（調査結果の要約）
- role の確定点は既にコード上に 3 か所ある: `remoteMediaApplication.ts`（remote answer）、`setLocalRole()`（local answer）、`dtls.ts start()`（`auto` 解決）。ここから SCTP へ通知する経路を 1 本追加すれば、採番時期を W3C に合わせられる。
- `dataChannelFlush()` は `while` 内で採番と送信を同時に行っているので、採番部分（`streamId === undefined` ブロック）を切り出して role 確定時のフックへ移す。送信側は ESTABLISHED チェックを維持する。
- 偶奇は `dtlsTransport.role` だけで決まる。`iceRoleAtStart` は SCTP の INIT 制御（`sctp.isServer`）にだけ残すか、別チケットで見直す。
- negotiation の変更（description apply 経路で SCTP の状態を変える）に該当するため、`packages/webrtc/AGENTS.md` Do 6〜8 に従い、`NegotiationTransaction` の TSDoc（SCTP 行）と `sctpManager.ts` の TSDoc（「Its client / server side follows the ICE role at the DTLS start」の記述）を更新する。pending 中の `channel.id` が live 値として何を追うかを `expectedLive` の表へ追記する。
- in-band の `id` を無視する処理（2.5）は `sctpManager.createDataChannel()` の 1 か所で済む。これを先に入れると、予約ロジックは「ローカルの in-band チャネルは常に未採番で来る」という前提だけで書ける。
- 変更が大きくなる場合は、(1) in-band `id` の無視、(2) `dtls.ts` の role 通知、(3) 採番と送信の分離、の順に独立コミットにしておくとレビューしやすい。

## 4. 制約・注意点
- **互換性**: 既定の構成（両端とも `actpass` → answerer が `active`）では、offerer = ICE controlling = DTLS server = 奇数となり、現状と結果は同じ。変わるのは `setup` を明示した構成（mediasoup 等の SFU、元 Issue のケース）と、ID が見えるタイミング。`id` が早く確定することを changelog に書く。
- 採番時期が早まるため、`dataChannelFlush()` 内の「ESTABLISHED まで採番しない」前提に依存したコード（`resetAssociation()` の `channel.id === undefined` フィルタ、`dataChannelClose()` の `queueItem[0].id !== channel.id` フィルタ）を見直す。採番済みでも OPEN 未送信の channel を正しく扱う必要がある。
- `dataChannelClose()` は `associationState !== ESTABLISHED` のとき queue を `id` で絞っている。予約済み ID が同じ別 channel を誤って消さないことを確認する（`channel` の同一性で比較する方が安全）。
- BUNDLE: SCTP transport が BUNDLE で別の DTLS transport に移る場合（`setDtlsTransport` / `resetAssociation(dtlsTransport)`）、移り先の role で採り直すかどうかを定める。確定済み role の transport 間で偶奇が変わることは通常ない。
- Event 購読は `eventDisposer` に登録し、`leakFootprint` / leak property（`tests/pbt/leak`）で増加しないことを確認する。
- **in-band `id` の無視は公開 API の挙動変更**（2.5）。`changelog.md` に「`negotiated:false` の `id` は W3C どおり無視される。固定 ID には `negotiated:true` を使う」と書き、README の DataChannel 記述にも 1 行加える。`examples/untested/google-nest/server.ts` の `{ id: 1 }` を削除し、`npm run doc` で `doc/_media` のコピーを再生成する。
- `enum` は使わず、`erasableSyntaxOnly` を守る。
- ICE-lite（`iceControlling` を強制）でも、DTLS role に基づく採番が正しく動くこと。

## 5. 回帰テスト
テストは Arrange / Act / Assert で書き、日本語コメントを付ける。共通の Arrange は既存のユーティリティ（`tests/utils.ts`、negotiation なら `tests/negotiation/harness/*`）に置く。

- [ ] passive answer で offerer が DTLS client になれば、ローカルで作成した DataChannel の ID は 0, 2, …（WPT「DTLS server uses even data channel IDs」相当。ICE 接続なしで `setRemoteDescription` 直後に確認する）。
- [ ] passive offer → active answer で offerer が DTLS server になれば、ID は 1, 3, …（WPT「DTLS client uses odd…」相当）。
- [ ] active answer で DTLS client になる answerer も偶数 ID。
- [ ] answer 適用後かつ SCTP established 前に、in-band DataChannel の `id` が取得できる（offerer / answerer の両方）。
- [ ] role 確定前の `createDataChannel()` では `id` が `undefined`。
- [ ] 両端から同時に OPEN してもストリーム ID が衝突せず、両端の channel が `open` になり、メッセージがそれぞれの相手に届く。
- [ ] 偶奇違反の `negotiated:true` チャネルと混在させても、自動採番が偶奇を守り、使用済み ID を避ける（WPT「Odd/even role should not be violated…」相当）。
- [ ] close 後の ID 再利用（WPT「ids are reusable after close event」相当）。
- [ ] rollback（pranswer で role 確定 → rollback）、`rejectApplication`、ICE restart、ICE role conflict、再交渉の各遷移で、ID の保持・解放が 2.4 の表どおりになる。negotiation の個別テストではなく、可能なら model property の oracle（`tests/pbt/model/oracles.ts`：in-band の自動採番 ID が自分の DTLS role の偶奇と一致する）として追加する。
- [ ] ID を使い切ったとき（上限超過）に `OperationError` / `closed` になる（小さな `maxChannels` を使うユニットテストで代替してもよい）。
- [ ] in-band の explicit `id` を無視する（2.5）: `createDataChannel("x", { id: 42 })` の直後は `id === undefined`。answer の適用後は自分の DTLS role の偶奇で自動採番される。両端が `id: 42` を指定しても、両方が 42 になることはなく、メッセージがそれぞれの相手に届く。`id: 65535` / `-1` を in-band で指定しても throw しない。
- [ ] 既存の `tests/datachannel/openLimit.test.ts` を更新する: `negotiated:false` の場合の `retry.id` は `42` ではなく `undefined` を期待する。「ID が解放される」という検証は、意味を持つ `negotiated:true` の場合に限る。
- [ ] 元 Issue #815 の再現ケース（`a=setup:passive` で ICE/DTLS の対応を逆転）を `tests/issue/815.test.ts` として追加する。
- [ ] WPT: `webrtc/RTCDataChannel-id.html` を `packages/webrtc/wpt/allowlist.json` に追加し、`npm run wpt` で通ることを確認する（必要なら `id` の `undefined` → `null` 変換と in-band `id` の無視は `tools/wpt-runner/*` wrapper で行う）。

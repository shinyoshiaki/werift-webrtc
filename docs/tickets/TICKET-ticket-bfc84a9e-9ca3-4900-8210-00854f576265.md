# [ICE] werift 起点の ICE restart の後、Firefox が werift からの RTP / DataChannel を受け取れなくなる

## 1. 目的と背景

- 親チケット #269（`190063e8-…`）の相互接続確認（親チケット §9.6）で見つかった、以前からある不具合。develop `1f007fe89` でも再現する。`bundleCandidates` とは関係がない（`legacy` で 6 回中 5 回、`compatible` で 6 回中 6 回失敗）。
- **手順**: werift ↔ Firefox 157 で、video 3 本と DataChannel を BUNDLE した接続を作る。そこで werift が `restartIce()` → `createOffer()` → `setLocalDescription()` を行い、Firefox の answer を `setRemoteDescription()` する。
- **結果**: werift は Firefox からの RTP を受け取り続ける。一方で Firefox 側は werift からの RTP が届かなくなり（inbound-rtp の `packetsReceived` が増えない）、DataChannel の ping も届かない。同じ手順は Chromium では成功する（`max-compat` で 1 回だけ、モードに関係ない別の失敗があった）。
- **再現方法**: 直結スクリプト（親チケットでは `/tmp/ffharness/interop.ts` を使った。Node 上の werift と Playwright の Firefox をつなぎ、SDP を `page.evaluate` で受け渡す。リポジトリの外にある一時ファイル）。`e2e/` の Firefox 実行（`e2e/vitest.firefox.config.mts`）は、この環境では基本テストも全件失敗しているので、判定には使えない。
- **範囲外**: Firefox 起点の ICE restart（Firefox の offer が `a=bundle-only` を使うため、別サブタスク「bundle-only 未対応」の不具合で確認できない）。Chromium 起点の restart の後に werift が `checking` のまま止まる、まれな失敗（親 §9.6）。後者は同じ原因の可能性があるので、修正後に再確認だけ行う。

## 3. 原因の仮説（優先度順）

### 仮説 A（最有力）: answer 適用前に届いた Firefox の check が commit で捨てられ、新 generation のペアができない

1. werift が offer を出すと、Firefox は `setRemoteDescription(offer)` / `setLocalDescription(answer)` の直後に、**新しい ICE context（新しいソケット・新しいポート）**で connectivity check を始める。answer が werift に届くより前に、新 ufrag 宛ての check が werift に届く。
2. werift はこれに応答する（Firefox から見るとペアは成功）。ただし内容は provisional generation に記録されるだけで、pranswer がなければ provisional のチェックは始まらない。
3. answer を適用すると `Connection.restart()` → `endProvisional()` が走り、**provisional の prflx 候補、ペア、受信した USE-CANDIDATE がすべて捨てられる**。`earlyChecks` も空になる。初回接続にある「early check を再生する」経路が、restart の commit にはない。
4. その後 werift が使える remote 候補は、answer とトリクルで届いたものだけになる。Firefox の host 候補が mDNS（`.local`）で、解決できない、または届くのが遅い場合、werift の checkList は空か、失敗だけになる。
5. **Firefox（nICEr）は、成功したペアに check を再送しない**。controlled 側として nomination を待つだけなので、werift が新しい prflx を学び直す機会がない。**Chrome（libwebrtc）は全ペアに ping を出し続ける**ので、commit の後に届いた check が live の checkList に prflx を作り、回復する。Chrome で成功し Firefox で失敗する理由も、これで説明できる。
6. Firefox は新しい ICE context が connected になるまで古い context で送り続けるので、werift は Firefox の RTP を受け取り続ける（ソケットは restart 後も残る）。werift 側は `nominated` がないので、何も送らない。観測された現象と一致する。
7. 6 回中 1 回の成功は、Firefox の check が werift の commit より後に届いたタイミングで説明できる。

### 仮説 B: aggressive nomination で選ばれたペアが、両側で一致しない

- werift は最初に成功したペアを、Firefox は nominated されたペアのうち優先度が最も高いものを選ぶ。新しい generation でペアがずれると、Firefox が werift の送信先や送信元を受け入れない可能性がある（nICEr が、選択ペア以外からの非 STUN パケットを捨てるかどうかは要確認）。初回接続は成功しているので優先度は低いが、仮説 A を直した後も失敗が残るなら調べる。

### 仮説 C: consent / DTLS の扱い

- commit で `stopConsentLifecycle()` が走り、新しいペアで `queryConsent()` が始まるまで送信できない。nominate の後に consent の要求が Firefox の新しい ufrag で失敗し続けると、`consentFresh=false` で送信が止まる（RFC 7675）。
- DTLS / SRTP は restart で張り直さない（RFC 8445 §9 のとおり、同じ DTLS association を続ける）。DTLS の状態が `connected` のままで、SCTP の送信が ICE 層の `send` で捨てられているのか、それより上で止まっているのかを切り分ける。

## 4. 調査手順

1. 直結スクリプトで `DEBUG=werift-ice*` を有効にし、restart の前後で次のログを記録する（`maxBundle` / `balanced` / `max-compat`、各 3 回以上）。
   - offer を作ってから answer を適用するまでの間に、staged ufrag 宛ての check を受信しているか（`checkIncomingProvisional` が呼ばれているか。必要なら一時的にログを追加する）。
   - commit 後の `addRemoteCandidate`、`check start`、`nominated`、`failure case`。新しい generation の `iceConnectionState` の遷移（`checking` で止まるか）。
   - Firefox 側の `pc.getStats()`（`candidate-pair` の state / nominated、`local-candidate` のポートが restart 前と変わったか）と `about:webrtc` 相当のログ（`MOZ_LOG=nicer:5,signaling:5` を Playwright の `env` で渡す）。
2. 仮説 A を確かめる方法: harness で werift への answer の適用を数百 ms 遅らせると失敗率が上がり、Firefox の check が届く前に answer を適用すると成功するか（例えば、Firefox の `setLocalDescription` の直後に answer を渡し、Firefox 側の ICE 開始を止める）を比べる。Chromium でも、ping の間隔を待つ前の状態では同じ穴があることを ICE 単体のテストで確かめる。
3. 仮説 A で説明できない場合は、Firefox と Chrome の STUN トラフィックを pcap（`tcpdump -i lo udp`）で取り、USE-CANDIDATE の有無、check の再送間隔、consent の要求先を比べて記録する。

## 5. 修正方針（仮説 A が正しい場合）

- **方針**: answer で restart を commit するとき、commit する ufrag と同じ provisional generation が受信した check を **live generation の early check として引き継ぐ**。初回接続の `earlyChecks` と同じ扱いになる。
  - 案 1（推奨）: provisional generation が、受信した check（`[Message, Address, Protocol]`）を記録しておく。`Connection.restart()` の後、`commitLocalCredentials()` のときに、それが commit する ufrag の provisional であれば、その check を `earlyChecks` に移す。`connect()`（新しい generation の `start()`）で再生すれば、prflx の学習、triggered check（werift が controlling なので USE-CANDIDATE 付き）、`remoteNominated` の反映が通常の経路で行われる。
  - 案 2: provisional の `remoteCandidates`（prflx）を live の `_remoteCandidates` に移す。ただし remote ufrag（answer が来るまで不明）との照合や、`pair.remoteCandidate.ufrag === this.remoteUsername` の条件（ice.ts L2195 付近）と矛盾しないように注意が必要。案 1 の方が既存の経路を再利用できる。
  - 順序の制約: `commitLocalRestartIfStaged()` の `restart()` が `endProvisional()` を呼ぶので、`restart()` の前に provisional を退避するか、`restart()` に引き継ぎ用の引数を足す。`Connection` の API を変えるときは `packages/ice/src/iceBase.ts` のインターフェースも更新する。
  - 引き継ぐのは、**commit する ufrag 宛ての check だけ**にする。rollback、置き換えの offer、別の generation の選択（`discardStagedLocalCredentials` / `selectGeneration`）で provisional を捨てる経路では、引き継がない。
  - 再生する check の USERNAME の remote 側（相手の ufrag）が、answer の ufrag と一致しないときは、再生時に既存の検証（`checkIncoming` 内の ufrag 判定）で捨てる。古い generation の check を新しい checkList に入れない。
  - pranswer の経路（`startProvisionalChecks` 済みで provisional が nominated）は今の挙動を変えない。修正の後も `provisional.test.ts` が通ること。
- **やらないこと**: タイマーで check を送り直すような対症療法、catch して無視すること、Firefox だけの分岐。
- 仮説 B / C が原因だった場合は、この章の方針を差し替え、根拠（ログ、RFC の条文）をこのチケットに追記してから実装する。

## 10. 調査結果と対応（2026-11-13、基準リビジョン `dc95a5a49`）

### 10.1 原因（仮説 A で確定）

- 直結スクリプト（`/tmp/ffharness/interop.ts`、Firefox 157 / Playwright 1.64.1。各側が gathering 完了まで待ってから SDP を渡す「vanilla」モードと、トリクルモードがある）で、修正前のコードは vanilla モードで 18 回中 4 回だけ成功した（`max-bundle`: legacy 0/3・compatible 1/3、`balanced`: 1/3・1/3、`max-compat`: 1/3・0/3）。失敗時の werift は `checking` のまま止まり、Firefox からの RTP は受け取り続けた。
- restart に対する Firefox の answer には **候補が 1 つもない**（`m=video 9`、`c=IN IP4 0.0.0.0`、`a=candidate` も `a=end-of-candidates` もない。`a=ice-ufrag` だけが新しい）。このため、werift が新しい generation の相手を知る手段は、届いた check から prflx 候補を学ぶことだけになる。
- Firefox は answer を返す前に新しい ufrag へ check を送る。この check は werift の provisional generation に記録されるが、commit（`Connection.restart()` → `endProvisional()`）で捨てられる。Firefox は成功した check を再送しないので、werift の checkList は空のままになり、`connect()` が `ICE negotiation failed` で終わる。
- `DEBUG=werift-ice*` を付けた回では、ログ出力による遅れで Firefox の check が commit の後に届き（`earlyChecks … 0` の直後に `Triggered Checks` が出て prflx を学び、`nominated` になる）、接続は成功した。これが「まれに成功する」理由に当たる。トリクルモードでは Firefox が新しい候補をトリクルするので、修正前でも成功する。
- 仮説 B / C を調べる必要はなかった（修正後は全件成功）。

### 10.2 修正（5 章の案 1）

- `packages/ice/src/ice.ts`:
  - `ProvisionalGeneration.receivedChecks`: staged ufrag 宛てに受信した check を、最大 32 件（`MAX_CARRIED_CHECKS`）まで記録する。
  - `restart()` は `endProvisional()` の前に、その記録を `endedStagedChecks` に退避する。`commitLocalCredentials(ufrag)` は、commit する ufrag と一致したときだけ、それを `carriedChecks` に移す。置き換えの offer（`stageLocalCredentials`）、rollback（`discardStagedLocalCredentials` の後の restart）、`restartRemote()`、`close()` では引き継がない。
  - `connect()` は、`carriedChecks` のうち **answer の remote ufrag から送られた check で、かつ今も使っているソケットに届いたもの** だけを、通常の early check と同じく `checkIncoming()` で再生する。prflx の学習と USE-CANDIDATE 付きの triggered check は、既存の経路で行われる。
  - `Connection` の公開 API と `iceBase.ts` のインターフェースは変えていない。SDP の出力も変わらない。
- `packages/webrtc/tests/pbt/leak/leakProbe.ts` に `ice.carriedChecks` を監視項目として追加した。
- webrtc の negotiation case は追加していない。werift 同士の場合、answer に必ず候補が入るので、この穴は再現しない。再現には他の実装の SDP の形（候補のない answer）が必要だが、`tests/negotiation/cases` でそれを作ることは禁止されている（`packages/webrtc/AGENTS.md`）。そのため、ICE 単体のテストと直結スクリプトで確認した。

## 元報告と判定
元Issue: #811（sidorares）。**妥当（developの静的検証）**。元Issueには正常終了とfingerprint不一致の再現コード、WPT失敗がある。今回は独立した実行試験はしていない。

## 原因
- [dtls.ts L600–607](https://github.com/shinyoshiaki/werift-webrtc/blob/6cef593e8a5ca0a429da64787dfeca5b9a49ec46/packages/webrtc/src/transport/dtls.ts#L600-L607) の `RTCDtlsTransport.runStop()` は`// todo impl send alert`を残し、ICE transportを先に停止してから内部DTLSをcloseする。
- [dtls.ts L305–310](https://github.com/shinyoshiaki/werift-webrtc/blob/6cef593e8a5ca0a429da64787dfeca5b9a49ec46/packages/webrtc/src/transport/dtls.ts#L305-L310) はremote fingerprint検証失敗をローカル`failed`にするだけで、相手にはfatal alertを送らない。
- 相手のDTLS stateが`connected`/`connecting`のまま残り、障害検知と後始末が不完全。

## 修正方針
1. `packages/dtls`にDTLS 1.2のAlert recordの送受信APIを設ける。確立済みの接続には適切なepoch・暗号・sequenceで保護して`close_notify`を送信し、**送信完了後**にICE/socketを閉じる。アラート送信失敗時も有限時間内に終了する。
2. fingerprint検証失敗では接続可能な期間に`bad_certificate`などのfatal alertを送る。ローカルは`failed`へ遷移し、相手が受信したfatal alertも`failed`として適切に通知する。
3. peerから`close_notify`を受けた時に`RTCDtlsTransport`の状態を`closed`へ、fatal alert時には`failed`へ伝播させる。可能な範囲でWebRTCの`error`イベント情報（`errorDetail: "dtls-failure"`, `receivedAlert`等）を提供。
4. alertの重複送信、handshake中のstop、ICE先行切断、SCTP/DataChannel停止、close多重呼び出しを扱い、callbackの再入や未捕捉rejectを防ぐ。DTLS 1.3を将来扱う場合はversionごとのAlert処理を分ける。

## 回帰テスト
- [ ] 2peer接続後、片側closeで暗号化された`close_notify`送信、相手側DTLSがclosedに遷移。
- [ ] SDP fingerprintを改ざんすると検証側からfatal alertが送られ相手がfailedへ遷移。
- [ ] close/ICE stop競合、未確立中の中断、重複alert、正常なSCTP closeに回帰なし。
- [ ] WPT `protocol/dtls-close.html`, `protocol/dtls-fingerprint-validation.html`, `RTCDtlsTransport-state.html`等。

参考: RFC 5246 §7.2。

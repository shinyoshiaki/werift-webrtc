# [DTLS] close_notifyと証明書検証失敗時のfatal alertを送受信して状態へ反映する（#811）

## 元報告と判定
元Issue: #811（sidorares）。**妥当（developの静的検証）**。元Issueには正常終了とfingerprint不一致の再現コード、WPT失敗がある。今回は独立した実行試験はしていない。

## 1. 目的と背景

- RFC 5246 §7.2: 接続を閉じる側は `close_notify` を送る。致命的なエラーを検出した側は fatal alert を送ってから接続を破棄する。受信側は fatal alert を受けたらその接続を無効にする。
- W3C webrtc-pc: `RTCDtlsTransport.state` は、close_notify を受信すると `closed`、fatal alert を送受信すると `failed` になる。`pc.close()` を呼んだ側のローカル遷移は同期で `closed` になり、`statechange` は発火しない。
- werift は現状どちらの alert も送らない。相手 peer は DTLS が `connected`/`connecting` のまま残り、ICE consent が切れる（約30秒）まで終了を検知できない。DataChannel / SCTP の `close` も遅れる。
- 目標: 正常終了と証明書検証失敗を DTLS Alert として相手へ伝え、両 peer の `RTCDtlsTransport.state`・SCTP・DataChannel・`connectionState` へすぐ反映すること。

## 3. 実装内容

### 3.1 packages/dtls: Alert 送受信 API
1. `record/const.ts` に `AlertLevel`（`warning: 1`, `fatal: 2`）を `as const` オブジェクトと同名の union 型（`@enum`）で追加する。TS の `enum` は使えない。
2. `DtlsSocket` に alert 送信 API を追加する（名前は例: `sendAlert(level, description): Promise<void>`）。
   - `createPlaintext(this.dtls)([{ type: ContentType.alert, fragment: new Alert(level, desc).serialize() }], ++this.dtls.recordSequenceNumber)` で record を作る。`dtls.epoch > 0` なら `cipher.encryptPacket()` で保護してから `transport.send()` する。epoch 0（ChangeCipherSpec 前）は平文で送る。
   - socket が close 済み（`transport.closedSignal.aborted`）、または同じ接続で fatal alert / close_notify を送信済みなら、何も送らずに resolve する（重複送信の防止）。
   - 送信失敗は reject させず、ログ出力にとどめる。呼び出し側が close 処理を続けられるようにするため。
3. `DtlsSocket` に「close_notify を送ってから transport を閉じる」API を追加する（例: `close({ notify?: boolean, timeoutMs?: number })`、または `closeNotify()` と `close()` に分ける）。
   - alert の送信完了（`transport.send()` の resolve）を待ってから `transport.close()` を呼ぶ。送信が終わらなくても上限時間（例: 数百 ms）で打ち切って close する。
   - 既存の同期 `close()` の呼び出し元（dtls tests / examples / `packages/webrtc`）との互換を保つ。引数なしの挙動を変えるかどうかは決めて README に書く。
4. 受信処理（`record/receive.ts` / `socket.ts`）
   - 暗号化の判定は「description が未知かどうか」ではなく `recordLayerHeader.epoch > 0` で行う。復号に失敗した record は破棄する（RFC 6347 §4.1.2.1 に従い、不正 record は黙って捨てる）。
   - decode した `{ level, description }` を `socket.ts` へ返す。throw はしない。
   - `DtlsSocket` に受信 alert のイベントを追加する（例: `onAlert: Event<[{ level, description }]>`）。
     - `close_notify`（level に関係なく description 0）: 状態を「相手から close」にし、`onClose` を発火する。RFC 5246 では応答の close_notify を送る（`notify` を返す）のが推奨。ただしその後は送信しない。
     - fatal（level 2）: `onError` に受信 alert を表す専用エラー（例: `DtlsAlertError`。`level` / `description` / `alertDescName` を持つ）を渡す。transport を閉じ、再送も止める。
     - その他の warning: ログ出力のみ（`user_canceled`、`no_renegotiation` など）。
   - ローカルで fatal alert を送った後や close 済みのときに届いた record は処理しない（コールバックの再入防止）。
5. handshake 中の証明書検証フック（推奨）
   - `Options` に `verifyRemoteCertificate?: (certificate: Buffer) => boolean`（名前は仮）を追加する。client の `flight5.ts` の Certificate 処理と、server の `flight6.ts` の Certificate 処理で呼ぶ。
   - false または throw なら `bad_certificate`（42）を fatal で送り、その時点の epoch で handshake を中止する。flight の再送を止め、`onError` にローカル検証失敗のエラーを渡す。
   - フックがあると、server 側は自分の Finished を送る前に、client 側は flight5（ChangeCipherSpec / Finished）を送る前に失敗を相手へ伝えられる。相手は `connected` へ進まずに fatal alert を受け取る。
6. `src/index.ts` から新しい定数・エラー型・型を export する。`packages/dtls/README.md` と、必要なら `examples/` も更新する。

### 3.2 packages/webrtc: RTCDtlsTransport
1. `runStop()` の順序を次のように変える。
   1. `setState("closed", false)`（同期。WPT の要求どおり statechange は発火しない）
   2. DTLS が確立済み、または handshake 中で送信可能なら `close_notify` を送り、完了を上限時間付きで待つ
   3. `dtls.close()`（再送停止と socket close）
   4. `iceTransport.stop()`
   5. `finally` で `onStopped` を発火
   - `stop()` は既存の共有 Promise（`stopPromise`）で多重呼び出しを吸収している。alert 送信もこの Promise の内側で 1 回だけ行う。
   - ICE がすでに `closed` / `failed` なら alert は送らない（または送信失敗を無視する）。どちらの場合も有限時間で終わること。
2. fingerprint 検証
   - 推奨: `start()` で `DtlsServer` / `DtlsClient` を生成するとき、3.1-5 のフックに `verifyRemoteCertificateFingerprint()` 相当の検証を渡し、handshake 中に `bad_certificate` を送る。
   - 後方互換のフォールバック: handshake 完了後の検証で失敗したら、`dtls.close()` の前に `bad_certificate` の fatal alert を送る（このときは epoch 1 で暗号化される）。
   - ローカルは `failed` にする。`start()` の reject は今と同じく維持する。
3. 受信 alert の伝播
   - `close_notify` を受けたら `closed` にする（statechange を発火する。相手起因なので）。
   - fatal alert を受けたら `failed` にする（handshake 中でも確立後でも）。`failed` / `closed` は最終状態とし、後から上書きしない。
   - ローカルで fatal alert を送ったときも `failed` にする。
   - 可能な範囲で `error` イベントを発火する。WebRTC の `RTCErrorEvent` に合わせ、`errorDetail: "dtls-failure"`、`receivedAlert` / `sentAlert`（alert 番号）を持たせる。werift には `RTCError` クラスがないので、`dataChannel.ts` の `RTCErrorEvent` の形を参考に最小限の型を定義する。追加する場合は `onerror` / `addEventListener("error")` の両方で受け取れるようにし、`tests/types/publicTypes.test.ts` も更新する。
4. 上位層への反映
   - `transport/sctp.ts`: DTLS が `failed` になったときも SCTP を `CLOSED` にし、DataChannel を close する。`closed` の既存処理と同じ扱い。
   - `secureTransportManager.ts`: 接続確立後に DTLS transport が `failed` になったら `connectionState = "failed"` にする（ICE の `failed` と同じく、`close()` 扱いにはしない）。リモートからの close_notify による `closed` を `connectionState` にどう反映するかは仕様（全 transport が closed のとき）とブラウザの挙動を確認して決め、TSDoc に書く。`createTransport()` で `dtlsTransport.onStateChange` を購読するのが自然。
   - `media/rtpSender.ts` の `syncNetworkAvailability()` は既存の購読で追従するが、`failed` / `closed` で送信が止まることを確認する。
5. upstream WPT に合わせるための厳密な挙動が必要になった場合は `tools/wpt-runner/*` に閉じ込め、`src` の既定 API の便利な挙動は変えない。

## 4. 技術的アプローチの要点
- **record 保護**: 送信 alert には `send()` と同じ `dtls.epoch` / `++dtls.recordSequenceNumber` / `cipher.encryptPacket()` を使い、epoch・暗号・sequence を applicationData と共有する。AEAD の AAD には content type（21）が入るので、`encryptPacket` は header の contentType をそのまま渡している現在の実装で正しく扱える。
- **受信判定**: epoch 0 は平文、epoch > 0 は復号する。現在の「description が未知なら復号」というヒューリスティックはやめる。
- **送信完了を待つ**: `IceConnection.send()` が resolve するまで待ち、`Promise.race` で上限時間を付ける。タイマーは `timers/promises` の `setTimeout` と `AbortSignal` を使い、終了後にタイマーを残さない（memleak / leak property の対象になる）。
- **再入防止**: alert の送信・受信・`stop()`・`onError` が同時に起きても、状態遷移とイベント発火が 1 回だけになるようにする。`DtlsSocket` 側に `closing` / `closed` / `alertSent` / `alertReceived` のフラグを持たせる。`RTCDtlsTransport` 側は `stopPromise` と最終状態の判定で守る。`Event.execute` 内から `stop()` が再入しても、同じ Promise を返す既存の設計を維持する。
- **未捕捉 reject の防止**: `void promise.catch(log)` の形で fire-and-forget にし、`start()` の外側 Promise とは独立させる。
- **DTLS 1.3**: 今回は DTLS 1.2 だけを対象とする。将来 1.3 を扱うときに alert 処理（1.3 では close_notify の後も相手の close を待たない、などの差分）をバージョンごとに分けられるよう、alert の encode / 処理をソケット本体から独立した関数にしておく。

- `packages/webrtc/AGENTS.md` / ルート `AGENTS.md` に従う。TS の `enum` とパラメータプロパティは使わない。テストは AAA 形式とし、Act / Assert に日本語コメントを付ける。共有する Arrange は `packages/webrtc/tests/fixture.ts`（`createDtlsSessions`, `dtlsTransportPair`）や `packages/dtls/tests/utils.ts` にまとめる。
- `RTCDtlsTransport.state` の `closed` は、pc.close() を呼んだ側では statechange なしの同期遷移にする（WPT `RTCDtlsTransport-state.html`）。alert 送信を待つのはその後。
- `onStopped` は「ICE が止まった」ことを表す既存の契約（changelog v0.27.0）。alert で `closed` / `failed` になっただけでは発火させない。`SecureTransportManager.ownedTransports` の所有も維持する。
- BUNDLE で 1 つの DTLS transport を複数の m-line が共有する場合や、transceiver を stop しても DTLS を閉じない挙動（WPT `stop bundled transceiver retains dtls transport state`）を壊さない。
- 再ネゴシエーション、ICE restart、rollback で transport を差し替えるとき（`negotiationTransaction.ts`、`transportActivation.ts`）に旧 transport へ close_notify を送るかどうかを確認する。negotiation のテスト基盤（`assertNegotiationInvariants`, `expectSessionContinues`）や `tools/negotiation-diff` で develop との差分が出たら、原因を調べる。
- 送信を待つ時間は `pc.close()` の完了時間に直接加わる。上限は短くする。テストやメモリリーク計測で close が遅くならないことを確認する。
- 相手が古い werift（alert を無視する）やブラウザでも相互運用できること。Chrome / Firefox は close_notify を受けると DTLS を `closed` に、fatal alert を受けると `failed` にする。
- fatal alert を受けた後に届いた applicationData / SRTP は処理しない。
- ICE が先に切断されて送信経路がないときも、例外を出さずに有限時間で終わること。

## 7. 完了条件
- 接続を終了すると、相手に暗号化された `close_notify` が届き、相手の `RTCDtlsTransport` / SCTP / DataChannel が `closed` になる。送信は ICE を止める前に完了し、送れない場合も有限時間で終わる。
- fingerprint（証明書）の検証に失敗すると、`bad_certificate` などの fatal alert が相手に届き、両 peer の DTLS と `connectionState` が `failed` になる。
- 受信した fatal alert は握り潰されず、`failed` として通知される（可能なら `errorDetail: "dtls-failure"` 付きの `error` イベントも）。
- 重複 alert、handshake 中の stop、ICE 先行切断、`close()` の多重呼び出しで、状態遷移やイベントが重複せず、未捕捉 reject がない。
- 上記の WPT が allowlist に入って通る。dtls / webrtc のテスト、`npm run type`、`npm run test:small` が通る。
- `packages/dtls/README.md`、`changelog.md`、生成ドキュメント（`npm run doc`）が新 API と挙動に合っている。

参考: RFC 5246 §7.2、RFC 6347 §4.1.2.1、W3C webrtc-pc `RTCDtlsTransportState` / `RTCErrorEvent`。

## 8. 追加要件（レビュー差し戻し後の打開策 A・B・C）

6回目のレビューで、fingerprint 不一致を `errorDetail: "dtls-failure"` で通知していることが W3C と違うと指摘された。修正のたびに別の不整合が出る形が続いたため、指摘箇所だけでなく、仕様と食い違う箇所もまとめて直し、状態の対応表で全経路を確かめる。チケット 3.2-3 は `"dtls-failure"` を一律に例示していたが、仕様と食い違う部分は仕様を正とする（AGENTS.md Do 11）。

### A. fingerprint 不一致は `fingerprint-failure`（必須）
- W3C webrtc-pc `RTCErrorDetailType`:
  - `fingerprint-failure`: リモート証明書が SDP のどの fingerprint とも一致しない場合。相手側は `bad_certificate`（42）を受けて `dtls-failure` になる。
  - `receivedAlert` / `sentAlert`: どちらも「errorDetail が `dtls-failure` で、fatal alert を送受信した場合」の値。それ以外は `null`。
- 検証した側: 不一致のときだけ `errorDetail: "fingerprint-failure"`、`sentAlert: null`、`receivedAlert: null` にする。`bad_certificate` は相手へ送り続け、そのことを TSDoc に書く。
  - handshake 中の検証フックと、handshake 後に検証するフォールバック経路の両方を同じ扱いにする。
  - 「remote certificate not available」「remote fingerprint not exist」「対応アルゴリズムなし」などの不一致以外の検証失敗は、`dtls-failure` と `sentAlert: 42` のまま。
- 相手側: 今までどおり `dtls-failure`、`receivedAlert: 42`。
- テスト・`publicTypes.test.ts`・TSDoc・`changelog.md`・生成ドキュメント（`npm run doc`）を合わせる。

### B. handshake 中に受けた `close_notify` は `closed`（強く推奨）
- W3C `RTCDtlsTransportState` の `closed` は「`close_notify` を受信した結果」。`close_notify` は fatal alert ではないので、`failed` にも `error` イベント（`receivedAlert: 0`）にもしない。
- handshake 中に相手の `close_notify` を受けた場合も DTLS は `closed`、`start()` は resolve する。
- `connectionState` は transport activation のガードで `failed` に決着させる（接続確立前に、現在の m-line が使う DTLS transport が `closed` / `failed` で終わったら `failed`）。このことを `transportActivation.ts` の TSDoc に書く。

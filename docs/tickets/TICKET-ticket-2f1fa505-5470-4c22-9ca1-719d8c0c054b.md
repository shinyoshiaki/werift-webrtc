# [ICE] Handle os.networkInterfaces() failures without crashing candidate gathering

## 1. 目的と背景

### 背景（元の報告）
- 下流（SimpleIM / KTPInfrastructure）から、制限された Linux / systemd 環境（`RestrictAddressFamilies=` で `AF_NETLINK` を禁止した環境など）で、ネットワークインターフェース列挙に失敗するとプロセスが終了するという報告が来ている。
- Linux の `os.networkInterfaces()` は libuv の `uv_interface_addresses()`（内部で `getifaddrs()`、つまり netlink）を使う。これが失敗すると Node.js は同期的に `SystemError`（`ERR_SYSTEM_ERROR`、例: `uv_interface_addresses returned Unknown system error 97`）を **throw** する。
- 下流の報告は影響が出ている証拠にはなるが、werift が根本原因だと示す最小再現はまだない。PR #803（close 時に pending の mDNS lookup をキャンセル）は、列挙で発生する例外を直接は扱っていない。エラー伝播全般の監査は #840 で別に扱う。

### 調査で分かったこと（develop `d6fc2d0d7` 時点）
`os.networkInterfaces()` は 2 系統から呼ばれている。性質は大きく異なる。

| # | 呼び出し元 | 実行コンテキスト | throw したときの結果 |
|---|---|---|---|
| A | `packages/ice/src/internal/hostInterfaces.ts` の `getHostInterfaceAddresses()` / `getAssignedInterfaceAddresses()`。`Connection.gatherCandidates()` の `packages/ice/src/ice.ts:745-760`（`resolveHostAddresses({ enumerated, assigned })` の引数評価中）から呼ばれる | `async gatherCandidates()` の中で同期的に呼ばれる | **プロセスは落ちない**が、gathering が壊れる（下記 A-1〜A-3） |
| B | `multicast-dns`（`node_modules/multicast-dns/index.js`）の `allInterfaces()` / `defaultInterface()` | `MdnsLookup` の生成時に作る mDNS ソケットの `'listening'` ハンドラ内の `that.update()` と、**5 秒ごとの `setInterval(that.update, 5000)`** | **uncaughtException でプロセスが終了する**（try/catch の外。werift からは捕捉できない） |
| C | `packages/ice/src/utils.ts` の公開 API `nodeIpAddress()` / `getHostAddresses()` | ライブラリ内部からは呼ばれていない（公開 export のみ） | 呼び出し元へ同期 throw（API 契約として妥当かどうかを判断する） |
| (参考) | `packages/ice-server/src/node/turnServer.ts:591` | TURN サーバー側 | 本チケットの対象外（必要なら別チケット） |

#### A の詳細（host 候補列挙の経路）
- A-1: `gatherCandidates()` は `localCandidatesStart = true` にしてから列挙する。そのため throw すると Promise は reject されるが、`localCandidatesStart` は true のまま、`localCandidatesEnd` は false のまま残る。**同じ世代で 2 回目に `gatherCandidates()` を呼ぶと、gathering ブロックを飛ばして `setState("completed")` に進み、候補 0 個のまま「成功」として扱われる**（期待挙動「成功を黙って報告しない」に反する）。
- A-2: ICE restart のときは、保持しているソケットの host 候補 / srflx を再 advertise した**後で**列挙が throw する。再 advertise 済みの候補はあるのに、世代の end-of-candidates が来ない。
- A-3: webrtc 側
  - `packages/webrtc/src/transport/ice.ts:1069-1100` の `RTCIceGatherer.gather()` は `setState("gathering")` の後に `await connection.gatherCandidates()` を呼ぶ。ここで reject されると、**`gatheringState` が `"gathering"` から抜けず、end-of-candidates（`onIceCandidate(undefined)`）も来ない**。
  - `packages/webrtc/src/secureTransportManager.ts:756` は `Promise.allSettled` で reject を握りつぶす。`packages/webrtc/src/peerConnection.ts:1727` も `.catch(log)` で握りつぶす。そのため `setLocalDescription` は成功して見えるが、利用者が受け取れるエラーはない（`iceGatheringState` が永久に `gathering` のまま）。
  - ICE restart 経路（`commitLocalRestartIfStaged()`, `transport/ice.ts:617-622`）でも `gathering.catch(log)` で握りつぶされる。

#### B の詳細（mDNS の経路。プロセスが終了する有力な原因）
- `MdnsLookup` は、リモートの `.local` 候補（ブラウザがデフォルトで送る mDNS 候補）を受け取った時点で遅延生成される（`ice.ts:1380-1383` の `addRemoteCandidate`、`ice.ts:296-298` の provisional checklist の `mdnsLookup`）。
- `multicast-dns` は bind 完了時（`'listening'`）に `update()` → `allInterfaces()` → `os.networkInterfaces()` を呼ぶ。このとき、`setInterval` が登録される前に throw するか、その後 5 秒ごとに throw する。どちらもイベントループのコールバックから直接投げられるので、**`uncaughtException` になる**。
- さらに `MdnsLookup` は `mdnsInstance` に `'error'` リスナーを登録していない。`multicast-dns` はソケットの `EACCES` / `EADDRINUSE` を `that.emit('error', err)` で再送出するため、制限環境で 5353/udp の bind や multicast が拒否されると、**リスナーのない `'error'` イベントでもプロセスが終了する**。同じ制限環境で起きやすい事象なので、本チケットで一緒に扱う。
- mDNS は「Linux/systemd 環境で mDNS 関連のセットアップから落ちる」という下流の報告と経路が一致する。A よりも B が根本原因である可能性が高い。

## 2. 実装すべき変更

### 2.1 インターフェース列挙を安全に包む（経路 A）
- `packages/ice/src/internal/hostInterfaces.ts` に、`os.networkInterfaces()` を try/catch で包む package-private ヘルパー（例: `readNetworkInterfaces(): { interfaces: NodeJS.Dict<os.NetworkInterfaceInfo[]>; error?: unknown }`）を追加する。`getHostInterfaceAddresses()` と `getAssignedInterfaceAddresses()` の両方をこのヘルパー経由にする。
  - 1 回の gathering で 2 回呼ぶのをやめ、1 回の列挙結果を共有する形にすると、2 つの経路で結果が食い違わず、失敗の判定も 1 か所で済む（任意だが推奨）。
- `Connection.gatherCandidates()`（`ice.ts`）の挙動
  - 列挙に失敗したら、`enumerated = []` / `assigned = []` として**処理を続ける**。`interfaceAddresses.udp4/udp6` の explicit 指定、`additionalHostAddresses`（wildcard bind）、STUN（wildcard ソケット経由）、TURN は列挙なしでも成立し得る。なお `additionalHostAddresses` は `assigned` が空のため wildcard bind になる。この挙動を明記する。
  - 失敗は `log()` に記録したうえで、利用者が受け取れる構造化エラーとして通知する（2.3）。
  - 例外が gathering の状態を壊さないようにする。少なくとも、throw されて `localCandidatesStart = true` / `localCandidatesEnd = false` のまま残る中途半端な状態を作らない（A-1 を解消する）。ヘルパーで例外を出さないようにすれば自然に解消するが、`resolveHostAddresses` や `candidatePromises` の同期部分が throw した場合の扱い（`localCandidatesStart` を戻すのか、gathering を終了扱いにするのか）も決めて、コメントに残す。

### 2.2 mDNS 経路の例外を止める（経路 B）
`multicast-dns` 内部の `setInterval` / `'listening'` ハンドラの throw は、ライブラリ外の try/catch では捕捉できない。次のいずれかで対処する（推奨は (a)+(c)）。
- (a) `MdnsLookup` のデフォルト factory で `mdns({ interface: ... })` を渡し、`multicast-dns` に `allInterfaces()` を呼ばせない。`opts.interface` があると `update()` はそれを使い、`defaultInterface()` も呼ばない。
  - 渡すインターフェースは werift 側の安全な列挙ヘルパーで得たもの（IPv4 の非 internal アドレスなど）にする。列挙に失敗したら **mDNS ソケットを作らず**、`.local` 候補の lookup を即座に reject する（`ice.ts:1380` の `catch { return; }` で候補が破棄されるだけになる）。
  - ただし `opts.interface` は bind アドレスとしても使われる（`socket.bind(port, opts.bind || opts.interface)`）。従来の `0.0.0.0` bind と挙動が変わらないように `bind: "0.0.0.0"` を併せて渡すなど、現行と同じ受信範囲を保つ。複数 NIC の membership を維持するかどうか（`interface` に配列を渡せる）も確認する。
- (b) `opts.multicast: false` + 自前で membership を管理する。変更量が大きいので (a) が使えない場合の代替とする。
- **採用: (b)+(c)**（追加要件 2.6 による）。(a) は作成時のインターフェース配列に固定されるため、後から増えたネットワークに join できない。また配列が `setMulticastInterface()` に渡るとエラーになる。`multicast-dns` の `update()` を差し替える方式（モンキーパッチ）も採らない。
- (c) `mdnsInstance.on("error", ...)` と `on("warning", ...)` を登録し、`log()` に記録する。`'error'` が来たら、その `MdnsLookup` の pending lookup を reject し、以降は lookup を失敗させる。`close()` / `destroy()` は冪等のまま保つ。
- いずれの方式でも、`MdnsLookup` の公開形状（`cache`, `mdnsInstance: MulticastDNS`, constructor の factory 引数）は維持する（PR #803 の互換性テストがある）。

### 2.3 失敗の通知（構造化エラー）— **方針確定**

#### 決定: W3C の既存通知は使わず、werift 拡張の `Event` を ICE 層 → `RTCIceTransport` → `RTCPeerConnection` の順で新設する

| 検討した案 | 採否 | 理由 |
|---|---|---|
| 既存の `icecandidateerror`（`RTCPeerConnection.onIceCandidateError` / `onicecandidateerror` / `addEventListener("icecandidateerror")`）に載せる | **不採用** | W3C では `url` が「失敗した STUN/TURN サーバーの URL」と定義されており、`errorCode` 701 も「サーバーに届かない」専用。STUN/TURN を設定していない構成ではそもそも URL が無い。さらに 701 は URL 単位の重複排除（`transport/ice.ts` の `unreachableUrls`、`peerConnection.ts` の `gatheringServerOutcomes` / `fireUnreachableServerErrors`）に組み込まれており、ここに混ぜると WPT が前提とする仕様挙動と既存利用者の URL 突き合わせが壊れる |
| `setLocalDescription()` / `gatherCandidates()` を reject させる | **不採用** | W3C で gathering は SLD の後に非同期で進むもので、SLD は gathering の失敗では reject しない。既存利用者のフローが壊れる |
| `connectionState` / `iceConnectionState` を `failed` にする | **不採用** | W3C の `failed` は ICE/DTLS 接続の失敗を表す。ローカル候補が 0 個でも、それを `failed` にする判断はチェックリストの結果に任せる（本チケットでは状態を強制しない） |
| `iceGatheringState` に `failed` を追加する | **不採用** | W3C の `RTCIceGatheringState` は `new` / `gathering` / `complete` のみ。列挙型を広げると既存の switch が壊れる |
| **werift 拡張の `Event` を新設する** | **採用** | 既存の拡張イベント（`RTCIceTransport.onIceCandidateError` / `onIceServerReached`、`IceConnection.onIceCandidateError?` / `onIceServerReached?`）と同じ形。W3C の名前空間（`on<event>` プロパティ / `addEventListener` の type）を消費しないので、将来の仕様追加とも衝突しない |

#### 公開する型とイベント（名称・ペイロードを確定）

ICE 層（`packages/ice`）。新規ファイル `src/gatheringError.ts` を `src/index.ts` から export する。

```ts
/**
 * Why a gathering reported an error (Connection.onGatheringError).
 * New reasons may be added in a minor release: handle unknown values.
 * @enum
 */
export const IceGatheringErrorReason = {
  /** os.networkInterfaces() threw: no host address was enumerated. */
  interfaceEnumerationFailed: "interface-enumeration-failed",
  /** The generation's gathering ended without any local candidate. */
  noCandidates: "no-candidates",
  /** gatherCandidates() failed with an unexpected exception. */
  gatheringFailed: "gathering-failed",
} as const;
/** @enum */
export type IceGatheringErrorReason =
  (typeof IceGatheringErrorReason)[keyof typeof IceGatheringErrorReason];

export type IceGatheringErrorInfo = {
  reason: IceGatheringErrorReason;
  /** Human-readable description, for logs. Not a stable identifier. */
  errorText: string;
  /** The original exception (e.g. the SystemError of os.networkInterfaces()), when there is one. */
  cause?: unknown;
  /** The generation whose gathering reported it. */
  generation: number;
};
```

- `Connection.onGatheringError = new Event<[IceGatheringErrorInfo]>()` を追加する。`IceConnection` interface（`iceBase.ts`）には、`onIceCandidateError?` と同じく **optional** で `readonly onGatheringError?: Event<[IceGatheringErrorInfo]>` を追加する。そうすれば独自に実装している `IceConnection` も壊れない。
- 発火規則（`emitCandidateError` と同じガードを使う）
  - `interface-enumeration-failed`: `gatherCandidates()` の列挙で失敗した時点で、世代ごとに 1 回だけ発火する。gathering はそのまま続ける（2.1）。
  - `no-candidates`: 世代の gathering が終わった時点（`localCandidatesEnd = true` にする直前。即時に終わる場合と background の query を待って終わる場合の両方）で、`localCandidates` にその世代の候補が 0 個なら発火する。原因（列挙失敗、relay-only で TURN 失敗など）は問わない。STUN/TURN の個別の失敗は従来どおり `onIceCandidateError` でも通知される。
  - `gathering-failed`: `gatherCandidates()` の中で想定外の例外が起きた場合に発火する。ガードを付けたうえで、`gatherCandidates()` 自体はこれまでどおり reject する。
  - 世代が置き換わった後や close 後（`stale()` / `closing.signal.aborted`）には発火しない。listener の throw は `log()` に記録して隔離し、gathering を止めない。
- `cause` はそのまま渡し、`errorText` は `error.message` を元に作る。credential を含むものは載せない。列挙の失敗ではもともと含まれない。

webrtc 層（`packages/webrtc`）

```ts
/** A gathering error of an ICE transport (werift extension, not W3C). */
export type IceGatheringErrorDetails = {
  reason: IceGatheringErrorReason; // ICE 層の型を re-export して使う
  errorText: string;
  cause?: unknown;
};
```

- `RTCIceGatherer`: `onGatheringError: (details: IceGatheringErrorDetails) => void = () => {}` を追加する。`connection.onGatheringError?.subscribe(...)` で受け、`generation` を落として転送する。listener の throw は既存の `onIceCandidateError` と同様に try/catch で隔離する。
  - `gather()` 内で `connection.gatherCandidates()` が reject した場合は、`IceConnection` に `onGatheringError` を持たない実装も考慮する。具体的には、ICE 層で未通知のときに限り `gathering-failed` を出し、`gatheringState` を `complete` まで進めて end-of-candidates を通知する。世代が置き換わった場合と close 済みの場合は既存の分岐に従う。
- `RTCIceTransport`: `readonly onGatheringError = new Event<[IceGatheringErrorDetails]>()` を追加する。`state === "closed"` なら転送しない。`close()` で `complete()` する（`onIceCandidateError` / `onIceServerReached` と同じ）。
- `RTCPeerConnection`: `readonly onIceGatheringError = new Event<[RTCIceGatheringErrorEvent]>({ onListenerError: (e) => log(...) })` を追加する。`on<event>` プロパティと `addEventListener` の type は**追加しない**（W3C 名前空間を消費しない）。
  ```ts
  export type RTCIceGatheringErrorEvent = IceGatheringErrorDetails & {
    /** The transport whose gathering reported it. */
    readonly iceTransport: RTCIceTransport;
  };
  ```
  - 購読場所は `peerConnection.ts:1103-1135` で `onIceCandidateError` を購読している箇所と同じにする。`isClosed` の場合と、rollback で破棄される transport（`negotiation.isPendingOnlyTransport(iceTransport.id)`）の場合は通知しない。
  - BUNDLE なしで transport が複数あると、列挙失敗は transport ごとに届く。そのため `iceTransport` を載せて **transport 単位で発火し、重複排除はしない**。PC 側での集約は、701 の集約と違って仕様上の要件が無く、過剰な状態管理になるため行わない。
- `secureTransportManager.gatherCandidates()` の `Promise.allSettled` と `peerConnection.ts:1727` の `.catch(log)` は残す（SLD を reject させない）。ただし rejected になった要素は `gathering-failed` として上記イベントで外部に出る（`RTCIceGatherer.gather()` 側で処理する）ので、「ログだけで消える」経路はなくなる。この判断をコメントに残す。
- upstream WPT 用の厳格な挙動は必要ない（新イベントは W3C 名前空間の外にある）。`packages/webrtc/tools/wpt-runner/*` は変更しない。

#### mDNS（経路 B）の失敗は本イベントに載せない
- mDNS はリモートの `.local` 候補の解決であり、ローカル候補の gathering ではない。失敗時は `log()` に記録し、該当するリモート候補を破棄する。これは現行の lookup タイムアウトと同じ扱いで、利用者に見える挙動は変わらない。通知が必要になったら別チケットで `reason` を追加する（`reason` は拡張可能と明記してあるので互換性は保てる）。

### 2.4 公開 API `nodeIpAddress()` / `getHostAddresses()`（経路 C）
- 公開 API の契約（列挙失敗時に throw するのか、`[]` を返すのか）を決める。ライブラリ内部からは使われていないため、**従来どおり throw（呼び出し側で catch 可能）**のままにし、JSDoc に `@throws` を明記する案を推奨する。挙動を変える場合は `changelog.md` に記載する。

### 2.5 ドキュメント
- 公開 API（新イベント、JSDoc）を変更したら `npm run doc` で `doc/` / `packages/*/doc` を再生成する。README / `changelog.md` に「インターフェース列挙が禁止された環境での挙動」を追記する。

### 2.6 追加要件: `multicast-dns` をモンキーパッチしない

- `packages/ice/src/dns/lookup.ts` で `multicast-dns` のインスタンスの `update()` を werift の関数に差し替えていた。この差し替え（モンキーパッチ）をやめる。代わりの方法を採るか、この部分の対応をやめるかのどちらかにする。
- 採用した方法: `multicast-dns` を公開オプション `multicast: false` で作る。ソケットは werift が作って `socket` オプションで渡しているので、multicast の設定は werift がそのソケットに対して Node.js の `dgram` API で行う。
  - `multicast: false` のとき、`multicast-dns` の `'listening'` ハンドラは `update()` を呼ばず、5 秒ごとの `setInterval` も登録しない。そのため `multicast-dns` は `os.networkInterfaces()` を一度も呼ばない。
  - werift はソケットの `'listening'` で `setMulticastTTL(255)` と `setMulticastLoopback(true)` を設定する。さらに、作成時の列挙結果で join し（各インターフェースの最初の IPv4 アドレス）、送信インターフェースを文字列で設定する。これは `multicast-dns` の既定と同じ値。
  - 5 秒ごとに werift が列挙し直し、増えたインターフェースに join する。列挙の失敗は `warning` になるだけで、次の周期に再試行する。interval はソケットの `'close'` で止める。
  - 作成時の列挙が失敗した場合は、従来どおりソケットを作らず、lookup を即座に reject する。
- 差し替えとの違い: interval はソケットの `'close'` で止める。Node.js はこれを次の tick に出すので、`close()` を呼んだ直後の同じ tick には interval がまだ残っている（5 秒の周期より十分早く止まる）。`destroy()` を包めば同時に止められるが、それもモンキーパッチになるので採らない。
- テスト（`packages/ice/tests/ice/mdns-enumeration.test.ts`）
  - 「multicast-dns never enumerates by itself: werift enumerates once at creation and once per 5 second update」を追加した。`multicast: false` を外すと、このテストを含む 4 件が落ちる。
  - 「an enumeration throwing on the 5 second membership update only warns, and close() leaves no timer」は、上記の違いに合わせて、`close()` の後に 1 tick 進めてから timer が 0 件であることを確かめるようにした。
- 実ソケットでの確認: 既定の `multicast-dns` で立てた応答側に対して、新しい `MdnsLookup` で `.local` 名を解決できた（multicast の join・loopback・問い合わせが動くことを確認。CI には入れていない）。

## 3. 技術的アプローチの要点

- **再現手段**: vitest で `vi.mock("node:os", ...)` を使い、`networkInterfaces` を差し替える。既存の例は `packages/ice/tests/ice/multi-nic.test.ts:14-22` と `candidate-error.test.ts:64-82`（`vi.hoisted` で `current` を切り替える方式）。`multicast-dns` は `require('os')` を使う CJS なので、`vi.mock("node:os")` が効かない可能性がある。mDNS 経路は `MdnsLookup` の factory 引数で fake を注入するか、`vi.spyOn(os, "networkInterfaces")` が CJS の `require("os")` にも効くかを確認する。`os` モジュールのオブジェクトは同一なので、spy は効く見込み。
- **uncaught の検出**: テスト内で `process.on("uncaughtException")` / `process.on("unhandledRejection")` を一時的に登録してカウントし、0 件であることを確認する。vitest もデフォルトで unhandled error を失敗として扱う。
- **mDNS の検証**: `'listening'` 後の `update()` と、5 秒後の interval 実行の両方で throw しないことを確認する。`vi.useFakeTimers()` か、factory 注入で interval を短縮して検証する。実ソケットを使う場合は 5353/udp の競合に注意する。
- **候補 0 個の判定**: `Connection.localCandidates` を見る。restart 時は再 advertise された候補も数える。
- 既存パターンを守る: manager 型の orchestration（webrtc 層）、カスタム `Event` クラスでの通知、broad catch-and-ignore をしない（catch したら必ず log とイベント通知を行う）。

## 4. 制約・注意点

- **根本原因は未確定**: 下流の現象は B（mDNS の interval / `'listening'` 内 throw、または未処理の `'error'`）が有力。ただし最小再現がないので、修正前の develop で fake により B のクラッシュを再現するテストを最初に書き、原因を確認する。A は「クラッシュしないがハングや偽の完了になる」問題として、別の不具合として直す。
- **#840 との分担**: TURN TCP / UDP ソケットエラー（#749）など、列挙以外の rejection 監査は #840 に任せ、重複実装しない。本チケットは「インターフェース列挙」と、同じ制限環境で起きる「mDNS ソケットの `'error'`」に限定する。
- **互換性**
  - `setLocalDescription` / `gatherCandidates()` の resolve / reject 挙動を変えるときは、`packages/webrtc` の既存テストと examples に影響が出ないか確認する。
  - `MdnsLookup` の公開形状を維持する。`additionalHostAddresses` は列挙失敗時に wildcard bind になる。
- **Windows 非対応**: Linux / macOS のみ考慮すればよい。
- **erasableSyntaxOnly**: `enum` は使わない。`reason` 種別は `as const` オブジェクト + 同名 union 型（`@enum`）で定義する。
- **ホスト依存のテスト**: このホストは multi-interface 環境で、HEAD でも失敗するテストがある（tcp active-only count、setConfiguration 系、modern_sdp）。回帰の判定は修正前後の差分で行う。
- **pattern kill 禁止**: 実ソケットを使う検証で残ったプロセスは PID で止める。
- テストは Arrange / Act / Assert で書き、Act / Assert の各ステップに日本語コメントを付ける。`os` の fake などの共通 Arrange は、テスト領域ごとに 1 つのユーティリティファイル（例: `packages/ice/tests/ice/interfaceEnumerationUtils.ts`）にまとめる。

## 5. 回帰テスト（追加するもの）

`packages/ice/tests/ice/`（ICE 層）
1. `os.networkInterfaces()` を throw させた状態で `Connection.gatherCandidates()` を呼ぶ。
   - STUN/TURN なし、explicit なし: プロセスが終了せず、uncaught が 0 件。gathering は終了し（`localCandidatesEnd === true`）、`Connection.onGatheringError` が `interface-enumeration-failed` → `no-candidates` の順にそれぞれ 1 回ずつ発火する（`cause` は stub が投げた例外、`generation` は現世代）。
   - `interfaceAddresses.udp4` の explicit 指定あり: explicit な host 候補が得られ、`interface-enumeration-failed` だけが発火し（`no-candidates` は発火しない）、gathering は完了する。
   - `additionalHostAddresses` あり: wildcard bind で host 候補が得られる。
   - STUN あり / TURN あり（既存のテスト用 STUN/TURN サーバー、または `candidateErrorUtils.ts` の fake）: srflx / relay が得られ、部分成功になる。
   - 2 回目の `gatherCandidates()` 呼び出しで、偽の `completed` にならない（A-1 の回帰）。
   - ICE restart 中に列挙が失敗した場合: 再 advertise された候補は残り、end-of-candidates に到達する。イベントは新世代の `generation` で発火し、`no-candidates` は発火しない。
   - `onGatheringError` の listener が throw しても gathering は完了する。close 後や世代が置き換わった後には発火しない。
   - 列挙が成功する通常の構成では `onGatheringError` が一度も発火しない（既存挙動の回帰確認）。
2. `getHostInterfaceAddresses()` と `getAssignedInterfaceAddresses()` を、それぞれ単独で throw させるケース（両方の経路を個別に検証する）。
3. mDNS: `.local` のリモート候補を追加した状態で
   - `os.networkInterfaces()` が `'listening'` 時に throw するケースと、interval 実行時に throw するケース: uncaught が 0 件で、lookup は reject され、候補は破棄される。
   - mDNS ソケットが `'error'`（`EACCES` / `EADDRINUSE`）を出すケース: uncaught が 0 件で、pending lookup が reject される。
   - `close()` 後に interval が残らない（タイマーリークがない）。

`packages/webrtc/tests/`（webrtc 層）
4. `os.networkInterfaces()` を throw させて `RTCPeerConnection` で offer → `setLocalDescription` を行う。
   - プロセスが終了せず、`iceGatheringState` が `"complete"` に到達し、`onIceCandidate(null)`（end-of-candidates）が来て、`RTCIceTransport.onGatheringError` と `RTCPeerConnection.onIceGatheringError`（`iceTransport` 付き）が通知される。
   - `icecandidateerror`（`onIceCandidateError` / `onicecandidateerror` / listener）は、列挙失敗では発火しない。STUN/TURN を設定して到達不能にした場合は、従来どおり 701 だけが発火する。
   - BUNDLE なしで transport が複数ある場合は、transport ごとに 1 回ずつ通知される。rollback で破棄される transport と close 後の場合は通知されない。
   - `connection.gatherCandidates()` を reject させる fake の `IceConnection`（`onGatheringError` を持たない実装）でも、`gathering-failed` が通知され、`gatheringState` が `complete` になる。
   - STUN/TURN ありとなしの両方で検証する。
5. リモートから `.local` 候補が届き、mDNS 列挙が失敗する場合に、`RTCPeerConnection` がクラッシュしない。

## 7. 受け入れテスト

- 目的（Before → After）: `os.networkInterfaces()` が throw する環境で、`RTCPeerConnection` は gathering が `gathering` のまま止まり、リモートの `.local` 候補でプロセスが終了していた。修正後は gathering が `complete` に達し、失敗が `onIceGatheringError` で届き、明示アドレスで接続してデータが届く。

  - (候補の取得元なし) / (iceInterfaceAddresses 指定) 2.1・2.3・6章: gathering は complete に達し、失敗が onIceGatheringError で届く
  - 2.1・2.2・6章: 列挙できなくても明示アドレスで接続してデータが届き、リモートの .local 候補でもプロセスは落ちない

### 作成中に見つけて直した問題

- `.local` 候補を `addIceCandidate()` で後から渡しても、werift の `setLocalDescription()` は gathering を待つので、offer には `a=end-of-candidates` が付いている。そのため受信側は候補を mDNS で解決せずに捨て、`MdnsLookup` は作られない。既存の `iceGatheringError.test.ts`「a remote .local candidate does not crash the peer connection」はこの形で、mDNS の修正を外しても通っていた（空振り）。共通ユーティリティに `withRemoteMdnsCandidate()`（offer の end-of-candidates の前に `.local` 候補を入れる）を足し、受け入れテストと既存テストの両方で使うようにした。修正後は、mDNS の修正を外すと両方とも落ちる。

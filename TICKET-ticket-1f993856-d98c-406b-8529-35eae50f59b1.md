## Summary

Large bursts of `RTCDataChannel.send()` can make werift's SCTP send/ACK path degrade badly enough to starve the Node.js event loop and miss ICE consent responses.

A downstream production workload in Georgetown MDI Alcove/PsiLink reproduced this with `werift@0.24.4`:

- ~17.5 MB burst: about 60 s without pacing, and the connection lost ICE consent around 28 s into the response send.
- ~35 MB burst: about 344 s without pacing.
- Adding application-level `bufferedAmount` backpressure (1 MiB high-water / 256 KiB low-water) reduced the same transfers to about 1 s and 2–3 s respectively, and 500k / 1M / 2M rows per side completed.

Downstream reference:
- https://github.com/georgetown-mdi/alcove/pull/1847

This is distinct from Alcove PR #1848, where application CPU work itself blocks the event loop. That case is not a werift bug.

## Likely cause in werift

The current SCTP implementation uses JavaScript arrays as FIFO queues and removes entries from the front with `Array.shift()` in hot paths.

In `packages/sctp/src/sctp.ts`, `receiveSackChunk()` repeatedly does:

```ts
while (
  this.sentQueue.length > 0 &&
  uint32Gte(this.lastSackedTsn, this.sentQueue[0].tsn)
) {
  const sChunk = this.sentQueue.shift()!;
  ...
}
```

The same implementation already contains a comment noting that repeated `shift()` calls can become very expensive in V8. PR #446 added "reset to [] when empty" as a mitigation:

- https://github.com/shinyoshiaki/werift-webrtc/pull/446

However, resetting after the queue becomes empty does not remove the cost of repeatedly shifting a large queue before it becomes empty.

There are other FIFO hot paths worth checking too:

- `SCTP.outboundQueue.shift()` in `transmitOnce()`
- `RTCSctpTransport.dataChannelQueue.shift()` in `dataChannelFlush()`

For large queued DataChannel workloads these can make dequeue cost grow with queue length and may produce effectively quadratic behavior across a burst.

## Why this should be fixed in werift

Applications should still use `bufferedAmount` / `bufferedamountlow` for backpressure, but a large legal DataChannel queue should not make ACK processing itself scale pathologically or block unrelated ICE/DTLS timers long enough to kill the connection.

The Alcove workaround is good application behavior, but it also masks a transport-level performance problem.

## Suggested fix

Replace front-shifted arrays in SCTP/DataChannel hot queues with a queue representation that has O(1) amortized dequeue, for example:

- an array plus a head index, compacted periodically, or
- a small internal deque/ring-buffer abstraction.

At minimum, investigate:

1. `sentQueue` cumulative ACK removal in `receiveSackChunk()`
2. `outboundQueue` dequeue in `transmitOnce()`
3. `dataChannelQueue` dequeue in `dataChannelFlush()`

The change must preserve TSN order, gap-ACK/loss handling, retransmission behavior, SCTP flow/congestion control, and `RTCDataChannel.bufferedAmount` semantics.

## Regression tests / acceptance criteria

Please add a stress/performance regression that:

- queues a large number of DataChannel messages/chunks;
- exercises repeated SACK processing;
- verifies transfer completion and ordering;
- verifies `bufferedAmount` returns to zero correctly;
- demonstrates scaling that is approximately linear rather than quadratic as queued message count increases;
- allows event-loop timers to continue running during the transfer (e.g. a short interval/heartbeat does not suffer multi-second starvation);
- ideally verifies an established PeerConnection does not lose ICE consent solely because SCTP queue processing monopolizes the event loop.

A lower-level SCTP benchmark can make the complexity regression deterministic, while an integration test can cover the DataChannel/ICE interaction.

## Related downstream observation

Alcove PR #1848 also showed that arbitrary synchronous CPU work can starve ICE consent handling. That is expected for a single-threaded Node.js event loop and should remain an application concern. This issue is specifically about avoiding avoidable event-loop starvation caused by werift's own queue data structures.

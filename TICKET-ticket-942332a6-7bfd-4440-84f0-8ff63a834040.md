## Summary

For TURN transactions with an integrity key, werift reparses every response using that key and drops the packet if MESSAGE-INTEGRITY validation fails or the attribute is absent.

That means an unsigned `401 (Unauthenticated)` / `438 (Stale Nonce)` error can be discarded before `TurnProtocol.requestWithRetry()` sees it.

With UDP TURN this causes the STUN transaction to retransmit until timeout instead of handling/failing the long-term-credential challenge immediately.

This is observable with Cloudflare TURN ChannelBind responses and can make ICE negotiation spend ~6.7 seconds per rejected peer address.

Downstream evidence:
- OpenHarness PR #1465: https://github.com/autonomous-ai/openharness/pull/1465

Their live Cloudflare test observed:
- ChannelBind to private peer addresses returns `401` without MESSAGE-INTEGRITY;
- werift logs `TURN STUN response failed MESSAGE-INTEGRITY check`;
- each peer is retried until timeout (~6.7s);
- four private peers serialized ahead of a usable pair exceed a 25s negotiation deadline;
- filtering impossible relay/private pairs downstream changed the same TURN-first negotiation from 0/3 to 3/3, ~0.9s ICE connection time.

## Current 0.25.1 behavior

`packages/ice/src/turn/protocol.ts::handleSTUNMessage()`:

```ts
const verified = transaction.integrityKey
  ? parseMessage(data, transaction.integrityKey)
  : message;
if (!verified) {
  log("TURN STUN response failed MESSAGE-INTEGRITY check");
  return;
}
transaction.responseReceived(verified, addr);
```

`Transaction.responseReceived()` also rejects any response without MESSAGE-INTEGRITY whenever `integrityKey` is set.

As a result, `requestWithRetry()` cannot inspect the unsigned 401/438:

```ts
const [errorCode] = error.response.getAttributeValue("ERROR-CODE");
...
if (((errorCode === 401 && realm) || (errorCode === 438 && this.realm)) && nonce) {
  ...
}
```

because the response can be discarded earlier at the protocol/transaction layer.

## RFC behavior

TURN uses the STUN long-term credential mechanism.

RFC 8489 §9.2.5 gives 401/438 special processing before the general response-integrity handling:

https://www.rfc-editor.org/rfc/rfc8489.html#section-9.2.5

In particular, a 401 can be a challenge that the client must inspect in order to decide whether/how to retry. RFC 8489 §9.2.4 also permits authentication-failure responses that do not carry MESSAGE-INTEGRITY.

For ordinary authenticated success/failure responses, integrity validation must remain strict. This issue should **not** weaken ICE consent or general STUN response authentication.

## Expected behavior

For TURN using long-term credentials:

- recognize a matching-transaction 401/438 error sufficiently to run the RFC 8489 long-term-credential state machine;
- validate required REALM/NONCE/security-feature fields before retrying;
- do not keep retransmitting an unsigned 401/438 until the full UDP transaction timeout;
- if retry is not valid (e.g. same credentials would be reused unchanged), surface the TURN error promptly rather than treating it as packet loss;
- continue requiring valid MESSAGE-INTEGRITY for normal authenticated responses.

Address/transaction-ID checks must remain strict.

## Important security note

Do **not** simply accept arbitrary unsigned error responses as authenticated responses.

The implementation should special-case only the long-term-credential challenge/error path defined by RFC 8489 §9.2.5, with the existing expected-address and transaction-ID checks intact.

## Suggested tests

1. Initial Allocate receives unsigned 401 with REALM/NONCE -> retry succeeds.
2. Authenticated TURN request receives valid signed success -> unchanged.
3. ChannelBind receives unsigned 401 -> transaction terminates/handles the challenge promptly rather than waiting through retransmissions.
4. 438 with fresh NONCE -> retry path works.
5. Unsigned non-401/438 error -> still rejected according to RFC rules.
6. Response from wrong address or transaction ID -> ignored.
7. Invalid signed MESSAGE-INTEGRITY -> rejected.
8. UDP and TCP/TLS TURN behavior follow the reliable/unreliable transport rules.

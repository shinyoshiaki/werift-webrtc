## Summary

With werift's default/max-compat transport layout, multiple m-lines can initially own separate DTLS/ICE transports. If the remote answer bundles those m-lines, werift reassigns later transceivers to the first bundled transport, but the replaced transports are no longer reachable from SecureTransportManager and are never closed.

This leaves their UDP sockets/ICE protocols alive after RTCPeerConnection.close().

Downstream reproduction:
https://github.com/ArnoldFamini21/livestream-studio/pull/300

## Current behavior

In RTCPeerConnection.setRemoteDescription(), when a remote BUNDLE answer is applied:

```ts
if (this.sdpManager.remoteIsBundled) {
  if (!bundleTransport) {
    bundleTransport = transceiver.dtlsTransport;
  } else {
    transceiver.setDtlsTransport(bundleTransport);
  }
}
```

For the second and later m-lines, `setDtlsTransport(bundleTransport)` replaces the transceiver's previous DTLS transport.

However, `SecureTransportManager.dtlsTransports` is computed dynamically only from the *current* transports referenced by transceivers and SCTP:

```ts
const transports = [
  ...this.transceiverManager.getTransceivers().map((t) => t?.dtlsTransport),
  this.sctpManager.sctpTransport?.dtlsTransport,
]
```

So after rebinding, the old transport disappears from `dtlsTransports`.

`SecureTransportManager.close()` later stops only the transports still returned by that getter:

```ts
await Promise.allSettled([...this.dtlsTransports.map((t) => t.stop())]);
```

The replaced transport therefore has no owner that closes it.

## Downstream reproduction

livestream-studio reproduced this deterministically in its SFU tests:

- default/max-compat creates separate ICE transports for audio and video;
- browser answer bundles them;
- one transport becomes orphaned;
- `pc.close()` leaves one UDP socket alive per audio+video subscriber;
- the test process only exited previously because it used `--test-force-exit`.

Their downstream workaround is to create the PeerConnection with `bundlePolicy: "max-bundle"`, avoiding the extra transport from the start.

PR:
https://github.com/ArnoldFamini21/livestream-studio/pull/300

## Expected behavior

When BUNDLE negotiation causes multiple m-lines to converge on one transport, any superseded DTLS/ICE transport must be explicitly stopped or otherwise retained in an owned transport registry so that `RTCPeerConnection.close()` closes it.

No UDP socket / ICE protocol should remain active after closing the PeerConnection.

## Suggested approaches

One of:

1. when rebinding a transceiver/SCTP transport to `bundleTransport`, detect that the old transport is no longer referenced and stop it;
2. make SecureTransportManager own every transport it creates, independent of current transceiver references, and close all of them;
3. maintain an explicit retired/orphan transport set and drain it safely once BUNDLE is applied.

The ownership model should also avoid accidentally stopping a transport still referenced by another m-line.

## Tests

Suggested regression test:

- create PeerConnection with default/max-compat;
- add audio + video so two transports are created;
- apply a BUNDLE answer that uses the first transport for both;
- verify only the bundled transport remains active;
- call `pc.close()`;
- assert all created DTLS/ICE transports are closed and no UDP handles remain.

Also cover BUNDLE involving SCTP/datachannel plus media.

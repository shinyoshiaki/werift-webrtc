## Summary

With werift's default/max-compat transport layout, multiple m-lines can initially own separate DTLS/ICE transports. If the remote answer bundles those m-lines, werift reassigns later transceivers to the first bundled transport, but the replaced transports are no longer reachable from SecureTransportManager and are never closed.

This leaves their UDP sockets/ICE protocols alive after RTCPeerConnection.close().

Downstream reproduction:
https://github.com/ArnoldFamini21/livestream-studio/pull/300

## Current behavior

In RTCPeerConnection.setRemoteDescription(), when a remote BUNDLE answer is applied:

```ts
if (this.sdpManager.remoteIsBundled) {
  if (!bundleTransport) {
    bundleTransport = transceiver.dtlsTransport;
  } else {
    transceiver.setDtlsTransport(bundleTransport);
  }
}
```

For the second and later m-lines, `setDtlsTransport(bundleTransport)` replaces the transceiver's previous DTLS transport.

However, `SecureTransportManager.dtlsTransports` is computed dynamically only from the *current* transports referenced by transceivers and SCTP:

```ts
const transports = [
  ...this.transceiverManager.getTransceivers().map((t) => t?.dtlsTransport),
  this.sctpManager.sctpTransport?.dtlsTransport,
]
```

So after rebinding, the old transport disappears from `dtlsTransports`.

`SecureTransportManager.close()` later stops only the transports still returned by that getter:

```ts
await Promise.allSettled([...this.dtlsTransports.map((t) => t.stop())]);
```

The replaced transport therefore has no owner that closes it.

## Downstream reproduction

livestream-studio reproduced this deterministically in its SFU tests:

- default/max-compat creates separate ICE transports for audio and video;
- browser answer bundles them;
- one transport becomes orphaned;
- `pc.close()` leaves one UDP socket alive per audio+video subscriber;
- the test process only exited previously because it used `--test-force-exit`.

Their downstream workaround is to create the PeerConnection with `bundlePolicy: "max-bundle"`, avoiding the extra transport from the start.

PR:
https://github.com/ArnoldFamini21/livestream-studio/pull/300

## Expected behavior

When BUNDLE negotiation causes multiple m-lines to converge on one transport, any superseded DTLS/ICE transport must be explicitly stopped or otherwise retained in an owned transport registry so that `RTCPeerConnection.close()` closes it.

No UDP socket / ICE protocol should remain active after closing the PeerConnection.

## Suggested approaches

One of:

1. when rebinding a transceiver/SCTP transport to `bundleTransport`, detect that the old transport is no longer referenced and stop it;
2. make SecureTransportManager own every transport it creates, independent of current transceiver references, and close all of them;
3. maintain an explicit retired/orphan transport set and drain it safely once BUNDLE is applied.

The ownership model should also avoid accidentally stopping a transport still referenced by another m-line.

## Tests

Suggested regression test:

- create PeerConnection with default/max-compat;
- add audio + video so two transports are created;
- apply a BUNDLE answer that uses the first transport for both;
- verify only the bundled transport remains active;
- call `pc.close()`;
- assert all created DTLS/ICE transports are closed and no UDP handles remain.

Also cover BUNDLE involving SCTP/datachannel plus media.

# 詳細化 (コードベース調査結果)

> 調査時点: `main` 系 HEAD `00796c81`。チケット本文の「Current behavior」のコード片は古い実装のもので、現在の実装は BUNDLE group ごとの所有権解決に置き換わっている。ただし **リーク自体は現行コードでも再現する構造のまま** である (下記参照)。

## 1. 目的と背景

- werift の既定 `bundlePolicy` は `"max-compat"` (`"balanced"` も `max-compat` に正規化、`packages/webrtc/src/peerConnection.ts:85` 付近の注記)。この場合 `findOrCreateTransport()` (`peerConnection.ts:653`) は remote が BUNDLE 済みでない限り m-line ごとに新しい `RTCDtlsTransport` (= 独立した `RTCIceGatherer` / ICE `Connection` / UDP socket) を作る。
- remote description が BUNDLE で m-line を 1 つの transport に寄せると、2 本目以降の transport は transceiver / SCTP から参照されなくなる。
- `SecureTransportManager` は transport を **保持しておらず**、`dtlsTransports` / `allDtlsTransports` を transceiver・SCTP の現在の参照から動的に計算している (`packages/webrtc/src/secureTransportManager.ts` の getter)。したがって付け替えで外れた transport はどこからも到達できず、`RTCPeerConnection.close()` → `SecureTransportManager.close()` でも `stop()` されない。
- 結果として UDP socket / ICE protocol (TURN を使っていれば allocation refresh timer も) が残り、Node プロセスが終了しない。downstream (livestream-studio PR #300) では `--test-force-exit` でしか終了できず、`bundlePolicy: "max-bundle"` で回避している。
- 目的: BUNDLE によって不要になった transport を werift 側が確実に所有・停止し、`pc.close()` 後に UDP handle が残らないようにする。

## 2. 現行コードの該当箇所と再現経路

### 2.1 transport 付け替え箇所

`RTCPeerConnection.setRemoteDescription()` の「transport ownership」ブロック (`packages/webrtc/src/peerConnection.ts` 約 1280–1345 行):

```ts
for (const group of bundleGroups) {
  ...
  let shared = members.map((e) => ownerOf(e)!.dtlsTransport).find(...);
  if (!shared) shared = this.createDtlsTransport({ inheritCredentials: false });
  ...
  for (const entry of members) {
    const owner = ownerOf(entry)!;
    if (owner.dtlsTransport !== shared) {
      owner.setDtlsTransport(shared);   // ← 旧 transport はここで参照を失う
    }
  }
}
if (isRemoteOffer) {
  // group 外 m-line で live でない / 他と共有している transport を新規作成で置換
  owner.setDtlsTransport(this.createDtlsTransport({ inheritCredentials: false }));
}
```

- `RTCRtpTransceiver.setDtlsTransport()` (`media/rtpTransceiver.ts:142`) は receiver/sender に差し替えるだけ。
- `RTCSctpTransport.setDtlsTransport()` (`transport/sctp.ts:59`) は旧 transport の event を dispose して SCTP を作り直すだけ。
- どちらも旧 transport を `stop()` しない。

### 2.2 既存のクリーンアップが拾わない理由

- `closeIdleTransports()` (`peerConnection.ts` 約 793 行) は **既定では stopped transceiver の transport のみ** を候補にしている。answer 適用後 (`remoteSdp.type === "answer"` ブロック) と `settleStoppingTransceivers()` で呼ばれるが、BUNDLE 付け替えで外れた transport は live transceiver が参照していた transport なので候補に入らない。
- `SecureTransportManager.close()` は `allDtlsTransports` (現在の参照から計算) だけを `stop()` する。

### 2.3 リークする具体シナリオ

| # | シナリオ | 旧 transport が作られる経路 | 付け替え契機 |
|---|---|---|---|
| A | offerer (既定 max-compat): `addTransceiver("audio")` + `addTransceiver("video")` → `createOffer`/`setLocalDescription` → BUNDLE answer | `findOrCreateTransport()` が m-line ごとに作成 | remote answer の group 処理 |
| B | A に `createDataChannel()` を加えたもの (SCTP + media) | `createSctpTransport()` 経由の `findOrCreateTransport()` | 同上 (`RTCSctpTransport.setDtlsTransport`) |
| C | answerer: remote offer 受信 **前** に app が `addTransceiver` / `createDataChannel` した後、BUNDLE offer を受信 | 同上 | remote offer の group 処理 |
| D | remote pranswer で BUNDLE → 最終 answer | 同上 | pranswer 適用時点で付け替え済み |

- A/B は SDP 交換時点で `setLocalDescription` により gather 済み (UDP bind 済み) のため、確実に socket が残る。
- C は gather 前に孤立する場合もあるが、`RTCIceGatherer` / `Connection` のリソースは残るので同様に停止対象とすべき。
- `connect()` は `this.dtlsTransports` しか start しないため、孤立 transport は ICE check こそ行わないが、gather 済み socket・TURN allocation は生きたまま。

## 3. 実装すべき変更

### 3.1 (必須) SecureTransportManager による transport の所有 (approach 2)

- `SecureTransportManager.createTransport()` で生成した全 `RTCDtlsTransport` を private な `Set` (例: `ownedTransports`) に登録する。
- `close()` は「現在参照されている transport」ではなく **登録済み全 transport** を `stop()` する (`allDtlsTransports` との和集合でもよいが、生成元は全て `createTransport()` なので登録集合で足りるはず。外部注入経路がないか実装時に確認)。
- transport が `closed` になったら集合から外す (`stop()` 後に削除、または `onStateChange` で削除) ことで、長寿命 PC で再ネゴのたびに集合が増え続けないようにする (memleak 観点)。
- 公開 getter `dtlsTransports` / `iceTransports` の意味 (live な m-line が使う transport) は **変えない**。`iceGatheringState` / `iceConnectionState` の集計、`getStats()`、`restartIce()`、`gatherCandidates()`、`setLocalRole()` に孤立 transport を混ぜないこと。

### 3.2 (必須) BUNDLE 付け替え時の即時退役 (approach 1 / 3)

- `setRemoteDescription()` の ownership ブロックで、`setDtlsTransport()` により置き換えられた旧 transport を `replaced` として収集する (group 処理・group 外の新規作成処理の両方)。
- 付け替え完了後、`replaced` を既存の `closeIdleTransports(candidates)` に渡して停止する。`closeIdleTransports()` は「live な `dtlsTransports` に含まれないものだけ stop」するので、**他 m-line (SCTP 含む) がまだ参照している transport を誤って止めない** という要件を既に満たしている。
- 停止タイミング:
  - remote `answer` (最終): 付け替え直後に停止してよい。
  - remote `pranswer`: JSEP 上 pranswer は暫定なので、即時停止せず「退役予定」として保持し、最終 answer 適用時に drain するのが安全。ただし現行実装は pranswer 時点で付け替え済みで、最終 answer で旧 transport に戻す経路は無い (`assertAnswerKeepsSharedTransports()` が共有 transport の分割を拒否する) ため、即時停止でも機能的な後退はない可能性が高い。実装時にどちらにするか判断し、テストで固定すること。いずれの場合も 3.1 により `close()` で必ず停止される。
  - remote `offer`: `rollbackRemoteOffer()` (`transceiverManager.ts:887`) は mid 等を戻すが **transport は復元しない**。よって offer 適用時に旧 transport を停止しても rollback で必要になることはない。ただし rollback 後に transceiver が共有 transport を使い続けることになる点は既存挙動のまま (本チケットのスコープ外) であることを確認しておく。
- 停止は `transport.stop().catch(log)` の既存パターン (closeIdleTransports) を踏襲し、broad catch-and-ignore にしない。

### 3.3 副作用の確認ポイント

- 旧 transport の `iceTransport.onIceCandidate` は `resolveLocalCandidateOwner()` が owner なしで無視するので、停止前に遅延候補が来ても `icecandidate` は発火しない (既存動作)。テストでも確認するとよい。
- 旧 transport の `iceTransport.onStateChange` → `updateIceConnectionState()` / gatherer の `onGatheringStateChange` → `updateIceGatheringState()` が停止時に呼ばれるが、集計対象 (`iceTransports`) には含まれないので PC の状態は変化しないはず。`iceconnectionstatechange` が余計に発火しないことを確認する。
- `RTCDtlsTransport.stop()` (`transport/dtls.ts:504`) → `RTCIceTransport.stop()` (`transport/ice.ts:257`) → ICE `Connection.close()` (`packages/ice/src/ice.ts:1058`) で protocol (UDP/TCP/TURN) が close される。ice パッケージ側の close 漏れが見つかった場合は ice パッケージで根本修正する。
- `createDtlsTransport()` で張っている `onRtp` / `onRtcp` / `onNegotiationNeeded` 購読は transport 停止で完了されるか確認 (Event の `complete()` 有無)。必要なら停止時に購読解除する。

## 5. 制約・注意点

- **live な共有 transport を止めない**: 停止判定は必ず「付け替え完了後の live 参照 (`this.dtlsTransports`)」に対して行う。SCTP の transport も live 参照に含まれる点に注意。
- **既存の公開挙動を変えない**: `pc.dtlsTransports` / `iceTransports` / `iceGatheringState` / `iceConnectionState` / `getStats()` の結果に退役 transport を含めない。
- **ICE credentials**: `createTransport({ inheritCredentials })` の既存 credential 継承ロジック (`iceTransports.find(...)` で既存 credential を引き継ぐ) に退役 transport が混ざらないよう、`iceTransports` は live のみのままにする。
- **rollback / re-offer**: remote offer の rollback (`rollbackRemoteOffer()` + `closeIdleTransports(transportsBeforeRollback)`) や re-negotiation 時の既存 transport 再利用を壊さないこと。
- **非同期停止**: `stop()` は非同期。`close()` は所有集合の stop を `Promise.allSettled` で待つ現行形を維持し、`sctpManager.close()` (SCTP ABORT 送信) → `secureManager.close()` の順序も維持する。
- **WPT**: `tools/wpt-runner` に厳格化を漏らさない。挙動変更は `src` 側の正しい資源解放のみ。
- **downstream workaround**: 修正後も `bundlePolicy: "max-bundle"` 利用者に影響がないこと (max-bundle では最初から transport が 1 つなので付け替えは発生しない)。
- `bundlePolicy: "disable"` では BUNDLE group を無視するため付け替えは起きない (`bundleGroups = []`)。挙動不変であることを確認。
- 必要に応じて `packages/webrtc/README` 等の transport ライフサイクルに関する記述があれば更新 (公開 API 変更は想定しない)。

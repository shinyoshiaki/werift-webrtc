## Summary

A PeerConnection that is initially established without an SCTP `m=application` section cannot reliably add DataChannel/SCTP later by SDP renegotiation.

This was reproduced downstream in RelayMessenger/Relay-SDK PR #440 with `werift 0.24.4`: audio establishes first, then a later SFU offer adds the `m=application ... webrtc-datachannel` section. The SDP renegotiation succeeds and the existing ICE/DTLS transport remains connected, but the SCTP association is never started, so the negotiated DataChannel stays `connecting`.

The same lifecycle gap is still visible in the current werift PeerConnection implementation.

Downstream reference:
https://github.com/RelayMessenger/Relay-SDK/pull/440

## Why this is a werift bug

Adding an SCTP/DataChannel media section through a later offer/answer exchange is a valid WebRTC/JSEP use case. RFC 8841 defines the SDP `m=application ... UDP/DTLS/SCTP webrtc-datachannel` association, and RFC 8831 / RFC 8864 allow data channels to be negotiated over that SCTP association.

The problem is caused by transport startup being tied to the *first* ICE/DTLS startup rather than independently ensuring the SCTP layer after each accepted negotiation.

Current `RTCPeerConnection.connect()` effectively does:

```ts
if (iceTransport.state === "connected") {
  return;
}

await iceTransport.start();

if (dtlsTransport.state === "connected") {
  return;
}

await dtlsTransport.start();

if (
  this.sctpTransport &&
  this.sctpTransport.dtlsTransport.id === dtlsTransport.id
) {
  await this.sctpManager.connectSctp();
}
```

On a later renegotiation:

1. the media-only PeerConnection already has ICE/DTLS connected;
2. the new remote SDP configures the SCTP transport and remote SCTP port;
3. `connect()` runs after the new answer is applied;
4. it returns early because ICE (or DTLS) is already connected;
5. `sctpManager.connectSctp()` is never reached.

Result: the application m-line is accepted, but the corresponding SCTP association is not established.

## Additional lifecycle hazard: passive SCTP can already be connected while `started === false`

The downstream reproduction also exposed a second condition that the fix must handle.

An SCTP association can be established because the remote peer initiated the SCTP handshake. In that case werift can reach:

```ts
sctp.state === "connected"
sctp.started === false
```

Calling `connectSctp()` / `SCTP.start()` after this is unsafe:

- `start()` changes the public SCTP connection state back to `connecting`;
- if the local side is the SCTP initiator, it may send a second INIT and move the association back toward COOKIE_WAIT;
- if it is passive, `connectSctp()` can wait for a new `connected` event that will never occur.

Therefore the fix must make SCTP startup idempotent and must treat an already-connected association as complete even if `started` is false.

## Proposed fix

### 1. Refactor `RTCPeerConnection.connect()` to ensure each transport layer independently

Do not return from the per-DTLS-transport task merely because ICE or DTLS is already connected.

Conceptually:

```ts
if (iceTransport.state is not already usable) {
  await iceTransport.start();
}

if (dtlsTransport.state !== "connected") {
  await dtlsTransport.start();
}

if (
  this.sctpTransport &&
  this.sctpTransport.dtlsTransport.id === dtlsTransport.id
) {
  await this.sctpManager.connectSctp();
}
```

The important invariant is:

> After an accepted negotiation, if an SCTP media section is bound to an already-usable DTLS transport, werift must ensure the SCTP association is started even when ICE and DTLS were established by an earlier negotiation.

Keep the existing ICE/DTLS start behavior for first negotiation and ICE restart; only remove the control-flow coupling that skips later layers.

### 2. Make `SctpTransportManager.connectSctp()` idempotent and passive-safe

Before calling `RTCSctpTransport.start()`, check the actual SCTP connection state.

Suggested behavior:

```ts
async connectSctp() {
  if (!this.sctpTransport || !this.sctpRemotePort) return;

  const sctp = this.sctpTransport.sctp;

  if (sctp.state === "connected") {
    return;
  }

  // Subscribe before start so a fast transition cannot be missed.
  const connected = sctp.stateChanged.connected.asPromise();

  await this.sctpTransport.start(this.sctpRemotePort);

  if (sctp.state !== "connected") {
    await connected;
  }
}
```

The exact implementation can differ, but it should guarantee:

- already-connected passive association: no restart;
- already-started but still handshaking association: wait, do not send a duplicate INIT;
- not-started association: start once;
- repeated renegotiation: no SCTP restart once established.

If needed, add an explicit `ensureStarted()` / `ensureConnected()` method rather than overloading `start()` semantics.

### 3. Do not trigger SCTP from `createDataChannel()` as the primary fix

The SCTP association belongs to the negotiated `m=application` section, not to the timing of a particular DataChannel object creation.

For out-of-band / `negotiated: true` channels, the remote peer may already have initiated SCTP before the application creates its local `RTCDataChannel`. Starting SCTP only from `createDataChannel()` therefore creates ordering races and risks restarting an association that is already connected.

The correct trigger is successful application-m-line negotiation plus an available DTLS transport.

## Regression tests

Please add PeerConnection-level tests, not only `RTCSctpTransport` unit tests.

### A. Remote re-offer adds SCTP after media-only connection

1. Create two `RTCPeerConnection` instances.
2. Establish an audio-only (or video-only) connection.
3. Assert ICE/DTLS are connected and no SCTP association exists yet.
4. On peer B create a DataChannel and generate a re-offer that adds `m=application`.
5. Apply the re-offer/answer without recreating either PeerConnection.
6. Assert SCTP reaches connected on both sides.
7. Assert the DataChannel opens and messages work in both directions.

This is the downstream Relay-SDK failure mode.

### B. Local re-offer adds SCTP

Repeat with the opposite peer initiating the DataChannel / re-offer.

### C. Negotiated/out-of-band DataChannel

Use:

```ts
createDataChannel("late", {
  negotiated: true,
  id: 2 or 3,
  ordered: false,
  maxRetransmits: 0,
});
```

and verify the channel opens after late SCTP negotiation.

### D. Passive association is already connected before local ensure-start

Exercise the case where the remote endpoint sends SCTP INIT first and the local SCTP reaches `connected` while `started === false`.

Then run the normal post-negotiation startup path and verify:

- it remains connected;
- no second INIT is emitted;
- association state does not regress to COOKIE_WAIT / connecting;
- bidirectional messages still work.

### E. Repeated negotiation is idempotent

Apply another offer/answer with the same application section and verify the established SCTP association is not restarted.

### F. Existing initial-DataChannel path remains green

A DataChannel present in the initial offer/answer must behave exactly as before.

## Acceptance criteria

- [ ] A PeerConnection initially established without SCTP can add `m=application` in a later renegotiation without recreating the PeerConnection.
- [ ] The SCTP association starts when its bound DTLS transport is already connected.
- [ ] A remotely initiated / already-connected SCTP association is never restarted.
- [ ] `connectSctp()` is safe to call repeatedly.
- [ ] Negotiated and in-band DataChannels open and exchange data after late SCTP negotiation.
- [ ] Both offerer/answerer directions are tested.
- [ ] Existing first-negotiation DataChannel behavior remains unchanged.

## Notes

Relay-SDK currently works around this by reaching into the private `sctpManager.connectSctp()` after renegotiation, while guarding against the already-connected passive-association case. That workaround should not be necessary for a standards-valid renegotiation flow.

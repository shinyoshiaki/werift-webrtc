# Changelog

## Unreleased

### 🚀 Features

- **DTLS alerts are sent and received** (`werift-dtls`, `werift`, #811, RFC 5246 §7.2).
  - `werift-dtls`: `DtlsSocket.sendAlert(level, description, { timeoutMs })` sends an alert protected with the current epoch (encrypted after ChangeCipherSpec, plaintext before it); it never rejects, and nothing is sent after close_notify / a fatal alert (sending one also stops the handshake flights, so nothing is retransmitted after it). Sending a fatal alert ends the connection on this side as well: `onError` fires with a local `DtlsAlertError` and the transport is closed once the alert was sent, so an `RTCDtlsTransport` that sends one becomes `failed`. `DtlsSocket.close({ notify: true, timeoutMs })` sends close_notify and closes the transport once it was sent (at most `DtlsSocket.AlertSendTimeoutMs`, 200 ms); `close()` without options keeps closing immediately without an alert, and now returns a promise. `onAlert` fires for every received alert. A received close_notify fires `onClose` and is answered with close_notify; a fatal alert fires `onError` with the new `DtlsAlertError` (`level`, `description`, `alertDescName`, `source: "remote" | "local"`) and closes the transport. Other warnings only fire `onAlert`. The connection is ended (close_notify answered, transport closed) before the listeners run, and an exception thrown by an `onAlert` / `onClose` / `onError` / `onData` / `onConnect` listener is logged instead of interrupting it. The new option `verifyRemoteCertificate(certificate)` checks the peer certificate during the handshake and aborts with a fatal `bad_certificate` before this side's Finished. New exports: `AlertLevel`, `AlertDesc`, `alertDescName`, `ContentType`, `DtlsAlertError`, `DtlsAlert`, `DtlsSocketOptions`, `createAlertRecord`, `classifyAlert`.
  - `werift`: `RTCDtlsTransport.stop()` (and so `RTCPeerConnection.close()`) sends close_notify before ICE stops, waiting at most `DTLS_ALERT_SEND_TIMEOUT_MS` (100 ms); the local state still becomes `closed` synchronously without statechange. ICE and the DTLS socket always stop and `onStopped` always fires, even if a state listener throws: an exception thrown by an `RTCDtlsTransport` listener (`onStateChange`, `onstatechange`, `statechange`, `onerror`, `error`, `onStopped`) is logged and no longer interrupts stop(), start() or the failure handling. The peer's DTLS transport becomes `closed` (with statechange), its SCTP transport `closed` and its data channels close right away instead of after ICE consent expiry. A fingerprint mismatch is detected during the handshake and sent to the peer as `bad_certificate`, so both DTLS transports and both `connectionState`s become `failed`. A close_notify from the peer makes the DTLS transport `closed` (never `failed`) also during the handshake; a DTLS transport in use that ends `closed` or `failed` before it was established makes `connectionState` `failed` instead of leaving it `connecting` (WPT `protocol/dtls-close.html`, `protocol/dtls-fingerprint-validation.html` and three subtests of `RTCDtlsTransport-state.html` are now allowlisted).
  - `werift`: `RTCDtlsTransport` fires `error` (`onerror` / `addEventListener("error")`) once with an `RTCError` when it becomes `failed` (W3C webrtc-pc `RTCErrorDetailType`): `errorDetail: "fingerprint-failure"` when the remote certificate matches none of the remote fingerprints (`receivedAlert` / `sentAlert` are null, which the spec defines only for `"dtls-failure"`; the peer still receives `bad_certificate` and reports `"dtls-failure"` with `receivedAlert: 42`), otherwise `errorDetail: "dtls-failure"` with the fatal alert received (`receivedAlert`) or sent (`sentAlert`). A close_notify does not fire it. `RTCSctpTransport.state` (`"connecting" | "connected" | "closed"`), `onstatechange` / `addEventListener("statechange")` and `onStateChange` are new.
  - `werift`: `RTCPeerConnection.close()` makes `connectionState`, every DTLS transport and the SCTP transport `closed` synchronously, before its first await and without statechange (W3C webrtc-pc `close()`; `connectionState` used to change only after the SCTP ABORT was sent and the DTLS transports stayed `connected` until then). The wire order is unchanged: SCTP ABORT, close_notify, then ICE stops. `connectionState` `closed` is final, and `connected` is reported only while no ICE / DTLS transport of a live m-line is `failed`: a transport that connects while another one stays failed (several transports, a renegotiation adding one) leaves `connectionState` `failed`. An exception thrown by an `RTCSctpTransport` state listener (`onStateChange`, `onstatechange`, `statechange`) or a `connectionState` listener (`connectionStateChange`, `onconnectionstatechange`, `connectionstatechange`) is logged and no longer interrupts `close()`, the SCTP ABORT or the propagation of a DTLS failure to SCTP and the data channels. These events (and `RTCDtlsTransport.onStateChange` / `onStopped`, the DOM-style `error` / `statechange` / `connectionstatechange` events of `addEventListener`, the `werift-dtls` socket events) isolate each subscriber, so a throwing subscriber also no longer skips the subscribers registered after it, e.g. werift's own SCTP subscriber when the application subscribed to the DTLS transport first.
  - `werift-common`: `Event.executeIsolated(onError, ...args)` runs every synchronous subscriber even if one throws, passing each exception to `onError`; `execute()` is unchanged.

### 🐛 Bug Fixes

- **A fatal DTLS alert is no longer swallowed** (`werift-dtls`, `werift`). It used to be thrown inside the receive loop and only logged, so the transport stayed `connected`. Every other alert (including warnings) used to close the connection like close_notify; now only close_notify closes it. A DTLS transport that receives a fatal alert, also after the connection was established, becomes `failed`, and so does `connectionState` while the transport is in use (a peer close_notify does not change `connectionState`). `failed` / `closed` are final: later alerts do not change them, and SRTP / application data arriving afterwards is dropped. `RTCSctpTransport` also closes when its DTLS transport fails.
- **The epoch-1 record sequence number starts at 0** (`werift-dtls`, RFC 6347 §4.1). The Finished record was sent with the sequence number following the epoch-0 records, and the counter was then reset, so a later record of the same epoch reused that number and a browser dropped it as a replay. Among the affected records was werift's close_notify after an SCTP ABORT, which Chrome ignored.
- **Encrypted alerts are recognized by the record epoch** (`werift-dtls`) instead of guessing from the description byte, so a ciphertext whose first bytes look like a known alert is no longer misread; an alert record that fails to decrypt is discarded (RFC 6347 §4.1.2.1). A record with an unknown content type is discarded instead of closing the connection.
- **RTX with RID-based simulcast is received.** An RTX packet carrying `repaired-rtp-stream-id` (Chrome sends simulcast without `a=ssrc` / `a=ssrc-group:FID`) is now delivered restored (media SSRC, sequence number and payload type, `{ type: "retransmission" }`) on the RID's track; it used to be dropped. The first packet with `rtp-stream-id` / `repaired-rtp-stream-id` registers its SSRC, so later packets without these extensions keep their route. Without SDP pairing, an RTX packet is restored to its RID's current media SSRC only when it fills a hole NACK detected there: NACK and RTX verification share one ledger of holes per media SSRC, so a packet is verifiable for as long as NACK asks for it (and after NACK's retries, until the ledger's bound of 1024 holes per SSRC; a hole leaves the ledger only together with its NACK request), and its timestamp must lie within those of the packets received around the gap, in either order and widened by 1 s of media clock (B-frames). A RID has one media SSRC at a time: a change without renegotiation resets the stream, ending the old SSRC's NACK requests and holes and dropping late packets of the old media SSRC and of the RTX SSRCs that repaired it. RTX that fits no hole (a duplicate of a received packet, a number NACK never asked for, another stream), has an unknown RID, or has no `apt` codec is dropped instead of being delivered broken. Streams whose sequence numbers and timestamps start at the same values (against RFC 3550 section 5.1) cannot be told apart. The packet-driven state is bounded while the receiver runs: per RID 1 media SSRC, 8 RTX SSRCs and 8 retired SSRCs, and NACK state for at most 16 media SSRCs per receiver.
- **NACK is tracked per media SSRC.** Simulcast layers no longer compare each other's sequence numbers (false losses) or send a NACK to the wrong SSRC. `receiver.onPacketLost` still fires once per sent NACK, and an idle NACK timer now stops when no loss remains. Sequence numbers are compared across the 16-bit wrap, so a late packet from before a wrap no longer opens a false gap of tens of thousands of numbers.
- **The track codec of a RID receiver and of `resyncCodecs` skips RTX / RED**, so a description that lists `video/rtx` first no longer gives the remote track the RTX codec.

## v0.27.0

This release collects everything merged since v0.26.0.

### ⚠️ Breaking changes

- **Public TypeScript `enum`s are now `as const` objects with a same-name union type** (`werift`, `werift-ice`, `werift-ice-server`, `werift-rtp`, `werift-sctp`): `CandidatePairState`, `classes`, `methods`, `PacketChunk`, `PacketStatus`, `H264NaluType` (`werift-rtp/extra`), `SCTP_STATE`, and `WEBRTC_PPID`. Node.js 26 removed its TypeScript transform mode, and Node.js type stripping cannot run `enum`. Every runtime value is unchanged, and so are value access (`SCTP_STATE.ESTABLISHED`), `===` / `switch` comparisons, type annotations (`state: CandidatePairState`) with `switch` exhaustiveness, `keyof typeof X`, the CJS / ESM export names, assignment from values of older `werift-*` versions, public field / argument / return types (`CandidatePair.state` is still `CandidatePairState`, `SCTP.associationState` is still `SCTP_STATE`), and the TypeDoc `enumerations/` pages. These uses change:
  - Reverse lookup (`X[value]`, for example `CandidatePairState[pair.state]`) no longer exists. Use `Object.entries(X).find(([, v]) => v === value)?.[0]` or keep your own reverse map.
  - `Object.keys/values/entries(X)` no longer contain the numeric reverse-mapping keys. Only member names remain, and `Object.values(X)` lists the values.
  - A member can no longer be written as a type (`x: PacketChunk.TypeTCCRunLengthChunk`). Write `typeof PacketChunk.TypeTCCRunLengthChunk`.
  - A plain `number` is no longer assignable to the type. Check the range first, then narrow with `as X`.
  - A variable initialized from a member without a type annotation (`let s = X.A; s = X.B;`) is inferred as that member's literal type. Annotate it: `let s: X = X.A`.
- **`sender.senderBWE` is a getter whose TypeScript type is `BandwidthEstimator`** (it was a `readonly` `SenderBandwidthEstimator` field). Replace the estimator with `sender.setBandwidthEstimator(impl)`, not by assigning the property. The `onCongestion` / `onCongestionScore` events of the default estimator still exist at runtime, and a one-release compatibility surface keeps those names on GCC / disabled estimators as no-op Events so `sender.senderBWE.onCongestion.subscribe(...)` compiles. Prefer `sender.senderBWE as LightweightBandwidthEstimator` or `isLightweightBandwidthEstimator`. The names are not part of the shared `BandwidthEstimator` contract and may be removed from the other estimators in a future major.
- **`SenderBandwidthEstimator` is renamed to `LightweightBandwidthEstimator`** (the default, lightweight cumulative estimator: TWCC send / receive rates only, no probing or pacing). `SenderBandwidthEstimator` remains as a deprecated alias of the same class, so `new SenderBandwidthEstimator()` and `instanceof` keep working.
- **`onAvailableBitrate` fires only when the estimate changes.** The default estimator used to fire on every update, even with the same value. The payload is still the bitrate in bps.
- **`werift-sctp`: `SCTP.send({ expiry })` is absolute time in `Date.now()` epoch milliseconds** (it was compared against epoch seconds, so it never took effect). A caller that passed epoch seconds now gets every chunk abandoned at its first retransmission decision; pass `Date.now() + lifetimeMs` instead.

### 🚀 Features

- **Selectable TWCC send-side bandwidth estimation** (`packages/webrtc`): estimators share the `BandwidthEstimator` contract, and each `RTCRtpSender` has its own instance.
  - `new RTCPeerConnection({ bandwidthEstimator })` picks the estimator for new senders: `"lightweight"` (default, the existing algorithm), `"gcc"`, `false` / `"none"` (disabled), or a factory `() => BandwidthEstimator`.
  - `RTCRtpSender.setBandwidthEstimator(impl)` swaps the estimator of one sender, e.g. `new GccBandwidthEstimator()`. The new estimator starts from a clean state.
  - `RTCRtpSender.onAvailableBitrate` (`Event<[number]>`, bps) notifies changes of the recommended send bitrate and keeps its subscriptions across `setBandwidthEstimator`. It may stay `0` until TWCC is negotiated and enough feedback has arrived.
  - `GccBandwidthEstimator` implements Google Congestion Control with libwebrtc as the reference (delay-based and loss-based estimation, probing, pacing). Known differences are listed in `GCC_KNOWN_DIFFERENCES`. With GCC, outgoing RTP goes through a bounded per-sender FIFO and a pacer, and `sender.onProbeClusterConfig` / `sender.pacingBitrateBps` expose the probe targets. Probe and loss padding is padding-only RTP on the RTX SSRC, so media sequence numbers are never shifted; without negotiated RTX, GCC sends no padding.
  - The default lightweight and disabled estimators keep the direct (unqueued, unpaced) send path.
  - New exports: `createBandwidthEstimator`, `BandwidthEstimatorOption`, `LightweightBandwidthEstimator`, `isLightweightBandwidthEstimator`, `DisabledBandwidthEstimator`, `GccBandwidthEstimator`, `TwccFeedbackAdapter`, and related types.
- **`TwccFeedbackAdapter` matches TWCC feedback to sent packets for every estimator**: 16-bit sequence numbers are unwrapped from the previous feedback, and each sent packet is counted as received at most once, including duplicate, reordered, and wrapped feedback. `onFeedback(feedback, nowMs)` takes the feedback arrival time and never matches a packet older than the history window (age is measured from `sendingAtMs` to the latest send completion / feedback time), even when the send confirmation completed late or feedback arrives after sending stopped. `SenderBandwidthEstimator` accepts `{ clock }` for tests, like `GccBandwidthEstimator`.
- **STUN `MESSAGE-INTEGRITY-SHA256` for ICE short-term credentials (RFC 8489)** (`werift-ice-server`, `werift-ice`, `werift`):
  - `parseMessage(data, key)` also verifies `MESSAGE-INTEGRITY-SHA256` (16-32 byte truncations). With both integrity attributes present, only `MESSAGE-INTEGRITY-SHA256` is verified, so ICE / consent responses signed with SHA-256 alone are now accepted over UDP, TCP and TURN (they used to be dropped).
  - `Message.addMessageIntegritySha256(key, length = 32)`, `Message.addIntegrity(key, "sha1" | "sha256" | "both")` and `Message.integrityAlgorithm`.
  - Binding success / error responses are signed with the algorithm of the request (`MESSAGE-INTEGRITY-SHA256` when the request carried it).
  - `IceOptions.messageIntegrity` / `PeerConfig.iceMessageIntegrity` (`"sha1"` default, `"sha256"`, `"both"`) and `TransactionRequestOptions.integrityAlgorithm` choose the attributes of outgoing checks and consent requests. The default stays SHA-1 for browser interoperability.
  - TURN long-term credentials stay `MESSAGE-INTEGRITY` only, and incoming checks are not verified yet (both are separate changes).
- **`ice2` ice-option (RFC 8445 §10)** (`werift`): `PeerConfig.iceOptionIce2` (default `false`, fixed at construction) writes `a=ice-options:trickle ice2`. `RTCPeerConnection.remoteIceOptionIce2`, `RTCIceTransport.remoteIce2` / `remoteIceOptions` and `Connection.remoteIce2` report the remote declaration. It does not change ICE behavior. `parseIceOptions()` / `descriptionIceOptions()` parse `a=ice-options`, also for `canTrickleIceCandidates`.
- **`PeerConfig.filterProbePaddingOnReceiveRtp`** (default `false`): `MediaStreamTrack.onReceiveRtp` keeps the wire sequence numbers and delivers padding-only packets with `{ type: "padding" }` as the third argument. Set `true` to drop padding-only probes and compact the sequence numbers of the following media.
- **Generic RTP send-side helpers in `werift-rtp`**: `RtpContinuity` (output sequence / timestamp across source switches), `buildSendHeaderExtensions` / `stampHopByHopExtensions` (send header extensions; TWCC and abs-send-time are written at send time and never copied from a forwarded packet), `appendRfc3550Padding` / `createRtxPaddingPacket`, `RedEncoder.serializedLengthWith()`, and the TWCC helpers `TransportWideSeqUnwrapper` / `TWCC_SEQ_MOD` / `compareTransportWideSeq` / `isOlderTransportWideSeq` / `sortPacketResultsByWideSeq`, `TwccReferenceTimeUnwrapper` / `TWCC_REFERENCE_TIME_MOD` / `TWCC_REFERENCE_TIME_UNIT_MS` and `hasTwccReceiveTiming`. `werift` re-exports them. `werift-rtp` now ships `THIRD_PARTY_LICENSES_LIBWEBRTC.txt` (the transport-wide sequence unwrapper is ported from libwebrtc).
- **`RTCDtlsTransport.sendRtpWithMeta()`** also returns the ICE enqueue time. `sendRtp()` still returns `Promise<number>`. `RTCDtlsTransport.transportSequenceNumberExtended` is the monotonic transport-wide sequence; `transportSequenceNumber` remains the 16-bit wire value.
- **Nonstandard `MediaRecorder` writes Ogg Opus** (`werift`, `werift-rtp`): `path: "*.ogg"` / `"*.opus"`, or `format: "ogg"` with `stream` (pass an `Event<[OggOutput]>`), records exactly one Opus audio track as Ogg Opus (RFC 7845). Without `format`, `stream` still produces WebM. A video track, a non-Opus track or more than one track is rejected with a `WeriftError`; an unsupported extension now throws a `WeriftError` with a message instead of an empty `Error`. `width`, `height`, `roll`, `defaultDuration`, `disableLipSync` and `lipsync` are ignored for Ogg.
  - `werift-rtp` adds the Ogg page writer (`OggPager`, `createOggPage`, `oggCrc32`, `createOpusHead`, `createOpusTags`, `getOpusPacketSamples`) and the `OggCallback` processor with the append-only `saveOggToFileSystem` (its first write replaces an existing file). Timestamp gaps of 2.5 ms or more (DTX, loss) are filled with empty Opus packets, so the granule position follows the media time.
  - `StreamEvent` takes an optional output type (`StreamEvent<OggOutput>`); `StreamEvent` alone is still `Event<[WebmOutput]>`.
  - A Chrome E2E test (`e2e/tests/mediachannel/recordPlaybackOgg.test.ts`) records Chrome's microphone to `.ogg`, sends the file back over a DataChannel, and checks the Ogg page structure, `<audio>` playback, and that Web Audio decodes as many samples as the last granule position.
  - The Ogg recording path reorders RTP with the jitter buffer (`jitterBuffer` option, default latency 200 ms). Packets that arrive after their range was filled are dropped instead of being written out of order.
- **`werift`: `RTCConfiguration.certificateScope` selects the default DTLS certificate.** With `"process"` (default, unchanged behavior), an `RTCPeerConnection` without `certificates` / `dtls.keys` reuses one process-wide certificate, so every such connection advertises the same `a=fingerprint`. With `"peerConnection"`, each connection generates its own certificate on its first `createOffer()` / `createAnswer()` (as browsers do) and its DTLS transports share it. `certificates` / `dtls.keys` still take precedence, and the scope cannot be changed by `setConfiguration()`. `RTCDtlsTransport.generateCertificate()` creates a new certificate on every call.
- **`PeerConfig.iceUseDefaultStunServer`** (`werift`, default `true`) and **`IceOptions.useDefaultStunServer`** (`werift-ice`): set `false` to stop falling back to the built-in public STUN server (`stun.l.google.com:19302`) when `iceServers` has no STUN URL (empty or TURN-only). Server-reflexive candidates are then gathered only from the STUN servers you configure.

### 🐛 Bug Fixes

- **`Vp8RtpPayload.deSerialize` now detects the TID/Y/KEYIDX octet by `T || K` instead of `L || K`** (`werift-rtp`, RFC 7741 §4.2): with `T=1, L=0, K=0` the octet was treated as the start of the VP8 payload (frame one byte too long, P bit / `isKeyframe` read from the wrong byte), and with the RFC-violating `L=1, T=0` the first payload header byte was skipped. `L=1, T=1` (browser temporal layers), `K=1` and werift's own X/I/M descriptor were already parsed correctly.
- **SRTP / SRTCP reject replayed packets** (`werift-rtp`, RFC 3711 §3.3.2). The receive side keeps a replay window per SSRC over the packet index (SRTP: ROC and sequence number, SRTCP: the SRTCP index) and rejects an index it already received or one older than the window with the new `SrtpReplayError`. It subclasses `SrtpAuthenticationError`, so `RTCDtlsTransport` drops replays like packets that fail authentication. A window is created and advanced only after a packet authenticated, so forged packets cannot add receiver state. The window is 1024 packets (`SRTP_REPLAY_WINDOW_SIZE`, the same as libwebrtc), so the NACK retransmission of a lost packet is still accepted. New exports: `SrtpReplayError`, `SrtpReplayWindow`, `SRTP_REPLAY_WINDOW_SIZE`.
  - Behavior change: RTP written with a sequence number the peer already received (for example `track.writeRtp()` of packets that all use the default `new RtpHeader()`) is now dropped by a werift receiver, as browsers already do. Advance the sequence number per packet.
- **SCTP association setup handles INIT collisions** (`werift-sctp`, RFC 9260 §5.2.1, §8.5.1).
  - An initiator in COOKIE-WAIT / COOKIE-ECHOED answers the peer's INIT with an INIT_ACK and accepts the COOKIE_ECHO that follows, instead of ignoring both. When both ends sent INIT (usrsctp and dcsctp do), the association no longer stalls.
  - INIT is always sent with verification tag 0. After answering the peer's INIT before `start()`, the INIT sent by `start()` used to carry the peer's tag. An INIT that carries our own tag (sent by werift 0.26 and older in that case) is also accepted.
  - `start()` does not send INIT when the peer's INIT / COOKIE_ECHO already established the association.
  - INIT and COOKIE_ECHO enter COOKIE-WAIT / COOKIE-ECHOED and start T1 before the chunk is sent. An INIT_ACK that arrives while the INIT send is still pending is no longer dropped, and a failed INIT send is retransmitted by T1 instead of leaving the association idle. The responder enters ESTABLISHED when it sends COOKIE_ACK.
- **A DataChannel / SCTP added by renegotiation opens on an already connected session** (`werift`). When an `RTCPeerConnection` connected without `m=application` and a later offer/answer added it, the SCTP association never started because ICE / DTLS were already connected, so DataChannels stayed `connecting`. Now the association starts when the answer (or pranswer) is applied, on the existing BUNDLE DTLS transport. Starting SCTP is idempotent: an association the peer already established, or one that is connecting, is not started again (no second INIT, no state rewind), and a rollback of the pranswer that added SCTP closes the pending association.
- **An incoming SCTP stream reset no longer drops the last DataChannel message when the reset overtakes a retransmitted DATA chunk** (`werift-sctp`, `werift`): an Outgoing SSN Reset Request whose Sender's Last Assigned TSN has not been received yet is now deferred (RFC 6525 §5.2.2) and answered with `In progress`. DATA up to that TSN (including retransmissions) is still reassembled and delivered; DATA for the reset streams beyond it is held for the new streams. Once DATA or FORWARD-TSN moves the cumulative TSN to the boundary, the inbound streams are reset, the reverse reset is sent and `onReconfigStreams` fires (so the DataChannel closes) after every message before the boundary has reached `onReceive`.
  - The Re-configuration Request Sequence Number is now checked (RFC 6525 §5.2.1): a retransmitted request gets the same result again without resetting twice, and an unexpected one gets `Error - Bad Sequence Number`.
  - An `In progress` answer to a reset werift sent is no longer logged as a failure; the request stays and is retransmitted, and the answer does not count toward closing the association.
  - When the peer's reverse reset request acknowledges a reset werift sent (its Re-configuration Response Sequence Number), werift keeps retransmitting the request until the peer's response arrives, without counting the retransmissions as failures. A lost `Success - Performed` response no longer leaves the request outstanding forever and blocking later resets.
  - `reconfigResult` (`werift-sctp/src/param`) has the other RFC 6525 §4.4 results (`SuccessNothingToDo`, `Denied`, `ErrorWrongSSN`, `ErrorRequestAlreadyInProgress`, `InProgress`).
  - Received TSNs are now ordered by serial number, so the cumulative TSN and SACK gap blocks advance correctly across the 2^32 wrap.
- **Every configured STUN / TURN URL takes part in gathering** (`werift`, `werift-ice`). `RTCPeerConnection({ iceServers })` used to use only the first STUN URL and the first TURN URL and drop the rest silently. Now every IPv4 UDP host socket queries every STUN server in parallel (equal mappings are advertised once, different mappings each), and every TURN URL gets its own allocation with the `username` / `credential` of the `RTCIceServer` that lists it and the transport of its URL (`?transport=`, then `turnTransport`, then `forceTurnTCP`). A server that fails or times out does not stop the others; gathering completes when the slowest server answers or times out (`iceStunGatherTimeout`, `iceTurnConnectTimeout`). `setConfiguration()` and ICE restart replace the whole list and close every previous allocation. A TURN URL without `username` / `credential` is still ignored (now logged), not rejected with `InvalidAccessError`.
  - `werift-ice`: new `IceOptions.stunServers` / `IceOptions.turnServers` (`TurnServerOptions`: `address`, `username`, `password`, `transport`), `Connection.stunServers` / `Connection.turnServers` (also optional on `IceConnection`), and `normalizeIceServerOptions()`. The singular `stunServer` / `turnServer` / `turnUsername` / `turnPassword` / `turnTransport` options are deprecated but keep working: they are merged in front of the plural lists, duplicates removed. `Connection.stunServer` / `turnServer` are deprecated accessors for the first entry.
  - `parseIceServers()` returns `stunServers` / `turnServers` for every URL; its singular fields (the first URL) are deprecated. `RTCPeerConnection` hands the ICE agent only the plural fields, so `iceTransport.connection.options.turnUsername` (and the other singular fields) are now `undefined`; read `connection.turnServers` instead.
- **TWCC is transport-wide on BUNDLE.** `ReceiverTWCC` is shared per DTLS transport, and incoming TWCC RTCP is fanned out to every `RTCRtpSender` on that transport (each estimator matches only its own sent packets). TWCC is delivered only to senders currently on the transport it arrived on, so a late feedback on a transport a sender has left never reaches it. Received TSNs are unwrapped against the highest one received, and pending packets are reported in windows of at most 32,767; after a loss that fills a whole window, the report start jumps to the next received packet, so feedback resumes instead of stalling until the sequence wraps.
- **Moving an `RTCRtpSender` to another DTLS transport resets the path-dependent state of its bandwidth estimator** (send history, transport-wide sequence origin, estimates, in-flight sends), because the new transport has its own sequence space. The estimate restarts from the new transport's feedback. Application constraints are kept: the new optional `BandwidthEstimator.resetNetworkRoute()` (implemented by `GccBandwidthEstimator`) keeps the min / start / max from `setBitrates`, also when the initial negotiation moves a sender onto a BUNDLE transport; estimators without it are `reset()`.
- **The transport-wide sequence number is allocated synchronously before each send** and used for the estimator input, so with BUNDLE a sender no longer picks up the number of another sender's packet. The TWCC and abs-send-time extensions of forwarded packets no longer overwrite the newly assigned values.
- **NACK retransmissions get a new transport-wide sequence number** instead of reusing the original one.
- **Padding-only packets are no longer stored in the NACK cache.**
- **The default (lightweight) estimator's send history is pruned to a 10 s window**; it used to grow without bound.
- **DataChannel `maxPacketLifeTime` abandons messages after the given milliseconds.** The lifetime was divided by 1000 and compared in epoch seconds, so lifetime-limited messages were never abandoned. Now an unacknowledged message is abandoned with PR-SCTP (RFC 3758) after `maxPacketLifeTime` ms, and FORWARD-TSN moves the peer past it.
- **PR-SCTP abandons only the fragments of the expired message** (`werift-sctp`). Abandonment used to start at the first DATA chunk of the send queue and could spread to the preceding message, so a different, still-valid message could be dropped.
- **PR-SCTP recovers from lost packets without dropping deliverable data** (`werift-sctp`). Fragments of an abandoned message that are still waiting to be sent are abandoned with it. A message whose lifetime runs out while it is still queued (cwnd / rwnd limited) is abandoned before its first transmission instead of being sent late. This also happens when nothing else runs the sender (e.g. a zero peer receive window with no DATA in flight) and when the expired message waits behind a message without a lifetime: a timer fires at the earliest expiry in the queue, marks expired messages abandoned in place (TSN order is kept, so they are never sent and the FORWARD-TSN skips them once they reach the head), and resolves their `send()` right away, so the DataChannel `bufferedAmount` drops without waiting for a SACK, another send, or the earlier messages. Abandoned chunks release their payload; only the metadata the FORWARD-TSN needs is kept. Likewise, a chunk whose lifetime runs out while it waits for retransmission is abandoned instead of being retransmitted. A lost FORWARD-TSN is resent until the peer acknowledges it. On receiving a FORWARD-TSN, complete ordered messages that were waiting behind the skipped one are delivered, only incomplete ones are discarded, and a stale entry no longer moves the expected stream sequence number backwards.
- **SCTP reassembly no longer stalls** (`werift-sctp`). After delivering a message, the next complete message is delivered even when its TSN is not contiguous (it used to wait for another DATA chunk), and a complete unordered message that directly follows a broken unordered fragment is no longer skipped.
- **SCTP no longer stops sending DATA after a T3-rtx timeout that follows a Gap ACK, and `flightSize` stays consistent under loss** (`werift-sctp`, #806). T3 used to retransmit gap-acked chunks and count them in `flightSize` again, and the later cumulative ACK never removed them, so `flightSize` stayed at or above `cwnd`: the DataChannel stopped sending (and sending HEARTBEAT) while the connection looked healthy, and `send()` never resolved. Each `DataChunk` now tracks whether it is counted with the new public `inFlight` field, so `flightSize` always equals the bytes of the in-flight chunks in the sent queue on every path (first send, Gap / cumulative ACK, fast retransmit, T3, retransmission, abandonment, FORWARD TSN). T3 skips gap-acked and abandoned chunks, and a chunk acked after it was marked for retransmission is not resent. A gap-acknowledged chunk that a later SACK no longer reports (the peer reneged on it) is made outstanding again and counted in `flightSize`; each later SACK that still misses it counts a miss indication, so it is fast-retransmitted on the third instead of waiting for T3-rtx, and T3-rtx is started if it is not running (RFC 9260 6.2.1).
- **TURN handles unsigned 401 / 438 long-term credential errors** (`werift-ice`): a 401 (Unauthenticated) or 438 (Stale Nonce) without MESSAGE-INTEGRITY answering Refresh, CreatePermission or ChannelBind on an authenticated allocation used to be dropped as an integrity failure and retransmitted until the transaction timed out (~6.7 s per request over UDP; with Cloudflare TURN, per rejected ChannelBind peer). It is now handled at once, over UDP and TCP/TLS, following RFC 8489 §9.2.5. A 438 with a new NONCE is retried once, and the retry is re-signed correctly: a retried request used to keep its old MESSAGE-INTEGRITY / FINGERPRINT inside the new signature, so even werift's own TURN server rejected it once a nonce expired. A 401 to an authenticated request with an unchanged REALM is not retried and rejects immediately; with a new REALM it is retried once, and the allocation's credentials change only if that retry succeeds. No retry is made when the NONCE is missing, its nonce cookie (`obMatJos2`) announces password algorithms or username anonymity, or PASSWORD-ALGORITHMS is present, since only MD5 MESSAGE-INTEGRITY with a plain USERNAME is supported. Only matching transaction-ID, source address and method responses count, and other unsigned errors, unsigned success responses, and responses with an invalid MESSAGE-INTEGRITY (401 / 438 included) are still dropped over UDP. Over TCP/TLS they now end the transaction with `TransactionIntegrityViolation` instead of waiting for a timeout, except an unsigned 400, which is still ignored. ICE connectivity checks and consent keep requiring MESSAGE-INTEGRITY. An unsigned 403 (the RFC 8656 answer for a forbidden peer) is still dropped and times out.
- **`MediaRecorder` WebM recordings of audio + video no longer lose their head** (`werift-rtp` `LipsyncBase` / `LipsyncCallback`, `werift` `MediaRecorder`): a track's frames get their NTP time only after its first RTCP SR, which can arrive seconds after the media (with Chrome, about 2 s for audio). Lipsync started on the first frame of whichever track was ready first and dropped everything older from the other track, so a 5 s Chrome recording lost about 2 s of audio. Now lipsync holds frames until a frame of every input kind has arrived and the late track's backlog has caught up, then starts from the earliest frame.
  - New optional `LipSyncOptions.kinds` (`MediaKind[]`, default `["audio", "video"]`): the kinds to wait for. `MediaRecorder` always sets it from the recorded tracks, so a video-only recording starts on its first frame as before. If you use `LipsyncCallback` directly for a single track, pass `kinds: ["video"]` / `["audio"]`; otherwise output waits for `startTimeout`.
  - New optional `LipSyncOptions.startTimeout` (ms, default `10000`): when some kind has not arrived by then (timer-based, so it also fires when no further frame arrives; a timeout detected on an input frame before the timer fires takes the same path, even if that frame completes every kind), the frames received so far are output immediately and output continues with the received tracks only. The timer start commits (including the `fillDummyAudioPacket` fill) only up to the latest received frame, never beyond it, so frames that keep arriving after the start are not dropped. Frames of a track that arrives later are still dropped if they are older than the already committed time. Until the start, frames are held in memory and output (including `stream`) is delayed by up to this time.
  - An EOL before the start outputs the held frames in time order before the EOL.
  - Not changed: a track whose sender never sends an SR is still never output by `NtpTimeCallback`, and `disableLipSync: true` still drops the head of the later track (its frames older than the first frame `WebmCallback` received).
- **DCEP `DATA_CHANNEL_OPEN` writes Label / Protocol Length as UTF-8 byte counts** (RFC 8832 §5.1) instead of UTF-16 `string.length`. A non-ASCII data channel `label` / `protocol` (e.g. `"日本語"`, emoji) used to arrive truncated or spill into the protocol on the remote side; ASCII values are unchanged on the wire.

### 🐛 Bug Fixes

- **`RTCRtpSender` RTT accepts Receiver Reports that reference older Sender Reports** (`werift`): the sender kept only the newest SR, so a delayed RR (queueing, TURN relay, congested path) whose `LSR` pointed at an earlier SR was dropped and `remote-inbound-rtp` `roundTripTime` / `totalRoundTripTime` / `roundTripTimeMeasurements` went stale. The sender now keeps a bounded SR history (32 entries, 30 s) and computes `now - SR send time - DLSR` for the SR the `LSR` identifies (RFC 3550 §6.4.1), with a monotonic clock instead of `Date.now()`. Reports with `LSR = 0`, an unknown or expired `LSR`, or a negative sample are ignored (packet loss stats are still updated); an RR with `DLSR = 0` now yields an RTT sample instead of being skipped. The EWMA, total and count updates are unchanged.
- **`RTCPeerConnection.close()` stops every DTLS / ICE transport the peer created** (`werift`): `SecureTransportManager` now owns each transport it creates until its `stop()` has stopped ICE (the new `RTCDtlsTransport.onStopped` event; a DTLS close by alert alone keeps it owned), and `close()` stops all of them, including one whose `stop()` is still in progress, not only the ones a transceiver or the SCTP transport still references. A transport no m-line uses any more (e.g. a per-m-line `max-compat` transport a remote BUNDLE answer replaced) can no longer keep its UDP socket or ICE agent alive after `close()`. `dtlsTransports`, `iceTransports`, the ICE state aggregation and `getStats()` still cover only live transports.
- **`JitterBufferBase` no longer drops received packets around a timeout** (`werift-rtp`, used by `MediaRecorder` WebM video and Ogg audio): when a missing packet timed out, the buffer moved its position to the newest arrival, so packets still waiting in the buffer (for example the second of two swapped packets) were discarded, and a timeout whose latest sequence number was `0` discarded the whole buffer. Now only sequence numbers that never arrived are given up, every packet delayed by less than `latency` is output once in sequence order (also across uint16 / uint32 wraparound), an in-order packet that triggers a timeout no longer drops buffered packets, and a full buffer releases its packets instead of dropping new ones.
  - `isPacketLost` now reports each missing range separately (`to` is the last missing sequence number; before, it was the last timed-out received packet), right before the packet that follows the gap. Missing ranges are also reported at `eol`.
- **`WeriftError` keeps its `message`, `payload` and `path`** (`werift-common`): the class field declaration overwrote the message set by `Error` with `undefined`, and `payload` / `path` were never stored. `toJSON()` no longer throws without a `payload`.
- `MediaRecorder.stop()` called before the asynchronous start finished now waits for the start instead of waiting 5 seconds for an end that never comes.
- **RTCP Sender Reports map the current NTP time to the matching RTP timestamp** (`packages/webrtc`, RFC 3550 §6.4.1): `RTCRtpSender` used to report the NTP time and RTP timestamp of the last sent RTP packet, so the SR's NTP time lagged its actual send time by the time since the last RTP packet (without bound while RTP was idle), and SRs sent while RTP was stopped repeated the same LSR. The SR now samples the wall-clock time when it is built and extrapolates the RTP timestamp to that instant from an NTP↔RTP anchor with the send codec's clock rate (32-bit wrap, as libwebrtc does).
  - The anchor is the send time of the first packet with a newer output timestamp (after continuity rewrite). Frame fragments with the same timestamp, timestamps up to 3 s older (reordering) and RTX retransmissions do not move it; a continuity rewrite (`replaceTrack` / `replaceRTP` / `onSourceChanged`), a clock rate change, or a backward timestamp step of more than 3 s (a source discontinuity without continuity rewrite) resets it.
  - Limitation: werift does not know the capture time, so for relayed RTP the send time approximates the sampling time and send jitter becomes SR mapping error.
  - `ntpTime()` accepts an optional epoch-ms argument.
  - NTP timestamps now encode the fractional part as RFC 3550 requires (`fraction / 2^32`) in `ntpTime()` and `ntpTimeToEpochMs()`, matching `ntpTime2Sec()`. Previously the sub-second part was the decimal digits, so two SRs within the same second could carry nearly identical NTP/LSR values, and abs-send-time was affected too.
  - `NtpTimeBase` (`werift-rtp`, used by `MediaRecorder` / `NtpTimeCallback`) takes the RTP timestamp difference to an SR as a signed 32-bit value. Because the SR RTP timestamp is now extrapolated, it can already be past the wraparound while a delayed packet is still before it; such a packet was placed about 26.5 hours (at 90 kHz) later instead of slightly before the SR.
- **`setConfiguration()` TURN options**: changing `turnTransport`, `turnTlsOptions` or `iceUseTcp` after gathering now requests an ICE restart like `iceServers`. Passing an explicit `undefined` for `turnTransport` / `turnTlsOptions` / `turnUdpFamily` unsets it; omitting the key keeps the current value.
- **ICE restart follows the new `iceTransportPolicy` / `iceUseTcp`** (`werift-ice`, `werift`): an ICE restart now keeps only the sockets that a fresh gathering with the new settings would open. With `iceTransportPolicy: "relay"`, the restart offer carries no host / server-reflexive candidates, only relay candidates are trickled, and the kept host sockets are closed. Turning `iceUseTcp` off closes the kept TCP host sockets, and turning it on gathers TCP host candidates for addresses whose UDP sockets were kept. Settings changed after the restart offer was created still apply to that restart's gathering at the commit, so a host candidate the offer announced before a switch to `"relay"` fails its checks, because its socket is closed. `werift-ice` exports the shared rule as `isCandidateAllowedByGatherOptions()` / `isRelayOnlyGathering()` and the ICE server merge as `mergeIceServerOptions()`.
- **`iceTransportPolicy: "relay"` no longer falls back to direct candidates** (`werift-ice`, `werift`): the relay policy (`forceTurn`) is relay-only whatever the TURN settings are. Without a TURN server, with an incomplete TURN credential, or on an ICE-lite agent, gathering — the first one and every ICE restart — produces no candidate instead of host / server-reflexive ones, so the local and public addresses are never advertised and no direct path is checked; the connection cannot be established until a usable TURN server is configured. `isRelayOnlyGathering()` now depends on `forceTurn` alone.
- **`iceTransportPolicy: "relay"` hides the related address of relay candidates** (`werift-ice`, `werift`): under the relay policy, a relay candidate advertises `raddr 0.0.0.0 rport 9` (`::` for IPv6), as RFC 8839 §5.1 specifies, instead of the address the TURN server saw the agent at. This applies in SDP and trickled candidates, for the first gathering and after an ICE restart into the relay policy, so the agent's public address does not reach the peer. With `"all"`, relay candidates keep the TURN-observed `raddr` / `rport`.
- **A staged ICE restart no longer uses a TURN allocation its new settings dropped** (`werift-ice`): until the restart is committed, the provisional checks of the staged generation use a kept TURN allocation only when that generation still has the same TURN server and credential. After the TURN server is removed or replaced (for example, a credential rotation), the old allocation takes no provisional pair, and checks arriving on it for the staged credentials get no response. A check on a host socket that a relay-only restart drops is not answered either. `isCandidateAllowedByGatherOptions()` allows a relay candidate only when the options carry a TURN server and credential, as checked by the new `hasTurnServer()`.
- **`RTCPeerConnection.setConfiguration({ iceServers })` after ICE gathering started now takes effect at the next ICE restart** (JSEP, RFC 9429 §4.1.18), so expiring TURN credentials can be rotated without recreating the `RTCPeerConnection`: call `setConfiguration()` with the new servers, then `restartIce()` and renegotiate. The restarted generation allocates with the new credentials, and the allocation made with the old ones is closed and not re-advertised. A changed STUN/TURN configuration (`iceServers`, `iceTransportPolicy`, `turnUdpFamily`) also sets the needs-ice-restart flag, so the next `createOffer()` restarts ICE even without `restartIce()`. It does not fire `negotiationneeded` by itself. Setting the same servers again requests no restart, and `setConfiguration()` before the first gathering (the WHIP flow) still applies the servers without a restart.
- **ICE `close()` cancels pending mDNS lookups of remote `.local` candidates** (`werift-ice`): a lookup used to keep its 10 s timer, `response` listener and promise after `Connection.close()`, delaying process exit, and a candidate resolved or added after `close()` could still be added to the closed agent (re-opening the mDNS socket). `MdnsLookup.close()` now rejects every pending lookup at once and is idempotent, a lookup after `close()` rejects immediately, and a closed `Connection` ignores remote candidates.

### 🚀 Features

- **`RTCRtpSender.onFullIntraRequest`**: a new `Event<[FullIntraRequest]>` fires when the sender receives a FIR (RFC 5104) whose FCI has an entry for its SSRC with a new sequence number. A retransmitted FIR does not fire it again: each FCI entry is compared with the last sequence number for its (FIR sender SSRC, target SSRC) pair (RFC 5104 §4.3.1.1), so entries for the primary and RTX SSRC resolved to one sender are judged independently. FIR is not delivered to `onPictureLossIndication`; applications that refresh on both should subscribe to `onKeyFrameRequest`.
- **`RTCRtpSender.onKeyFrameRequest`**: a new `Event<["pli" | "fir"]>` that fires for every PLI and every non-retransmitted FIR addressed to the sender, so applications that only need to request a key frame can use one subscription. `onPictureLossIndication` / `onFullIntraRequest` and the stats counters are unchanged.
- **`firCount` in outbound-rtp stats**: every FIR packet with an entry addressed to the sender is now counted once (retransmissions included, as the W3C webrtc-stats definition counts FIR packets), so `getStats()` reports `firCount`. A packet whose primary and RTX entries both resolve to the sender counts as one.
- **`FullIntraRequest` is exported** from `werift-rtp` and `werift`.
- **`keyFrameRequestRouting` peer configuration** (`"compatible"` default / `"strict"`): decides where a PLI / FIR goes when no route has its target SSRC (the PLI media SSRC or a FIR FCI entry SSRC). `"compatible"` delivers it to the sender whose RTX SSRC it is, else to the only video sender of the PeerConnection, so a request naming the RTX stream, SSRC 0 or a stale SSRC still produces a key frame (`onPictureLossIndication` / `onFullIntraRequest` / `onKeyFrameRequest`, `pliCount` / `firCount`). `"strict"` does not deliver it, as RFC 4585 / RFC 5104 define the target. A registered target SSRC is routed as is in both modes, and the sender SSRC of the request is never used.
- `RTCIceCandidate` now exposes the readonly W3C fields parsed from its candidate a-line: `foundation`, `component` (`"rtp"` / `"rtcp"`), `priority`, `address`, `protocol` (`"udp"` / `"tcp"`), `port`, `type` (`"host"` / `"srflx"` / `"prflx"` / `"relay"`), `tcpType`, `relatedAddress` and `relatedPort` (`null` when absent or unparsable). This covers `icecandidate` events, `RTCIceCandidate.fromSdp()`, `new RTCIceCandidate(init)`, and `RTCIceTransport.getSelectedCandidatePair()` / `getLocalCandidates()` / `getRemoteCandidates()`, so `pair.local.type === "relay"` works without parsing the candidate string. `toJSON()` still returns only the signaling fields. `relayProtocol` and `url` are not implemented yet.
  - Which candidates give `null` fields is one contract documented on `RTCIceCandidateFields`: an RFC 8839 §5.1 grammar violation (foundation, component-id 1-256, priority 1-2^31-1, address, port, `typ`, `raddr` / `rport`, `tcptype`, single-space separation) gives all `null`; so does a value the W3C attributes cannot represent (component other than 1/2, protocol other than udp/tcp, unknown type). `tcpType` alone is `null` for non-TCP candidates.
  - `new RTCIceCandidate(init)` reads only the `RTCIceCandidateInit` members (`candidate` defaults to `""`); parsed fields passed in `init` are ignored. `RTCIceCandidate.fromSdp(sdp)` now parses like `new RTCIceCandidate({ candidate: sdp })` and keeps the given string instead of re-serializing it; as before, it sets `usernameFragment` from the `ufrag` attribute (only for a valid candidate).

Browser candidates (mDNS `.local`, `generation`, `ufrag`, `network-id`, `network-cost`, TCP port 9, uppercase `UDP`) are still accepted. a=candidate lines in a remote description are parsed as before.
- **TURN follows `300 Try Alternate`** (`werift-ice`): an Allocate answered with 300 and an `ALTERNATE-SERVER` is retried on that server (RFC 8656 §7.4, RFC 8489 §10), up to 3 redirects. A redirect that cannot be followed (missing `ALTERNATE-SERVER`, a server already tried, too many redirects, or a TCP/TLS transport without a reconnect hook) rejects with the new `TurnRedirectError` (`reason` is a `TurnRedirectFailureReason`; the 300 response is kept as `cause`). `TurnStreamReconnect` lets a stream transport reconnect to the alternate server.
- **`iceInterfaceAddresses` advertises the address it binds** (`werift-ice`, `packages/webrtc`): the configured address is used as the host candidate even when it is not in the OS interface list, and `iceAdditionalHostAddresses` entries of a bound family are ignored. If binding that address fails, ICE reports the error instead of silently falling back to another address. An ICE restart reuses the bound UDP sockets, so the advertised candidate stays consistent. Before, ICE could bind one address and advertise a different host candidate.
- **SRTP rollover counter helpers** (`werift-rtp`): `Context.estimateRolloverCounter()` and `Context.commitPacketIndex()` implement RFC 3711 Appendix A; `Context.updateRolloverCount()` is deprecated and kept as a wrapper. A ROC overflow throws `SrtpRolloverCounterOverflowError` (surfaced as `SrtpAuthenticationError` on the receive side).

### 🐛 Bug Fixes

- **`RTCPeerConnection` negotiation is a single transaction** (`packages/webrtc`, `werift-ice`): an offered or provisionally answered description is staged, the committed session keeps carrying media (RTP / RTCP, the selected ICE pair, DTLS, SCTP), and only the final answer commits negotiated state. Rollback, replacement offers, ICE restarts, BUNDLE changes, DTLS / SCTP updates and routing changes follow the same rule. This fixes cases where a pending offer, a rolled-back offer or a rejected description broke the live connection. `NegotiationTransaction` and the helpers in `src/negotiation/*` own this; no public API value was added.
  - BUNDLE in `max-compat` / `balanced` offers is only a proposal until the remote accepts it (RFC 8843 §7.2); end-of-candidates and ICE generations are tracked per proposed generation.
  - ICE: background gathering is bound to its generation, provisional checks follow the live checklist rules, an ICE-lite peer that changes credentials in its answer still connects, and a relay-only ICE restart waits for its own gathering.
- **Late TURN relay candidates are paired with remote candidates that already arrived** (`werift-ice`): a relay allocation that completed after the remote candidates (early signaling, ICE restart) was never paired. With trickle ICE the check list now fails only after both sides signaled end-of-candidates (RFC 8838 §8), and once a pair is selected no new check starts (RFC 8445 §8.1.2).
- **SRTP: NACK retransmissions no longer corrupt the rollover counter** (`werift-rtp`): a retransmitted packet with a sequence number just after a wrap moved the shared ROC one cycle ahead, so every following packet failed authentication. Each packet now estimates its own ROC and only the highest accepted index is committed (RFC 3711 Appendix A).
  - `srtpSSRCStates[ssrc].rolloverCounter` holds the ROC of the highest accepted index, not that of the last processed packet. A forward jump of more than 32768 is read as an older packet of the previous cycle (as libsrtp does).
- **DTLS server uses the `client_random` of the cookie-bearing ClientHello** (`werift-dtls`): after a HelloVerifyRequest the server kept the random from the first ClientHello, so the ServerKeyExchange signature and key derivation failed with peers that send a different random in the second one.
- **Memory leaks after `close()` and across repeated negotiations are fixed** (`packages/webrtc`, `werift-ice`, `werift-dtls`): remote DataChannel list and listener, stopped sender DTLS subscription, rollback-baseline transport, transport-cc feedback history, ICE credential history, STUN transactions surviving close, retired checklists, TURN close races, and DTLS flight retransmission after the transport stopped.
- **Large `RTCDataChannel.send()` bursts no longer slow down quadratically or starve the event loop** (`werift-sctp`, `packages/webrtc`): queuing thousands of messages at once took time growing with the square of the queue length (2,000 × 1 KB: ~12 s, 5,000: minutes) and blocked the event loop for seconds per SACK, long enough to lose ICE consent mid-transfer.
  - `SCTP.send()` now resolves when its own last chunk is handed to the network (moved from the outbound queue to the sent queue) instead of waiting until the whole outbound queue drains. Previously every pending `send()` waited on the `flush` event, so each transmit woke all N waiters and each re-subscribed with an O(N) unsubscribe.
  - Pending `send()` calls settle when the association closes instead of staying pending forever.
  - The SCTP sent / outbound queues and the DataChannel send queue use `FifoQueue` (amortized O(1) `shift()`).
  - `RTCSctpTransport` hands queued DataChannel messages to SCTP in a single synchronous pass instead of starting one concurrent flush loop per `send()`. `bufferedAmount` now decreases per message as it is transmitted (previously only after the whole SCTP outbound queue drained), so `bufferedamountlow` fires during a burst. Messages not yet handed to SCTP are discarded when the transport stops.
- **RTCP PLI / FIR routed to the targeted media source**: `RtpRouter.routeRtcp()` used to look up a payload-specific feedback by its sender SSRC first, so a PLI whose sender SSRC matched another local stream (e.g. a werift or Chrome peer in a sendrecv video session, or an SFU viewer's own stream) was delivered to the wrong `RTCRtpReceiver` / `RTCRtpSender` and never raised `onPictureLossIndication`. PLI is now routed only by its media SSRC (RFC 4585 §6.1), and FIR by the SSRC of each FCI entry (RFC 5104 §4.3.1; the media SSRC of the common header is 0 for libwebrtc), delivering once per target sender. A PLI whose media SSRC is not registered is no longer delivered to the stream matching its sender SSRC (see `keyFrameRequestRouting` for where it goes instead). Unknown payload-specific feedback types (SLI, RPSI, ...) are no longer routed, instead of throwing.
- **Compound RTCP packets are split at each packet's declared length** (`werift-rtp` `RtcpPacketConverter.deSerialize`): each packet's payload used to extend to the end of the compound packet, so a FIR followed by another packet (e.g. `RR + SDES + FIR + PLI`) gained bogus FCI entries from the following bytes. With FIR routing these reached other senders as extra FIR notifications and `firCount`. Padding is also read from the end of its own packet instead of the end of the compound packet.
- **`FullIntraRequest` serializes the RFC 5104 header length**: the RTCP length field was one word short (3 instead of 4 for one entry; RFC 5104 §4.3.1.1: 2 + 2 × N), so peers could fail to parse a FIR sent by werift.
- **WebM files saved with `saveToFileSystem` no longer contain unknown-size Clusters** (`werift-rtp`, `MediaRecorder` WebM output): when the recording ends, each Cluster's size field is rewritten in place with its real size. Before this fix, ffprobe warned `Unknown-sized element ... inside parent with finite size`, mkvalidator reported errors, and libwebm rejected the files.
  - `WebmOutput.eol.clusters` (new; `{ position, size }[]`), `replaceClusterSize()` and `ClusterSizeOffset` are exported for custom writers. Streaming output (`WebmStream` without rewriting) still uses unknown-size Segment / Clusters.
  - `replaceSegmentSize()` now writes an 8 byte VINT instead of a short VINT followed by a Void element. The old value was too large by the length of the size field, because it counted the field itself. Its Void padding also moved the Segment body start, so every CueClusterPosition pointed past its Cluster.
  - The record examples now use `saveToFileSystem`.
- **`ntpTime2Sec()` now converts the NTP fraction correctly** (`werift-rtp`, used by `NtpTimeCallback` / `MediaRecorder` A/V sync): the low 32 bits of an RTCP SR NTP timestamp are a binary fraction (1/2^32 s), but they were read as decimal digits (`0x80000000`, i.e. 0.5 s, became 0.2147483648 s). Each track's frame times could be off by up to about 1 s, so lipsync dropped most or all audio from short recordings of a browser's audio and video. A new E2E test (`e2e/tests/mediachannel/recordPlayback.test.ts`) records browser media with `MediaRecorder`, sends the WebM back over a DataChannel, and checks that Chrome plays it.
- **`werift-common` `UdpTransport` always handles dgram socket `error` events** (`werift-common`, `werift-ice`): before this fix, a socket error with no listener (for example Bun's asynchronous `recvmsg ECONNREFUSED` after the remote peer closed) became an uncaught process exception.
  - Runtime socket errors are logged and emitted on the new `UdpTransport.onError` (`Event<[Error]>`). The socket stays open. `StunProtocol` / `TurnProtocol` subscribe to it and log. `Transport.onError` is optional for custom transports.
  - A bind failure (e.g. `EADDRINUSE`, including a synchronous `bind()` throw) or a `findPort()` failure now rejects `UdpTransport.init()` and closes the socket. Before, a bind failure caused an uncaught exception or `init()` waited forever.
  - `close()` can be called more than once, including after an error or a failed bind.
- **`werift`: unordered partially reliable DataChannels now announce an unordered DCEP channel type.** `ordered: false` with `maxRetransmits` or `maxPacketLifeTime` sent channel type `0x01` / `0x02` in `DATA_CHANNEL_OPEN` instead of `0x81` / `0x82` (RFC 8832 §5.1), so the remote peer created the channel as ordered. Workarounds that set the `0x80` bit on the queued OPEN message are no longer needed.
- PEM passed to `dtls.keys` / `RTCCertificate` / `CipherContext` may still be indented (for example inside an indented template literal), as it was with `@fidm/x509`. `werift-dtls` exports the `normalizePem()` helper used for this.

- **AV1 Chrome RTP playback**: the packetizer packs up to three OBU elements per packet (W=1..3), aggregates the Sequence Header with the start of its frame, and omits internal `obu_size` fields so Chrome decodes the temporal unit correctly. W=0 payloads are still accepted by the depacketizer.

- **VP8 payload descriptor now carries PictureID** (`packages/webrtc` file playback / encoded-binary / dummy media, `packages/rtp` `Vp8Packetizer`): werift-generated VP8 RTP uses the browser single-layer form `X=1, I=1, M=1` + 15-bit PictureID (4 octets; `90 80 ..` on the first fragment, `80 80 ..` on continuations; L/T/K unset). PictureID starts random (dummy media: deterministic per source), advances once per frame and wraps at `0x7fff`; file playback keeps it continuous across `loop`. Fragment size is `maxPayloadSize - 4`, so payloads stay within `maxPayloadSize`. Previously the 1-octet `X=0` descriptor was dropped by mediasoup ≤ 3.19.2 (before versatica/mediasoup#1612), which could not detect its keyframes, so subscribers received nothing; it now works on those versions without upgrading the SFU. - **File playback VP8 PictureID no longer resets at the first `loop`** (`packages/webrtc` `createFileMediaPlayer`): the per-track packetizer was recreated whenever `RTCRtpSender` assigned a new (equivalent) codec object or filled in the payload type after playback started, restarting PictureID at a random value. - **Dummy media VP8 is decodable** (`packages/webrtc` `dummyMedia` / `createDummyRegister()`): the previous synthetic keyframe (2x2 header with an empty first partition) was rejected by libvpx, so Chrome decoded 0 frames and kept sending PLI. - **AAC (RFC 3640 §3.2.3.1)**: every fragment now carries its AU Header Section; the depacketizer strips it from continuations and validates AU-size. - **H.264 / H.265**: length-prefixed input whose prefix looks like a start code (e.g. length 300 = `00 00 01 2c`) is no longer misread as Annex-B.
- **AV1**: adjacent fragmented OBUs are no longer merged; boundaries come from Z/Y.
- **Audio marker** (G.711 / G.722 / Opus): marker is set only on the first packet of a talkspurt (`startTalkspurt()` to re-arm), per RFC 3551 §4.1 / RFC 7587 §4.1.
- **H.264 / H.265 input layout**: new `inputFormat: "auto" | "annexb" | "length-prefixed"` on the packetizers and `split*NalUnits`. `auto` (default) treats a leading start code as Annex-B (a 3-byte `00 00 01 HH` is otherwise indistinguishable from a 4-byte length `0x1HH`); pass `"length-prefixed"` for MP4/MKV samples. - **telephone-event**: `event` / `volume` / `duration` outside 0–255 / 0–63 / 0–0xFFFF now throw `RangeError` instead of being masked (RFC 4733 §2.5.1.3: split longer events).
- **AAC**: a complete AU arriving while a fragment is pending drops the stale fragment instead of throwing. **H.265 FU** with S=E=1 is rejected.

- **AV1 N bit** (RFC 9628 §4.4): `Av1Packetizer` no longer sets N on every keyframe. N is set when `startsNewCodedVideoSequence` is `true`, or by default for a keyframe whose temporal unit contains a Sequence Header OBU; mid-sequence keyframes keep N=0.
- **H.264 Annex-B split** no longer drops NAL types ≥ 14 (prefix NAL, subset SPS, slice extension, ...); RFC 6184 §5.6 carries types 1–23 as Single NAL / FU-A.
- **`useH264()`** now returns `video/H264` (uppercase, as Chrome expects); codec names are compared case-insensitively.
- **AV1 ↔ AV1X** normalization now applies to SDP answer, codec matching, and file playback validation, not only `findCodecByMimeType`.
- **AV1 packetizer → Chrome**: `Av1Packetizer` drops Temporal Delimiter OBUs, clears `obu_has_size_field` on RTP OBU elements, and packs up to three OBU elements per packet (W=1..3), splitting OBUs across packet boundaries like libwebrtc. Without a dependency descriptor libwebrtc treats Z=0 / Y=0 as frame start / end, so the previous one-OBU-per-packet layout split a temporal unit into two frames and Chrome 155 never rendered it.
- **fMP4 muxer no longer loops forever when video dimensions are undefined** (`packages/rtp` `Mp4Container` / `MP4Processor`): a video config without `codedWidth` / `codedHeight` now reaches the "missing coded video dimensions" guard. When `Track.width` / `height` are not both positive integers, the coded size, `avcC`, and display aspect ratio (coded size × SAR, exact integers) come from the SPS of the first usable keyframe; if they cannot be resolved the keyframe is skipped and the muxer waits for the next one.

### 🐛 Bug Fixes

- **TURN hostname resolution matches the bound UDP socket family** (`werift-ice`, #731): `TurnProtocol.request` now resolves the server hostname with the same family preference as the `udp4` socket `createTurnClient` binds. Previously, a dual-stack resolver that answered IPv6 first (e.g. `turn.cloudflare.com`) sent every `Allocate` to an address the socket could not reach, so the transaction retransmitted for ~6.4 s, timed out, and gathering silently fell back to TURN over TCP, holding `setLocalDescription` for the whole wait.
- **TURN server endpoint pinned and taken from the transport** (`werift-ice`, #725, #726, #731): `Transport` gains optional public `addressFamily` / `remoteAddress` fields (reported by `UdpTransport`, `TcpTransport`, `TlsTransport`); STUN and TURN read these instead of casting to `UdpTransport`'s private socket type. `TurnProtocol` resolves and pins one concrete server endpoint on the first request instead of re-resolving per request, which could previously drift to a different address.
- **IPv6 TURN/STUN transaction addresses compared in canonical form** (`werift-ice`, #731): an IPv6 literal server written in non-canonical notation (e.g. `0:0:0:0:0:0:0:1`) never matched the socket-reported source address, so valid responses were dropped until the transaction timed out.
- **ICE-TCP: both agents now select the same TCP connection** (`werift-ice`, #721): the controlling agent no longer attaches `USE-CANDIDATE` to every TCP connectivity check (aggressive nomination). It waits until every higher-priority TCP pair has finished its check, then nominates the highest-priority valid TCP pair with a separate `USE-CANDIDATE` check (RFC 8445 regular nomination). Before this change, the two agents could each pick a different TCP connection and then close the connection the peer had picked while pruning, so the first `send()` failed with `EPIPE` / `ECONNRESET`. UDP and relay pairs, and connections to ICE-lite peers, keep their current nomination behavior.
- **ICE-TCP connectivity check timeout** (`werift-ice`, #721): TCP checks are still sent once without retransmission (RFC 5389 §7.2.2), but the response timeout is now `TCP_CHECK_RESPONSE_TIMEOUT_MS` (3 s) instead of 50 ms, and that timeout also covers the TCP connect. A refused TCP connect or a failed write fails the check immediately instead of waiting for the timeout.
- **ICE-TCP selected connection loss** (`werift-ice`, #721): a TCP socket that is already closed is discarded before reuse, and a failed write discards the socket and rejects `send()` with the socket error. When the selected TCP connection closes, the agent moves to `failed` right away (the same end state as a consent expiry) instead of waiting 30 s for consent to expire.
- **`NodeTurnServer.listen()` bind conflict** (`werift-ice-server`, #721): with `port: 0`, UDP and TCP share one port number that UDP picks. If that number is already in use for TCP, `listen()` now picks a new number (up to 10 attempts) instead of failing with `EADDRINUSE`. If `listen()` fails, it now closes any socket it has already opened and resets its state.
- **Reject unsupported RTP m-lines in the answer instead of throwing** (#705, #721): `setRemoteDescription()` no longer fails with `negotiate codecs failed.` when an audio/video section has no common codec. The answer keeps the m-line count, order, MID, type and proto, and rejects only that section with port 0 and one offered fmt token. Audio-only peers no longer need to add VP8 to accept a browser offer that bundles video.
  - The answer BUNDLE group contains only accepted offered members; an offerer-tagged section rejected in the initial answer moves the tag to the first accepted member, and a fully rejected group is omitted. An established tag is kept.
  - Accepted m-lines outside the offered BUNDLE group get their own transport and ICE credentials, including with `bundlePolicy: "max-bundle"`. A re-offer that moves an established BUNDLE member out of its group or splits the members into different groups is rejected with `InvalidAccessError` before any state changes. For a remote offer, transport ownership follows only the offered BUNDLE groups regardless of `bundlePolicy` (`max-bundle` affects only local offers): each offered group gets its own transport, and m-lines outside any group (including an offer without BUNDLE) get independent transports. ICE / DTLS parameters come from the first accepted member of a group, not from a codec-rejected tag. A new independent transport gathers its own ICE candidates even when an established BUNDLE is connected, and each transport takes the DTLS role from the `a=setup` of the m-lines it serves. As an offerer, a remote answer that moves m-lines sharing one offered transport out of a common BUNDLE group with different ICE credentials is rejected with `InvalidAccessError` before any state changes. Local trickle candidates carry the MID / index of the accepted section that owns the ICE transport (not always m-line 0); remote candidates for rejected sections are recorded without throwing. SCTP before RTP keeps the original indexes.
  - A non-zero remote answer / pranswer without a common codec is rejected with `InvalidAccessError` before any state changes. An unsupported re-offer keeps the existing track and RTP pipeline while pending and after rollback, and is released only when the port 0 answer is applied.
  - `removeTrack()` detaches the track without stopping the sender, so the same sender can resume. `addTrack()` reuses only unsent, non-stopped, non-rejected senders. Re-offers no longer fire `ontrack` again for an already receiving transceiver, and remote-initiated stops do not fire `negotiationneeded`.
  - `negotiationneeded` is coalesced: changes in the same tick (including `removeTrack()`) fire it once, and an event queued before a local offer that already covers the change is dropped once that offer is answered. This avoids duplicate offers and `InvalidStateError` in `onnegotiationneeded`-driven signaling.
  - A local transceiver that reserved a stopped position before its own offer releases the reservation when a remote offer reuses that position (e.g. with another kind), and is appended in the next offer instead of taking the remote MID.
  - Design note: `docs/design/705-media-rejection-and-removetrack.md`.
- **Received audio RED tracks labeled with the delivered primary codec** (`packages/webrtc`, #729): `RTCRtpReceiver` unwraps audio RED and delivers primary (e.g. Opus) packets to the track, but the remote track's codec was set to the first negotiated codec (`audio/red`). With fixed-source constraints this made `replaceTrack()` reject echoing a received RED track back on a RED sender (`InvalidModificationError`), breaking the `red-record-gst` and `red-sendrecv` example e2e flows. Remote audio tracks are now labeled with the primary codec referenced by RED (or the first primary codec) on creation and on codec resync.

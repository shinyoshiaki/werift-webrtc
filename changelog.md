# Changelog

## v0.29.0

This release collects everything merged since v0.28.0. DTLS 1.3, SPED (DTLS handshake in ICE Binding) and WARP are opt-ins: a default `RTCPeerConnection` stays on DTLS 1.2 without SPED, and the DTLS / ICE changes that reach it are listed under "Breaking changes".

### ⚠️ Breaking changes

- **DTLS 1.2 association lifecycle** (`werift-dtls`): a local `close()` now fires `onClose` once (also on `DtlsServer`). After the connection ended (local `close()`, the peer's close_notify, a fatal alert or handshake failure), `exportKeyingMaterial()`, `remoteCertificate` and `connect()` throw `DTLS association is closed`, and `send()` resolves without sending. The peer's close_notify fires `onClose` once the reply was sent (or timed out). A fatal alert fires `onError` only. `RTCDtlsTransport` is unaffected.
- **DTLS 1.2 HelloVerifyRequest cookie** (`werift-dtls`): the cookie is an HMAC over the peer binding and the ClientHello parameters (except `random` and the cookie), 104 bytes, valid for 60 s; a cookie-bearing ClientHello whose parameters differ is challenged again. Over ICE (`peerIdentityMode: "authenticated-single-peer"`, every `RTCDtlsTransport`) the cookie is not bound to an address; otherwise it is bound to the ClientHello source.
- **A received `protocol_version` alert ends the DTLS 1.2 connection at any level** (`werift-dtls`) and is reported as `ProtocolVersionError` (not `DtlsAlertError`). A ClientHello whose `supported_versions` shares no version with this side is answered with `protocol_version`.
- **Wire renegotiation is not supported** (`werift-dtls`): a ClientHello after the handshake completed is ignored (it used to call `renegotiation()`).
- **DTLS 1.2 record acceptance** (`werift-dtls`): once this side's write epoch advanced (the client after its Flight5), an epoch-0 handshake record is dropped, so a retransmitted Flight4 no longer triggers an immediate Flight5 resend (the client's own retransmission timer recovers). After the handshake completed, an epoch-0 alert is ignored; epoch-0 application data is always dropped. A plaintext alert before the handshake completed (e.g. the server's `bad_certificate`) is still accepted.
- **DTLS 1.2 ClientHello negotiation** (`werift-dtls`): the curve, signature, `use_srtp` and cipher-suite checks run on the cookie-bearing ClientHello (after the HelloVerifyRequest), so a mismatched peer is rejected one round trip later and with new error messages (e.g. "no overlapping named curve"); a ClientHello without `elliptic_curves` uses the first locally supported curve.
- **Smaller DTLS 1.2 wire changes** (`werift-dtls`): the epoch-0 record sequence number keeps increasing across a HelloVerifyRequest (it was reset); a client answers a second HelloVerifyRequest (a server re-challenge) while waiting for Flight4; an all-zero X25519 public key or shared secret fails the handshake; received alerts are logged at the error level.
- **ICE** (`werift-ice`): `restart()` abandons the STUN transactions still in flight on host / server-reflexive sockets (relay pairs keep theirs and stop through the generation checks); a trickled candidate that matches a learned peer-reflexive one updates its type and priority instead of being added again; `connect()` reports `failed` itself and succeeds once a pair is nominated even if other checks did not complete.
- **STUN serialization** (`werift-ice`, `werift-ice-server`): comprehension-optional (unknown) attributes keep their wire position, before `MESSAGE-INTEGRITY` / `FINGERPRINT`, instead of being appended at the end; `Message.rawAttributes` is an accessor; a transaction retransmits the bytes of its first send. Messages with known attributes only serialize as before.
- **Smaller API changes** (`werift`, `werift-dtls`, `werift-ice`): `RTCDtlsTransport.lastError` and `DtlsTransportConfig` are public; an `RTCDtlsTransport` keeps the configuration it was created with, so `setConfiguration({ debug })` applies to transports created afterwards; `setConfiguration({ dtls })` merges into the current `dtls` options instead of replacing them; a concurrent second SCTP connect shares the first one; `TcpPassiveProtocol.close()` rejects when closing its server fails. `RTCDtlsTransport.start()` returns at once when already connected and waits for a start in progress (it threw "state must be new"); `getStats()` reports the remote certificate only while connected; `DtlsSocket.waitForReady()` rejects with an `Error`; `CipherSuite`, `AlertDesc`, `ContentType` and `HandshakeType` have DTLS 1.3 members; `generateDefaultPeerConfig()` returns `Required<PeerConfig>`; `getConfiguration().dtls` lists `protocolVersions` / `helloRetryRequest`.
- **`RTCDataChannel.bufferedAmount` is read-only** (W3C webrtc-pc): it is a getter, the value lives in a private field. Assigning it throws `TypeError` in strict mode (ES modules, classes) and is ignored otherwise; it used to be a writable field, and writing it broke werift's own accounting and the `bufferedamountlow` notification. These DataChannel changes are about the API and the semantics of `bufferedAmount` / `close()` only; the queue performance (#730) was fixed in v0.26.0 and is unchanged here.
- **`bufferedAmount` does not drop for data that was never sent** (W3C webrtc-pc, WPT `RTCDataChannel-bufferedAmount.html` "should not decrease after closing the peer connection"): messages thrown away unsent by `RTCPeerConnection.close()`, `RTCSctpTransport.stop()` or the end of the association stay in `bufferedAmount`, and `bufferedamountlow` never fires once the channel is `closed`. They used to be subtracted, so `bufferedAmount` fell to 0 (and `bufferedamountlow` could fire) as if they had been sent. Messages handed to the network while the channel is `closing`, and messages PR-SCTP abandons (`maxRetransmits` / `maxPacketLifeTime`), are still subtracted. Code that waited for `bufferedAmount === 0` after closing should wait for the channel's `close` event instead (see "Graceful close" in `packages/webrtc/README.md`).
- **`MediaStreamTrack` / `MediaStream` follow the DOM types** (`werift`): `MediaStreamTrack.id` is `string` (it was `string | undefined`; the constructor still fills it with `uuid` when omitted), `MediaStream.getTrackById()` returns `null` instead of `undefined` for an unknown ID, `MediaStream` extends werift's `EventTarget` (an `EventEmitter`), an exception thrown by an `"ended"` listener no longer reaches the caller of `MediaStreamTrack.stop()` (it is logged, like the DOM reports it), and `MediaStreamTrack` takes its `kind` as a type parameter (`MediaStreamTrack<K extends Kind = Kind>`; `new MediaStreamTrack({ kind: "audio" })` is a `MediaStreamTrack<"audio">`, and `MediaStream.getAudioTracks()` / `getVideoTracks()` return `MediaStreamTrack<"audio">[]` / `MediaStreamTrack<"video">[]`).
- **The DTLS role decides the SCTP initiator** (`werift`, RFC 8832 §6; it was the ICE role at the DTLS start; the DataChannel stream ID parity follows the DTLS role too, see "DataChannel stream IDs follow the DTLS role" under Bug Fixes). The DTLS server sends SCTP INIT; the DTLS client waits for it and sends INIT itself when none arrived 1 s (`PASSIVE_INIT_FALLBACK_MS`) after DTLS authentication, and an initiator answers a colliding INIT (RFC 9260 §5.2.1). So when the ICE and DTLS roles do not line up (for example an older werift ICE-lite offerer that ends up as DTLS server, or an explicit `a=setup` reversing the roles), the association still starts with werift up to 0.28.0, which picks the initiator by the ICE role. In that configuration such a peer also opens its DataChannels on this side's stream ID parity; an OPEN on an unused stream of that parity is now accepted instead of being reset. Channels opened from both ends at the same moment can still pick the same ID there; the colliding stream is reset. Aligned configurations (the usual offerer = ICE controlling = DTLS server) are unchanged.
- **`compatibility: "standard"` now also sets `dataChannelBinaryType` to `"standard"`** (#375; a run-time change for applications using the v0.28.0 preset): data channels of such a connection deliver binary messages as `ArrayBuffer` (the W3C `binaryType` default) instead of `Buffer`. **Migration:** keep `Buffer`s with `{ compatibility: "standard", dataChannelBinaryType: "nodebuffer" }` (an explicit value wins over the preset), or use `channel.onMessage`, which always receives a `Buffer` or a string. Connections without `compatibility` are unchanged.
- **`pc.createDataChannel()` ignores the `id` of an in-band channel** (#815): with `negotiated` not `true`, `createDataChannel(label, { id })` now creates the channel with `id === undefined` and the stream ID comes from the DTLS role, as W3C webrtc-pc and every browser do (an out-of-range `id` is ignored too, nothing is thrown; a debug log records it). A given ID used to be taken as is, so it could collide with the IDs of the peer. **For a fixed stream ID, use `{ negotiated: true, id }`.** This is the behavior of `pc.createDataChannel()`; constructing `RTCDataChannel` / `RTCDataChannelParameters` directly is internal.

These are type-level changes only: with the default configuration, applications behave as before at run time.

- **`MessageEvent.data` (`onmessage`, `"message"`) of `RTCDataChannel` is `string | Buffer | ArrayBuffer | Blob`** (`RTCDataChannelMessageData`, #375) instead of `string | Buffer`, because `binaryType` can now deliver `ArrayBuffer` or `Blob`. By default (`"nodebuffer"`) binary messages are still `Buffer`s. `data.toString()`, `data as Buffer` and a `Buffer.isBuffer(data)` / `typeof data === "string"` check still compile; code that uses a member only `string` and `Buffer` share (e.g. `data.length`) no longer does. **Migration:** narrow with `Buffer.isBuffer(data)` / `typeof data === "string"`, or use `channel.onMessage` (werift `Event`), which always receives a `Buffer` or a string.
- **`RTCSessionDescription.type` is `RTCSdpType`** (`"offer" | "answer" | "pranswer" | "rollback"`, #375) instead of `"offer" | "answer" | "pranswer"`, because the W3C constructor accepts `{ type: "rollback" }`. The return types of `createOffer()` / `createAnswer()` / `localDescription` are unchanged (`RTCSessionDescription`). **Migration:** code assigning `description.type` to a variable of the narrower union narrows first (e.g. `if (description.type !== "rollback")`).

### 🚀 Features

- **DTLS 1.3 opt-in** (`werift-dtls`, `werift`, RFC 9147): `dtls.protocolVersions` (`werift`) / `protocolVersions` (`werift-dtls`) takes `DtlsVersion.V1_3` alone or with `V1_2` (preferred first); omitted keeps DTLS 1.2 only. `dtls.helloRetryRequest: true` sends a cookie-bearing HelloRetryRequest (off by default on the ICE path). `getStats()` transport `tlsVersion` is `"DTLS 1.2"` / `"DTLS 1.3"`. A 1.3-only × 1.2-only pair fails with `ProtocolVersionError`. A client offering both versions sends the DTLS 1.2 extensions (`extended_master_secret`, `renegotiation_info`) in its first ClientHello as well, so a DTLS 1.2-only server that reads them from that ClientHello (werift before this release) completes the handshake. Over ICE (`peerIdentityMode: "authenticated-single-peer"`) such a client stops retransmitting its first ClientHello once a HelloVerifyRequest came, so a lost Flight4 no longer makes a DTLS 1.2 server challenge again in the middle of the handshake (which werift before this release could not complete).
- **SPED opt-in** (`werift`, `werift-ice`, `draft-hancke-webrtc-sped-00`): `new RTCPeerConnection({ sped: true, dtls: { protocolVersions: [DtlsVersion.V1_3] } })` carries the DTLS 1.3 handshake in authenticated ICE Binding requests / responses (`0xC070` / `0xC071`) and falls back to direct DTLS with the same bytes against a peer without SPED. When `dtls.protocolVersions` also offers `"1.2"`, that first, dual-version ClientHello carries the DTLS 1.2 extensions, so a DTLS 1.2-only peer without SPED (werift before this release, other implementations) answers it and the connection completes DTLS 1.2 (draft §3.3.4); the bytes are sent as generated, never re-serialized. A selected relay / TURN pair (which carries no SPED) before the peer's SPED support was known also falls back to direct DTLS on that pair; such a connection used to never start its DTLS handshake. Only such a PeerConnection's ICE agent verifies the `MESSAGE-INTEGRITY` of incoming Binding requests (others are dropped), keeps an older generation's check out of the current checklist and pairs checks that arrive before `connect()` at once; without `sped` the ICE request handling is unchanged. A `sped: true` PeerConnection advertises `a=ice-options:sped` in its offers and answers, since Chromium (`WebRTC-IceHandshakeDtls`) and Pion (pion/webrtc#3362) use SPED only when the offer advertises it, and it also takes a Binding that carries only DTLS-IN-STUN-ACK as SPED support (Pion sends such Bindings before its own flight exists). Checked against Chromium 156 with SPED on and pion/webrtc#3362 in both offer directions.
- **WARP opt-ins** (`werift`, `PeerConfig.warp`, on top of the DTLS 1.3 and SPED opt-ins above). Defaults are unchanged: `new RTCPeerConnection()` keeps DTLS 1.2 only, starts DTLS after ICE completes, and sends nothing before the SDP fingerprint is verified.
  - `PeerConfig.warp: { allowEarlyServerData?: boolean; earlyMediaPolicy?: "drop" | "buffer" }`. `allowEarlyServerData` (default `false`) lets the DTLS server send application data / media before the peer fingerprint is verified; it requires `sped: true` and DTLS 1.3. `earlyMediaPolicy` (default `"drop"`) decides whether inbound encrypted media received before authentication is dropped or kept in a bounded buffer. Inbound data, RTP and RTCP are never delivered before authentication. `setConfiguration({ warp })` merges the fields and applies them to every open DTLS transport.
  - Invalid combinations throw synchronously from the constructor and `setConfiguration()`, which leaves the configuration unchanged. `sped` / `dtls.protocolVersions` / `dtls.helloRetryRequest` cannot be changed after a DTLS transport is created.
  - `PeerConfig.warp.sendBeforeNomination` (default `false`, requires `sped: true`): once the DTLS handshake is done on this side (the DTLS client right after its Finished) and the peer is authenticated, application data and media use a valid candidate pair (its own connectivity check succeeded) instead of waiting for ICE nomination and consent (RFC 8445 §12.1, SPED draft-00 §3.1.2.2). It applies only until ICE has a selected pair, never during an ICE restart and never on relay pairs; `RTCTransportStats.warpPreNominationSendUsed` reports when it was used. Checked against werift, the published `werift@0.26.0`, Chromium (SPED disabled, DTLS 1.3) and a released `pion/ice` agent.
  - `RTCTransportStats` adds `warpSpedState`, `warpCarrier`, `warpHandshakeRttMs`, `warpDtlsRetransmissions`, `warpSpedRetransmissions`, `warpEarlyBufferedPackets` / `warpEarlyBufferedBytes`, `warpEarlyDroppedPackets` / `warpEarlyDroppedBytes`, `warpEarlyServerSendUsed`, and `iceGeneration` (the ICE restart generation of the transport). `RTCPeerConnection.iceGeneration` exposes the generation of the first ICE transport.
- **`dtlsHandshakeValidation` compatibility option** (`werift`, `"lenient"` default / `"standard"`; `handshakeValidation` in `werift-dtls`): `"standard"` validates the DTLS 1.2 handshake strictly (a malformed `supported_versions` is answered with `protocol_version`, duplicate extensions and a malformed `use_srtp` fail the handshake); `"lenient"` keeps the previous behavior. `compatibility: "standard"` sets it to `"standard"`. Cannot be changed after construction. DTLS 1.3 always validates strictly.
- **`peerIdentityMode`** (`werift-dtls`): `"datagram-address"` pins a DTLS association to its peer's address (datagrams from another source are dropped and the TX goes to the pinned peer; before the pin unauthenticated alerts and handshake errors are ignored), `"authenticated-single-peer"` treats the transport path as the peer (WebRTC over ICE), and `"unpinned"` keeps the previous behavior. Default: `"unpinned"` for DTLS 1.2 only, `"datagram-address"` when DTLS 1.3 is offered.
- **`RTCDataChannel.onbufferedamountlow`**: called with the `bufferedAmountLow` event and the `bufferedamountlow` listeners, with the same `Event` object as those listeners, each time `bufferedAmount` falls from above `bufferedAmountLowThreshold` to at or below it. The flow-control contract (what `bufferedAmount` counts, when it shrinks, and a high / low water mark example) is documented in the TSDoc and in "DataChannel backpressure" in `packages/webrtc/README.md`. The `bufferedAmountLow` event, `onbufferedamountlow` and the `"bufferedamountlow"` listeners are notified in this order, synchronously (a browser queues a task), and each one is isolated. During the notification the event's `target` and `currentTarget` are the channel; `currentTarget` is `null` afterwards (#375).
- **`werift-sctp`: `SCTP.send()` resolves with `SctpSendResult`** (`"sent" | "abandoned" | "discarded"`, an `as const` object and a union type exported from `werift-sctp`): `sent` once the message's last chunk is handed to the network (not acknowledged), `abandoned` when PR-SCTP gave it up before that, `discarded` when the association closed (or was stopped) first. It used to resolve `void` in all three cases. Code that only `await`s it is unaffected; code that replaces `sctp.send` with a function returning `Promise<void>` needs to return the result. An empty `userData` now creates no chunk, resolves `sent` at once and no longer consumes a stream sequence number.
- **`RTCDataChannel.binaryType` and `PeerConfig.dataChannelBinaryType`** (#375): `binaryType` is `"nodebuffer"` (werift extension, named after `ws`; the core default, binary messages are `Buffer`s as before), `"arraybuffer"` (the W3C default) or `"blob"`. `dataChannelBinaryType` is a compatibility option (`CompatibilityOptionValues`, `DataChannelBinaryTypeModes`, type `DataChannelBinaryTypeOption`): `"standard"` gives channels the W3C default `"arraybuffer"` (their `binaryType` reads `"arraybuffer"`), `"nodebuffer"` (default) is werift's own value, and `"arraybuffer"` / `"blob"` select those values. `binaryType` changes how a channel's `onmessage` / `"message"` deliver binary messages (one conversion per message, the same object for both; an `ArrayBuffer` is a copy that does not share the `Buffer` pool); text messages are always strings and `onMessage` always gets a `Buffer` or a string. The setter follows the WebIDL enum attribute rules: it converts the value with `ToString` (an object's `toString()` is used, a Symbol is a `TypeError`) and ignores a result that is not one of the three, without an exception (WPT `RTCDataChannel-binaryType.window.js`, now run and gated by the WPT runner). `dataChannelBinaryType` is the initial value of every channel the connection creates, by `createDataChannel()` or announced by the peer; another value is a `TypeError`, and `setConfiguration()` may change it for channels created afterwards. `werift/polyfill` creates its connections with `"arraybuffer"` unless its `peerConnectionConfig` or the constructor configuration gives another value; the upstream WPT runner gets `"standard"` from `compatibility: "standard"`. `RTCDataChannelBinaryType` / `RTCDataChannelBinaryTypes` and `RTCDataChannelMessageData` are exported. Because `"nodebuffer"` is not a DOM `BinaryType`, werift's `binaryType` is not assignable to `lib.dom`'s (the other way round is). Sending `ArrayBuffer` / `Blob` is not part of this change.
- **`new RTCSessionDescription({ type, sdp })`** (#375): the core class accepts the W3C dictionary. The dictionary is converted with the WebIDL rules: its members are read once each (`sdp`, then `type`), `type` is required and converted with `ToString` before it is matched (a missing or unknown one is a `TypeError`), `sdp` defaults to `""` only when it is `undefined` (`null` is `"null"`, a Symbol is a `TypeError`), and `"rollback"` is accepted; see "WebIDL value conversion" in `docs/browser-api-compatibility.md`. The `(sdp, type)` form of earlier versions is kept for a string first argument and behaves as before (a second argument after a dictionary is ignored), and `toJSON()` returns exactly `{ sdp, type }` (so `JSON.stringify` is unchanged). `werift/polyfill` installs this same class as the global `RTCSessionDescription` (and exports it) instead of a separate polyfill class, so `pc.localDescription instanceof RTCSessionDescription` holds from both sides, as in a browser; the polyfill global also accepts the `(sdp, type)` form. `RTCSessionDescriptionInit` / `RTCSdpType` are defined in `sdp.ts` and still exported from the same entry points.
- **`werift/polyfill` always installs an `RTCPeerConnection` subclass** that applies its defaults (`dataChannelBinaryType: "arraybuffer"`), also without `peerConnectionConfig`; instances are still `instanceof` werift's `RTCPeerConnection`.
- **werift tracks are assignable to the DOM `MediaStreamTrack` / `MediaStream`** (`werift`, `werift/polyfill`): passing a werift track to a DOM-typed library such as `mediasoup-client` (`sendTransport.produce({ track })`) no longer needs `as unknown as ProducerOptions["track"]`.
  - `MediaStreamTrack` adds `contentHint` (stored only), `onended` / `onmute` / `onunmute`, `getSettings()`, `getConstraints()`, `getCapabilities()` and `applyConstraints()`. A `getUserMedia()` track reports the `deviceId` / `groupId` / `mimeType` its register was selected by and the supported constraints it was requested with; another track reports its codec (`mimeType`, and `sampleRate` / `channelCount` for audio); an ended track reports only `deviceId` / `groupId`. `applyConstraints()` rejects with `OverconstrainedError` when a required `deviceId` / `groupId` / `mimeType` does not match the current settings or a required (`exact` / `min` / `max`) constraint names anything else (for example `width`), keeping the previous constraints; otherwise it stores the constraints as given (an optional `ideal` on another name included). `clone()` keeps `contentHint`, the settings and the constraints. The new types are `WeriftMediaTrackSettings`, `WeriftMediaTrackConstraints`, `WeriftMediaTrackConstraintSet`, `WeriftMediaTrackCapabilities` and `WeriftConstrainDOMString`.
  - `MediaStream` adds `onaddtrack` / `onremovetrack`, and both classes share `DomEventTarget`, which follows the DOM `EventTarget`: `addEventListener` accepts `{ handleEvent }` objects, ignores duplicates and honors `once` / `passive` / `signal`; an `on<type>` handler is a listener at the position it was first set, called by `dispatchEvent`, and cancels a cancelable event by returning `false`; `dispatchEvent` returns `false` only for a canceled cancelable event; a throwing listener or handler is logged and does not stop the other listeners. werift dispatches `"ended"` on `stop()` and never dispatches `"mute"` / `"unmute"` / `"addtrack"` / `"removetrack"` itself.
  - `werift/polyfill/dom` exports `MediaStreamTrack` / `MediaStream`: werift's classes typed as constructors of the DOM classes, because `lib.dom`'s global `MediaStreamTrack` constructor takes no argument. Its `MediaStreamTrack` augmentation is derived from werift's class (`onReceiveRtp` now also carries `RtpReceiveInfo`).
  - `werift/polyfill` (without `lib.dom`) declares the global `MediaStreamTrack` / `MediaStream` types as werift's classes, so `MediaStreamTrack` can be used as a type and a library's `.d.ts` keeps its track types.
- **Gathering errors are reported** (werift extension, not W3C): `Connection.onGatheringError` (`werift-ice`, optional `IceConnection.onGatheringError`), `RTCIceTransport.onGatheringError` and `RTCPeerConnection.onIceGatheringError` (with the `iceTransport`; no `on<event>` property or `addEventListener` type) give an `IceGatheringErrorReason`: `interface-enumeration-failed` (the interfaces could not be enumerated), `no-candidates` (a generation's gathering ended without any local candidate) or `gathering-failed` (an unexpected exception; also given by `RTCIceGatherer` when an `IceConnection` without `onGatheringError` rejects). **New reasons may be added in a minor release: handle unknown values.** Types: `IceGatheringErrorReason`, `IceGatheringErrorInfo`, `IceGatheringErrorDetails`, `RTCIceGatheringErrorEvent`. Nothing is fired for a replaced generation, after close or for a transport a rollback discards; a throwing listener does not stop the gathering. `icecandidateerror`, `iceGatheringState` and `setLocalDescription()` behave as before.
- **ICE: the selected pair fails over to another path without an ICE restart, as in libwebrtc** (`werift-ice`, `werift`). With semi-aggressive nomination (the default) or negotiated renomination, a full ICE agent used to stay on its selected pair until consent expired (30 s) and then went `failed`, needing an ICE restart, even when another path (a TURN relay, another interface) still worked.
  - After the selection the agent keeps one backup pair per local socket (UDP socket or TURN allocation; on the selected pair's socket, a lower pair to another remote address, so a break of only the remote side is covered too) and checks it (900 ms until it answered 3 times, then every 2–3 s). A socket whose backups all failed is tried again after 1, 2, 4, 8 and 16 s and then every 16 s, so a path that comes back later is found again. Lower-priority pairs of other sockets are no longer failed at the selection, and candidates gathered or trickled after it still pair with them; one that outranks a socket's backup replaces it.
  - Once a consent check of the selected pair goes unanswered, or nothing was received on it for 2.5 s, consent checks are sent every 900 ms (an idle pair is checked about every 2.5 s); checks keep this pacing while earlier ones still wait for their RTT-based response timeout, so slow responses are not cancelled and a dead high-RTT path is still told within about 10 s; a check counts as unanswered at its RTT-based deadline, but a late response within 5 s still counts. The pair is unwritable after 5 unanswered checks and 5 s without a response (about 5–10 s after the path broke); a controlling agent then nominates the best writable backup (`USE-CANDIDATE`, or the next `NOMINATION` value) and the selection, consent and data move to it. The old pair stays a backup, and the selection moves back to its socket only after 3 consecutive responses, also when the old pair answered again while the failover nomination was in flight.
  - Faster than the unwritable rule, as libwebrtc: a controlling agent moves to a backup that receives once the selected pair has not been receiving for 1 s (`receiving_switching_delay`, `RECEIVING_SWITCHING_DELAY`), counted from the later of 2.5 s of silence and one of its checks going unanswered: about 4 s after a path broke both ways instead of 5–10 s (the switch is the receiving rule of the next entry). An idle pair whose checks are answered, a slow path whose checks are answered in time, a shorter loss burst and a one-way break (the peer's data still arrives) keep the unwritable rule. A controlled agent follows the peer's USE-CANDIDATE in that state too. The first consent check after a selection now also comes after 2.5 s of silence instead of the 4–6 s consent interval.
  - A path reported gone fails over at once: a UDP send that fails with a routing error (`ENETUNREACH`, `EHOSTUNREACH`, `ENETDOWN`, `EHOSTDOWN`, `EADDRNOTAVAIL`, `EPERM`; `PATH_BROKEN_SEND_ERRORS`) or a TURN allocation that is lost (its TCP / TLS connection to the server closed, a Refresh failed, the server unreachable) makes the monitored pairs on that path unwritable (`Protocol.onPathBroken`, `TurnProtocol.onAllocationLost`). STUN messages are sent with a completion callback, and application data one datagram per 100 ms per socket (`DATA_SEND_CONFIRM_INTERVAL_MS`), so a route that goes away while data flows fails over within about 100 ms; without a writable backup the agent is `disconnected` at once. `werift-common`: `Transport.send()` takes `TransportSendOptions` (`confirm`: a datagram's send error rejects), and `TcpTransport` / `TlsTransport` (and `Transport.onClosed`) report a connection the peer closed.
  - The thresholds are options, after libwebrtc's `RTCConfiguration`: `IceOptions.failover` / `PeerConfig.iceFailover` (`IceFailoverOptions`: `unwritableMinChecks` 5, `unwritableTimeout` 5000 ms, `receivingTimeout` 2500 ms, `receivingSwitchingDelay` 1000 ms by default; an invalid value keeps its default).
  - Every eligible pair on another path (another socket, or another remote address on the selected socket), above or below the selection, is a backup candidate whatever the role; a controlling agent leaves the pairs above the selection on its socket to the checks that move the selection up, which are now retried every 16 s for as long as failover applies and checked at once when no backup is writable.
  - A controlled agent monitors too, but follows the peer's nomination and data (as before); while its selected pair is down, the peer's USE-CANDIDATE on a valid pair moves the selection without waiting for data. A Chrome E2E test (`e2e/tests/ice/failover.test.ts`) cuts werift's host sockets while werift is controlling: werift moves to its TURN relay pair and Chrome (controlled) follows, with semi-aggressive nomination and with renomination.
  - `IceState` / `iceConnectionState` go `disconnected` while neither the selected pair nor a backup is writable, back to `connected` once the selected pair works again (it answers, or the selection moved to a backup), and `failed` when consent expires with no writable backup. When consent expires while a backup is writable, nothing more is sent and the agent is `disconnected` for up to 10 s (`FAILOVER_CONSENT_EXPIRED_GRACE`) waiting for the selection to move to the backup (a controlled agent waits for the peer's nomination); otherwise it fails, so an ICE restart can recover. `RTCPeerConnection.connectionState` now also returns from `disconnected` to `connected`.
  - Unchanged: regular nomination, ICE-TCP selections and ICE-lite (either side). New constants with their libwebrtc names (`WEAK_OR_STABILIZING_WRITABLE_CONNECTION_PING_INTERVAL`, `STABLE_WRITABLE_CONNECTION_PING_INTERVAL`, `MIN_PINGS_AT_WEAK_PING_INTERVAL`, `CONNECTION_WRITE_CONNECT_FAILURES`, `CONNECTION_WRITE_CONNECT_TIMEOUT`, `WEAK_CONNECTION_RECEIVE_TIMEOUT`, `DEAD_CONNECTION_RECEIVE_TIMEOUT`, `FAILOVER_BACKUP_ATTEMPTS`, `FAILOVER_RECOVERY_RESPONSES`, `BACKUP_UNKNOWN_RTT_RESPONSE_TIMEOUT`, `FAILOVER_CONSENT_EXPIRED_GRACE`). See "Failover of the selected pair" in the `werift-ice` README.
- **ICE: the controlling agent chooses the selected pair by receiving state, priority and RTT, as libwebrtc's ICE controller** (`werift-ice`, `werift`). Within the failover scope above (semi-aggressive nomination or renomination, full ICE, not ICE-TCP), a controlling agent compares its selection with each backup whenever a check, consent check or backup check is answered or goes unanswered: writable first, then receiving, then priority, then RTT.
  - Receiving: a backup that is receiving wins over a selection that is not receiving (nothing received for 2.5 s and a check unanswered; `IceFailoverOptions.receivingTimeout`) once the selection has not been receiving for 1 s (`receivingSwitchingDelay`, `RECEIVING_SWITCHING_DELAY`); the decision is checked again then and a selection that recovered meanwhile stays. This is the receiving rule of the failover entry above: among several backups the receiving one wins, then the higher priority, then the lower RTT, and the old pair waits for 3 responses before the selection moves back, as after a failover. A pair counts as not receiving from the later of the 2.5 s of silence and the unanswered check, so when the check is confirmed unanswered late the 1 s hold starts at that check; a switch made within the hold (by RTT, for example) is not taken as a failover and the old pair is not demoted.
  - RTT: between pairs of equal priority (relays on two TURN servers, for example) the selection moves to a pair whose smoothed RTT is at least 10 ms lower (`RTT_SWITCH_MIN_IMPROVEMENT`). `CandidatePair.smoothedRtt` is the median of the last 5 samples (`RTT_SMOOTHING_SAMPLES`, at least `RTT_SMOOTHING_MIN_SAMPLES` = 3), so one outlier does not cause a switch; `CandidatePair.recordRoundTrip()` records a sample. `getStats()` `currentRoundTripTime` stays the last sample.
  - Each move nominates the new pair (`USE-CANDIDATE`, or the next `NOMINATION` value); a controlled agent still only follows the peer. The RTT values are constants, not options (the receiving thresholds are the `IceOptions.failover` / `PeerConfig.iceFailover` options above); network cost is not used. See "Choosing the selected pair" in the `werift-ice` README.

### 🐛 Bug Fixes

- **A renegotiation while the first connectivity checks run no longer leaves ICE without a nomination** (`werift-ice`, `werift`, RFC 8445 §6.1.1). Each `setLocalDescription` assigned the ICE role again (offer → controlling, answer → controlled) until a pair was selected. A later offer or answer without an ICE restart while the checks were still running (for example a re-offer from the answerer, or glare, right after the first answer) could leave both agents controlling or both controlled. When the checks had already succeeded, no agent nominated, so the connection stayed `checking` and the DTLS transport never started. The role set by offer/answer now stays fixed once a generation's checks begin (`Connection.iceControlling` setter); only a role-conflict repair changes it, and an ICE restart lets offer/answer assign it again, as before.
- **ICE consent no longer expires while the peer keeps answering on a high-RTT or lossy path** (`werift-ice`, RFC 7675). Since #649, a consent request waited only for its RTT-based timeout (2×RTT + 200 ms, at least 500 ms, 1 s when the RTT is unknown) and the next request (4–6 s later) cancelled the previous one; with failover, the transaction stayed open for at most 5 s. A response that came later was dropped as an unknown transaction, and since the RTT estimate is only updated by a response that was taken, a path whose RTT rose above the estimate after the selection (e.g. 10 ms at the selection, then 1 s) dropped every genuine response and went `failed` after 30 s. A round trip longer than the interval (≥ 4–6 s) was always dropped. Reported downstream with netfilter-injected delay and loss (500 ms / 2000 ms one way + 20 % loss, about 1 in 4 runs failed).
  - Each consent request is still sent once (no retransmission, a fresh transaction ID, every 4–6 s), but its transaction now stays open for `CONSENT_TIMEOUT` (30 s), whatever the RTT estimate or the nomination mode (regular, ICE-TCP, ICE-lite peers too), and a later request no longer cancels it, so a response to an earlier request still refreshes the consent (§5.1: "the response may be for a previous request"). At most 35 requests are open at once (30 s of the 900 ms failover weak interval, plus one; the oldest one ends beyond that, so the limit never ends a request that can still be answered within 30 s); expiry, `close()`, an ICE restart and a new selection end them all, so a response after the expiry still does not bring consent back.
  - The checks on a response are unchanged: remote address, MESSAGE-INTEGRITY with the remote password, transaction ID, consent session, selected pair, remote generation and password. The pair's current RTT comes from the newest request answered (an older response arriving out of order only counts in the RTT totals).
  - `consentResponseTimeoutMs()`, `CONSENT_RESPONSE_TIMEOUT` and `CONSENT_RESPONSE_TIMEOUT_MIN` are kept: they are now the deadline after which a consent request counts as unanswered (failover) and the response timeout of a backup check, not the lifetime of the consent transaction.
  - The downstream patch's other part, an extra consent check 1 s after 5 s without a response, is not adopted: RFC 7675 §5.1 forbids an interval below 4 s, and it adds load on a lossy path. Failover's 900 ms pacing of a weak selected pair (libwebrtc's) is unchanged and applies only with failover.
  - Separate from #860 (the `disconnected` transition when a path is really gone) and #730 (consent failures caused by a starved event loop).
- **ICE no longer fails at once when it has no candidate pair of its own to check** (`werift-ice`, `werift`): a peer that offers only active TCP candidates (Firefox with ICE-TCP, RFC 6544) or no reachable candidate left werift's check list empty after end-of-candidates, and `connect()` threw `ICE negotiation failed` (`iceConnectionState` `failed`) about 1 ms after `checking`, before the peer's own check arrived. Now the agent waits for a check from the peer, which adds a peer-reflexive pair and connects. Without one it fails after `incomingCheckTimeout` seconds (`IceOptions`; `iceIncomingCheckTimeout` in `PeerConfig`; default 30, `0` keeps the immediate failure). An ICE-lite agent, which sends no checks and used to wait for a nomination indefinitely, waits the same time whenever it has no candidate pair, also while it still gathers; it fails as soon as its gathering ends without a socket that could receive a check. The deadline does not move once the wait began, and concurrent `connect()` calls of one generation all wake when a pair is added. An agent without any local candidate still fails at once. When the generation `connect()` checks ends, `connect()` settles at once wherever it waits (scheduling, the wait for a check, the wait for the result, ICE-lite): an ICE restart (local or remote-only) cancels it with the new `IceRestartedError` and it no longer checks the next generation's pairs; `close()` fails it with `ICE negotiation failed` (a connect() waiting for the result, or an ICE-lite one, used to stay pending after a restart or close). `RTCIceTransport` and `RTCPeerConnection` leave the state of the next generation alone: the outcome of a replaced generation (failed, cancelled or connected), also for a connect awaiting checks another one started, no longer sets `failed` (or `connected`). An `RTCIceTransport.start()` whose generation ends (restart, remote-only restart, `stop()`) before its checks begin no longer runs them on the next generation: it is cancelled and the next generation's checks start once. This also holds when a synchronous state event subscriber (`checking`, `new`, `connectionstatechange` `connecting`) restarts ICE or starts the next generation.
- **An ICE restart no longer keeps the previous gathering's candidates until close** (`werift-ice`). Each candidate gathering raced its work against a promise that resolves only when the agent closes, so every restart left a reaction on it that held that generation's gathering results (candidates) for the agent's lifetime. Gathering now waits on the agent's close through an abort listener that is removed when the gathering settles.
- **`os.networkInterfaces()` failures no longer crash the process or break gathering** (`werift-ice`, `werift`). Where enumerating the interfaces is not allowed (e.g. systemd `RestrictAddressFamilies=` denying `AF_NETLINK`), Node.js throws a `SystemError` (`uv_interface_addresses returned Unknown system error 97`):
  - mDNS (remote `.local` candidates): multicast-dns enumerated the interfaces itself when its socket started listening and every 5 seconds, and that throw was an `uncaughtException` that ended the process; so was an `error` event of the socket (`EACCES` / `EADDRINUSE`) without a listener. `MdnsLookup` now creates multicast-dns with its `multicast: false` option, so multicast-dns never enumerates, and joins the multicast group itself on the same socket (bound to `0.0.0.0` as before; the first IPv4 address of every interface, checked again every 5 seconds, where a failed enumeration is only a `warning`); when the enumeration fails it opens no listening socket and every lookup rejects at once, and a socket `error` rejects the pending and later lookups. The candidate is dropped, as on a lookup timeout. The public shape of `MdnsLookup` is unchanged.
  - Gathering: the failure used to reject `gatherCandidates()` and leave the generation started but never ended, so `iceGatheringState` stayed `"gathering"` without end-of-candidates and a second `gatherCandidates()` reported `"completed"` with no candidate. Gathering now goes on without enumerated addresses (explicit `interfaceAddresses`, `additionalHostAddresses` on a wildcard socket, STUN and TURN still work) and completes. An unexpected exception in `gatherCandidates()` ends the generation's gathering (it still rejects).
  - `nodeIpAddress()` / `getHostAddresses()` keep throwing; their JSDoc now states it (`@throws`).
- **DTLS handshake fragments are reassembled only once every byte was received** (`werift-dtls`, RFC 6347 §4.2.3). A fragmented handshake message used to be assembled as soon as the last fragment received ended the message, so when the fragment ending a large ClientHello (e.g. Chrome's post-quantum `X25519MLKEM768` one, three fragments) arrived before its first fragment over TURN / WAN, the missing bytes were zero-filled and the handshake failed (`dtls cipher suite negotiation failed`). Fragments are now grouped by record epoch, `msg_type`, `message_seq` and `length`, and a message is delivered only when `[0, length)` is fully covered, whatever the order. Duplicate fragments and retransmissions split at other boundaries are accepted when the overlapping bytes match; a mismatch discards the partial message. Truncated fragments, fragments beyond their message length and messages over 64 KiB are dropped. The buffered messages (16), bytes (256 KiB), byte ranges per message (256) and their lifetime (60 s without a new fragment, checked when the next fragment is added) and are freed when the connection ends are bounded. Unfragmented messages and their retransmissions are delivered as before. The unvalidated internal `FragmentedHandshake.assemble()` / `findAllFragments()` are removed.
- **`addIceCandidate()` resolves an empty `sdpMid` by `sdpMLineIndex`** (Pion interoperability): Pion's `ICECandidate.ToJSON()` (and SFUs built on it) send `sdpMid: ""` with a numeric `sdpMLineIndex`, which werift rejected with `OperationError("Media section for sdpMid was not found")`. Such a candidate (or end-of-candidates) now targets the m-line of the index, as libwebrtc and Firefox do, before it is queued, so the ICE generation choice and the m-line it is recorded in agree; a `usernameFragment` that does not match that m-line, or an index out of range, is still an `OperationError`. An empty `sdpMid` without an index is still rejected, now with `"sdpMid is empty and no sdpMLineIndex was given"`. The W3C steps reject an empty `sdpMid`; werift keeps the interoperable behavior (no upstream WPT subtest covers it).
- **Rollback of a remote offer keeps a transceiver `addTrack()` took after its track was detached** (#817, W3C webrtc-pc rollback). A transceiver created by a remote offer that the application took with `addTrack()` and then emptied with `sender.replaceTrack(null)` or `removeTrack()` was removed and stopped by `setRemoteDescription({ type: "rollback" })`; it now stays (the same object, not stopped, without MID) like one that still has its track. A remote-created transceiver `addTrack()` never used is still removed, also after only `stop()`, a direction or codec preferences (WPT `RTCPeerConnection-setRemoteDescription-rollback.html?rest` "rollback of a remote offer should keep a transceiver without tracks" is now allowlisted).
- **Rollback after `addTrack()` added a transceiver during a pending remote offer no longer throws.** When no transceiver could be reused, `addTrack()` created one without a DTLS transport and attached it afterwards, so `setRemoteDescription({ type: "rollback" })` returned it to a created state without a transport and failed with `TypeError`. The transceiver now gets its DTLS transport when it is created.
- **RID simulcast from a description that also lists `a=ssrc` / `a=ssrc-group:FID` gives the RID tracks only, and its RTX is restored onto them** (Firefox simulcast). On an m-line the remote sends by RID, werift created an extra SSRC track besides the RID tracks, and the high layer's RTX was restored onto that track instead of the `high` RID track. The `a=ssrc` lines of such an m-line now create no track or media route (the layer SSRCs are learned from RID / repaired-RID packets, as for Chrome's simulcast) and `transceiver.onTrack` fires once per RID; the FID pairs only map an RTX SSRC to its media SSRC, so RTX is restored onto the right RID track also without the `repaired-rtp-stream-id` extension (the mapping follows the negotiation: staged while pending, replaced at commit, restored on rollback). `a=rid` restrictions (`a=rid:h send max-width=1280`) are parsed apart from the direction (`RTCRtpSimulcastParameters.restrictions`, new; `direction` used to hold them too), and an answer no longer echoes the offerer's restrictions. Non-simulcast SSRC receive and Chrome-style simulcast are unchanged.
- **Looped file playback keeps the VP8 PictureID when the answer adds fmtp** (`createFileMediaPlayer`): the packetizer was created again when `track.codec.parameters` changed (for example Firefox answers VP8 with `max-fs` / `max-fr`), so the PictureID jumped to a new random value at the next loop. The packetizer is now created again only when a value it reads changes (mime type, clock rate, channels, and the H.264 `packetization-mode`).
- **Dummy media sources pick a random SSRC, initial sequence number and initial PictureID** (`werift/nonstandard` `Navigator` dummy media, `createDummyRegister`, RFC 3550 §5.1 / §8.1). They were numbered from a process-wide counter (deterministic per source); each source now draws its own values when it is created, so tracks from different `MediaDevices` or registers sent on one PeerConnection never share an SSRC. Sequence numbers and PictureIDs still advance by one per packet / frame.
- **WebM file saving survives a transient file access error and reports write failures** (`werift-rtp` `saveToFileSystem`, `werift` `MediaRecorder`):
  - `saveToFileSystem(path)` writes each chunk at its byte offset (positional write) instead of appending it, so a retried chunk is never appended twice. It opens and closes the file once per chunk and once for the eol header rewrite, and closes it on every failure path. The Segment size is computed from the bytes written instead of a separate `stat(path)`, and bytes past the end are truncated on eol.
  - A transient file access error (`EBUSY`, e.g. a sharing violation on a CIFS/SMB mount or a FUSE file system) is retried a limited number of times (at most 8 attempts and 1 s of waiting, with a short backoff). Any other error, including `EPERM`, `EACCES` and `ENOSPC`, fails immediately as before; once the limits are reached the last error is thrown with its `code`. Nothing waits on the normal path. After a failure the writer writes nothing more.
  - The first chunk truncates an existing file, so a file that could not be deleted (`unlink` failed) is replaced instead of being appended to and corrupted.
  - `WebmOutput.position` (new, optional): the byte offset of `saveToFile` from the start of the output, or the total output length on the `eol` output. `WebmBase` sets it. A writer created per output (as `MediaRecorder` used to do) keeps working; for outputs without `position`, it appends after the current end of the file.
  - `WebmCallback.onError` reports a failed output callback instead of an unhandled rejection. `MediaRecorder` forwards a WebM write failure to `onError` (as for Ogg), stops the recording and its RTP / RTCP subscriptions, and `stop()` no longer waits 5 seconds for it. A WebM write failure used to crash the process with an unhandled rejection.
  - `MediaRecorder` creates one WebM file writer per recording.
- **SCTP no longer floods the network with small DataChannel messages** (`werift-sctp`, `werift`). Two congestion-control bugs made a burst of small messages (for example 7,200 one-byte messages) send about 250 datagrams per message: 1.8 million datagrams, almost all dropped by the receiver's socket buffer, so the transfer took 25 s instead of about 3 s, and the ICE consent checks drowned in the flood until consent expired and the connection failed (`npm run memleak` `datachannel`).
  - flightSize, cwnd and the peer's receive window counted only the user data of a DATA chunk. A cwnd of a few KiB therefore let thousands of 1-byte messages be in flight, each in its own datagram. A chunk now counts its whole size on the wire: its 16-byte header and the payload padded to 4 bytes (RFC 9260 §6.1, as libwebrtc's dcsctp and usrsctp book it; `dataChunkBookSize()` is exported).
  - A chunk was fast-retransmitted again every 3 SACKs that still reported it missing. Most of those SACKs had been sent before its retransmission arrived, so under loss one chunk was resent up to 74 times. A chunk is now fast-retransmitted once (RFC 9260 §7.2.4); if that retransmission is lost too, the T3-rtx timer resends it, which makes it eligible for Fast Retransmit again.
- **DataChannel stream IDs follow the DTLS role and are assigned when it is decided** (#815, RFC 8832 section 6, W3C webrtc-pc 4.4.1.6). The DTLS client uses even IDs and the DTLS server odd ones; werift used to derive the parity from the ICE role, which only matched with `a=setup:actpass` / `active`, so an explicit `a=setup:passive` answer (SFUs such as mediasoup, the #815 report) made both peers pick IDs of the same parity and collide. An in-band channel now gets its ID as soon as a local or remote answer / pranswer (or the DTLS start resolving `auto`) decides the role, before the description's promise resolves, so `channel.id` is readable before the SCTP association connects; a channel created after that gets its ID at once. Before the role is decided `id` stays `undefined`. The lowest free ID of the parity is used (negotiated channels of either parity and channels the peer opened are skipped, a closed channel's ID is reused); when none is left the channel closes with an `OperationError` (`error`, then `close`), or `createDataChannel()` throws it once the role is decided. A rollback or a final answer rejecting the application gives back the IDs of channels whose DCEP OPEN was not sent; the next answer assigns them again. A DCEP OPEN from the peer on an ID this side uses is no longer acknowledged: as RFC 8832 section 6 requires, the stream is reset (RFC 8831 section 6.7), so the peer's channel closes instead of staying `connecting`, and the local channel on that stream closes too (both ends claimed it; channels on other streams are not affected). A DCEP OPEN on an unused stream ID of this side's parity (the peer violating the odd/even rule of its DTLS role) is not acknowledged either: the stream is reset and nothing is announced (unless the ICE and DTLS roles are reversed, see "The DTLS role decides the SCTP initiator" under Breaking changes). A peer choosing the parity from the ICE role (werift up to this release) is affected only with an explicit `a=setup` that reverses the ICE / DTLS pairing, where its IDs already collided. The SCTP initiator follows the DTLS role as well (see "The DTLS role decides the SCTP initiator"). `RTCDtlsTransport.onRoleChange` (`Event<[DtlsRole]>`) is new; `RTCDtlsTransport.role` is now an accessor.
- **`pc.close()` closes every DataChannel, also one still without a stream ID, and a throwing DataChannel listener no longer breaks it** (#815). An in-band channel created before the DTLS role was decided used to stay `connecting` after `pc.close()`; it now closes and fires `close` like the others, at the same point: `connectionState`, the SCTP and the DTLS transports are already `closed` when its `close` listeners run. The `open` / `closing` / `close` listeners of a DataChannel (`stateChange`, `stateChanged`, `onopen`, `onclosing`, `onclose`, `addEventListener`) are isolated as DOM events are: a throwing one is logged and skips neither the later listeners nor the other channels, and no longer makes `pc.close()` or a rollback reject halfway (leaving DTLS / ICE running).
- **A `close` listener can create a DataChannel on the stream ID of the channel that closed** (#815, W3C: IDs are reusable after the close event). A channel closes as RFC 8831 section 6.7 describes: the first reset of its stream (ours from `close()`, or the peer's) makes it `closing`, a reset by the peer is always answered with ours (werift used to answer only for a stream it had sent ordered data on, so after unordered data or none a browser peer stayed `closing`), and `close` fires once both directions are reset. Its ID is released just before `close` fires; it used to be released afterwards, so a `close` listener got the next ID, or an `OperationError` when it was the only free one. No reset of the closed channel is left to arrive, so a channel created on the ID is neither closed by it nor left `open` when the peer closes it (ordered or unordered, negotiated or in-band, whichever end closes). A peer that never resets its side (werift up to this release, for a stream it sent no ordered data on) is waited for 5 seconds (one retransmission of a lost reset request at the SCTP initial RTO of 3 seconds fits in it); then the channel closes anyway, but its stream ID stays in use until the peer's reset arrives (or the association ends): a late reset could otherwise close a channel created on it, so an automatic ID skips it and a negotiated channel on it throws `OperationError` (RFC 8831 section 6.7: a stream is reusable after its reset). While a channel is `closing`, a message from the peer is discarded, as W3C webrtc-pc ("Receiving messages on a data channel": not `open` discards it) and libwebrtc do; it used to be delivered. A DCEP OPEN on the stream of a closing channel the peer had opened is ignored (no ACK). `werift-sctp`: `SCTP.onReconfigStreams` passes the direction as a second argument (`"outgoing"` when the peer performed our reset, `"incoming"` when we performed the peer's); `SCTP.isOutgoingResetPending(streamId)` is new.
- **A throwing `datachannel` / `message` / `bufferedamountlow` listener no longer breaks the DataChannel** (#815). Every listener of these notifications (`pc.onDataChannel`, `ondatachannel`, `addEventListener("datachannel")`; `channel.onMessage`, `addEventListener("message")`, `onmessage`; `channel.bufferedAmountLow`, `addEventListener("bufferedamountlow")`) is isolated as DOM events are: a throwing one is logged and skips neither the later listeners, nor the `open` of a channel the peer announced and its DCEP ACK, nor later messages; it is no longer an unhandled rejection of the SCTP receive path. A DCEP ACK on an unknown stream ID and a message with an unknown PPID are ignored (logged) instead of rejecting there. `createDataChannel()` now also throws `InvalidStateError` from a listener running while `pc.close()` closes the connection (W3C `[[IsClosed]]`), as it already did once `close()` had finished, so no channel outlives the close.
- **`send("")` / `send(Buffer.alloc(0))` sends an empty message** (RFC 8831 §6.6): it was silently dropped. It now goes out as one byte with PPID 56 (`WEBRTC_STRING_EMPTY`) / 57 (`WEBRTC_BINARY_EMPTY`) and arrives as `""` / an empty `Buffer`, in order with the other messages; it adds 0 to `bufferedAmount` and `bytesSent` and 1 to `messagesSent`, and the receiver adds 0 to `bytesReceived` (it used to add 1). These DataChannel changes are about the API and the semantics of `bufferedAmount` / `close()` only; the queue performance (#730) was fixed in v0.26.0 and is unchanged here.
- **`close()` no longer drops what was sent before it** (W3C closing procedure): a channel closed while the association is not established yet (for example a negotiated channel before the connection) stays `closing`, keeps its queued messages, sends them once the association is established and then resets its stream, so the peer gets every message before `close`. A `closing` channel's queued messages are sent instead of dropped. A channel whose DATA_CHANNEL_OPEN was not sent yet (the peer does not know it) still closes at once without sending anything, and a channel whose transport stops before the association is established closes and drops its messages (they stay in `bufferedAmount`). `send()` on a `closing` / `closed` channel is ignored (it used to be queued and dropped).
- **`close()` in a `datachannel` handler no longer resets the stream before the DATA_CHANNEL_ACK**: the ACK is handed to SCTP before the handler runs, so the opener sees the channel open and then closed. A channel closed in the handler is no longer set back to `open` after it, and a late ACK no longer reopens a `closing` channel. A DATA_CHANNEL_ACK for an unknown stream (late, for a channel already closed) is logged and ignored instead of throwing `"channel not found"` as an unhandled rejection (#870).
- **`RTCDataChannel` fires the `closing` event** to `addEventListener("closing")` listeners; only `onclosing` was called.
- **`RTCDataChannel.onopen` / `onclose` / `onclosing` / `onbufferedamountlow` receive the event** (W3C event handlers): the same `Event` object the `addEventListener` listeners get, with `type` set; they were called without an argument. A handler that takes no argument (for example a Promise's `resolve`) is still accepted. `onmessage` gets the same event object as the `message` listeners, with `type: "message"` (it got a separate object without `type`).
- **A `send()` no longer waits for later messages** (`werift-sctp` `SCTP.send()`, and so `RTCDataChannel.bufferedAmount`): it resolves once its own message is handed to the network, even while the lower transport is still sending a message queued after it. It used to wait for the whole transmit pass, so `bufferedAmount` kept bytes already handed over and `bufferedamountlow` came late while a later send was slow.
- These DataChannel changes remove the need for the workarounds that read `dataChannelQueue`, call `dataChannelFlush()` / `addBufferedAmount()` or watch `sctp.flush` / `outboundQueue`: `ch.close()` and `ch.send("")` are enough. The guarantees are in the TSDoc of `RTCDataChannel.close()` / `send()` and in `packages/webrtc/README.md`. werift deliberately adds no non-standard "unacknowledged amount" API; the close guarantee covers "everything sent before `close()` arrives".
- **A werift-initiated ICE restart reconnects with Firefox** (`werift-ice`). Firefox applies the restart offer and checks the new ufrag before its answer reaches werift, sends an answer without candidates, and does not repeat a check that succeeded. werift answered those checks but dropped what they taught at the commit, so the new generation had no pair: werift stayed `checking` and Firefox received no more RTP or DataChannel messages from werift. Checks the staged generation received before the answer (at most 32) are now replayed when the answer commits that generation, as the early checks of a first connection are. Only checks addressed to the committed ufrag, from the remote ufrag of the answer and on a socket the generation still uses, are replayed, each path with the largest nomination (USE-CANDIDATE / NOMINATION) it received, and with the same SPED handling as an early check. A replacement offer or a rollback carries nothing, and a restart negotiated with a pranswer keeps its provisional checklist's behavior.

### 🗑️ Deprecations

- **`RTCDataChannel.addBufferedAmount()`** is `@deprecated` / `@internal` and will be removed in v0.30.0; its behavior is unchanged in this release. werift maintains `bufferedAmount`; send an empty message with `send("")`.
- **`werift-sctp`: `SCTP.outboundQueue`** is `@deprecated` / `@internal` and becomes private in v0.30.0. Use the `SctpSendResult` of `SCTP.send()`, or `RTCDataChannel.bufferedAmount` / `bufferedamountlow` in werift. `FifoQueue` stays exported.
- `RTCSctpTransport.dataChannelQueue` / `dataChannelFlush()` were always private and their structure may change without notice; a hand-queued 3-element entry (the empty-message workaround) still works in this release only.

### 🧪 Testing & tooling

- **`npm run pbt:deep -- --baseline <worktree>`** (#890): a confirmed property-test failure is replayed in a baseline worktree (for example a `develop` worktree) with the same file, title pattern and environment; one that fails there with the same signature is reported as pre-existing and leaves the exit code alone. ### ⚠️ Breaking changes

- **The spec / browser value of the compatibility options is `"standard"`** (`certificateScope`, `mLineReuse`, `keyFrameRequestRouting`; also `transceiverPairing`): each option takes `"standard"` for the behavior the specifications and browsers have, and a value naming werift's own behavior. The old names of the spec / browser side and of `keyFrameRequestRouting`'s default are still accepted on input, so existing configurations keep their behavior, but `getConfiguration()` now returns the current name, the TypeScript types `MLineReuse` / `KeyFrameRequestRouting` / `CertificateScope` and `KeyFrameRequestRoutingModes` list the current names, and the `TypeError` message lists them. `SDPManager` (`mLineReuse`) and `RtpRouter.keyFrameRequestRouting`, set directly, accept only the current names. Defaults and behavior are unchanged.

  | Option | Up to v0.27.0 | Now (default first) | Old names still accepted |
  | --- | --- | --- | --- |
  | `certificateScope` | `"process"` (default) / `"peerConnection"` | `"process"` / `"standard"` | `"peerConnection"` |
  | `mLineReuse` | `"compatible"` (default) / `"aggressive"` | `"standard"` / `"aggressive"` | `"compatible"` |
  | `keyFrameRequestRouting` | `"compatible"` (default) / `"strict"` | `"fallback"` / `"standard"` | `"compatible"`, `"strict"` |

- **ICE nomination: semi-aggressive by default, and the controlled side follows later nominations** (`werift-ice`, `werift`). A controlling full ICE agent used aggressive nomination for UDP / relay pairs and the controlled side kept the first pair nominated to it; now the controlling side nominates semi-aggressively (as libwebrtc / Chrome), the controlled side uses the pair with the largest nomination, and `RTCIceTransport.getSelectedCandidatePair()` returns `null` until a pair is nominated. - **A malformed `a=rtcp` is a parse error** (#355): `SessionDescription.parse()` / `setRemoteDescription()` reject an `a=rtcp` whose port is not a decimal 1–65535 or whose value is neither `<port>` nor `<port> IN IP4|IP6 <address>` (it used to be stored as `NaN` or throw `"exception"`). See the `a=rtcp` entry under Bug Fixes.
- **`DtlsSocket.close()` returns a promise, and only close_notify closes a DTLS connection** (`werift-dtls`): a warning alert other than close_notify no longer closes it, and a fatal alert makes the transport `failed` instead of being swallowed. See "DTLS alerts are sent and received" and "A fatal DTLS alert is no longer swallowed".

- **`bundleCandidates` peer configuration** (`"legacy"` default / `"compatible"`, Issue #269): decides which m-lines of a BUNDLE group carry the local ICE candidates. werift writes every candidate and `a=end-of-candidates` on each m-line (`"legacy"`), so in a long BUNDLE session each renegotiation that adds m-lines (`addTrack`, `createDataChannel`) grows the SDP by "m-lines × candidates" (12 candidates and 7 m-lines: 84 `a=candidate` lines). `"compatible"` writes them as Chrome does: a transport's candidates appear once, on the tag m-line of its BUNDLE group, in every offer, answer and pranswer (including the first answer and a first `max-bundle` offer; RFC 8843 §7.1.3 / §7.3.1, RFC 8859). ### 🐛 Bug Fixes

- **The codecs of a remote offer are resolved with the transceiver it is applied to** (#816): `setRemoteDescription(offer)` resolves codecs before its implicit rollback, replacement or unapplied-`createOffer` revert, and used to pair m-lines with the transceivers as they were before (a local transceiver whose MID only the rolled-back local offer gave could lend its codec preferences or track to an m-line another transceiver then took). Both now pair with the state after them.
- **A replacement remote offer keeps the transceiver the replaced one created for a MID it describes again**, instead of dropping its MID and pairing it again by kind.
- **`a=rtcp` without an address is accepted, and `a=rtcp` / `a=rtcp-mux` survive a parse and re-serialization** (#355, RFC 3605). `SessionDescription.parse()` threw `"exception"` on `a=rtcp:<port>` (sent by SIP/WebRTC gateways such as RingCentral, FreeSWITCH and Asterisk), so `setRemoteDescription()` failed. The address-less form now parses with `MediaDescription.rtcpHost` left `undefined` (the effective RTCP address is the media-level `c=`, else the session-level `c=`) and is serialized back as `a=rtcp:<port>`. `a=rtcp-mux` is now serialized whenever `rtcpMux` is `true`, independent of `a=rtcp`, so `remoteDescription.sdp` no longer drops an `a=rtcp-mux` received without `a=rtcp`. **A malformed `a=rtcp` is now a parse error** (it used to be stored as `NaN` or throw `"exception"`): the port must be a decimal 1–65535 and the value either `<port>` or `<port> IN IP4|IP6 <address>`; the message includes the value (`invalid a=rtcp attribute: "abc"`). `rtcpAttributeFromSdp()` / `rtcpAttributeToSdp()` are exported; the parsed addrtype is kept in `MediaDescription.rtcpAddrType`, so `a=rtcp:<port> IN IP4 host.example.com` is not re-serialized as `IP6`. SDP created by werift is unchanged: rejected / stopped m-lines (port 0) still carry neither `a=rtcp` nor `a=rtcp-mux`.
- **RTP from a remote m-line without `a=ssrc` is received (#356).** SIP gateways, SBCs and media servers (RingCentral, for example) send offers with neither `a=ssrc` nor RIDs; their RTP used to be dropped with `ssrcReceiver not found`. Following RFC 9143 section 9.2, an SSRC no description names is now learned from its first packet: for the m-line its MID header extension names, or, without a MID, for the m-line on that DTLS transport whose payload type no other receiving m-line uses, if that m-line has no SSRC / RID in SDP (BUNDLE audio and video with distinct payload types are told apart). The packet goes to the track `ontrack` already announced, from the first packet on, and remote SRs, NACK / PLI and `getStats()` (`inbound-rtp`) use the learned SSRC. Ambiguous candidates, another transport, RTX and unknown payload types are dropped as before (the `werift:packages/webrtc/src/media/router.ts` debug log names the reason). A new SSRC (a re-INVITE, a media server switch) is learned beside the earlier ones, which keep reaching the same track, so late packets of the old stream are delivered and reset nothing; `track.ssrc` shows the newest, and at most 8 are kept per m-line. A MID updates the mapping only from a packet newer than the last update (RFC 9143 section 9.2), and a packet whose payload type the m-line does not receive as media moves neither the mapping nor its sequence state. A pending offer or pranswer does not change such an m-line: the SSRCs and RIDs it gives apply at the commit, so the current stream keeps flowing (and may change its SSRC) until then. When a description gives such an m-line its first SSRC, the announced track takes that SSRC instead of being replaced, so `ontrack` does not fire again. Receiver SSRC routes, learned from packets (this fallback and RID / simulcast learning) or given by a description, are scoped to the receiver's DTLS transport (RTP session): RTP and RTCP of another transport that uses the same numeric SSRC reach that transport's own receiver, never the first one, and a description giving another transport's receiver an SSRC learned here does not take it away. A local sender's SSRC is scoped the same way: a remote stream on another transport may use it, and registering a sender, a description (also another m-line's description naming the same SSRC on another transport) or a learned SSRC never takes another transport's route away; within one RTP session a sender outranks a description, which outranks a learned SSRC (whose receiver then forgets it, whether it was learned by the fallback or as a RID's media / RTX SSRC), and an RTP packet using a local sender's SSRC is dropped even when it carries a RID or a repaired RID. A description route a pending description added on one transport is applied again on the transport its m-line has at the commit (a BUNDLE merge), so the later description replaces the earlier one there. With `keyFrameRequestRouting: "fallback"`, a PLI / FIR for an unknown SSRC falls back only to senders of the transport it arrived on. RID (`rtp-stream-id`), RRID (`repaired-rtp-stream-id`) and MID resolve within the packet's transport too: a simulcast receiver on another transport never takes a packet, and a MID naming an m-line of another transport drops it. SSRC 0 is handled like any other SSRC (statistics included).
- **Firefox `a=bundle-only` offers are answered** (RFC 8843 §6 / §7.3.3). Firefox offers the non-tagged BUNDLE m-lines as port 0 + `a=bundle-only` in a re-offer that adds an m-line, in an ICE restart offer, and in a first `max-bundle` offer. werift treated these m-lines as rejected, so it stopped transceivers that were already negotiated, left the m-lines out of the answer's BUNDLE group, and could not negotiate with Firefox. When werift accepts BUNDLE, such an m-line is now accepted into the group and answered like any bundled non-tagged m-line (port 9 + `c=IN IP4 0.0.0.0`, without `a=bundle-only`, as Chrome and Firefox answer it). `remoteDescription` still shows the m-line as received. It stays rejected with `bundlePolicy: "disable"`, when its MID is in no BUNDLE group, or when it is the group's tag (JSEP §5.10). When the answerer rejects the tag (for example no common codec), another accepted m-line with a usable port in the offer becomes the new tag (RFC 8843 §7.3.1), and the BUNDLE transport takes that m-line's ICE / DTLS parameters and candidates (a bundle-only m-line may carry no candidates); with no such m-line, the bundle-only m-line is rejected (port 0 + `c=`). `MediaDescription` reads and writes `bundleOnly`. werift's own offers still do not use `a=bundle-only`.
- **Rejected m-lines in an answer have a `c=` line** (RFC 8866 §5.7). An m-line that answers a remote port 0 m-line had no `c=` line, and Firefox refused such an answer (`c= connection line not specified for every media level`). Such an m-line now has `c=IN IP4 0.0.0.0`.
- **An m-line without ICE credentials takes them from its BUNDLE group by MID.** The SDP parser used to look up the group by m-line index, and it threw when a MID was not that index.
- **A fatal DTLS alert is no longer swallowed** (`werift-dtls`, `werift`). It used to be thrown inside the receive loop and only logged, so the transport stayed `connected`. Every other alert (including warnings) used to close the connection like close_notify; now only close_notify closes it. A DTLS transport that receives a fatal alert, also after the connection was established, becomes `failed`, and so does `connectionState` while the transport is in use (a peer close_notify does not change `connectionState`). `failed` / `closed` are final: later alerts do not change them, and SRTP / application data arriving afterwards is dropped. A received close_notify or fatal alert only detaches DTLS from the shared ICE connection; ICE keeps running until `RTCDtlsTransport.stop()` / `RTCPeerConnection.close()` (a received fatal alert used to close the ICE agent). A `closed` / `failed` `RTCDtlsTransport` also sends nothing any more, even while ICE is still up (after the peer's close_notify): `sendRtp` / `sendRtpWithMeta` (size 0) and `sendRtcp`, so periodic sender / receiver reports, NACK, PLI and TWCC feedback stop with it. `RTCSctpTransport` also closes when its DTLS transport fails.
- **The epoch-1 record sequence number starts at 0** (`werift-dtls`, RFC 6347 §4.1). The Finished record was sent with the sequence number following the epoch-0 records, and the counter was then reset, so a later record of the same epoch reused that number and a browser dropped it as a replay. Among the affected records was werift's close_notify after an SCTP ABORT, which Chrome ignored.
- **Every alert in a DTLS record is handled** (`werift-dtls`, RFC 5246 §6.2.1 / RFC 6347 §4.1). Only the first alert of a record was read, so a close_notify or fatal alert after a warning in the same record was lost. Alerts are now handled in order, stopping at the first close_notify / fatal alert. A datagram ending with a truncated record no longer throws out of the receive handler (losing the valid records before it); the truncated record is discarded. An alert whose level is neither warning nor fatal ends the connection like a fatal alert instead of being ignored as a warning.
- **An alert being sent is not dropped by `DtlsSocket.close()`** (`werift-dtls`). `close()` without `notify` closed the transport at once, so a `sendAlert()` just before it, or the close_notify answering the peer's when `close()` was called from `onClose`, was lost on UDP. It now waits for that alert (at most the alert send timeout). After this side sent close_notify, a repeated peer flight no longer makes it resend its last flight or complete the handshake.
- **Encrypted alerts are recognized by the record epoch** (`werift-dtls`) instead of guessing from the description byte, so a ciphertext whose first bytes look like a known alert is no longer misread; an alert record that fails to decrypt is discarded (RFC 6347 §4.1.2.1). Once the peer's protected records were accepted, an older-epoch (plaintext) alert is discarded, and once the handshake completed, so is an older-epoch handshake record: an epoch-0 Certificate or ClientHello injected on the path can no longer replace the peer certificate (and fail its check) or reset the session (`renegotiation()`). A record with an unknown content type is discarded instead of closing the connection.
- **RTX with RID-based simulcast is received.** An RTX packet carrying `repaired-rtp-stream-id` (Chrome sends simulcast without `a=ssrc` / `a=ssrc-group:FID`) is now delivered restored (media SSRC, sequence number and payload type, `{ type: "retransmission" }`) on the RID's track; it used to be dropped. The first packet with `rtp-stream-id` / `repaired-rtp-stream-id` registers its SSRC, so later packets without these extensions keep their route. Without SDP pairing, an RTX packet is restored to its RID's current media SSRC only when it fills a hole NACK detected there: NACK and RTX verification share one ledger of holes per media SSRC, so a packet is verifiable for as long as NACK asks for it (and after NACK's retries, until the ledger's bound of 1024 holes per SSRC; a hole leaves the ledger only together with its NACK request), and its timestamp must lie within those of the packets received around the gap, in either order and widened by 1 s of media clock (B-frames). A RID has one media SSRC at a time: a change without renegotiation resets the stream, ending the old SSRC's NACK requests and holes and dropping late packets of the old media SSRC and of the RTX SSRCs that repaired it. RTX that fits no hole (a duplicate of a received packet, a number NACK never asked for, another stream), has an unknown RID, or has no `apt` codec is dropped instead of being delivered broken. Streams whose sequence numbers and timestamps start at the same values (against RFC 3550 section 5.1) cannot be told apart. The packet-driven state is bounded while the receiver runs: per RID 1 media SSRC, 8 RTX SSRCs and 8 retired SSRCs, and NACK state for at most 16 media SSRCs per receiver.
- **NACK is tracked per media SSRC.** Simulcast layers no longer compare each other's sequence numbers (false losses) or send a NACK to the wrong SSRC. `receiver.onPacketLost` still fires once per sent NACK, and an idle NACK timer now stops when no loss remains. Sequence numbers are compared across the 16-bit wrap, so a late packet from before a wrap no longer opens a false gap of tens of thousands of numbers.
- **The track codec of a RID receiver and of `resyncCodecs` skips RTX / RED**, so a description that lists `video/rtx` first no longer gives the remote track the RTX codec.
- **A subsequent offer lists every codec the transceiver supports** (#818, RFC 8829 section 5.2.2), including codecs an earlier answer left out, so a later answer can move to them. Codec preferences and a fixed track source still narrow the offer. A negotiated codec is offered as negotiated: its payload type, fmtp and rtcp-fb stay as the answer committed them, also when that is the remote peer's form (another H264 level or packetization-mode, other Opus fmtp, other feedback), and a configured codec is paired with it by the same rule negotiation uses (`pairCodecs`: exactly the same format (rtpmap and every fmtp parameter) first, then a compatible one, then the same MIME type), so a peer configured differently gets the same re-offer as before. Another format of a negotiated MIME type that the answer left out (H264 mode 1 next to a negotiated mode 0, VP9 profile 0 next to a negotiated profile 2) is offered again too, so a later answer can move to it. `isCodecCompatible` (used for fixed track sources and `replaceTrack()`) now also tells VP9 `profile-id` and AV1 `profile` apart, as it did H264 `packetization-mode` / `profile-level-id`; an omitted value still matches any. Negotiation now also pairs each local codec with the remote codec of its own format first: an offer listing H264 mode 1 and mode 0 (or VP9 profile 0 and profile 2) is answered with mode 0 (profile 2) by a peer configured for that format only (it used to pair by MIME type and commit the first one listed, a format the peer is not configured for). A codec offered again takes its configured payload type, or a free dynamic one when another codec in the session uses that type (a codec with other format parameters or RTCP feedback, such as an H264 `packetization-mode` / `profile-level-id`, an RTX `apt`, the primaries of a RED or other `rtcp-fb`, counts as another codec: RFC 8859 requires one `a=fmtp` and `a=rtcp-fb` per payload type in a BUNDLE group), and RTX `apt` / RED references follow it. A direction change (`direction`, `removeTrack()`) never takes a negotiated codec off the m-line, even one configured with a `direction` that no longer matches, so such a re-offer no longer throws `NotSupportedError`; only an answer removes codecs. An `inactive` transceiver can use every configured codec, so an inactive first offer with only direction-tagged codecs no longer throws either. `transceiver.codecs`, `getPayloadType()`, codec stats, the sender and the receiver keep the negotiated codecs until an answer commits new ones: `createOffer()`, an applied offer and a rollback do not change them, and `setCodecPreferences()` / `addTrack()` on a negotiated transceiver no longer empty `transceiver.codecs`.
- **Host candidates match the source address of their packets on multi-NIC hosts (#814).** Without `interfaceAddresses` / `iceInterfaceAddresses`, each enumerated interface address used to be gathered over a wildcard (`0.0.0.0` / `::`) socket, so a socket's packets could leave from another interface's address and the peer learned an unneeded peer-reflexive candidate (a selected pair that did not match the advertised candidates, failed checks). Each enumerated address now gets a UDP host socket bound to that address (an IPv6 link-local one with its zone), and the candidate advertises the bound address and port. An address whose bind fails (removed during gathering, IPv6 tentative, ...) is not advertised and does not fall back to a wildcard socket; the other addresses are unaffected. `additionalHostAddresses` / `iceAdditionalHostAddresses` that are not assigned to a local interface (1:1 NAT public addresses) keep using wildcard sockets. To keep wildcard sockets for the enumerated addresses (addresses that change later, for example), set the family to `0.0.0.0` / `::` in `interfaceAddresses`; that family now advertises its enumerated addresses instead of the wildcard address. `UdpTransport.init()` (`werift-common`) accepts `bindAddress`, and `StunProtocol.connectionMade()` takes an optional fourth `{ bindAddress }` argument.
- **Multi-NIC gathering no longer stalls on an interface that cannot reach the STUN server, and works behind a full-tunnel VPN (#814).** Without `interfaceAddresses` / `iceInterfaceAddresses`:
  - With a STUN server, each family gets one more UDP socket bound to the wildcard address. It advertises no host candidate; its server-reflexive candidate (related address `0.0.0.0` / `::`) follows the route the OS picks, so a server-reflexive path exists even when the only way out is an interface the host sockets do not cover, and it receives whatever reaches its port. It checks only the remote candidates whose route leaves from an address no UDP host socket is bound to, so a peer on a covered path learns no peer-reflexive candidate from it. TURN allocations keep their own wildcard-bound UDP socket.
  - `gatherCandidates()` / `setLocalDescription()` wait only for the representative sockets' STUN queries: the wildcard socket and the host socket of the default-route address. The other host sockets' server-reflexive candidates trickle through `onIceCandidate` / `onicecandidate`, and end-of-candidates (`localCandidatesEnd`, `iceGatheringState === "complete"`, the `null` candidate, `a=end-of-candidates`) follows the last of them, at most `stunGatherTimeout` later. On a host whose interfaces all reach the STUN server nothing changes. `Connection.waitForLocalCandidatesEnd()` resolves when gathering has ended.
  - VPN / tunnel interfaces (`ipsec`, `tun`, `utun`, `tap`) are gathered with a low local preference instead of being dropped; `vmnet` / `veth` stay excluded. `getHostAddresses()` / `nodeIpAddress()` keep returning the addresses without them.
  - The host candidate of the default-route address gets the highest local preference (65535; other interfaces 32767, VPN / tunnel 16383, each decreasing in gathering order), so checks start with the path the OS uses. The default-route address is the source address of the route to the first configured STUN / TURN server that resolves in the family and has a route (in priority order; a hostname is resolved within 1 s), so the route the server queries actually take is preferred, also on networks without an Internet route. Without such a server there is no default-route address (the host candidates keep the gathering order): no other address, in particular no public one, is probed in its place. The probes only `connect()` a UDP socket to the configured servers (and, for the wildcard socket's pairing, to remote candidates); no packet is sent.
  - `serverReflexiveCandidate()` takes an optional `base` (the wildcard socket's base).
- **`RTCRtpSender` RTT accepts Receiver Reports that reference older Sender Reports** (`werift`): the sender kept only the newest SR, so a delayed RR (queueing, TURN relay, congested path) whose `LSR` pointed at an earlier SR was dropped and `remote-inbound-rtp` `roundTripTime` / `totalRoundTripTime` / `roundTripTimeMeasurements` went stale. The sender now keeps a bounded SR history (32 entries, 30 s) and computes `now - SR send time - DLSR` for the SR the `LSR` identifies (RFC 3550 §6.4.1), with a monotonic clock instead of `Date.now()`. Reports with `LSR = 0`, an unknown or expired `LSR`, or a negative sample are ignored (packet loss stats are still updated); an RR with `DLSR = 0` now yields an RTT sample instead of being skipped. The EWMA, total and count updates are unchanged.
- **ICE candidate pairs are ordered by the RFC 8445 pair priority** (`werift-ice`): `candidatePairPriority()` computed `1 << 32` (which is `1` in JavaScript) instead of 2^32. Pairs were therefore ranked mostly by `MAX(G,D)`: a pair with candidate priorities (100, 1000) was checked and preferred before (200, 300), although RFC 8445 §6.1.2.3 ranks the larger `MIN(G,D)` first. `sortCandidatePairs()` and nomination now use the new exact `compareCandidatePairPriority()`, and pairs of equal priority keep their order. The value of `candidatePairPriority()` / `CandidatePair.priority` now follows the RFC formula; it can exceed `Number.MAX_SAFE_INTEGER`, so treat it as approximate and order pairs with `compareCandidatePairPriority()`.
- **ICE: semi-aggressive nomination by default, so a better pair that succeeds later replaces the selection** (`werift-ice`, `werift`): a controlling full ICE agent used aggressive nomination for UDP / relay pairs: every check carried `USE-CANDIDATE`, the first one to succeed was selected, and no other pair could replace it without an ICE restart. A lower-priority TURN/TCP relay pair that succeeded first therefore kept the session even when a TURN/UDP relay candidate trickled moments later; a reported Chrome ↔ werift session stayed on TURN/TCP with about 6.2 s RTT instead of about 88 ms over TURN/UDP.
  - The default is now semi-aggressive nomination, as in libwebrtc / Chrome (`IceOptions.nomination` / `PeerConfig.iceNomination`, default `"semi-aggressive"`). Checks carry `USE-CANDIDATE` until a pair is selected and afterwards only for pairs that outrank the selected one. The first pair whose check succeeds is selected at once, so connecting takes no extra round trip or delay. Checks of higher-priority pairs continue after `connect()` resolves, a higher-priority candidate trickled later (or a relay allocation that finishes later) is still paired and checked, and a pair that succeeds later replaces the selection: application data and consent checks move to it. Consent checks of the selected pair carry `USE-CANDIDATE`, as in libwebrtc. Lower-priority pairs are not checked after the selection. A higher-priority pair whose check (or nomination) failed is checked again 1, 2, 4, 8 and 16 s after each failure while it still outranks the selection (about 31 s in total, as libwebrtc keeps pinging a connection for 30 s), so a path that was briefly unreachable when the agents connected is still taken when it recovers, even when the peer's own check of it failed too.
  - **The controlled side follows the peer's later nominations** (behavior change): it used to keep the first pair nominated to it. It now uses the nominated pair with the largest nomination (`USE-CANDIDATE` counts as 1). Between equal nominations it uses the pair the peer last sent application data on, as libwebrtc does, and the higher-priority one while neither received data (RFC 5245 §8.1.1.2). Both agents therefore settle on the same path when the peer replaces its selection, also when a libwebrtc peer moves to a lower-priority pair by itself (for example when the selected one stops working): the werift agent moves with the peer's data instead of sending on the path the peer left. A nomination of a pair the peer sends no data on does not replace a selection the peer sends data on until data arrives on it. ICE-TCP pairs are not selected this way (selecting one prunes the other TCP connections). A check the agent cancels when it connects (its pair outranks the selected one but was still waiting for an answer) puts the pair back to Waiting, so the peer's later checks and nomination of it are followed. A peer that nominates once (regular nomination) sees no difference.
  - **Renomination** (`IceOptions.renomination` / `PeerConfig.iceRenomination`, default `false`; draft-thatcher-ice-renomination as libwebrtc implements it): when enabled, every description advertises `a=ice-options:trickle renomination`. When the remote description advertises `renomination` too, the controlling agent nominates with the `NOMINATION` STUN attribute (0xC001) and an increasing value instead of `USE-CANDIDATE`. Ordinary checks carry neither; the first valid pair and every better pair that becomes valid later are nominated with a separate check, and the selection moves when the peer answers it. A controlled agent always honours `NOMINATION` (the largest value wins, whatever the pair priority), like Chrome. Chrome itself advertises renomination only when its SDP is modified before `setLocalDescription` (it has no API option); as the controlled side it follows werift's renominations without that. The new `CandidatePair.nomination` / `CandidatePair.remoteNomination` and `IceConnection.remoteRenomination` expose what was sent and received. `Protocol.onDataReceived` (custom protocols) now also passes the remote address the data came from.
  - `nomination: "regular"` (opt-in) keeps RFC 8445 §8.1.1 regular nomination: ordinary checks of every transport, in the live checklist and in a provisional (pranswer) ICE restart generation, carry no `USE-CANDIDATE`, and the agent nominates the highest-priority valid pair once with a separate `USE-CANDIDATE` check, at once when both sides signalled end-of-candidates and no higher-priority pair is still being checked, otherwise `nominationDelayMs` after the later of the first valid pair and the last added pair that outranks the best valid pair (never longer for an unreachable higher-priority pair). The nomination check adds one round trip, so `connect()` completes up to `nominationDelayMs` plus one round trip later than with semi-aggressive nomination. New options: `IceOptions.nominationDelayMs` / `PeerConfig.iceNominationDelayMs` (milliseconds, default 300, `0` nominates the first valid pair at once, negative or non-finite values fall back to the default).
  - ICE-TCP pairs keep regular nomination in every mode (each TCP pair is its own connection, and nominating several could leave the agents on different connections after pruning, #721), with the same deadline instead of waiting without limit for every higher-priority TCP pair; they never replace a selection. With regular nomination (and for TCP pairs): if the peer answers a nomination check with an error (or the request is never sent, e.g. a refused TCP connect), only that pair fails, and the next best valid pair is nominated. If a nomination check gets no response, the peer may already have selected that pair. The agent then repeats `USE-CANDIDATE` on the same pair, up to 3 transactions in total, and an error answering a repeat does not move it to another pair. If no attempt succeeds, it nominates no other pair: `connect()` (and `RTCIceTransport.start()`) rejects and the agent moves to `failed`, so an ICE restart can recover. A role change (RFC 8445 role-conflict repair) cancels a nomination in flight: its late answer, timeout or repeats no longer select a pair or fail the agent under the new role. A `487 (Role Conflict)` answering a nomination now switches the agent to controlled and keeps the pair valid, as for an ordinary check, instead of failing the pair. A `USE-CANDIDATE` the agent received while controlled no longer selects the pair once a role-conflict repair made it controlling (its successful check used to select the pair without sending `USE-CANDIDATE`, so the now-controlled peer waited forever); the agent nominates by itself. If the peer's nomination had already selected the pair, the selection stays, and the agent, now controlling, sends `USE-CANDIDATE` (with renomination, `NOMINATION`) for that pair so a peer that became controlled is not left waiting. This applies to the live and the provisional checklist. Connections to ICE-lite peers are unchanged.
  - With regular nomination, at the final answer of an ICE restart negotiated with a pranswer, the live checklist still checks from scratch, but the controlling agent nominates only the pair with the same 5-tuple as the one its provisional checklist nominated (or sent `USE-CANDIDATE` to without a refusal), as soon as that pair is valid. The peer may already have selected it: a `USE-CANDIDATE` retransmission can reach the peer's committed checklist (same credentials), and a JSEP peer may keep its provisional selection. If that pair fails, or is not in the checklist 3 s after the live checks began (also after end-of-candidates and with an empty checklist: a peer-reflexive or passive TCP pair only forms when the peer's check arrives, and `connect()` keeps waiting meanwhile), the agent nominates no other pair and fails as for an unanswered nomination (`connect()` rejects; an ICE restart recovers). This only happens when the final answer keeps the pranswer's credentials and the agent keeps that pair's local socket: when the commit closes it (the ICE restart allocates TURN afresh, or the new gather options exclude the socket), the path is gone for the peer too, and the usual rule chooses the pair. Before this fix, an ICE restart negotiated with a pranswer over a relay pair (`iceTransportPolicy: "relay"` / `forceTurn`) always failed after 3 s. With semi-aggressive nomination the provisional checklist selects the first pair that succeeds, and the live checklist after the final answer selects and replaces as above.
  - `RTCIceTransport.getSelectedCandidatePair()` now returns only the pair the agent selected (nominated), and `null` otherwise. Before, with no nominated pair it returned a pair whose ordinary check had succeeded; that reported an unselected path while a regular nomination waited, and after it gave up (or on the controlled side before the peer nominated). `getStats()` already reported only the nominated pair. After a replacement both report the new pair.
  - With `forceTurn`, a host pair that the agent never checks no longer restarts the nomination delay, is never nominated semi-aggressively, and the provisional checklist no longer checks host pairs, matching the live checklist.
  - A Chrome E2E test (`e2e/tests/ice/nomination.test.ts`) starts on a TURN relay path and then signals werift's host candidates: with Chrome or werift controlling, and with and without renomination (Chrome's SDP modified to advertise it), both ends move to the same host path and keep exchanging data.

### ⚠️ Breaking changes

- **Public TypeScript `enum`s are now `as const` objects with a same-name union type** (`werift`, `werift-ice`, `werift-ice-server`, `werift-rtp`, `werift-sctp`): `CandidatePairState`, `classes`, `methods`, `PacketChunk`, `PacketStatus`, `H264NaluType` (`werift-rtp/extra`), `SCTP_STATE`, and `WEBRTC_PPID`. Node.js 26 removed its TypeScript transform mode, and Node.js type stripping cannot run `enum`. Every runtime value is unchanged, and so are value access (`SCTP_STATE.ESTABLISHED`), `===` / `switch` comparisons, type annotations (`state: CandidatePairState`) with `switch` exhaustiveness, `keyof typeof X`, the CJS / ESM export names, assignment from values of older `werift-*` versions, public field / argument / return types (`CandidatePair.state` is still `CandidatePairState`, `SCTP.associationState` is still `SCTP_STATE`), and the TypeDoc `enumerations/` pages. These uses change:
  - Reverse lookup (`X[value]`, for example `CandidatePairState[pair.state]`) no longer exists. Use `Object.entries(X).find(([, v]) => v === value)?.[0]` or keep your own reverse map.
  - `Object.keys/values/entries(X)` no longer contain the numeric reverse-mapping keys. Only member names remain, and `Object.values(X)` lists the values.
  - A member can no longer be written as a type (`x: PacketChunk.TypeTCCRunLengthChunk`). Write `typeof PacketChunk.TypeTCCRunLengthChunk`.
  - A plain `number` is no longer assignable to the type. Check the range first, then narrow with `as X`.
  - A variable initialized from a member without a type annotation (`let s = X.A; s = X.B;`) is inferred as that member's literal type. Annotate it: `let s: X = X.A`.
- **`sender.senderBWE` is a getter whose TypeScript type is `BandwidthEstimator`** (it was a `readonly` `SenderBandwidthEstimator` field). Replace the estimator with `sender.setBandwidthEstimator(impl)`, not by assigning the property. The `onCongestion` / `onCongestionScore` events of the default estimator still exist at runtime, and a one-release compatibility surface keeps those names on GCC / disabled estimators as no-op Events so `sender.senderBWE.onCongestion.subscribe(...)` compiles. Prefer `sender.senderBWE as LightweightBandwidthEstimator` or `isLightweightBandwidthEstimator`. The names are not part of the shared `BandwidthEstimator` contract and may be removed from the other estimators in a future major.
- **`SenderBandwidthEstimator` is renamed to `LightweightBandwidthEstimator`** (the default, lightweight cumulative estimator: TWCC send / receive rates only, no probing or pacing). `SenderBandwidthEstimator` remains as a deprecated alias of the same class, so `new SenderBandwidthEstimator()` and `instanceof` keep working.
- **`onAvailableBitrate` fires only when the estimate changes.** The default estimator used to fire on every update, even with the same value. The payload is still the bitrate in bps.
- **`werift-sctp`: `SCTP.send({ expiry })` is absolute time in `Date.now()` epoch milliseconds** (it was compared against epoch seconds, so it never took effect). A caller that passed epoch seconds now gets every chunk abandoned at its first retransmission decision; pass `Date.now() + lifetimeMs` instead.

### 🚀 Features

- **Selectable TWCC send-side bandwidth estimation** (`packages/webrtc`): estimators share the `BandwidthEstimator` contract, and each `RTCRtpSender` has its own instance.
  - `new RTCPeerConnection({ bandwidthEstimator })` picks the estimator for new senders: `"lightweight"` (default, the existing algorithm), `"gcc"`, `false` / `"none"` (disabled), or a factory `() => BandwidthEstimator`.
  - `RTCRtpSender.setBandwidthEstimator(impl)` swaps the estimator of one sender, e.g. `new GccBandwidthEstimator()`. The new estimator starts from a clean state.
  - `RTCRtpSender.onAvailableBitrate` (`Event<[number]>`, bps) notifies changes of the recommended send bitrate and keeps its subscriptions across `setBandwidthEstimator`. It may stay `0` until TWCC is negotiated and enough feedback has arrived.
  - `GccBandwidthEstimator` implements Google Congestion Control with libwebrtc as the reference (delay-based and loss-based estimation, probing, pacing). Known differences are listed in `GCC_KNOWN_DIFFERENCES`. With GCC, outgoing RTP goes through a bounded per-sender FIFO and a pacer, and `sender.onProbeClusterConfig` / `sender.pacingBitrateBps` expose the probe targets. Probe and loss padding is padding-only RTP on the RTX SSRC, so media sequence numbers are never shifted; without negotiated RTX, GCC sends no padding.
  - The default lightweight and disabled estimators keep the direct (unqueued, unpaced) send path.
  - New exports: `createBandwidthEstimator`, `BandwidthEstimatorOption`, `LightweightBandwidthEstimator`, `isLightweightBandwidthEstimator`, `DisabledBandwidthEstimator`, `GccBandwidthEstimator`, `TwccFeedbackAdapter`, and related types.
- **`TwccFeedbackAdapter` matches TWCC feedback to sent packets for every estimator**: 16-bit sequence numbers are unwrapped from the previous feedback, and each sent packet is counted as received at most once, including duplicate, reordered, and wrapped feedback. `onFeedback(feedback, nowMs)` takes the feedback arrival time and never matches a packet older than the history window (age is measured from `sendingAtMs` to the latest send completion / feedback time), even when the send confirmation completed late or feedback arrives after sending stopped. `SenderBandwidthEstimator` accepts `{ clock }` for tests, like `GccBandwidthEstimator`.
- **`PeerConfig.filterProbePaddingOnReceiveRtp`** (default `false`): `MediaStreamTrack.onReceiveRtp` keeps the wire sequence numbers and delivers padding-only packets with `{ type: "padding" }` as the third argument. Set `true` to drop padding-only probes and compact the sequence numbers of the following media.
- **Generic RTP send-side helpers in `werift-rtp`**: `RtpContinuity` (output sequence / timestamp across source switches), `buildSendHeaderExtensions` / `stampHopByHopExtensions` (send header extensions; TWCC and abs-send-time are written at send time and never copied from a forwarded packet), `appendRfc3550Padding` / `createRtxPaddingPacket`, `RedEncoder.serializedLengthWith()`, and the TWCC helpers `TransportWideSeqUnwrapper` / `TWCC_SEQ_MOD` / `compareTransportWideSeq` / `isOlderTransportWideSeq` / `sortPacketResultsByWideSeq`, `TwccReferenceTimeUnwrapper` / `TWCC_REFERENCE_TIME_MOD` / `TWCC_REFERENCE_TIME_UNIT_MS` and `hasTwccReceiveTiming`. `werift` re-exports them. `werift-rtp` now ships `THIRD_PARTY_LICENSES_LIBWEBRTC.txt` (the transport-wide sequence unwrapper is ported from libwebrtc).
- **`RTCDtlsTransport.sendRtpWithMeta()`** also returns the ICE enqueue time. `sendRtp()` still returns `Promise<number>`. `RTCDtlsTransport.transportSequenceNumberExtended` is the monotonic transport-wide sequence; `transportSequenceNumber` remains the 16-bit wire value.
- **Nonstandard `MediaRecorder` writes Ogg Opus** (`werift`, `werift-rtp`): `path: "*.ogg"` / `"*.opus"`, or `format: "ogg"` with `stream` (pass an `Event<[OggOutput]>`), records exactly one Opus audio track as Ogg Opus (RFC 7845). Without `format`, `stream` still produces WebM. A video track, a non-Opus track or more than one track is rejected with a `WeriftError`; an unsupported extension now throws a `WeriftError` with a message instead of an empty `Error`. `width`, `height`, `roll`, `defaultDuration`, `disableLipSync` and `lipsync` are ignored for Ogg.
  - `werift-rtp` adds the Ogg page writer (`OggPager`, `createOggPage`, `oggCrc32`, `createOpusHead`, `createOpusTags`, `getOpusPacketSamples`) and the `OggCallback` processor with the append-only `saveOggToFileSystem` (its first write replaces an existing file). Timestamp gaps of 2.5 ms or more (DTX, loss) are filled with empty Opus packets, so the granule position follows the media time.
  - `StreamEvent` takes an optional output type (`StreamEvent<OggOutput>`); `StreamEvent` alone is still `Event<[WebmOutput]>`.
  - A Chrome E2E test (`e2e/tests/mediachannel/recordPlaybackOgg.test.ts`) records Chrome's microphone to `.ogg`, sends the file back over a DataChannel, and checks the Ogg page structure, `<audio>` playback, and that Web Audio decodes as many samples as the last granule position.
  - The Ogg recording path reorders RTP with the jitter buffer (`jitterBuffer` option, default latency 200 ms). Packets that arrive after their range was filled are dropped instead of being written out of order.
- **`werift`: `RTCConfiguration.certificateScope` selects the default DTLS certificate.** With `"process"` (default, unchanged behavior), an `RTCPeerConnection` without `certificates` / `dtls.keys` reuses one process-wide certificate, so every such connection advertises the same `a=fingerprint`. With `"peerConnection"`, each connection generates its own certificate on its first `createOffer()` / `createAnswer()` (as browsers do) and its DTLS transports share it. `certificates` / `dtls.keys` still take precedence, and the scope cannot be changed by `setConfiguration()`. `RTCDtlsTransport.generateCertificate()` creates a new certificate on every call.

Server-reflexive candidates are then gathered only from the STUN servers you configure.

### 🐛 Bug Fixes

- **`Vp8RtpPayload.deSerialize` now detects the TID/Y/KEYIDX octet by `T || K` instead of `L || K`** (`werift-rtp`, RFC 7741 §4.2): with `T=1, L=0, K=0` the octet was treated as the start of the VP8 payload (frame one byte too long, P bit / `isKeyframe` read from the wrong byte), and with the RFC-violating `L=1, T=0` the first payload header byte was skipped. `L=1, T=1` (browser temporal layers), `K=1` and werift's own X/I/M descriptor were already parsed correctly.
- **SRTP / SRTCP reject replayed packets** (`werift-rtp`, RFC 3711 §3.3.2). The receive side keeps a replay window per SSRC over the packet index (SRTP: ROC and sequence number, SRTCP: the SRTCP index) and rejects an index it already received or one older than the window with the new `SrtpReplayError`. It subclasses `SrtpAuthenticationError`, so `RTCDtlsTransport` drops replays like packets that fail authentication. A window is created and advanced only after a packet authenticated, so forged packets cannot add receiver state. The window is 1024 packets (`SRTP_REPLAY_WINDOW_SIZE`, the same as libwebrtc), so the NACK retransmission of a lost packet is still accepted. New exports: `SrtpReplayError`, `SrtpReplayWindow`, `SRTP_REPLAY_WINDOW_SIZE`.
  - Behavior change: RTP written with a sequence number the peer already received (for example `track.writeRtp()` of packets that all use the default `new RtpHeader()`) is now dropped by a werift receiver, as browsers already do. Advance the sequence number per packet.
- **SCTP association setup handles INIT collisions** (`werift-sctp`, RFC 9260 §5.2.1, §8.5.1).
  - An initiator in COOKIE-WAIT / COOKIE-ECHOED answers the peer's INIT with an INIT_ACK and accepts the COOKIE_ECHO that follows, instead of ignoring both. When both ends sent INIT (usrsctp and dcsctp do), the association no longer stalls.
  - INIT is always sent with verification tag 0. After answering the peer's INIT before `start()`, the INIT sent by `start()` used to carry the peer's tag. An INIT that carries our own tag (sent by werift 0.26 and older in that case) is also accepted.
  - `start()` does not send INIT when the peer's INIT / COOKIE_ECHO already established the association.
  - INIT and COOKIE_ECHO enter COOKIE-WAIT / COOKIE-ECHOED and start T1 before the chunk is sent. An INIT_ACK that arrives while the INIT send is still pending is no longer dropped, and a failed INIT send is retransmitted by T1 instead of leaving the association idle. The responder enters ESTABLISHED when it sends COOKIE_ACK.
- **A DataChannel / SCTP added by renegotiation opens on an already connected session** (`werift`). When an `RTCPeerConnection` connected without `m=application` and a later offer/answer added it, the SCTP association never started because ICE / DTLS were already connected, so DataChannels stayed `connecting`. Now the association starts when the answer (or pranswer) is applied, on the existing BUNDLE DTLS transport. Starting SCTP is idempotent: an association the peer already established, or one that is connecting, is not started again (no second INIT, no state rewind), and a rollback of the pranswer that added SCTP closes the pending association.
- **An incoming SCTP stream reset no longer drops the last DataChannel message when the reset overtakes a retransmitted DATA chunk** (`werift-sctp`, `werift`): an Outgoing SSN Reset Request whose Sender's Last Assigned TSN has not been received yet is now deferred (RFC 6525 §5.2.2) and answered with `In progress`. DATA up to that TSN (including retransmissions) is still reassembled and delivered; DATA for the reset streams beyond it is held for the new streams. Once DATA or FORWARD-TSN moves the cumulative TSN to the boundary, the inbound streams are reset, the reverse reset is sent and `onReconfigStreams` fires (so the DataChannel closes) after every message before the boundary has reached `onReceive`.
  - The Re-configuration Request Sequence Number is now checked (RFC 6525 §5.2.1): a retransmitted request gets the same result again without resetting twice, and an unexpected one gets `Error - Bad Sequence Number`.
  - An `In progress` answer to a reset werift sent is no longer logged as a failure; the request stays and is retransmitted, and the answer does not count toward closing the association.
  - When the peer's reverse reset request acknowledges a reset werift sent (its Re-configuration Response Sequence Number), werift keeps retransmitting the request until the peer's response arrives, without counting the retransmissions as failures. A lost `Success - Performed` response no longer leaves the request outstanding forever and blocking later resets.
  - `reconfigResult` (`werift-sctp/src/param`) has the other RFC 6525 §4.4 results (`SuccessNothingToDo`, `Denied`, `ErrorWrongSSN`, `ErrorRequestAlreadyInProgress`, `InProgress`).
  - Received TSNs are now ordered by serial number, so the cumulative TSN and SACK gap blocks advance correctly across the 2^32 wrap.
- **Every configured STUN / TURN URL takes part in gathering** (`werift`, `werift-ice`). `RTCPeerConnection({ iceServers })` used to use only the first STUN URL and the first TURN URL and drop the rest silently. Now every IPv4 UDP host socket queries every STUN server in parallel (equal mappings are advertised once, different mappings each), and every TURN URL gets its own allocation with the `username` / `credential` of the `RTCIceServer` that lists it and the transport of its URL (`?transport=`, then `turnTransport`, then `forceTurnTCP`). A server that fails or times out does not stop the others; gathering completes when the slowest server answers or times out (`iceStunGatherTimeout`, `iceTurnConnectTimeout`). `setConfiguration()` and ICE restart replace the whole list and close every previous allocation. A TURN URL without `username` / `credential` is still ignored (now logged), not rejected with `InvalidAccessError`.
  - `werift-ice`: new `IceOptions.stunServers` / `IceOptions.turnServers` (`TurnServerOptions`: `address`, `username`, `password`, `transport`), `Connection.stunServers` / `Connection.turnServers` (also optional on `IceConnection`), and `normalizeIceServerOptions()`. The singular `stunServer` / `turnServer` / `turnUsername` / `turnPassword` / `turnTransport` options are deprecated but keep working: they are merged in front of the plural lists, duplicates removed. `Connection.stunServer` / `turnServer` are deprecated accessors for the first entry.
  - `parseIceServers()` returns `stunServers` / `turnServers` for every URL; its singular fields (the first URL) are deprecated. `RTCPeerConnection` hands the ICE agent only the plural fields, so `iceTransport.connection.options.turnUsername` (and the other singular fields) are now `undefined`; read `connection.turnServers` instead.
- **TWCC is transport-wide on BUNDLE.** `ReceiverTWCC` is shared per DTLS transport, and incoming TWCC RTCP is fanned out to every `RTCRtpSender` on that transport (each estimator matches only its own sent packets). TWCC is delivered only to senders currently on the transport it arrived on, so a late feedback on a transport a sender has left never reaches it. Received TSNs are unwrapped against the highest one received, and pending packets are reported in windows of at most 32,767; after a loss that fills a whole window, the report start jumps to the next received packet, so feedback resumes instead of stalling until the sequence wraps.
- **Moving an `RTCRtpSender` to another DTLS transport resets the path-dependent state of its bandwidth estimator** (send history, transport-wide sequence origin, estimates, in-flight sends), because the new transport has its own sequence space. The estimate restarts from the new transport's feedback. Application constraints are kept: the new optional `BandwidthEstimator.resetNetworkRoute()` (implemented by `GccBandwidthEstimator`) keeps the min / start / max from `setBitrates`, also when the initial negotiation moves a sender onto a BUNDLE transport; estimators without it are `reset()`.
- **The transport-wide sequence number is allocated synchronously before each send** and used for the estimator input, so with BUNDLE a sender no longer picks up the number of another sender's packet. The TWCC and abs-send-time extensions of forwarded packets no longer overwrite the newly assigned values.
- **NACK retransmissions get a new transport-wide sequence number** instead of reusing the original one.
- **Padding-only packets are no longer stored in the NACK cache.**
- **The default (lightweight) estimator's send history is pruned to a 10 s window**; it used to grow without bound.
- **DataChannel `maxPacketLifeTime` abandons messages after the given milliseconds.** The lifetime was divided by 1000 and compared in epoch seconds, so lifetime-limited messages were never abandoned. Now an unacknowledged message is abandoned with PR-SCTP (RFC 3758) after `maxPacketLifeTime` ms, and FORWARD-TSN moves the peer past it.
- **PR-SCTP abandons only the fragments of the expired message** (`werift-sctp`). Abandonment used to start at the first DATA chunk of the send queue and could spread to the preceding message, so a different, still-valid message could be dropped.
- **PR-SCTP recovers from lost packets without dropping deliverable data** (`werift-sctp`). Fragments of an abandoned message that are still waiting to be sent are abandoned with it. A message whose lifetime runs out while it is still queued (cwnd / rwnd limited) is abandoned before its first transmission instead of being sent late. This also happens when nothing else runs the sender (e.g. a zero peer receive window with no DATA in flight) and when the expired message waits behind a message without a lifetime: a timer fires at the earliest expiry in the queue, marks expired messages abandoned in place (TSN order is kept, so they are never sent and the FORWARD-TSN skips them once they reach the head), and resolves their `send()` right away, so the DataChannel `bufferedAmount` drops without waiting for a SACK, another send, or the earlier messages. Abandoned chunks release their payload; only the metadata the FORWARD-TSN needs is kept. Likewise, a chunk whose lifetime runs out while it waits for retransmission is abandoned instead of being retransmitted. A lost FORWARD-TSN is resent until the peer acknowledges it. On receiving a FORWARD-TSN, complete ordered messages that were waiting behind the skipped one are delivered, only incomplete ones are discarded, and a stale entry no longer moves the expected stream sequence number backwards.
- **SCTP reassembly no longer stalls** (`werift-sctp`). After delivering a message, the next complete message is delivered even when its TSN is not contiguous (it used to wait for another DATA chunk), and a complete unordered message that directly follows a broken unordered fragment is no longer skipped.
- **SCTP no longer stops sending DATA after a T3-rtx timeout that follows a Gap ACK, and `flightSize` stays consistent under loss** (`werift-sctp`, #806). T3 used to retransmit gap-acked chunks and count them in `flightSize` again, and the later cumulative ACK never removed them, so `flightSize` stayed at or above `cwnd`: the DataChannel stopped sending (and sending HEARTBEAT) while the connection looked healthy, and `send()` never resolved. Each `DataChunk` now tracks whether it is counted with the new public `inFlight` field, so `flightSize` always equals the bytes of the in-flight chunks in the sent queue on every path (first send, Gap / cumulative ACK, fast retransmit, T3, retransmission, abandonment, FORWARD TSN). T3 skips gap-acked and abandoned chunks, and a chunk acked after it was marked for retransmission is not resent. A gap-acknowledged chunk that a later SACK no longer reports (the peer reneged on it) is made outstanding again and counted in `flightSize`; each later SACK that still misses it counts a miss indication, so it is fast-retransmitted on the third instead of waiting for T3-rtx, and T3-rtx is started if it is not running (RFC 9260 6.2.1).
- **TURN handles unsigned 401 / 438 long-term credential errors** (`werift-ice`): a 401 (Unauthenticated) or 438 (Stale Nonce) without MESSAGE-INTEGRITY answering Refresh, CreatePermission or ChannelBind on an authenticated allocation used to be dropped as an integrity failure and retransmitted until the transaction timed out (~6.7 s per request over UDP; with Cloudflare TURN, per rejected ChannelBind peer). It is now handled at once, over UDP and TCP/TLS, following RFC 8489 §9.2.5. A 438 with a new NONCE is retried once, and the retry is re-signed correctly: a retried request used to keep its old MESSAGE-INTEGRITY / FINGERPRINT inside the new signature, so even werift's own TURN server rejected it once a nonce expired. A 401 to an authenticated request with an unchanged REALM is not retried and rejects immediately; with a new REALM it is retried once, and the allocation's credentials change only if that retry succeeds. No retry is made when the NONCE is missing, its nonce cookie (`obMatJos2`) announces password algorithms or username anonymity, or PASSWORD-ALGORITHMS is present, since only MD5 MESSAGE-INTEGRITY with a plain USERNAME is supported. Only matching transaction-ID, source address and method responses count, and other unsigned errors, unsigned success responses, and responses with an invalid MESSAGE-INTEGRITY (401 / 438 included) are still dropped over UDP. Over TCP/TLS they now end the transaction with `TransactionIntegrityViolation` instead of waiting for a timeout, except an unsigned 400, which is still ignored. ICE connectivity checks and consent keep requiring MESSAGE-INTEGRITY. An unsigned 403 (the RFC 8656 answer for a forbidden peer) is still dropped and times out.
- **`MediaRecorder` WebM recordings of audio + video no longer lose their head** (`werift-rtp` `LipsyncBase` / `LipsyncCallback`, `werift` `MediaRecorder`): a track's frames get their NTP time only after its first RTCP SR, which can arrive seconds after the media (with Chrome, about 2 s for audio). Lipsync started on the first frame of whichever track was ready first and dropped everything older from the other track, so a 5 s Chrome recording lost about 2 s of audio. Now lipsync holds frames until a frame of every input kind has arrived and the late track's backlog has caught up, then starts from the earliest frame.
  - New optional `LipSyncOptions.kinds` (`MediaKind[]`, default `["audio", "video"]`): the kinds to wait for. `MediaRecorder` always sets it from the recorded tracks, so a video-only recording starts on its first frame as before. If you use `LipsyncCallback` directly for a single track, pass `kinds: ["video"]` / `["audio"]`; otherwise output waits for `startTimeout`.
  - New optional `LipSyncOptions.startTimeout` (ms, default `10000`): when some kind has not arrived by then (timer-based, so it also fires when no further frame arrives; a timeout detected on an input frame before the timer fires takes the same path, even if that frame completes every kind), the frames received so far are output immediately and output continues with the received tracks only. The timer start commits (including the `fillDummyAudioPacket` fill) only up to the latest received frame, never beyond it, so frames that keep arriving after the start are not dropped. Frames of a track that arrives later are still dropped if they are older than the already committed time. Until the start, frames are held in memory and output (including `stream`) is delayed by up to this time.
  - An EOL before the start outputs the held frames in time order before the EOL.
  - Not changed: a track whose sender never sends an SR is still never output by `NtpTimeCallback`, and `disableLipSync: true` still drops the head of the later track (its frames older than the first frame `WebmCallback` received).
- **DCEP `DATA_CHANNEL_OPEN` writes Label / Protocol Length as UTF-8 byte counts** (RFC 8832 §5.1) instead of UTF-16 `string.length`. A non-ASCII data channel `label` / `protocol` (e.g. `"日本語"`, emoji) used to arrive truncated or spill into the protocol on the remote side; ASCII values are unchanged on the wire.
- **`RTCPeerConnection.close()` stops every DTLS / ICE transport the peer created** (`werift`): `SecureTransportManager` now owns each transport it creates until its `stop()` has stopped ICE (the new `RTCDtlsTransport.onStopped` event; a DTLS close by alert alone keeps it owned), and `close()` stops all of them, including one whose `stop()` is still in progress, not only the ones a transceiver or the SCTP transport still references. A transport no m-line uses any more (e.g. a per-m-line `max-compat` transport a remote BUNDLE answer replaced) can no longer keep its UDP socket or ICE agent alive after `close()`. `dtlsTransports`, `iceTransports`, the ICE state aggregation and `getStats()` still cover only live transports.
- **`JitterBufferBase` no longer drops received packets around a timeout** (`werift-rtp`, used by `MediaRecorder` WebM video and Ogg audio): when a missing packet timed out, the buffer moved its position to the newest arrival, so packets still waiting in the buffer (for example the second of two swapped packets) were discarded, and a timeout whose latest sequence number was `0` discarded the whole buffer. Now only sequence numbers that never arrived are given up, every packet delayed by less than `latency` is output once in sequence order (also across uint16 / uint32 wraparound), an in-order packet that triggers a timeout no longer drops buffered packets, and a full buffer releases its packets instead of dropping new ones.
  - `isPacketLost` now reports each missing range separately (`to` is the last missing sequence number; before, it was the last timed-out received packet), right before the packet that follows the gap. Missing ranges are also reported at `eol`.
- **`WeriftError` keeps its `message`, `payload` and `path`** (`werift-common`): the class field declaration overwrote the message set by `Error` with `undefined`, and `payload` / `path` were never stored. `toJSON()` no longer throws without a `payload`.
- `MediaRecorder.stop()` called before the asynchronous start finished now waits for the start instead of waiting 5 seconds for an end that never comes.
- **RTCP Sender Reports map the current NTP time to the matching RTP timestamp** (`packages/webrtc`, RFC 3550 §6.4.1): `RTCRtpSender` used to report the NTP time and RTP timestamp of the last sent RTP packet, so the SR's NTP time lagged its actual send time by the time since the last RTP packet (without bound while RTP was idle), and SRs sent while RTP was stopped repeated the same LSR. The SR now samples the wall-clock time when it is built and extrapolates the RTP timestamp to that instant from an NTP↔RTP anchor with the send codec's clock rate (32-bit wrap, as libwebrtc does).
  - The anchor is the send time of the first packet with a newer output timestamp (after continuity rewrite). Frame fragments with the same timestamp, timestamps up to 3 s older (reordering) and RTX retransmissions do not move it; a continuity rewrite (`replaceTrack` / `replaceRTP` / `onSourceChanged`), a clock rate change, or a backward timestamp step of more than 3 s (a source discontinuity without continuity rewrite) resets it.
  - Limitation: werift does not know the capture time, so for relayed RTP the send time approximates the sampling time and send jitter becomes SR mapping error.
  - `ntpTime()` accepts an optional epoch-ms argument.
  - NTP timestamps now encode the fractional part as RFC 3550 requires (`fraction / 2^32`) in `ntpTime()` and `ntpTimeToEpochMs()`, matching `ntpTime2Sec()`. Previously the sub-second part was the decimal digits, so two SRs within the same second could carry nearly identical NTP/LSR values, and abs-send-time was affected too.
  - `NtpTimeBase` (`werift-rtp`, used by `MediaRecorder` / `NtpTimeCallback`) takes the RTP timestamp difference to an SR as a signed 32-bit value. Because the SR RTP timestamp is now extrapolated, it can already be past the wraparound while a delayed packet is still before it; such a packet was placed about 26.5 hours (at 90 kHz) later instead of slightly before the SR.
- **`setConfiguration()` TURN options**: changing `turnTransport`, `turnTlsOptions` or `iceUseTcp` after gathering now requests an ICE restart like `iceServers`. Passing an explicit `undefined` for `turnTransport` / `turnTlsOptions` / `turnUdpFamily` unsets it; omitting the key keeps the current value.
- **ICE restart follows the new `iceTransportPolicy` / `iceUseTcp`** (`werift-ice`, `werift`): an ICE restart now keeps only the sockets that a fresh gathering with the new settings would open. With `iceTransportPolicy: "relay"`, the restart offer carries no host / server-reflexive candidates, only relay candidates are trickled, and the kept host sockets are closed. Turning `iceUseTcp` off closes the kept TCP host sockets, and turning it on gathers TCP host candidates for addresses whose UDP sockets were kept. Settings changed after the restart offer was created still apply to that restart's gathering at the commit, so a host candidate the offer announced before a switch to `"relay"` fails its checks, because its socket is closed. `werift-ice` exports the shared rule as `isCandidateAllowedByGatherOptions()` / `isRelayOnlyGathering()` and the ICE server merge as `mergeIceServerOptions()`.
- **`iceTransportPolicy: "relay"` no longer falls back to direct candidates** (`werift-ice`, `werift`): the relay policy (`forceTurn`) is relay-only whatever the TURN settings are. Without a TURN server, with an incomplete TURN credential, or on an ICE-lite agent, gathering — the first one and every ICE restart — produces no candidate instead of host / server-reflexive ones, so the local and public addresses are never advertised and no direct path is checked; the connection cannot be established until a usable TURN server is configured. `isRelayOnlyGathering()` now depends on `forceTurn` alone.
- **`iceTransportPolicy: "relay"` hides the related address of relay candidates** (`werift-ice`, `werift`): under the relay policy, a relay candidate advertises `raddr 0.0.0.0 rport 9` (`::` for IPv6), as RFC 8839 §5.1 specifies, instead of the address the TURN server saw the agent at. This applies in SDP and trickled candidates, for the first gathering and after an ICE restart into the relay policy, so the agent's public address does not reach the peer. With `"all"`, relay candidates keep the TURN-observed `raddr` / `rport`.
- **A staged ICE restart no longer uses a TURN allocation its new settings dropped** (`werift-ice`): until the restart is committed, the provisional checks of the staged generation use a kept TURN allocation only when that generation still has the same TURN server and credential. After the TURN server is removed or replaced (for example, a credential rotation), the old allocation takes no provisional pair, and checks arriving on it for the staged credentials get no response. A check on a host socket that a relay-only restart drops is not answered either. `isCandidateAllowedByGatherOptions()` allows a relay candidate only when the options carry a TURN server and credential, as checked by the new `hasTurnServer()`.
- **`RTCPeerConnection.setConfiguration({ iceServers })` after ICE gathering started now takes effect at the next ICE restart** (JSEP, RFC 9429 §4.1.18), so expiring TURN credentials can be rotated without recreating the `RTCPeerConnection`: call `setConfiguration()` with the new servers, then `restartIce()` and renegotiate. The restarted generation allocates with the new credentials, and the allocation made with the old ones is closed and not re-advertised. A changed STUN/TURN configuration (`iceServers`, `iceTransportPolicy`, `turnUdpFamily`) also sets the needs-ice-restart flag, so the next `createOffer()` restarts ICE even without `restartIce()`. It does not fire `negotiationneeded` by itself. Setting the same servers again requests no restart, and `setConfiguration()` before the first gathering (the WHIP flow) still applies the servers without a restart.
- **ICE `close()` cancels pending mDNS lookups of remote `.local` candidates** (`werift-ice`): a lookup used to keep its 10 s timer, `response` listener and promise after `Connection.close()`, delaying process exit, and a candidate resolved or added after `close()` could still be added to the closed agent (re-opening the mDNS socket). `MdnsLookup.close()` now rejects every pending lookup at once and is idempotent, a lookup after `close()` rejects immediately, and a closed `Connection` ignores remote candidates.

## v0.26.0

This release collects everything merged since v0.25.2, including the `rc/0.26.0` branch (negotiation transaction, SCTP queue, PLI / FIR routing).

### ⚠️ Breaking changes

- **`werift-dtls`: `CipherContext.localPrivateKey` is now a Node `KeyObject`** instead of the `@fidm/x509` `PrivateKey`. Replace `localPrivateKey.toPEM()` with `localPrivateKey.export({ type: "pkcs8", format: "pem" })`; replace `localPrivateKey.sign(data, hash)` with `createSign(hash).update(data).sign(localPrivateKey)`.
- **werift logging no longer follows the application's `debug` package instance.** Use `debug.enable("werift*")` or `debug.disable()` from `werift`, or set `DEBUG=werift*` before startup. The built-in logger does not implement `DEBUG_HIDE_DATE`, `DEBUG_DEPTH`, `DEBUG_SHOW_HIDDEN`, `logger.extend()`, `logger.log`, `debug.log`, `debug.formatters`, `logger.destroy()`, `logger.color`, `useColors`, or `inspectOpts`. In browsers, `localStorage.debug` is still read at load time.
- **`werift-sctp`: `SCTP.outboundQueue` is now a `FifoQueue<DataChunk>` instead of `DataChunk[]`**: the field is `readonly` and has no array-compatibility layer. `FifoQueue` is exported from `werift-common` and re-exported from `werift-sctp`. Migration: use `outboundQueue.length`, `peek()`, `at(i)`, `last()`, `toArray()` or `for...of` instead of array indexing / array methods, and do not reassign the field. Reason: draining a large queue with `Array.prototype.shift()` was quadratic and contributed to the DataChannel burst slowdown below.

### 🚀 Features

- **`RTCRtpSender.onFullIntraRequest`**: a new `Event<[FullIntraRequest]>` fires when the sender receives a FIR (RFC 5104) whose FCI has an entry for its SSRC with a new sequence number. A retransmitted FIR does not fire it again: each FCI entry is compared with the last sequence number for its (FIR sender SSRC, target SSRC) pair (RFC 5104 §4.3.1.1), so entries for the primary and RTX SSRC resolved to one sender are judged independently. FIR is not delivered to `onPictureLossIndication`; applications that refresh on both should subscribe to `onKeyFrameRequest`.
- **`RTCRtpSender.onKeyFrameRequest`**: a new `Event<["pli" | "fir"]>` that fires for every PLI and every non-retransmitted FIR addressed to the sender, so applications that only need to request a key frame can use one subscription. `onPictureLossIndication` / `onFullIntraRequest` and the stats counters are unchanged.
- **`firCount` in outbound-rtp stats**: every FIR packet with an entry addressed to the sender is now counted once (retransmissions included, as the W3C webrtc-stats definition counts FIR packets), so `getStats()` reports `firCount`. A packet whose primary and RTX entries both resolve to the sender counts as one.
- **`FullIntraRequest` is exported** from `werift-rtp` and `werift`.
- **`keyFrameRequestRouting` peer configuration** (`"compatible"` default / `"strict"`): decides where a PLI / FIR goes when no route has its target SSRC (the PLI media SSRC or a FIR FCI entry SSRC). `"compatible"` delivers it to the sender whose RTX SSRC it is, else to the only video sender of the PeerConnection, so a request naming the RTX stream, SSRC 0 or a stale SSRC still produces a key frame (`onPictureLossIndication` / `onFullIntraRequest` / `onKeyFrameRequest`, `pliCount` / `firCount`). `"strict"` does not deliver it, as RFC 4585 / RFC 5104 define the target. A registered target SSRC is routed as is in both modes, and the sender SSRC of the request is never used.
- `RTCIceCandidate` now exposes the readonly W3C fields parsed from its candidate a-line: `foundation`, `component` (`"rtp"` / `"rtcp"`), `priority`, `address`, `protocol` (`"udp"` / `"tcp"`), `port`, `type` (`"host"` / `"srflx"` / `"prflx"` / `"relay"`), `tcpType`, `relatedAddress` and `relatedPort` (`null` when absent or unparsable). This covers `icecandidate` events, `RTCIceCandidate.fromSdp()`, `new RTCIceCandidate(init)`, and `RTCIceTransport.getSelectedCandidatePair()` / `getLocalCandidates()` / `getRemoteCandidates()`, so `pair.local.type === "relay"` works without parsing the candidate string. `toJSON()` still returns only the signaling fields. `relayProtocol` and `url` are not implemented yet.
  - Which candidates give `null` fields is one contract documented on `RTCIceCandidateFields`: an RFC 8839 §5.1 grammar violation (foundation, component-id 1-256, priority 1-2^31-1, address, port, `typ`, `raddr` / `rport`, `tcptype`, single-space separation) gives all `null`; so does a value the W3C attributes cannot represent (component other than 1/2, protocol other than udp/tcp, unknown type). `tcpType` alone is `null` for non-TCP candidates.
  - `new RTCIceCandidate(init)` reads only the `RTCIceCandidateInit` members (`candidate` defaults to `""`); parsed fields passed in `init` are ignored. `RTCIceCandidate.fromSdp(sdp)` now parses like `new RTCIceCandidate({ candidate: sdp })` and keeps the given string instead of re-serializing it; as before, it sets `usernameFragment` from the `ufrag` attribute (only for a valid candidate).
- **Behavior change:** `addIceCandidate()` now rejects a candidate that violates the RFC 8839 grammar above with `OperationError` ("Failed to parse ICE candidate"), as browsers do; before, the lenient parser could pass e.g. `NaN` ports or a missing `typ` keyword to the ICE agent. Browser candidates (mDNS `.local`, `generation`, `ufrag`, `network-id`, `network-cost`, TCP port 9, uppercase `UDP`) are still accepted. a=candidate lines in a remote description are parsed as before.
- **TURN follows `300 Try Alternate`** (`werift-ice`): an Allocate answered with 300 and an `ALTERNATE-SERVER` is retried on that server (RFC 8656 §7.4, RFC 8489 §10), up to 3 redirects. A redirect that cannot be followed (missing `ALTERNATE-SERVER`, a server already tried, too many redirects, or a TCP/TLS transport without a reconnect hook) rejects with the new `TurnRedirectError` (`reason` is a `TurnRedirectFailureReason`; the 300 response is kept as `cause`). `TurnStreamReconnect` lets a stream transport reconnect to the alternate server.
- **`iceInterfaceAddresses` advertises the address it binds** (`werift-ice`, `packages/webrtc`): the configured address is used as the host candidate even when it is not in the OS interface list, and `iceAdditionalHostAddresses` entries of a bound family are ignored. If binding that address fails, ICE reports the error instead of silently falling back to another address. An ICE restart reuses the bound UDP sockets, so the advertised candidate stays consistent. Before, ICE could bind one address and advertise a different host candidate.
- **SRTP rollover counter helpers** (`werift-rtp`): `Context.estimateRolloverCounter()` and `Context.commitPacketIndex()` implement RFC 3711 Appendix A; `Context.updateRolloverCount()` is deprecated and kept as a wrapper. A ROC overflow throws `SrtpRolloverCounterOverflowError` (surfaced as `SrtpAuthenticationError` on the receive side).

### 🐛 Bug Fixes

- **`RTCPeerConnection` negotiation is a single transaction** (`packages/webrtc`, `werift-ice`): an offered or provisionally answered description is staged, the committed session keeps carrying media (RTP / RTCP, the selected ICE pair, DTLS, SCTP), and only the final answer commits negotiated state. Rollback, replacement offers, ICE restarts, BUNDLE changes, DTLS / SCTP updates and routing changes follow the same rule. This fixes cases where a pending offer, a rolled-back offer or a rejected description broke the live connection. `NegotiationTransaction` and the helpers in `src/negotiation/*` own this; no public API value was added.
  - BUNDLE in `max-compat` / `balanced` offers is only a proposal until the remote accepts it (RFC 8843 §7.2); end-of-candidates and ICE generations are tracked per proposed generation.
  - ICE: background gathering is bound to its generation, provisional checks follow the live checklist rules, an ICE-lite peer that changes credentials in its answer still connects, and a relay-only ICE restart waits for its own gathering.
- **Late TURN relay candidates are paired with remote candidates that already arrived** (`werift-ice`): a relay allocation that completed after the remote candidates (early signaling, ICE restart) was never paired. With trickle ICE the check list now fails only after both sides signaled end-of-candidates (RFC 8838 §8), and once a pair is selected no new check starts (RFC 8445 §8.1.2).
- **SRTP: NACK retransmissions no longer corrupt the rollover counter** (`werift-rtp`): a retransmitted packet with a sequence number just after a wrap moved the shared ROC one cycle ahead, so every following packet failed authentication. Each packet now estimates its own ROC and only the highest accepted index is committed (RFC 3711 Appendix A).
  - `srtpSSRCStates[ssrc].rolloverCounter` holds the ROC of the highest accepted index, not that of the last processed packet. A forward jump of more than 32768 is read as an older packet of the previous cycle (as libsrtp does).
- **DTLS server uses the `client_random` of the cookie-bearing ClientHello** (`werift-dtls`): after a HelloVerifyRequest the server kept the random from the first ClientHello, so the ServerKeyExchange signature and key derivation failed with peers that send a different random in the second one.
- **Memory leaks after `close()` and across repeated negotiations are fixed** (`packages/webrtc`, `werift-ice`, `werift-dtls`): remote DataChannel list and listener, stopped sender DTLS subscription, rollback-baseline transport, transport-cc feedback history, ICE credential history, STUN transactions surviving close, retired checklists, TURN close races, and DTLS flight retransmission after the transport stopped.
- **Large `RTCDataChannel.send()` bursts no longer slow down quadratically or starve the event loop** (`werift-sctp`, `packages/webrtc`): queuing thousands of messages at once took time growing with the square of the queue length (2,000 × 1 KB: ~12 s, 5,000: minutes) and blocked the event loop for seconds per SACK, long enough to lose ICE consent mid-transfer.
  - `SCTP.send()` now resolves when its own last chunk is handed to the network (moved from the outbound queue to the sent queue) instead of waiting until the whole outbound queue drains. Previously every pending `send()` waited on the `flush` event, so each transmit woke all N waiters and each re-subscribed with an O(N) unsubscribe.
  - Pending `send()` calls settle when the association closes instead of staying pending forever.
  - The SCTP sent / outbound queues and the DataChannel send queue use `FifoQueue` (amortized O(1) `shift()`).
  - `RTCSctpTransport` hands queued DataChannel messages to SCTP in a single synchronous pass instead of starting one concurrent flush loop per `send()`. `bufferedAmount` now decreases per message as it is transmitted (previously only after the whole SCTP outbound queue drained), so `bufferedamountlow` fires during a burst. Messages not yet handed to SCTP are discarded when the transport stops.
- **RTCP PLI / FIR routed to the targeted media source**: `RtpRouter.routeRtcp()` used to look up a payload-specific feedback by its sender SSRC first, so a PLI whose sender SSRC matched another local stream (e.g. a werift or Chrome peer in a sendrecv video session, or an SFU viewer's own stream) was delivered to the wrong `RTCRtpReceiver` / `RTCRtpSender` and never raised `onPictureLossIndication`. PLI is now routed only by its media SSRC (RFC 4585 §6.1), and FIR by the SSRC of each FCI entry (RFC 5104 §4.3.1; the media SSRC of the common header is 0 for libwebrtc), delivering once per target sender. A PLI whose media SSRC is not registered is no longer delivered to the stream matching its sender SSRC (see `keyFrameRequestRouting` for where it goes instead). Unknown payload-specific feedback types (SLI, RPSI, ...) are no longer routed, instead of throwing.
- **Compound RTCP packets are split at each packet's declared length** (`werift-rtp` `RtcpPacketConverter.deSerialize`): each packet's payload used to extend to the end of the compound packet, so a FIR followed by another packet (e.g. `RR + SDES + FIR + PLI`) gained bogus FCI entries from the following bytes. With FIR routing these reached other senders as extra FIR notifications and `firCount`. Padding is also read from the end of its own packet instead of the end of the compound packet.
- **`FullIntraRequest` serializes the RFC 5104 header length**: the RTCP length field was one word short (3 instead of 4 for one entry; RFC 5104 §4.3.1.1: 2 + 2 × N), so peers could fail to parse a FIR sent by werift.
- **WebM files saved with `saveToFileSystem` no longer contain unknown-size Clusters** (`werift-rtp`, `MediaRecorder` WebM output): when the recording ends, each Cluster's size field is rewritten in place with its real size. Before this fix, ffprobe warned `Unknown-sized element ... inside parent with finite size`, mkvalidator reported errors, and libwebm rejected the files.
  - `WebmOutput.eol.clusters` (new; `{ position, size }[]`), `replaceClusterSize()` and `ClusterSizeOffset` are exported for custom writers. Streaming output (`WebmStream` without rewriting) still uses unknown-size Segment / Clusters.
  - `replaceSegmentSize()` now writes an 8 byte VINT instead of a short VINT followed by a Void element. The old value was too large by the length of the size field, because it counted the field itself. Its Void padding also moved the Segment body start, so every CueClusterPosition pointed past its Cluster.
  - The record examples now use `saveToFileSystem`.
- **`ntpTime2Sec()` now converts the NTP fraction correctly** (`werift-rtp`, used by `NtpTimeCallback` / `MediaRecorder` A/V sync): the low 32 bits of an RTCP SR NTP timestamp are a binary fraction (1/2^32 s), but they were read as decimal digits (`0x80000000`, i.e. 0.5 s, became 0.2147483648 s). Each track's frame times could be off by up to about 1 s, so lipsync dropped most or all audio from short recordings of a browser's audio and video. A new E2E test (`e2e/tests/mediachannel/recordPlayback.test.ts`) records browser media with `MediaRecorder`, sends the WebM back over a DataChannel, and checks that Chrome plays it.
- **`werift-common` `UdpTransport` always handles dgram socket `error` events** (`werift-common`, `werift-ice`): before this fix, a socket error with no listener (for example Bun's asynchronous `recvmsg ECONNREFUSED` after the remote peer closed) became an uncaught process exception.
  - Runtime socket errors are logged and emitted on the new `UdpTransport.onError` (`Event<[Error]>`). The socket stays open. `StunProtocol` / `TurnProtocol` subscribe to it and log. `Transport.onError` is optional for custom transports.
  - A bind failure (e.g. `EADDRINUSE`, including a synchronous `bind()` throw) or a `findPort()` failure now rejects `UdpTransport.init()` and closes the socket. Before, a bind failure caused an uncaught exception or `init()` waited forever.
  - `close()` can be called more than once, including after an error or a failed bind.
- **`werift`: unordered partially reliable DataChannels now announce an unordered DCEP channel type.** `ordered: false` with `maxRetransmits` or `maxPacketLifeTime` sent channel type `0x01` / `0x02` in `DATA_CHANNEL_OPEN` instead of `0x81` / `0x82` (RFC 8832 §5.1), so the remote peer created the channel as ordered. Workarounds that set the `0x80` bit on the queued OPEN message are no longer needed.
- PEM passed to `dtls.keys` / `RTCCertificate` / `CipherContext` may still be indented (for example inside an indented template literal), as it was with `@fidm/x509`. `werift-dtls` exports the `normalizePem()` helper used for this.

### 🐛 Fixes (review follow-ups)

- **AV1 Chrome RTP playback**: the packetizer packs up to three OBU elements per packet (W=1..3), aggregates the Sequence Header with the start of its frame, and omits internal `obu_size` fields so Chrome decodes the temporal unit correctly. W=0 payloads are still accepted by the depacketizer.
- **H.264 `isKeyframe`** (RFC 6184 §5.7.1 / §5.8): the 2nd octet is read as an FU header only for FU-A / FU-B. A non-IDR STAP-A whose first NALU size upper byte has low 5 bits = 5 (e.g. size `0x05xx`) is no longer reported as a keyframe; STAP-A is a keyframe only when it aggregates an IDR slice (new `H264RtpPayload.aggregatedNalUnitTypes`). This affects `dePacketizeRtpPackets`, `waitForKeyframe` in the depacketizer, and WebM / MP4 key samples.

- **VP8 payload descriptor now carries PictureID** (`packages/webrtc` file playback / encoded-binary / dummy media, `packages/rtp` `Vp8Packetizer`): werift-generated VP8 RTP uses the browser single-layer form `X=1, I=1, M=1` + 15-bit PictureID (4 octets; `90 80 ..` on the first fragment, `80 80 ..` on continuations; L/T/K unset). PictureID starts random (dummy media: deterministic per source), advances once per frame and wraps at `0x7fff`; file playback keeps it continuous across `loop`. Fragment size is `maxPayloadSize - 4`, so payloads stay within `maxPayloadSize`. Previously the 1-octet `X=0` descriptor was dropped by mediasoup ≤ 3.19.2 (before versatica/mediasoup#1612), which could not detect its keyframes, so subscribers received nothing; it now works on those versions without upgrading the SFU. Code that assumed a 1-octet descriptor must parse X/I/M (e.g. `Vp8RtpPayload`). `packages/rtp` `Vp8Packetizer` accepts `pictureId` to set the initial value; `createVp8PayloadDescriptor()` is exported.
- **File playback VP8 PictureID no longer resets at the first `loop`** (`packages/webrtc` `createFileMediaPlayer`): the per-track packetizer was recreated whenever `RTCRtpSender` assigned a new (equivalent) codec object or filled in the payload type after playback started, restarting PictureID at a random value. - **Dummy media VP8 is decodable** (`packages/webrtc` `dummyMedia` / `createDummyRegister()`): the previous synthetic keyframe (2x2 header with an empty first partition) was rejected by libvpx, so Chrome decoded 0 frames and kept sending PLI. It now sends a libvpx-encoded 16x16 black keyframe plus an error-resilient delta frame.
- **AAC (RFC 3640 §3.2.3.1)**: every fragment now carries its AU Header Section; the depacketizer strips it from continuations and validates AU-size. Multi-AU splits give each packet a distinct timestamp (`auDurationInSamples`, default 1024). Extended CTS/DTS headers accept non-16-bit lengths with trailing padding.
- **H.264 / H.265**: length-prefixed input whose prefix looks like a start code (e.g. length 300 = `00 00 01 2c`) is no longer misread as Annex-B.
- **AV1**: adjacent fragmented OBUs are no longer merged; boundaries come from Z/Y.
- **Audio marker** (G.711 / G.722 / Opus): marker is set only on the first packet of a talkspurt (`startTalkspurt()` to re-arm), per RFC 3551 §4.1 / RFC 7587 §4.1.
- **H.264 / H.265 input layout**: new `inputFormat: "auto" | "annexb" | "length-prefixed"` on the packetizers and `split*NalUnits`. `auto` (default) treats a leading start code as Annex-B (a 3-byte `00 00 01 HH` is otherwise indistinguishable from a 4-byte length `0x1HH`); pass `"length-prefixed"` for MP4/MKV samples. Supersedes the earlier length-first heuristic, which corrupted 3-byte-start-code NALs.
- **telephone-event**: `event` / `volume` / `duration` outside 0–255 / 0–63 / 0–0xFFFF now throw `RangeError` instead of being masked (RFC 4733 §2.5.1.3: split longer events).
- **AAC**: a complete AU arriving while a fragment is pending drops the stale fragment instead of throwing. **H.265 FU** with S=E=1 is rejected.

- **AV1 N bit** (RFC 9628 §4.4): `Av1Packetizer` no longer sets N on every keyframe. N is set when `startsNewCodedVideoSequence` is `true`, or by default for a keyframe whose temporal unit contains a Sequence Header OBU; mid-sequence keyframes keep N=0.

- **`useH264()`** now returns `video/H264` (uppercase, as Chrome expects); codec names are compared case-insensitively.
- **AV1 ↔ AV1X** normalization now applies to SDP answer, codec matching, and file playback validation, not only `findCodecByMimeType`.
- **AV1 packetizer → Chrome**: `Av1Packetizer` drops Temporal Delimiter OBUs, clears `obu_has_size_field` on RTP OBU elements, and packs up to three OBU elements per packet (W=1..3), splitting OBUs across packet boundaries like libwebrtc. - **fMP4 muxer no longer loops forever when video dimensions are undefined** (`packages/rtp` `Mp4Container` / `MP4Processor`): a video config without `codedWidth` / `codedHeight` now reaches the "missing coded video dimensions" guard. ## v0.25.0

### ⚠️ Breaking changes

- **`werift/polyfill` fixed-codec sources no longer expand `RTCPeerConnection` codec capability implicitly** (#729): A track from a polyfill `MediaRegister` (MP4/WebM, callback, RTP/RTCP, encoded binary) now treats its codec as a hard constraint — `addTrack()` / `addTransceiver()` throws `NotSupportedError` instead of silently adding the codec to the PeerConnection capability. The public `adoptSenderTrackCodec` helper was removed. Plain, non-polyfill `MediaStreamTrack`s (e.g. ordinary live sources) are unaffected.
- **Removed `getUserMedia({ path | buffer | stream })` from `werift/nonstandard`** (#729). File playback now goes through `werift/polyfill`: `installPolyfill({ mediaRegister: [createMp4WebmRegister({ path })] })` then `navigator.mediaDevices.getUserMedia({ audio: true, video: true })`.
- **m-line reuse behavior changed, default `PeerConfig.mLineReuse: "compatible"`** (#705, #721): Accepted `inactive` m-lines now keep port 9 instead of port 0, and `addTransceiver()` / `addTrack()` no longer take over an `inactive` m-line left by `removeTrack()` — only a position whose port 0 stop/rejection has been negotiated is reused (with a new MID). **To keep the pre-v0.25 behavior, set `mLineReuse: "aggressive"`.** Note that in `"aggressive"` mode a negotiated inactive m-line becomes permanently stopped and cannot resume with `direction = "sendrecv"`, so pause/resume (mute/unmute, hold/resume) workflows should stay on `"compatible"`. See the `PeerConfig.mLineReuse` entry under Features for the full compatibility matrix.

### 🚀 Features

- **`PeerConfig.turnUdpFamily`** (#726, #731): preferred TURN/UDP socket family (`"udp4"` / `"udp6"`) for hostname TURN servers, passed through `RTCIceGatherer` to `IceOptions.turnUdpFamily` and propagated by `setConfiguration()` before the next gathering. Defaults to `undefined` (`udp4`), so existing configurations are unchanged. An IP-literal server address still selects the UDP socket family directly; a conflicting `turnUdpFamily` is ignored with a debug log instead of making the configured server unreachable.
- **Polyfill codec integration** (#729): `installPolyfill()` accepts `peerConnectionConfig`, and `RTCRtpTransceiver.setCodecPreferences()` now filters and orders codecs independently from fixed-source constraints.
- **Empty media tracks for `werift/polyfill`** (#729): `mediaRegister: []` now lets `getUserMedia()` return plain audio/video tracks instead of `NotFoundError`, and the new `createEmptyRegister()` exposes the same no-RTP, codec-unset behavior explicitly.
- **Configurable SCTP outbound MTU** (#708, #716): `SCTP` and `RTCPeerConnection({ sctp: { mtu } })` now accept an outbound packet MTU. The default is 1191 bytes, changing DATA fragmentation and congestion-control units from a 1200-byte payload to 1160 bytes (maximum serialized DATA packet: 1188 bytes).
- **`werift/polyfill`** (#689): Opt-in installer that puts werift WebRTC constructors on `globalThis` (or a `target` sandbox) and implements `navigator.mediaDevices.getUserMedia` via `mediaRegister` (MP4/WebM, RTP/RTCP, encoded binary, or `createCallbackRegister`).
- **`PeerConfig.mLineReuse`** (#705, #721): `"compatible"` (default) keeps accepted `inactive` m-lines on a non-zero port and uses port 0 only for rejected / stopped m-lines; `"aggressive"` keeps the legacy inactive port 0. The value is validated on construction and cannot be changed by `setConfiguration()`.
- **`RTCRtpTransceiver.stop()` and m-line reuse** (#705, #721): `stop()` is idempotent, releases the sender / receiver / router registrations immediately, and negotiates port 0 in the next local offer. A new `addTransceiver()` reuses a port 0 position of the same kind only after the rejection has been negotiated, with a new MID and a new transceiver.

### 🐛 Bug Fixes

- **TURN hostname resolution matches the bound UDP socket family** (`werift-ice`, #731): `TurnProtocol.request` now resolves the server hostname with the same family preference as the `udp4` socket `createTurnClient` binds. Previously, a dual-stack resolver that answered IPv6 first (e.g. `turn.cloudflare.com`) sent every `Allocate` to an address the socket could not reach, so the transaction retransmitted for ~6.4 s, timed out, and gathering silently fell back to TURN over TCP, holding `setLocalDescription` for the whole wait.
- **TURN server endpoint pinned and taken from the transport** (`werift-ice`, #725, #726, #731): `Transport` gains optional public `addressFamily` / `remoteAddress` fields (reported by `UdpTransport`, `TcpTransport`, `TlsTransport`); STUN and TURN read these instead of casting to `UdpTransport`'s private socket type. `TurnProtocol` resolves and pins one concrete server endpoint on the first request instead of re-resolving per request, which could previously drift to a different address.
- **IPv6 TURN/STUN transaction addresses compared in canonical form** (`werift-ice`, #731): an IPv6 literal server written in non-canonical notation (e.g. `0:0:0:0:0:0:0:1`) never matched the socket-reported source address, so valid responses were dropped until the transaction timed out.
- **ICE-TCP: both agents now select the same TCP connection** (`werift-ice`, #721): the controlling agent no longer attaches `USE-CANDIDATE` to every TCP connectivity check (aggressive nomination). It waits until every higher-priority TCP pair has finished its check, then nominates the highest-priority valid TCP pair with a separate `USE-CANDIDATE` check (RFC 8445 regular nomination). Before this change, the two agents could each pick a different TCP connection and then close the connection the peer had picked while pruning, so the first `send()` failed with `EPIPE` / `ECONNRESET`. UDP and relay pairs, and connections to ICE-lite peers, keep their current nomination behavior. (UDP and relay pairs later moved to semi-aggressive nomination by default, with regular nomination as an option; see the entry "ICE: semi-aggressive nomination by default, so a better pair that succeeds later replaces the selection".)
- **ICE-TCP connectivity check timeout** (`werift-ice`, #721): TCP checks are still sent once without retransmission (RFC 5389 §7.2.2), but the response timeout is now `TCP_CHECK_RESPONSE_TIMEOUT_MS` (3 s) instead of 50 ms, and that timeout also covers the TCP connect. A refused TCP connect or a failed write fails the check immediately instead of waiting for the timeout.
- **ICE-TCP selected connection loss** (`werift-ice`, #721): a TCP socket that is already closed is discarded before reuse, and a failed write discards the socket and rejects `send()` with the socket error. When the selected TCP connection closes, the agent moves to `failed` right away (the same end state as a consent expiry) instead of waiting 30 s for consent to expire.
- **`NodeTurnServer.listen()` bind conflict** (`werift-ice-server`, #721): with `port: 0`, UDP and TCP share one port number that UDP picks. If that number is already in use for TCP, `listen()` now picks a new number (up to 10 attempts) instead of failing with `EADDRINUSE`. If `listen()` fails, it now closes any socket it has already opened and resets its state.
- **Reject unsupported RTP m-lines in the answer instead of throwing** (#705, #721): `setRemoteDescription()` no longer fails with `negotiate codecs failed.` when an audio/video section has no common codec. The answer keeps the m-line count, order, MID, type and proto, and rejects only that section with port 0 and one offered fmt token. Audio-only peers no longer need to add VP8 to accept a browser offer that bundles video.
  - The answer BUNDLE group contains only accepted offered members; an offerer-tagged section rejected in the initial answer moves the tag to the first accepted member, and a fully rejected group is omitted. An established tag is kept.
  - Accepted m-lines outside the offered BUNDLE group get their own transport and ICE credentials, including with `bundlePolicy: "max-bundle"`. A re-offer that moves an established BUNDLE member out of its group or splits the members into different groups is rejected with `InvalidAccessError` before any state changes. For a remote offer, transport ownership follows only the offered BUNDLE groups regardless of `bundlePolicy` (`max-bundle` affects only local offers): each offered group gets its own transport, and m-lines outside any group (including an offer without BUNDLE) get independent transports. ICE / DTLS parameters come from the first accepted member of a group, not from a codec-rejected tag. A new independent transport gathers its own ICE candidates even when an established BUNDLE is connected, and each transport takes the DTLS role from the `a=setup` of the m-lines it serves. As an offerer, a remote answer that moves m-lines sharing one offered transport out of a common BUNDLE group with different ICE credentials is rejected with `InvalidAccessError` before any state changes. Local trickle candidates carry the MID / index of the accepted section that owns the ICE transport (not always m-line 0); remote candidates for rejected sections are recorded without throwing. SCTP before RTP keeps the original indexes.
  - A non-zero remote answer / pranswer without a common codec is rejected with `InvalidAccessError` before any state changes. An unsupported re-offer keeps the existing track and RTP pipeline while pending and after rollback, and is released only when the port 0 answer is applied.
  - `removeTrack()` detaches the track without stopping the sender, so the same sender can resume. `addTrack()` reuses only unsent, non-stopped, non-rejected senders. Re-offers no longer fire `ontrack` again for an already receiving transceiver, and remote-initiated stops do not fire `negotiationneeded`.
  - `negotiationneeded` is coalesced: changes in the same tick (including `removeTrack()`) fire it once, and an event queued before a local offer that already covers the change is dropped once that offer is answered. This avoids duplicate offers and `InvalidStateError` in `onnegotiationneeded`-driven signaling.
  - A local transceiver that reserved a stopped position before its own offer releases the reservation when a remote offer reuses that position (e.g. with another kind), and is appended in the next offer instead of taking the remote MID.
  - Design note: `docs/design/705-media-rejection-and-removetrack.md`.
- **Received audio RED tracks labeled with the delivered primary codec** (`packages/webrtc`, #729): `RTCRtpReceiver` unwraps audio RED and delivers primary (e.g. Opus) packets to the track, but the remote track's codec was set to the first negotiated codec (`audio/red`). With fixed-source constraints this made `replaceTrack()` reject echoing a received RED track back on a RED sender (`InvalidModificationError`), breaking the `red-record-gst` and `red-sendrecv` example e2e flows. Remote audio tracks are now labeled with the primary codec referenced by RED (or the first primary codec) on creation and on codec resync.

## v0.24.2

### 🐛 Bug Fixes

- **ICE consent freshness (RFC 7675)** (#649): Align consent-to-send monitoring with RFC 7675 so long-lived sessions against **ICE-lite** peers (e.g. OpenAI Realtime) no longer drop media after ~30s.
  - **Cadence**: Schedule the next consent Binding from the previous *request start* time at 0.8–1.2× `CONSENT_INTERVAL` (5s base), not after response completion.
  - **Expiry**: Independent 30s timer from the last valid consent response (`CONSENT_TIMEOUT`); a single request timeout no longer stops monitoring.
  - **Single-shot requests**: Consent transactions use `retransmissions: 0` with an RTT-based response wait (`consentResponseTimeoutMs`, min 500ms / default 1s) instead of a ~50ms RTO death.
  - **Authenticity**: Accept only responses from the selected-pair remote address, and require `MESSAGE-INTEGRITY` when an integrity key is set.
  - **Protocols**: UDP / ICE-TCP / TURN (`StunOverTurnProtocol`) all honor the same `TransactionRequestOptions` (TURN no longer drops `retransmissions`).
  - **ICE-lite interop**: When controlling against a remote ICE-lite selected pair, attach `USE-CANDIDATE` on consent requests (libwebrtc-style semi-aggressive nomination).
  - **On expiry**: Mark transport `failed` (not `closed`), gate application data via `consentFresh`, and leave the transport available for ICE restart.
- **ICE restart role reassignment** (#649): After consent gating made app-data depend on a fresh selected pair, Chrome-initiated ICE restart could leave both sides controlling.
  - Allow ICE role to be reassigned from offer/answer once `nominated` is cleared; keep `switchRole` force-switch for RFC 8445 role conflict.
  - E2E `ice_restart_web_trigger`: apply the restart answer via `setRemoteDescription` and flush candidates so media recovers.
- **DTLS send destination** (#648): Add optional `addr?: Address` to `DtlsSocket.send` / `TransportContext.send` and forward it to the underlying transport.
  - Avoids mis-routing application data when a shared UDP socket’s last `rinfo` changes between a sync reply and a later async send (e.g. multi-client DTLS server).

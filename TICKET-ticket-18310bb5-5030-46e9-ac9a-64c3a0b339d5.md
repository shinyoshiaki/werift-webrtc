## Summary

werift currently reuses one process-wide default DTLS certificate across multiple `RTCPeerConnection` instances when `RTCConfiguration.certificates` is not supplied.

This differs from browser/WebRTC behavior, where a certificate set is generated automatically for each `RTCPeerConnection` instance unless the caller explicitly supplies certificates.

The behavior is observable through the SDP fingerprint and can make independent peer connections from the same Node.js process appear to have a stable identity.

## Current implementation

In `packages/webrtc/src/transport/dtls.ts`, `RTCDtlsTransport` stores the default certificate in static state:

```ts
static localCertificate?: RTCCertificate;
static localCertificatePromise?: Promise<RTCCertificate>;

static async SetupCertificate() {
  if (this.localCertificate) {
    return this.localCertificate;
  }

  if (this.localCertificatePromise) {
    return this.localCertificatePromise;
  }

  this.localCertificatePromise = (async () => {
    // generate certificate
    this.localCertificate = new RTCCertificate(...);
    return this.localCertificate;
  })();

  return this.localCertificatePromise;
}
```

`SecureTransportManager.ensureCerts()` uses that static certificate whenever a certificate was not explicitly configured:

```ts
async ensureCerts() {
  if (!this.certificate) {
    this.certificate = await RTCDtlsTransport.SetupCertificate();
  }

  for (const dtlsTransport of this.dtlsTransports) {
    dtlsTransport.localCertificate = this.certificate;
  }
}
```

As a result:

```ts
const a = new RTCPeerConnection();
const b = new RTCPeerConnection();

// after offer creation / certificate setup
// a and b advertise the same DTLS fingerprint
```

for peer connections created in the same process.

## Why this matters

### 1. WebRTC compatibility / certificate lifecycle

When `RTCConfiguration.certificates` is omitted, implementations are expected to generate certificates automatically for each `RTCPeerConnection` instance.

If an application wants certificate continuity across connections, that should be an explicit choice by passing the same `RTCCertificate` through `RTCConfiguration.certificates`.

werift already supports that explicit API, so implicit process-wide reuse is surprising and unnecessary.

### 2. Cross-connection correlation

The SDP DTLS fingerprint becomes stable across otherwise independent peer connections in the same process.

That creates an avoidable correlation identifier for a long-lived Node.js process.

### 3. It can hide application bugs

This was observed downstream in CodeTrellis:

https://github.com/lionroseway/codetrellis/pull/52

The application incorrectly used the DTLS fingerprint as a durable peer identity.

Its werift↔werift tests ran both peers in one process, so werift's process-wide certificate reuse made fingerprints look stable and the tests passed.

On a real device, `react-native-webrtc` generated a new certificate for a new `RTCPeerConnection`, exposing the bug. Restarting the desktop process similarly changed werift's fingerprint.

So the current behavior can make werift-only tests disagree with browser/native WebRTC implementations in an important identity/security property.

## Expected behavior

Without explicit certificates:

```ts
const a = new RTCPeerConnection();
const b = new RTCPeerConnection();
```

should result in distinct automatically generated certificates/fingerprints.

Within one `RTCPeerConnection`, all DTLS transports that belong to that peer connection can still share that peer connection's certificate.

If the caller explicitly supplies the same certificate:

```ts
const cert = new RTCCertificate(keyPem, certPem, signatureHash);

const a = new RTCPeerConnection({ certificates: [cert] });
const b = new RTCPeerConnection({ certificates: [cert] });
```

then stable fingerprints across those peer connections are expected.

## Suggested implementation

Move automatic certificate ownership to the `SecureTransportManager` / `RTCPeerConnection` instance rather than `RTCDtlsTransport` static state.

Conceptually:

- if `config.certificates[0]` exists, use it;
- else if legacy `dtls.keys` is provided, construct the certificate from those keys;
- otherwise generate one certificate for that `SecureTransportManager`;
- assign that instance certificate to all DTLS transports created by that peer connection.

The process-wide `RTCDtlsTransport.localCertificate` / `localCertificatePromise` cache should not be used for the default path.

## Tests

Please add coverage for:

1. two default `RTCPeerConnection` instances produce different fingerprints;
2. DTLS transports inside the same peer connection use the same certificate;
3. two peer connections configured with the same explicit `RTCCertificate` produce the same fingerprint;
4. existing offer/answer and DataChannel interoperability remains unchanged.

## Compatibility note

This changes an observable fingerprint for applications that accidentally relied on process-wide default certificate reuse.

Applications that intentionally require stable DTLS identity should pass an explicit persistent `RTCCertificate`, which is already supported by `RTCConfiguration.certificates`.

# 詳細化（コードベース調査結果）

## 1. 目的と背景

- `RTCConfiguration.certificates` を指定しない場合、werift はプロセス全体で 1 枚の DTLS 証明書を共有している（`RTCDtlsTransport` の static キャッシュ）。
- W3C WebRTC 仕様およびブラウザ / libwebrtc / react-native-webrtc では、証明書未指定時は **`RTCPeerConnection` インスタンスごと** に自動生成される。
- 結果として以下の問題がある:
  - 同一プロセス内の独立した PC 間で SDP `a=fingerprint` が一致し、相関可能な識別子になる（プライバシー）。
  - werift 同士のテストではフィンガープリントが安定して見えるため、「fingerprint を永続 ID として使う」といったアプリのバグが隠れる（CodeTrellis PR #52 で実際に発生）。
- 目的: 自動生成証明書の所有者を PC（`SecureTransportManager`）単位に移し、ブラウザと同じライフサイクルにする。証明書の継続性が必要な場合は既存の `RTCConfiguration.certificates` / `dtls.keys` で明示する。

## 3. 実装内容

### 3.1 `RTCDtlsTransport`（`packages/webrtc/src/transport/dtls.ts`）

- キャッシュしない証明書生成関数を追加する（例: `static async generateCertificate(): Promise<RTCCertificate>` もしくはモジュール関数 `generateDefaultCertificate()`）。アルゴリズムは現行と同じ ECDSA(secp256r1) + SHA-256 を維持する。
- コンストラクタの `this.localCertificate ??= RTCDtlsTransport.localCertificate;` を削除し、static キャッシュへの暗黙フォールバックをなくす。
- `static localCertificate` / `localCertificatePromise` / `SetupCertificate()` の扱い（推奨）:
  - 公開 API なので即削除はせず `@deprecated` を付けて残す（既存の低レベル利用者向け）。ただし **デフォルト経路（`SecureTransportManager`）からは一切参照しない**。
  - 互換を割り切れるなら削除も可。その場合は changelog の Breaking changes に記載する。

### 3.2 `SecureTransportManager`（`packages/webrtc/src/secureTransportManager.ts`）

- インスタンス単位の生成 Promise を持つ（例: `private certificatePromise?: Promise<RTCCertificate>`）。
- `ensureCerts()` を以下に変更:
  1. `this.certificate` があればそれを使う（`config.certificates[0]` / `dtls.keys` 由来）。
  2. なければ `this.certificatePromise ??= RTCDtlsTransport.generateCertificate()` を await して `this.certificate` に設定（`createOffer()` / `createAnswer()` の並行呼び出しで二重生成しないため）。
  3. live な全 `dtlsTransports` に `this.certificate` を代入（現行どおり）。
- `createTransport()` は現行どおり `this.certificate` を渡す。`ensureCerts()` 前に作られた transport は `ensureCerts()` で後から代入されるため、`addTransceiver()` / `createDataChannel()` → `createOffer()` や `setRemoteDescription()` → `createAnswer()` の順でも同一 PC 内で証明書は 1 つに揃う。
- 生成失敗時は Promise をクリアして次回再試行できるようにするか、エラーを伝播させる（握りつぶさない）。
- （任意）`if (this.config.dtls)` ガードの外で `certificates[0]` を評価するよう整理してもよい。

### 3.3 テスト fixture の移行

- `tests/fixture.ts` の `dtlsTransportPair()` と `tests/transport/dtls.test.ts` の `createDtlsSessions()` は static フォールバック前提なので、生成した証明書を `new RTCDtlsTransport(config, ice, certificate)` に明示的に渡すよう変更する。
- AGENTS.md の方針に従い、証明書生成やフィンガープリント抽出などの Arrange ヘルパーは `tests/fixture.ts` に集約する（例: `createTestCertificate()`、`getSdpFingerprints(sdp)`、`getLocalFingerprint(pc)`）。`createAudioCodec` などと同様にそこから import して再利用する。
- `createDtlsSessions()` を `fixture.ts` に寄せて `dtlsTransportPair()` と共通化できるなら検討する。

### 3.4 追加テスト

配置候補: `tests/integrate/peerConnection.test.ts` の `describe("initial config") > describe("dtls")`、または新規 `tests/integrate/certificate.test.ts`。Arrange / Act / Assert の 3 フェーズで書き、Act / Assert には日本語コメントを付ける。

1. **デフォルト PC 2 つで fingerprint が異なる**: `new RTCPeerConnection()` ×2 → それぞれ `createOffer()`（DataChannel か transceiver を追加）→ SDP の `a=fingerprint` 値が異なることを確認。
2. **同一 PC 内の DTLS transport は同じ証明書を使う**: `bundlePolicy: "max-compat"`（デフォルト）で audio / video / DataChannel など複数 m-line を作り、`pc.dtlsTransports` が複数あること、全 transport の `localCertificate` が同一インスタンス（または同一 fingerprint）であること、SDP 内の全 `a=fingerprint` が一致することを確認。
3. **明示的に同じ `RTCCertificate` を渡した 2 PC は fingerprint が一致**: `createSelfSignedCertificate()` → `new RTCCertificate(keyPem, certPem, signatureHash)` を `{ certificates: [cert] }` で 2 PC に渡し一致を確認。`dtls.keys` 経由の既存挙動も同様に一致すること。
4. **並行呼び出しでも 1 PC 1 証明書**: `Promise.all([pc.createOffer(), pc.createOffer()])` 等で生成が 1 回に収まり、fingerprint が一致すること（`ensureCerts` の Promise 共有の検証）。
5. **既存の相互接続が壊れない**: 既存の `datachannel` / `integrate` / `transport/dtls.test.ts` / `getStats`（certificate stats）テストがすべて通ること。デフォルト証明書同士（互いに異なる証明書）での DataChannel 接続を 1 本明示的に確認するとよい。

## 4. 制約・注意点

- **互換性**: 同一プロセスの複数 PC で fingerprint が同じことに（意図せず）依存していたアプリは挙動が変わる。正規の回避策は明示証明書。
- **性能**: PC ごとに ECDSA P-256 鍵生成 + 自己署名（WebCrypto + `@peculiar/x509`）が走る。1 回あたりは軽いが、大量に PC を作る `loadtest/` / `benchmark/` / memleak シナリオで遅延が増えないか確認する。生成は `createOffer()` / `createAnswer()` まで遅延させ（現行と同じタイミング）、コンストラクタでは生成しない。
- **memleak**: PC ごとの証明書は PC と一緒に GC されるべき。static に保持しないこと。
- **`setConfiguration()`**: 自動生成証明書は `config.certificates` に書き戻さない（`getConfiguration().certificates` は `[]` のまま）ことで、既存の `"certificates cannot be changed"` 判定との衝突を避ける。仕様上も自動生成時は `certificates` は未設定扱いでよい。
- **ICE restart / 再ネゴシエーション**: 同じ PC 内では証明書を変えないこと（fingerprint 変化は DTLS 再ハンドシェイク・相手側検証失敗を招く）。`this.certificate` は一度決まったら PC の寿命中固定。
- **WPT**: `RTCPeerConnection.generateCertificate()` は未実装のまま（本チケットの範囲外）。WPT ランナー側の挙動を変える必要はないが、念のため `npm run wpt` で回帰がないことを確認する。
- **低レベル API 利用者**: `new RTCDtlsTransport(config, ice)` を証明書なしで生成し `SetupCertificate()` に頼っていたコードは、フォールバック削除後は証明書を明示的に渡す必要がある（changelog に明記）。
- 下位パッケージ（`packages/dtls`）の変更は不要。修正は `packages/webrtc` 内で完結する。
